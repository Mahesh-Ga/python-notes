# HNSW (Hierarchical Navigable Small World)

> Concise concept notes, based on the Pinecone/FAISS HNSW article (https://www.pinecone.io/learn/series/faiss/hnsw/). Companion to `31.vector_store.md`. Goal here: understand *what each piece is and why it exists*, not implementation-level depth.

---

## What HNSW Is

An **ANN (Approximate Nearest Neighbor)** algorithm — a graph you build once, then greedily walk to find vectors close to a query, without comparing against every stored vector. It's built from two older ideas combined:

1. **Skip Lists** — gives it the *layered* structure.
2. **Navigable Small World (NSW) graphs** — gives it the *greedy graph search*.

---

## Ingredient 1: Skip Lists

A skip list speeds up search in a sorted linked list by adding extra "express lane" layers on top — fewer nodes, longer jumps. Search starts at the top (sparse) layer, jumps as far as possible without overshooting, then drops a layer and repeats.

**What HNSW borrows:** the idea of stacking multiple layers — long-range links up top for speed, short-range links at the bottom for precision.

---

## Ingredient 2: Navigable Small World (NSW) Graphs

A single-layer graph where each vector ("vertex") is linked to its nearby vectors (its "friend list").

**Search on NSW:** start at a fixed entry point, greedily hop to whichever neighbor is closer to the query, stop when no neighbor improves (a **local minimum**).

**Two phases of this walk:**
- **Zoom-out phase** — early hops, through sparse/low-degree areas, covering large distances.
- **Zoom-in phase** — later hops, through dense areas, refining the answer.

**Problem with plain NSW:** if the walk hits a local minimum too early (common in sparse regions), it stops before reaching the true nearest neighbor → hurts recall (accuracy). There's no clean way to force "zoom-out first, then zoom-in."

---

## HNSW = NSW + Skip-List Layering

HNSW fixes NSW's early-stopping problem by explicitly splitting the zoom-out/zoom-in phases across layers:

- **Top layer**: fewest vectors, longest links → forces the zoom-out phase to happen here.
- **Lower layers**: more vectors, shorter links → zoom-in phase.
- **Layer 0**: contains *every* vector, densely connected → final precise answer.

Because each layer already narrows down the search area before dropping to the next, the walk naturally starts in "zoom-in mode" by the time it reaches the dense bottom layer — solving NSW's local-minimum problem.

---

## Key Parameters

| Parameter | What it controls | Effect |
|---|---|---|
| **M** | Number of neighbor links assigned to each new vector | Higher M → denser graph, better recall, more memory |
| **Mmax** | Max links allowed per node on layers above 0 | Keeps upper layers sparse |
| **Mmax0** | Max links allowed per node at layer 0 (usually `2 × M`) | Layer 0 needs more connectivity since it does the final precise search |
| **mL (level multiplier)** | Controls the probability a vector gets pushed to higher layers | Optimal ≈ `1 / ln(M)`; lower mL → more vectors stuck at layer 0 (less overlap between layers, but longer walks) |
| **efConstruction** | How many candidate neighbors are considered *while building* the graph | Higher → better quality graph, slower to build; barely affects search-time cost |
| **efSearch** | How many candidates are explored *while querying* | Higher → better recall, slower query |

**Random layer assignment**: each inserted vector gets a randomly chosen top layer (weighted so most land only on layer 0, exponentially fewer reach higher layers) — same mechanism as a skip list deciding how tall a node's tower is.



---

## Insertion (Building the Index)

Vectors are added **one at a time** (not all at once like IVF's k-means):

1. Pick a random layer for the new vector (via `mL`).
2. Starting from the top layer's entry point, greedily walk toward the new vector using `ef = 1` (cheap, coarse search) — just to find a good entry node per layer.
3. Once the walk reaches the vector's assigned layer, switch to `ef = efConstruction` (thorough search) to find good candidate neighbors.
4. Connect the new vector to its `M` closest candidates at that layer, and repeat at each layer below down to layer 0.

**Same vector, multiple layers**: a vector isn't placed at just its assigned layer — it exists at that layer *and every layer below it*, down to layer 0, each with its own separate set of neighbor links (fewer/longer links up top, more/shorter links at the bottom). This is why layer 0 is the only layer guaranteed to contain *every* vector — same idea as a skip-list node's "tower" spanning multiple lanes, not different values per lane.

---

## Search (Querying)

1. Start at the entry point on the **top layer**.
2. Greedily hop to closer neighbors until a local minimum (no closer neighbor) — this is the *zoom-out* stage.
3. Drop to the next layer down, resume greedy search from where you stopped — *zoom-in* refinement.
4. Repeat until **layer 0**, where the search keeps a running candidate list of size `efSearch` to avoid stopping too early, and finally returns the top-k closest found.

**Important:** the output is only the final top-k vectors — the path taken through the layers is discarded, it's just how the answer was found.

---

## Performance Tradeoffs

| Aspect | Behavior |
|---|---|
| **Recall vs. speed** | Higher `M` / `efSearch` → much better recall, but query time grows (roughly 80% recall at ~1ms vs. 100% recall at ~50ms, in the article's benchmark) |
| **efConstruction** | Improves recall almost "for free" at low query volume (one-time build cost); matters more at high query volume |
| **Memory** | Dominated by `M` — more links = more memory (e.g., M=2 → 500MB+, M=512 → ~5GB in their test); `efConstruction`/`efSearch` don't affect memory, only `M` does |

**Common ways to control memory/speed:**
- Use **Product Quantization (PQ)** alongside HNSW to compress stored vectors (less memory, some accuracy loss).
- Combine with **IVF** (cluster first, then HNSW inside clusters) for very large datasets.

---

## One-Line Summary

**HNSW builds a multi-layer graph — sparse/long-range links on top (skip-list idea), dense/short-range links at the bottom — so that greedy nearest-neighbor search (NSW idea) naturally zooms out fast at the top and zooms in precisely at the bottom, giving near-exact results in roughly logarithmic time; the main knobs are `M` (graph density/memory), `efConstruction` (build-time quality), and `efSearch` (query-time recall vs. speed).**
