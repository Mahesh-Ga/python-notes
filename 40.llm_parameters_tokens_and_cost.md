# LLM API Parameters, Tokens, and Cost Estimation
---

## 1. Two categories of "parameters"

It helps to split every knob an LLM API exposes into two buckets:

| Category | What it controls | Examples |
|---|---|---|
| **Decoding / sampling parameters** | *How* the model picks the next token from its probability distribution | `temperature`, `top_p`, `top_k`, `frequency_penalty`, `presence_penalty`, `seed` |
| **Request / control parameters** | *What* gets sent, *how much* comes back, and *how* the call behaves | `model`, `messages`/`system`, `max_tokens`, `stop_sequences`, `stream`, `tools`/`tool_choice`, `response_format` |

The first bucket changes the *content* of the output; the second bucket changes the *shape and cost* of the request/response without touching the model's underlying reasoning. Cost estimation cares mostly about the second bucket (token counts) but `max_tokens` and `stop_sequences` in particular are where the two buckets meet.

---

## 2. Full parameter reference

| Parameter | Typical range / values | What it does | Notes |
|---|---|---|---|
| **`max_tokens`** | 1 → model's max output (e.g., 4K–128K depending on model) | **Required on Claude**, optional-with-default elsewhere. Hard ceiling on *generated* output tokens | Does **not** guarantee that many tokens are generated — it's a cap, not a target. Hitting it truncates output mid-thought (`stop_reason`/`finish_reason` = `"max_tokens"`/`"length"`) |
| **`temperature`** | `0`–`1` (Claude) or `0`–`2` (OpenAI-style APIs) | Scales the logits before softmax — higher = flatter distribution = more random/creative; `0` ≈ deterministic (greedy) | See §3 for the formula |
| **`top_p`** (nucleus sampling) | `0`–`1`, default `1` | Restricts sampling to the smallest set of tokens whose cumulative probability ≥ `p` | Common guidance: tune **either** `temperature` **or** `top_p`, not both aggressively — they compound in ways that are hard to reason about |
| **`top_k`** | positive integer | Restricts sampling to the `k` most-likely next tokens | Less commonly exposed than `top_p`; Claude supports it, OpenAI's chat API historically doesn't |
| **`stop_sequences`** / **`stop`** | list of strings | Generation halts immediately if any listed string is produced | Useful for structured output (e.g., stop at `"\n\n"` or a closing delimiter) without paying for tokens after it |
| **`stream`** | boolean | Return tokens incrementally via SSE instead of one final blob | Doesn't change token count/cost, but avoids client-side timeouts on long generations — required practice once `max_tokens` gets large (see [[28.llm_architecture.md]] on autoregressive generation being inherently sequential) |
| **`frequency_penalty`** | e.g. `-2.0`–`2.0` (OpenAI-style) | Penalizes tokens proportionally to how many times they've *already appeared* — reduces repetition | Not part of Claude's API — Claude relies on training/prompting instead |
| **`presence_penalty`** | e.g. `-2.0`–`2.0` (OpenAI-style) | Penalizes any token that has appeared **at all**, regardless of count — encourages introducing new topics | Same caveat as above |
| **`n`** | positive integer | Number of independent completions to generate per request | Multiplies **output** token cost by `n`; not supported by Claude's Messages API (call `n` times, or use the Batches API for volume) |
| **`seed`** | integer | Best-effort determinism — same seed + same inputs tends to reproduce the same output | "Best-effort," not guaranteed, even at `temperature=0` |
| **`logprobs`** / **`top_logprobs`** | boolean / integer | Return the model's per-token log-probabilities alongside the output | Useful for confidence scoring, classification-via-logprobs, or debugging |
| **`tools`** / **`tool_choice`** | list of tool schemas / `"auto"` \| `"any"` \| `{"type":"tool","name":...}` \| `"none"` | Defines callable tools and whether the model must/may/mustn't call one | Tool *definitions* themselves consume input tokens on every call — a large tool list is a hidden cost multiplier |
| **`response_format`** / **`output_config.format`** | e.g. `{"type": "json_schema", ...}` | Constrains output to valid JSON matching a schema | Removes the need for a "please respond in JSON" prompt instruction and post-hoc parsing/retries |
| **`user`** / **`metadata`** | string / object | Opaque caller-supplied identifier for abuse monitoring/analytics | No effect on model behavior or cost |

## 3. Temperature, top_p, top_k — the actual math

Temperature:  the model's raw logits are divided by T before the softmax (P_i = exp(z_i/T) / Σ exp(z_j/T)), so T<1 stretches the gaps between logits (sharper, more peaked distribution) and T>1 shrinks them (flatter distribution).
- High (e.g., 1.2–2.0): the model becomes more willing to pick lower-probability, less "obvious" words. Output gets more varied, creative, sometimes surprising — but also more likely to ramble, contradict itself, or hallucinate. Same prompt gives noticeably different answers each run.
- Low (e.g., 0–0.3): the model almost always picks its top-choice word. Output is focused, repetitive, predictable, and close to deterministic. Good for factual answers, code, extraction — bad for brainstorming (feels stale/samey).
- 0: essentially "always pick the single most likely next word" — as deterministic as it gets.

top_p (nucleus sampling): sort probabilities descending and keep adding tokens until their cumulative sum first reaches p, then renormalize just that subset — a variable-size candidate pool driven by the model's actual confidence at that step.
- High (close to 1.0, e.g., 0.95–1.0): almost the full vocabulary is eligible at each step, so it barely restricts anything — behavior is dominated by whatever temperature is doing. More variety, more chance of a weird/off-topic token slipping in.
- Low (e.g., 0.1–0.5): only a small handful of the most-likely-next-words are even allowed to be picked, everything else is excluded outright. Output stays safe and on-script, at the cost of variety.

top_k:  after computing the probabilities, keep only the k highest and zero out the rest, then renormalize so they sum to 1 — a fixed-size candidate pool.
- High (e.g., 100+): a large pool of candidate words is allowed at every step, so again it barely constrains anything, similar effect to a high top_p.
- Low (e.g., 1–10, and top_k=1 = greedy): only the top few candidates are ever allowed, so output is very safe/repetitive, regardless of how confident the model actually is at that step (this is the main weakness vs top_p — the cutoff is a fixed count, not based on actual confidence).

**Practical rule of thumb:** pick one primary lever for your use case (usually `temperature` for "how creative", occasionally `top_p` for "how narrow the candidate pool") and leave the other at its default — tuning both away from default simultaneously makes behavior much harder to predict and debug.

## 4. `max_tokens` — what it actually caps, and common gotchas

- **It caps generated *output* tokens only** — it does not include the input/prompt tokens, and it does not count against the *context window* on its own (input + output together must still fit under the model's context window).
- **It is not a target.** The model still decides naturally when to stop (`end_turn`/`stop`); `max_tokens` only forcibly cuts it off if that natural stop hasn't happened yet. Setting it too low is a top cause of silently truncated/broken JSON output — always check the stop reason (`max_tokens`/`length`) before trusting output is complete.
- **Setting it too low is a real bug, not just a minor inefficiency** — a cut-off response usually has to be retried (wasting the tokens already spent), so under-provisioning `max_tokens` can cost *more* than a generous cap, not less.
- **Reasoning/thinking tokens count against it** on models with extended/adaptive thinking — a low `max_tokens` on a hard reasoning task can exhaust the budget on internal reasoning before any visible answer is produced.
- **Large values usually require streaming** (`stream: true`) — a non-streaming HTTP request that might take minutes to fully generate risks client/gateway timeouts; streaming returns tokens incrementally as they're produced.
---

### Tokens vs context window vs max_tokens — the three numbers that trip people up

| Term | What it is |
|---|---|
| **Context window** | Max **input + output combined** tokens the model can attend to in one request (e.g., 200K, 1M) |
| **`max_tokens`** | Max **output-only** tokens for *this specific request* — a request-level cap you set, always ≤ the model's max output |
| **Prompt/input tokens** | Everything you send: system prompt + message history + tool definitions + any retrieved RAG context |

A request fails or gets truncated if `input_tokens + max_tokens` would exceed the context window — this is a common failure mode in long conversations or RAG apps with large retrieved context (mitigated by compaction/summarization, or trimming history — see [[39.llm_response_caching.md]] for a related angle on managing repeated-context cost).

---

for a single LLM API call, `input_tokens + output_tokens ≤ context_window`.

since the API can't know your actual output length in advance, most providers check `input_tokens + max_tokens ≤ context_window` at request time, not the true final output count. So:

- If input_tokens + max_tokens exceeds the context window, the request is rejected
  upfront (a 400-type error), even if the model would have naturally stopped well short
  of max_tokens.
- If the request is accepted, the model can still stop early (end_turn) — the real input_tokens + output_tokens at the end will always be ≤ context window, often with room to spare.

Practical implication for long conversations/RAG apps: as history or retrieved context grows, you must shrink max_tokens (or trim/compact the input) to keep input + max_tokens under the ceiling — this is exactly why context compaction/summarization exists once conversations get long.

## 6. Cost estimation for LLM applications

### The core formula

```
cost_per_request = (input_tokens / 1,000,000) × input_price_per_MTok
                  + (output_tokens / 1,000,000) × output_price_per_MTok
```

Pricing is quoted **per million tokens ("MTok")**, and **input and output are priced differently** — output is almost always several times more expensive than input, because generation (one forward pass per output token, autoregressively) is far more compute-intensive than the single forward pass needed to process the whole input at once.

### Current Anthropic pricing (verified reference point)

| Model | Context | Input $/MTok | Output $/MTok |
|---|---|---|---|
| Claude Haiku 4.5 | 200K | $1.00 | $5.00 |
| Claude Sonnet 5 | 1M | $2.00 | $10.00 |
| Claude Sonnet 4.6 | 1M | $3.00 | $15.00 |
| Claude Opus 5 / 4.8 / 4.7 / 4.6 | 1M | $5.00 | $25.00 |
| Claude Fable 5 / Claude Fable 5.1 | 1M | $10.00 | $50.00 |

*(Anthropic first-party API rates; other providers publish their own tables — same formula applies, just swap the $/MTok numbers. Always pull current numbers from the provider's pricing page before finalizing a budget — these change over time.)*

**Prompt caching changes the input side of the formula** (see [[39.llm_response_caching.md]] for the caching architecture itself).

Without caching, the formula treats `input_tokens` as one uniform block — every input token costs the same `input_price_per_MTok`, on every request, even if 90% of that input is identical to the previous request (a long system prompt, a big tool list, a RAG knowledge-base chunk). Caching breaks that single block into up to three differently-priced pieces:

```
cost_input = (cache_write_tokens / 1e6) × input_price × 1.25
           + (cache_read_tokens  / 1e6) × input_price × 0.1
           + (uncached_tokens    / 1e6) × input_price × 1.0
```

- **Uncached tokens** — anything not marked for caching (e.g., the fresh user query each turn) — priced normally, exactly as in §6's base formula.
- **Cache write** (a token range hits the API for the *first* time, or the cache expired and is being rewritten): ≈**1.25×** normal input price. It costs *more* than a normal token because the server does extra work — computing and storing the model's internal KV-cache state for that prefix so it can be reused later, instead of just processing and discarding it.
- **Cache read** (a *later* request reuses a prefix that's still warm in cache): ≈**0.1×** normal input price — a ~90% discount. The server skips reprocessing that prefix entirely and reuses the stored KV-cache state, so you're paying mostly for the lookup, not the compute.


**Net effect:** the *first* request against a new cache entry is slightly more expensive than uncached (1.25× on the to-be-cached portion), but every subsequent request that hits it drops that portion's cost by ~90%. For any workload where the same large prefix repeats across many requests — RAG systems, agents with big tool schemas, multi-turn chat with a long system prompt — caching pays for itself after just the 2nd or 3rd reuse and compounds from there (see Worked Example 2 below, ~64% cheaper per query once warm).


### Worked example 1 — simple Q&A chatbot (no caching)

Assume Claude Sonnet 5 ($2/$10 per MTok), average conversation turn: 500 input tokens (short history + system prompt), 200 output tokens.

```
cost_per_turn = (500 / 1e6) × 2.00 + (200 / 1e6) × 10.00
              = 0.0010 + 0.0020
              = $0.0030 per turn
```

At 10,000 turns/day: `10,000 × $0.003 = $30/day ≈ $900/month`.

### Worked example 2 — RAG app with a cached system prompt/knowledge base

Same model, but now each query carries a large retrieved-context block reused across many queries: 4,000 tokens of system+retrieved-context (cached after the first hit) + 150 tokens of actual user query, 300 output tokens.

**Without caching**, every request pays full input price on all 4,150 input tokens:
```
cost_per_query = (4150/1e6)×2.00 + (300/1e6)×10.00 = 0.0083 + 0.0030 = $0.0113
```

**With caching** (after the first request warms the cache), the 4,000-token block reads at ~0.1× input price:
```
cached_portion = (4000/1e6) × (2.00 × 0.1) = 0.0008
uncached_portion = (150/1e6) × 2.00 = 0.0003
output = (300/1e6) × 10.00 = 0.0030
cost_per_query ≈ $0.0041
```
→ roughly **64% cheaper per query** once the cache is warm — this is why RAG/agent systems with a large, stable system prompt or tool list should almost always use prompt caching (Topic 39).

### Worked example 3 — batch classification job

Classifying 100,000 support tickets, ~300 input tokens each, ~20 output tokens each (a label), using Claude Haiku 4.5 ($1/$5 per MTok) via the **Batch API** (50% discount, appropriate since results aren't needed in real time):

```
per_item = (300/1e6)×1.00 + (20/1e6)×5.00 = 0.0003 + 0.0001 = $0.0004
batch_total = 100,000 × 0.0004 × 0.5 (batch discount) = $20
```

**Takeaway pattern for estimating any app's cost:** identify (1) the cheapest model that meets the quality bar for the task (classification/extraction rarely needs a frontier model), (2) whether requests share a large stable prefix worth caching, and (3) whether the workload can tolerate async batch processing — those three levers, applied in that order, are usually where the majority of realistic cost savings come from, before ever touching a paid upgrade to a larger model.

### Monthly cost projection template

```
monthly_cost = requests_per_day × 30 × cost_per_request
```

Always model at least three volume scenarios (current, 10×, 100×) — LLM apps often go from prototype to production with an order-of-magnitude traffic jump, and that's exactly when an uncached, unbatched, wrong-model-tier design becomes an expensive surprise instead of a cheap one.

## 7. Quick interview-answer summary

- **"What's the difference between temperature and top_p?"** — temperature rescales the whole probability distribution (softmax with a divisor); top_p truncates the candidate pool to the smallest set covering a cumulative probability mass. Tune one, not both, for predictable behavior.
- **"What does `max_tokens` actually control?"** — a hard ceiling on *generated output* tokens for that request, not a target length and not the same as the context window; hitting it truncates output and requires checking the stop/finish reason.
- **"How many tokens is a word?"** — roughly 0.75 words per token / 4 characters per token in English, but always verify with the provider's own token-counting endpoint for anything cost-sensitive — tokenizers differ across providers.
- **"How do you estimate cost for an LLM feature before shipping it?"** — `(input_tokens/1M)×input_price + (output_tokens/1M)×output_price` per request, multiplied by expected volume; then check whether prompt caching (repeated context) or the Batch API (non-real-time workloads) meaningfully cut that before considering a smaller model.
- **"Why is output more expensive than input per token?"** — output generation is autoregressive (one sequential forward pass per token); input processing happens once, in parallel, over the whole prompt.
