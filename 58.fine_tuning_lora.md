## 1. What is Fine-Tuning?

**Fine-tuning** is the process of taking a pre-trained model and training it further on a smaller, task-specific dataset so that it performs better on that task.

A pre-trained LLM (like Llama or Mistral) already knows grammar, facts and reasoning because it was trained on trillions of tokens. But it is a general model. It does not know your company's tone, your support ticket format, or your medical or legal terminology.

In simple words:

> **Pre-training** = going through school and learning general knowledge.
> **Fine-tuning** = a specialised job training for one role.

During fine-tuning the weights of the model are updated (fully or partly) using a new dataset, so the model's behaviour changes permanently (until you retrain).

---

## 2. Why Do We Need Fine-Tuning?

- **Domain adaptation:** teach the model medical, legal, financial or code-specific language.
- **Style and tone:** make the model always answer in a fixed brand voice or format (for example, strict JSON).
- **Task specialisation:** classification, extraction, summarisation, SQL generation.
- **Smaller and cheaper models:** a fine-tuned 7B model can match a much larger general model on one narrow task, which reduces inference cost and latency.
- **Shorter prompts:** behaviour learned in the weights does not need long instructions or many few-shot examples in every request.
- **Private data:** keep the logic inside your own model instead of sending long prompts to an external API.

---

## 3. Fine-Tuning vs Prompt Engineering vs RAG

| Feature | Prompt Engineering | RAG | Fine-Tuning |
|---|---|---|---|
| What changes | Only the input text | Input + retrieved documents | Model weights |
| Best for | Quick experiments, simple tasks | Fresh or private **knowledge** | Changing **behaviour, style, format** |
| New knowledge | Limited to context window | Easy, just update the index | Hard, can be forgotten or hallucinated |
| Cost to start | Almost zero | Medium (vector DB, pipeline) | High (GPUs, data, training) |
| Update speed | Instant | Fast | Slow (retrain) |
| Inference cost | Long prompts cost more | Retrieval + longer prompts | Short prompts, cheaper per call |
| Risk | Prompt fragility | Bad retrieval | Overfitting, catastrophic forgetting |

**Rule of thumb:**

- Need the model to **know** something new or changing → use **RAG**.
- Need the model to **behave** differently (format, tone, skill) → use **fine-tuning**.
- Often the best systems use **both**: a fine-tuned model plus RAG.

Always try prompt engineering first, then RAG, and fine-tune only when those are not enough.

---

## 4. Types of Fine-Tuning

1. **Supervised Fine-Tuning (SFT):** train on (prompt, ideal response) pairs. This is the most common type.
2. **Instruction Tuning:** SFT on a wide variety of instructions so the model follows commands (this is how a base model becomes a chat model).
3. **Domain-Adaptive (Continued) Pre-Training:** keep training on raw domain text (no labels) to absorb vocabulary and knowledge.
4. **Preference Tuning:** align the model with human preferences using RLHF, DPO, ORPO and similar methods. See [[37.RLHF.md]].
5. **Task-Specific Fine-Tuning:** classification, NER, summarisation, etc.

Based on how many weights are updated:

- **Full fine-tuning:** all weights are updated.
- **Parameter-efficient fine-tuning (PEFT):** only a tiny number of extra or selected weights are updated (LoRA, QLoRA, adapters, etc.).

---

## 5. Full Fine-Tuning and Its Problems

In full fine-tuning every parameter of the model gets gradients and is updated.

**Memory needed during training** (mixed precision with Adam optimizer), roughly per parameter:

| Item | Bytes per parameter |
|---|---|
| Weights (FP16) | 2 |
| Gradients (FP16) | 2 |
| Optimizer states (Adam: momentum + variance in FP32) | 8 |
| FP32 master copy of weights | 4 |
| **Total** | **~16 bytes** |

For a 7B model: 7 billion × 16 bytes ≈ **112 GB**, and that is before activations. A 70B model needs over 1 TB. This does not fit on a normal GPU.

**Problems of full fine-tuning:**

- Very high GPU memory and compute cost.
- A separate full copy of the model (14 GB for 7B in FP16) must be stored for **every** task.
- **Catastrophic forgetting:** the model can lose its general abilities while learning the new task.
- Slow to train and slow to switch between tasks at serving time.

This is why PEFT methods became popular.

---

## 6. Parameter-Efficient Fine-Tuning (PEFT)

**PEFT** means freezing most or all of the pre-trained weights and training only a very small number of parameters (often under 1%).

Benefits:

- Needs far less GPU memory (no gradients or optimizer states for the frozen weights).
- Trains faster.
- The saved output is tiny (a few MB to a few hundred MB instead of many GB).
- The frozen base model keeps its general knowledge, so less forgetting.
- One base model can serve many tasks by swapping small adapters.

The most widely used PEFT method is **LoRA**.

---

## 7. What is LoRA?

**LoRA (Low-Rank Adaptation)** was introduced by Microsoft researchers in 2021. Instead of updating a large weight matrix directly, LoRA keeps the original weights **frozen** and learns the *change* to the weights as the product of two small matrices.

**Key idea:** When we fine-tune a large model, the weight update ΔW has a **low intrinsic rank**. This means the useful change can be represented by a much smaller number of values than the full matrix holds.

So instead of learning a huge ΔW of size d × k, LoRA learns two small matrices:

- **A** of size r × k
- **B** of size d × r

where **r** (the rank) is very small compared to d and k (for example 8 or 16).

```
        Input x
          │
   ┌──────┴───────────────┐
   │                      │
   ▼                      ▼
Frozen weight W      LoRA path
 (d × k)             ┌─────────┐
   │                 │  A      │  (r × k)  down-projection
   │                 └────┬────┘
   │                      │
   │                 ┌────▼────┐
   │                 │  B      │  (d × r)  up-projection
   │                 └────┬────┘
   │                      │  × (alpha / r)
   ▼                      ▼
   └──────────►  ( + ) ◄──┘
                   │
                   ▼
                Output h
```

The output of the layer becomes:

```
h = W·x + (alpha / r) · B·A·x
```

Only **A** and **B** are trained. **W** never changes.

---

## 8. The Math Behind LoRA

In a normal fine-tuning step, a weight matrix W₀ is updated to:

```
W = W₀ + ΔW          (ΔW has size d × k)
```

LoRA says: restrict ΔW to be a low-rank product.

```
ΔW = B · A
B ∈ R^(d × r),   A ∈ R^(r × k),   r << min(d, k)
```

**Forward pass:**

```
h = W₀·x + ΔW·x = W₀·x + B·(A·x)
```

Note that we compute `A·x` first (a small r-dimensional vector) and then `B` times that, so we never build the full d × k matrix during training.

**Scaling factor:** the LoRA output is multiplied by `alpha / r`. This keeps the size of the update stable when you change r, so you do not need to retune the learning rate every time.

**Initialisation:**

- **A** is initialised with small random values (Gaussian / Kaiming).
- **B** is initialised with **zeros**.

Because B = 0, ΔW = B·A = 0 at the start. This means the model starts exactly equal to the pre-trained model and training moves away from it smoothly.

**Number of trainable parameters:**

```
Full matrix:   d × k
LoRA:          r × (d + k)
```

**No inference overhead:** after training, we can compute `W = W₀ + (alpha/r)·B·A` once and store it as a normal weight matrix. The merged model has the same size and speed as the original.

---

## 9. Worked Example with Numbers

Take one attention weight matrix of size 4096 × 4096 (common in a 7B model) and rank r = 8.

- Full matrix parameters: 4096 × 4096 = **16,777,216** (about 16.8 M)
- LoRA parameters: r × (d + k) = 8 × (4096 + 4096) = **65,536**

```
Reduction = 16,777,216 / 65,536 = 256 times fewer parameters
```

The LoRA matrices use only about **0.39%** of the parameters of that layer.

For a full 7B model with LoRA on the attention projections, the trainable parameters are usually around **0.1% to 1%** of the total (roughly 4 M to 40 M parameters, depending on r and target modules).

Memory view for a 7B model:

| Method | Approx. GPU memory |
|---|---|
| Full fine-tuning (FP16 + Adam) | ~110 GB+ |
| LoRA (FP16 base frozen) | ~16–20 GB |
| QLoRA (4-bit base frozen) | ~6–10 GB |

(The numbers vary with batch size, sequence length and gradient checkpointing.)

## 10. Important LoRA Hyperparameters

| Parameter | Meaning | Typical values |
|---|---|---|
| **r (rank)** | Size of the low-rank bottleneck. Higher = more capacity, more parameters | 8, 16, 32, 64 |
| **lora_alpha** | Scaling constant. Final scale = alpha / r | Usually r or 2×r (e.g. 16, 32) |
| **lora_dropout** | Dropout applied on the LoRA path to reduce overfitting | 0.0 – 0.1 |
| **target_modules** | Which layers get LoRA matrices | q_proj, v_proj (minimum); all linear layers for best quality |
| **bias** | Whether to train bias terms | "none" (default) |
| **learning rate** | LoRA uses a higher LR than full fine-tuning | 1e-4 to 3e-4 |
| **task_type** | Type of task, e.g. CAUSAL_LM | CAUSAL_LM |

**How to choose r:**

- Small, simple tasks (style, format): r = 8 or 16 is usually enough.
- Complex tasks or new domains (maths, code): r = 32 to 128 may help.
- Bigger r does not always give a better result; it may just overfit and cost more memory.

**About alpha:** a common starting point is `alpha = 2 × r`. A larger alpha/r ratio means the adapter has a stronger effect.

---

## 11. Where is LoRA Applied?

A transformer block has two main parts: attention (Wq, Wk, Wv, Wo) and the feed-forward network (gate, up, down projections).

- The **original paper** applied LoRA only to the **query (Wq)** and **value (Wv)** matrices.
- Later practice (and QLoRA paper) showed that applying LoRA to **all linear layers** (q, k, v, o, gate, up, down) gives better quality for the same rank.
- Embeddings and the final LM head are usually left frozen (unless you add new tokens).

Rule: more target modules = more trainable parameters and better quality, but also more memory.

## 12. Merging and Serving LoRA Adapters

After training, the output is a small **adapter** file (the A and B matrices), usually 10 MB to a few hundred MB.

You have two options for serving:

**1. Merge into the base model**

```
W_merged = W₀ + (alpha / r) · B · A
```

- Result is a normal model with zero extra latency.
- Good when you have only one task.
- Downside: you now store a full copy of the model again.

**2. Keep adapters separate (multi-LoRA serving)**

- Load one base model in GPU memory once.
- Load many small adapters (one per customer or task) and pick one per request.
- Engines like **vLLM**, LoRAX and Hugging Face TGI support this. See [[54.vllm.md]].
- Very cost effective for multi-tenant systems: one GPU can serve hundreds of fine-tuned variants.
- Small extra latency because the LoRA path is computed alongside the base layer.

You can also **combine** adapters (adding or weighting them) to mix skills, though results vary.

## 13. QLoRA

**QLoRA (Quantized LoRA)**, introduced in 2023, lets you fine-tune a large model on a single consumer or mid-range GPU. For example, a 65B model can be fine-tuned on one 48 GB GPU.

It combines three ideas:

1. **4-bit NormalFloat (NF4) quantisation:** the frozen base model is stored in 4-bit precision, which uses about 4 times less memory than FP16. NF4 is designed for weights that follow a normal distribution.
2. **Double quantisation:** the quantisation constants themselves are quantised again to save a little more memory.
3. **Paged optimizers:** optimizer states are moved to CPU RAM automatically when GPU memory spikes, avoiding out-of-memory crashes.

**How it works during training:**

- The base weights are stored in 4-bit.
- When a layer is needed, its weights are **de-quantised to BF16** on the fly for the forward and backward calculation.
- The LoRA adapters (A and B) are kept in BF16/FP16 and are the **only** parameters that receive gradients.
- Gradients flow through the frozen 4-bit weights into the adapters.

**LoRA vs QLoRA:**

| Feature | LoRA | QLoRA |
|---|---|---|
| Base model precision | FP16 / BF16 | 4-bit (NF4) |
| GPU memory | Medium | Very low |
| Training speed | Faster | Slower (~20–30%) because of de-quantisation |
| Quality | Full precision base | Almost the same as LoRA in most cases |
| Use when | You have enough GPU memory | GPU memory is limited |

## 14. Other PEFT Methods

| Method | Idea |
|---|---|
| **Adapters** | Insert small bottleneck layers inside each transformer block; only those are trained. Adds a little inference latency. |
| **Prefix Tuning** | Learn trainable "virtual token" vectors prepended to the keys and values at every layer. |
| **Prompt Tuning** | Learn trainable soft prompt embeddings only at the input layer. Very cheap but weaker on small models. |
| **P-Tuning** | Uses a small network to produce the soft prompts. |
| **IA³** | Learns vectors that rescale activations (keys, values, FFN). Even fewer parameters than LoRA. |
| **DoRA** | Splits the weight into magnitude and direction; applies LoRA to direction. Often closer to full fine-tuning quality. |
| **LoRA+** | Uses different learning rates for A and B for faster convergence. |
| **AdaLoRA** | Adjusts the rank per layer automatically based on importance. |
| **BitFit** | Trains only the bias terms. |

LoRA is the default choice mainly because it adds **no inference latency after merging**, is simple, and has strong tooling support.

## 15. Preparing the Dataset

Data quality matters more than data quantity. A few thousand clean, diverse examples often beat a hundred thousand noisy ones.

**Common formats:**

Instruction format:

```json
{
  "instruction": "Summarise the following support ticket.",
  "input": "Customer says the app crashes when uploading a PDF...",
  "output": "App crashes on PDF upload. Needs a bug fix."
}
```

Chat format (preferred for chat models):

```json
{
  "messages": [
    {"role": "system", "content": "You are a helpful support agent."},
    {"role": "user", "content": "How do I reset my password?"},
    {"role": "assistant", "content": "Go to Settings > Security > Reset password."}
  ]
}
```

**Tips:**

- Use the **same chat template** that the base model was trained with (special tokens matter).
- Compute loss only on the **assistant response** tokens, not on the prompt (loss masking).
- Remove duplicates, wrong answers and personal data.
- Keep the data distribution close to what you expect in production.
- Hold out a validation set (about 5–10%).
- Typical sizes: 500–5,000 examples for style/format, 10k+ for new skills.

## 16. Step-by-Step LoRA Fine-Tuning Code

Using Hugging Face `transformers`, `peft`, `trl` and `bitsandbytes` (QLoRA setup).

```python
import torch
from datasets import load_dataset
from transformers import (
    AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig
)
from peft import LoraConfig, prepare_model_for_kbit_training, get_peft_model
from trl import SFTTrainer, SFTConfig

model_name = "meta-llama/Llama-3.1-8B"

# 1. Load the base model in 4-bit (QLoRA). Remove this config for plain LoRA.
bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_use_double_quant=True,
    bnb_4bit_compute_dtype=torch.bfloat16,
)

tokenizer = AutoTokenizer.from_pretrained(model_name)
tokenizer.pad_token = tokenizer.eos_token

model = AutoModelForCausalLM.from_pretrained(
    model_name,
    quantization_config=bnb_config,
    device_map="auto",
)
model = prepare_model_for_kbit_training(model)

# 2. Define the LoRA configuration
lora_config = LoraConfig(
    r=16,
    lora_alpha=32,
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM",
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                    "gate_proj", "up_proj", "down_proj"],
)

model = get_peft_model(model, lora_config)
model.print_trainable_parameters()
# trainable params: ~42M || all params: ~8B || trainable%: ~0.5

# 3. Load the dataset
dataset = load_dataset("json", data_files="train.jsonl", split="train")

# 4. Training arguments
args = SFTConfig(
    output_dir="./lora-out",
    num_train_epochs=3,
    per_device_train_batch_size=4,
    gradient_accumulation_steps=4,      # effective batch size = 16
    learning_rate=2e-4,
    lr_scheduler_type="cosine",
    warmup_ratio=0.03,
    bf16=True,
    logging_steps=10,
    save_strategy="epoch",
    gradient_checkpointing=True,        # saves memory, costs some speed
    max_seq_length=2048,
)

# 5. Train
trainer = SFTTrainer(
    model=model,
    train_dataset=dataset,
    args=args,
    processing_class=tokenizer,
)
trainer.train()

# 6. Save only the adapter (a few MB)
trainer.model.save_pretrained("./lora-adapter")
```

**Loading and merging later:**

```python
from peft import PeftModel
from transformers import AutoModelForCausalLM

base = AutoModelForCausalLM.from_pretrained(model_name, torch_dtype=torch.bfloat16)
model = PeftModel.from_pretrained(base, "./lora-adapter")

merged = model.merge_and_unload()      # W = W0 + (alpha/r) * B * A
merged.save_pretrained("./merged-model")
```

**Serving with vLLM (multi-LoRA):**

```bash
vllm serve meta-llama/Llama-3.1-8B --enable-lora \
    --lora-modules support-bot=./lora-adapter
```

## 17. Evaluating a Fine-Tuned Model

- **Loss curves:** training loss should go down; if validation loss starts going up while training loss keeps falling, the model is **overfitting**.
- **Task metrics:** accuracy, F1, ROUGE, exact match, JSON validity rate, depending on the task. See [[47.accuracy_precision_recall_f1.md]].
- **LLM-as-a-judge** and human review for open-ended generation. See [[38.AI evaluation.md]].
- **Regression check:** run a few general benchmarks (MMLU, HellaSwag) to confirm the model did not forget general skills.
- **Compare with baselines:** the base model with a good prompt, and the base model with RAG. If fine-tuning does not beat them, it is not worth it.

## 18. Common Problems and Fixes

| Problem | Cause | Fix |
|---|---|---|
| Overfitting | Too many epochs, too little data, too high r | Fewer epochs, more data, add dropout, lower r |
| Catastrophic forgetting | Learning rate too high, narrow data | Lower LR, mix in general data, lower r |
| Out of memory | Large batch, long sequences | Gradient checkpointing, smaller batch + gradient accumulation, QLoRA |
| Model repeats or rambles | Missing EOS token in training data | Add EOS token to each example |
| Poor output format | Wrong chat template | Use the model's official template |
| No improvement | Low-quality data or r too small | Clean data, target all linear layers, increase r |
| Hallucinated facts | Fine-tuning does not reliably add knowledge | Use RAG for knowledge |
| Loss is NaN | LR too high or FP16 instability | Lower LR, use BF16 |

## 19. Advantages and Disadvantages

**Advantages of LoRA**

- Trains 0.1–1% of parameters, so it is cheap and fast.
- Small adapter files, easy to store, share and version.
- Base model stays frozen, reducing forgetting.
- Many adapters can share one base model (multi-tenant serving).
- No inference latency once merged.
- Works well with quantisation (QLoRA).

**Disadvantages of LoRA**

- Can underperform full fine-tuning on very large distribution shifts (e.g. learning a new language from scratch).
- Extra hyperparameters to tune (r, alpha, target modules).
- Not ideal for injecting large amounts of new factual knowledge.
- Unmerged adapters add small latency and complexity at serving.
- Learns less and forgets less than full fine-tuning (the "LoRA learns less, forgets less" trade-off).

## 20. Interview Questions

**Q1. What is LoRA and why is it used?**
LoRA freezes the pre-trained weights and learns the weight update as the product of two small low-rank matrices (B and A). It cuts trainable parameters by hundreds of times, so fine-tuning needs far less memory and produces tiny adapter files.

**Q2. Why does low-rank adaptation work?**
Research on over-parameterised models shows that the change needed for adapting to a new task lies in a low-dimensional subspace. So a low-rank ΔW captures most of what is needed.

**Q3. Why is B initialised to zero and A random?**
So that ΔW = B·A is zero at the start and the model begins exactly as the pre-trained one. If both were zero, gradients would be zero and nothing would learn. If both were random, the model would start with random noise added to it.

**Q4. What do r and alpha do?**
r is the rank (capacity of the adapter). alpha scales the update by alpha/r. Larger alpha/r means a stronger effect of the adapter on the output.

**Q5. Does LoRA slow down inference?**
Not after merging, because the adapter is folded into the weights. If kept separate there is a small overhead from the extra matrix multiplications.

**Q6. Which layers should you apply LoRA on?**
At minimum the query and value projections; for best quality all linear layers (attention and MLP projections).

**Q7. What is QLoRA and how is it different?**
QLoRA stores the frozen base model in 4-bit NF4, uses double quantisation and paged optimizers, and trains LoRA adapters in BF16 on top. It allows fine-tuning very large models on a single GPU with almost no quality loss.

**Q8. LoRA vs full fine-tuning?**
Full fine-tuning updates all weights, needs about 16 bytes per parameter in memory and produces a full model copy per task. LoRA updates a tiny fraction, uses much less memory, and produces small adapters, with slightly lower ceiling on hard tasks.

**Q9. Fine-tuning or RAG for adding company knowledge?**
RAG. Fine-tuning is for behaviour, style and format. Knowledge changes often and RAG gives source citations and easy updates. Use fine-tuning plus RAG when you need both.

**Q10. How do you serve hundreds of fine-tuned models cheaply?**
Keep one base model in GPU memory and load LoRA adapters per request (multi-LoRA serving in vLLM or LoRAX). Each adapter is a few MB, so one GPU can host many tenants.

**Q11. How do you prevent catastrophic forgetting?**
Use PEFT (frozen base), keep learning rate low, mix some general data into the training set, limit epochs and use a small rank.

**Q12. How do you decide whether fine-tuning is worth it?**
Start with a strong prompt and a baseline evaluation. If prompting and RAG cannot hit the quality, latency or cost target, collect clean data and fine-tune. Then compare against the baseline on the same test set.

**Q13. How many parameters does LoRA add for a d × k matrix?**
r × (d + k). For 4096 × 4096 with r = 8 that is 65,536 instead of about 16.8 million.

**Q14. What is DoRA?**
Weight-Decomposed LoRA. It splits each weight into magnitude and direction, applies LoRA to the direction and trains the magnitude separately. It usually gets closer to full fine-tuning quality at the same rank.

**Q15. What is loss masking in SFT?**
Computing the loss only on the response tokens so the model learns to produce answers, not to repeat the prompt.
