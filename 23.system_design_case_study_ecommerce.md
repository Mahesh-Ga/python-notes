# Worked System Design Example — E-Commerce Order Platform

> One end-to-end example applying every concept from `22.system_design_data_modeling_architecture_notes.md`. Follow the Part 4 framework from that file: requirements → estimation → high-level design → deep dive → tradeoffs. Use this as the walkthrough you'd actually narrate in an interview.

---

## 1. Requirements

**Functional:**
- Browse/search a product catalog.
- Add to cart, check out, pay.
- View order status and history.
- Inventory must never be oversold.
- Sellers can update stock/price.

**Non-functional (drives every later decision):**
- Read-heavy on catalog/search (100:1 read:write), write-heavy and consistency-critical on orders/payments/inventory.
- Must survive a flash-sale traffic spike (10-50x normal QPS for a few minutes) on a small set of "hot" products.
- Payment and inventory must be **strongly consistent** (never double-charge, never oversell). Search index and recommendations can be **eventually consistent** (a few seconds of staleness is fine).
- Global user base → need low read latency worldwide.

## 2. Back-of-envelope estimation

- 10M DAU, 5 catalog page views/user/day → 50M reads/day ≈ 580 catalog reads/sec average, design for 10x peak ≈ 6,000/sec.
- 200K orders/day ≈ 2.3 orders/sec average, but concentrated in bursts (flash sales) → design order path for 500-1000/sec burst.
- Product catalog: 10M SKUs × ~2KB (with images referenced, not embedded) ≈ 20GB — fits comfortably in a document store, even fully cached in Redis if needed.
- Orders: 200K/day × 365 × 5 years × ~1KB ≈ 365M rows, ~365GB — this is the table that eventually needs sharding.

**Conclusion from the math**: catalog reads are the dominant traffic (cache + CDN heavy); orders are lower-volume but need strong consistency and will need sharding only at a multi-year horizon — don't over-engineer sharding on day one, but design the schema so it's shardable later (see §6).

## 4. Domain-Driven Design: Bounded Contexts

Each service above = one **bounded context**, drawn along the seams where the domain model actually changes meaning:

| Bounded Context | Owns | Aggregate Root |
|---|---|---|
| Catalog | Product info, pricing, seller data | `Product` |
| Inventory | Stock levels, reservations | `StockItem` |
| Cart | In-progress selections before checkout | `Cart` |
| Order | Order lifecycle, line items | `Order` (line items only mutate through it) |
| Payment | Charges, refunds | `Payment` |
| Search | Read-optimized denormalized product index | — (read model, not a domain owner) |

Note "Customer" means something different in each context (Catalog cares about a customer's browsing/pricing tier; Payment cares about their billing details) — that's the classic bounded-context signal from DDD.

## 5. Data Modeling per Service

**Catalog (MongoDB, document store)** — chosen because product attributes vary wildly by category (a book has an ISBN, a shirt has a size/color matrix) and reads dominate; embed variant/attribute data directly in the product document since it's always read together:

```json
{
  "_id": "prod_123",
  "name": "Wireless Mouse",
  "category": "electronics",
  "price_cents": 2999,
  "seller_id": "seller_88",
  "attributes": { "color": "black", "wireless": true },
  "variants": [{ "sku": "WM-BLK-1", "stock_hint": 42 }]
}
```
`stock_hint` is a **denormalized, eventually-consistent copy** for display only — the real, authoritative stock count lives in Inventory (strong consistency required there, not here — a stale "42 in stock" shown on a page is fine; an actual oversell is not).

**Inventory (PostgreSQL, relational, strong consistency)** — this is where correctness matters most, so it's SQL with real transactions:

```sql
CREATE TABLE stock_items (
    sku            TEXT PRIMARY KEY,
    available_qty  INT NOT NULL CHECK (available_qty >= 0),
    reserved_qty   INT NOT NULL DEFAULT 0,
    version        INT NOT NULL DEFAULT 0   -- optimistic concurrency
);
```
Reserving stock is a single row `UPDATE ... WHERE available_qty >= :qty` (atomic, the `CHECK` constraint is the last line of defense against a race condition ever oversell­ing).

**Orders (PostgreSQL, relational)** — orders need joins (order → line items → product refs) and ACID transactions around checkout:

```sql
CREATE TABLE orders (
    id           UUID PRIMARY KEY,
    user_id      UUID NOT NULL,
    status       TEXT NOT NULL,   -- PENDING, PAID, SHIPPED, CANCELLED
    total_cents  INT NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE TABLE order_items (
    order_id     UUID REFERENCES orders(id),
    sku          TEXT NOT NULL,
    qty          INT NOT NULL,
    price_cents  INT NOT NULL
);
CREATE INDEX idx_orders_user_id ON orders(user_id);   -- most common query pattern
```

**Search (Elasticsearch)** — a **denormalized read model**, populated asynchronously from Catalog+Inventory events, not queried directly against MongoDB — full-text search and faceted filtering need a purpose-built index, and it's fine for it to lag by a few seconds (eventual consistency).

This mix — MongoDB + Postgres + Redis + Elasticsearch in one system — is **polyglot persistence**: pick the storage model per workload instead of forcing one database to do everything (§2.3 of the data-modeling notes).

## 6. Deep Dive: Placing an Order (the hard part)

Order placement spans three services (Order, Inventory, Payment) that each own their own database — no shared ACID transaction is possible across them. This is a textbook **Saga pattern**, orchestrated (chosen over choreography here because checkout has a strict, easy-to-reason-about step order and needs a clear compensating-action path on failure):

```
Order Service (orchestrator)
   1. Create order (status=PENDING)
   2. Call Inventory: reserve stock  ──fail──► mark order FAILED, stop
        │success
   3. Call Payment: charge card (with Idempotency-Key = order_id) ──fail──► compensate: release stock reservation, mark order FAILED
        │success
   4. Mark order PAID, emit OrderPlaced event to Kafka
   5. (async, via event) Notification service sends confirmation
   6. (async, via event) Search/analytics read models update
```

- **Idempotency key = `order_id`** on the payment call — if the orchestrator's call to Payment times out and retries, Payment recognizes the same key and returns the original result instead of charging twice. This is the same principle as REST API idempotency (§1.8) and Celery task idempotency.
- **Compensating action** — if payment fails after stock was reserved, the saga explicitly releases the reservation (a compensating transaction), since there's no distributed rollback across two separate databases.
- **CQRS** in action — the `orders` Postgres table is the write model (source of truth); the Elasticsearch/analytics view of "my orders" is a separate, denormalized read model kept in sync via the `OrderPlaced`/`OrderShipped` events on Kafka, optimized purely for fast reads, decoupled from the write path.
- **Event sourcing (partial)** — rather than only storing current `status`, also append every status transition (`OrderPlaced`, `PaymentConfirmed`, `Shipped`) as an event on the Kafka topic; this event log is what both Search's read model *and* Notification service consume independently, and it doubles as a full audit trail.

## 7. Caching Strategy

- **Product pages**: cache-aside in Redis, key `product:{sku}`, TTL 5 min. On a price/stock update, explicitly invalidate the key (write-through invalidation) rather than waiting for TTL, since stale prices are a worse failure mode than a cache miss.
- **CDN**: all product images and static assets served from CDN edge nodes — removes the vast majority of bytes from the origin entirely.
- **Cart**: stored in Redis directly (not cached-from-DB) since a cart is inherently short-lived, session-scoped data — TTL-expired if abandoned.
- **Thundering herd mitigation**: for a flash-sale product page, a naive TTL expiry could cause thousands of concurrent requests to simultaneously miss cache and hammer MongoDB. Mitigate with request coalescing (first request to miss repopulates the cache while others wait on it) and staggered TTLs so hot keys don't all expire at the same instant.

## 8. Hot Partition: the Flash-Sale Problem

If `orders` were sharded by `sku` (product), a flash sale on one product would slam a single shard — a textbook **hot partition** (§1.10). Fix: shard `orders` by `user_id` or `order_id` instead (evenly distributes load — no single customer or single order ID range should dominate traffic), and handle "is this SKU in stock" as a **separate, single-row hot-key problem** in Inventory, not a sharding problem: a single `stock_items` row for a viral SKU under extreme write contention is mitigated by a short-lived in-memory reservation counter (e.g. a Redis `DECR`, atomic, sub-millisecond) in front of the authoritative Postgres row, which absorbs the burst and reconciles to Postgres — the same "cache absorbs write contention, source of truth stays correct" pattern used broadly in flash-sale designs.

This is also a good moment to note the **shard-key choice principle** from §1.5: pick the key that matches your dominant query pattern (`user_id`, since "get my orders" is the hot read) *and* distributes load evenly — a `sku`-based shard key fails the second criterion under exactly the traffic pattern this system must survive.

## 9. Consistency & CAP Tradeoffs, Per Component

| Component | Chosen model | Why |
|---|---|---|
| Inventory | Strong consistency (CP) | Overselling is a real business/legal problem — a stale read that says "in stock" when it's not is unacceptable. |
| Payment | Strong consistency (CP) + idempotency | Double-charging a customer is unacceptable. |
| Catalog display / stock_hint | Eventual consistency (AP) | A page showing "42 in stock" when it's actually 40 for a few seconds is a fine tradeoff for availability/speed. |
| Search index | Eventual consistency (AP) | A few seconds of lag before a new product appears in search is acceptable. |
| Order history read model | Eventual consistency (AP) | Slightly stale "my orders" list is fine; the authoritative order write path (§6) stays strongly consistent. |

This is the practical answer to "how do you handle CAP in a real system": **you don't pick one answer for the whole system — you pick per component, based on which failure (staleness vs unavailability) is actually cheaper for that specific piece of data.**

## 10. Scaling & Load Balancing

- **API Gateway** is an L7 load balancer — routes `/catalog/*`, `/cart/*`, `/orders/*` to the right service, terminates TLS, and is the single place rate limiting and auth are enforced (rather than reimplemented per service).
- **Rate limiting**: token bucket per user/API key at the gateway — critical on the checkout endpoint specifically during flash sales, to stop a retry storm (buggy client retries) or bot traffic from amplifying load on Inventory/Payment.
- All services are **stateless** (session/cart state lives in Redis, not in-process) so the gateway can freely round-robin/least-connections load balance across any number of horizontally-scaled instances.
- **Catalog reads** scale via Postgres/Mongo **read replicas** + the Redis cache layer absorbing the vast majority of traffic before it ever reaches a DB.
- **Service mesh** (optional, once the service count grows past what's manageable per-service): sidecar proxies handle retries, mTLS, and load balancing between internal services uniformly, instead of each service reimplementing that logic.

## 11. Failure Handling (tying back to the failure-mode vocabulary)

- **SPOF** — every stateful store (Postgres, MongoDB, Redis, Kafka) runs as a replicated cluster, not a single node; the API Gateway itself runs as multiple instances behind DNS/anycast, not one box.
- **Cascading failure** — the Order Service's call to Payment is wrapped in a **circuit breaker**: if Payment's error rate spikes, the breaker trips and Order Service fails fast (returns "try again shortly") instead of piling up slow/blocked requests that would eventually exhaust Order Service's own thread/connection pool and take it down too.
- **Retry storms** — the orchestrator's retry to Payment on timeout uses **exponential backoff with jitter**, and caps attempts — not a tight retry loop that would pile more load onto an already-struggling Payment service.
- **Bulkheads** — Order Service's connection pool to Payment is separate from its pool to Inventory, so Payment being slow can't starve Order Service's ability to still talk to Inventory (or anything else).
- **Split brain** — Postgres primary election (for Inventory/Orders/Payment) goes through a consensus-based failover tool (e.g. Patroni using etcd/Raft under the hood) requiring a quorum before promoting a new primary, so a network partition can never produce two nodes both accepting writes as "the leader" simultaneously.

## 12. Architecture Patterns Applied Inside a Single Service

Inside, say, the **Order Service**, apply **hexagonal architecture** (§3.2): the core domain logic (`Order` aggregate, saga orchestration steps, business rules like "can't cancel a shipped order") has no direct dependency on Postgres, Kafka, or the HTTP framework — it depends only on interfaces (`OrderRepository`, `PaymentGateway`, `EventPublisher`) that the outer layer implements. This is what makes it possible to unit-test checkout logic without a real database, and to swap the payment provider or move from Kafka to another event bus without touching business rules — a direct application of the **Dependency Inversion Principle**.

## 13. What changes at 10x / 100x scale (the senior-level closing point)

- **10x**: current design mostly holds — add more read replicas, tune cache TTLs/sizes, possibly move `orders` from a single Postgres instance to a leader + multiple read replicas for order-history reads.
- **100x**: `orders` genuinely needs **sharding** now (by `user_id`, per §8) since a single Postgres primary can't sustain that write volume; Inventory for the very top N hot SKUs may need dedicated handling (the Redis-counter-in-front pattern from §8 becomes mandatory, not optional); Kafka partition count and consumer group sizing need revisiting to keep event-processing lag acceptable; and it's the point where a **service mesh** typically earns its operational cost as the number of services and their interactions grows past what ad hoc HTTP-client-level resilience code can manage.
