## Module 1: What an "AI Agent" Actually Is

### 1.1 Definition

An **AI agent** = an LLM used as a **reasoning/decision-making engine** inside a loop, where it can:
1. Observe a goal/state,
2. Decide an action (call a tool, ask a question, produce a final answer),
3. Execute that action (or have it executed),
4. Observe the result,
5. Repeat until it decides it's done or hits a stop condition.

```
Goal → [ LLM reasons ] → Action (tool call) → Observation → [ LLM reasons ] → ... → Final Answer
```

The key distinguishing property vs. a plain LLM call or a fixed chain: **the control flow itself is decided by the model at runtime**, not hard-coded by the developer. A chain always executes steps A→B→C; an agent might do A→C→A→B→done depending on what it learns along the way.

### 1.2 Agent vs. Chain vs. Workflow — spectrum of autonomy

| | Fixed chain (LCEL) | Workflow (LangGraph, fixed graph) | Agent (dynamic) |
|---|---|---|---|
| Control flow | Hard-coded, linear/branching, no cycles | Hard-coded graph shape, but with loops/conditionals | LLM decides next action at runtime |
| Predictability | High | Medium — bounded set of paths | Lower — open-ended action space |
| Failure mode | Rare, easy to debug | Bounded | Can loop, pick wrong tool, run away in cost/time |
| When to use | Task has one known shape | Task has a few known shapes/branches | Task shape is genuinely unknown ahead of time (open-ended research, multi-hop problem solving) |

Practical guidance: **use the least autonomy that solves the problem.** Most "agentic" production systems are actually workflows (fixed graph, LLM only decides *within* bounded branches) — pure open-ended agents are harder to make reliable and are reserved for tasks where the path truly can't be predetermined.

### 1.3 Core components of an agent

| Component | Role |
|---|---|
| **LLM (reasoning engine)** | Decides what to do next given the current state/history |
| **Tools / Actions** | Functions the agent can call to affect or query the world (search, code exec, DB query, API call) |
| **Memory** | Short-term (current task context) and long-term (persisted across sessions) |
| **Planning** | Decomposing a goal into steps, possibly revising the plan as new info arrives |
| **Orchestration / control loop** | The mechanism that runs observe→decide→act→repeat and enforces stop conditions |

## Module 2: Tool Use / Function Calling

### 2.1 How function calling works

The developer declares tools as structured schemas (name, description, JSON-schema parameters). The LLM, given the conversation + tool schemas, outputs a structured request to call a specific tool with specific arguments **instead of** natural-language text — the calling code parses that, executes the real function, and feeds the result back into the conversation as an "observation"/tool message.

```python
from langchain_core.tools import tool

@tool
def get_weather(city: str) -> str:
    """Get current weather for a city."""
    return call_weather_api(city)

llm_with_tools = llm.bind_tools([get_weather])
response = llm_with_tools.invoke("What's the weather in Tokyo?")
# response.tool_calls == [{"name": "get_weather", "args": {"city": "Tokyo"}, "id": "..."}]
```

- The model **never actually executes** the tool — it only emits a structured intent. Execution, sandboxing, and error handling are entirely the calling application's responsibility. This is the core safety boundary: the model proposes, your code disposes.
- **Parallel tool calls** — modern models can request multiple independent tool calls in one turn (e.g. look up weather in 3 cities at once); the orchestrator executes them concurrently and returns all results before the next LLM turn.
- **Tool description quality matters as much as prompt quality** — the model picks a tool based on its name + docstring/description, so vague descriptions cause wrong-tool selection just like vague prompts cause bad completions.

### 2.2 Structured output as a tool-adjacent pattern

Forcing an LLM to return validated structured data (Pydantic model / JSON schema) uses the same underlying mechanism as tool calling (constrained decoding or a "fake tool call") — libraries like `instructor` and LangChain's `with_structured_output` wrap this. Important because it's the standard way to make an agent's *decision* machine-parseable and reliable rather than parsing free text.

```python
llm.with_structured_output(RouteDecision)   # forces output to match a Pydantic schema
```

### 2.3 Model Context Protocol (MCP)

An open standard (originated by Anthropic) for exposing tools/data sources to LLM applications through a uniform client-server protocol, instead of every app writing bespoke tool integrations per data source. An **MCP server** exposes a set of tools/resources; any **MCP client** (agent framework) can discover and call them the same way regardless of what's behind the server (a database, a SaaS API, a filesystem). Matters because it decouples "which agent framework you use" from "which tools/data you can reach" — tools become portable across agent implementations.

## Module 3: Agentic Design Patterns

(These generalize the RAG-specific patterns from `15.RAG.md` §7–8 to agents in general.)

### 3.1 ReAct (Reason + Act)

Interleave explicit reasoning ("Thought: I need to look up X") with tool calls ("Action: search(X)") and observations, looping until the model decides it has enough to answer. The most common baseline agent loop; LangGraph ships `create_react_agent` as a prebuilt implementation.

### 3.2 Plan-and-Execute

A planner call first decomposes the goal into an explicit ordered step list; an executor then works through steps one at a time (each step possibly its own tool call or sub-agent), replanning if a step fails or reveals the plan was wrong. More token-efficient and predictable than pure ReAct for long multi-hop tasks (avoids re-deriving the whole plan implicitly on every turn), at the cost of upfront planning latency and being less adaptive turn-to-turn.

### 3.3 Reflection / Self-Critique

After producing an output, a separate critique step (same model or a different one) evaluates it against criteria (correctness, completeness, style) and triggers a revise loop if it fails. Generalizes Self-RAG/CRAG's correction loop beyond retrieval — applies to code generation (write → run tests → fix), writing (draft → critique → revise), planning (plan → sanity-check → replan).

### 3.4 Tree of Thoughts / Search-based reasoning

Instead of a single linear chain of thought, explore **multiple reasoning branches** at each step, score/prune them, and backtrack — analogous to tree search (BFS/DFS/beam search) over reasoning paths rather than committing to the first plausible next step. Higher quality on problems with many plausible-looking but wrong intermediate steps (puzzles, complex planning), at significantly higher token/latency cost since multiple branches are evaluated.

### 3.5 Orchestrator–Worker (a.k.a. Supervisor pattern)

One "orchestrator" LLM call breaks a task into subtasks and delegates each to a specialized "worker" (sub-agent, tool, or sub-chain), then synthesizes worker outputs into a final answer. Foundation of most multi-agent systems (Module 5) — the orchestrator doesn't do the work itself, it routes and integrates.

## Module 4: Agent Memory

### 4.1 Short-term (working) memory

The context passed into the current reasoning step — conversation history, retrieved documents, tool outputs so far in this task. Bounded by the model's context window; long-running agent loops must actively manage this (truncate, summarize, or selectively retrieve) or they'll overflow or drown the model in irrelevant history.

### 4.2 Long-term (persistent) memory

Survives across sessions/conversations. Common implementations:

| Type | Storage | Use |
|---|---|---|
| **Conversation summary memory** | Rolling LLM-generated summary replacing raw history | Keep long chats within budget without losing gist |
| **Vector-store memory** | Past interactions/facts embedded and stored in a vector DB, retrieved by similarity when relevant | "Remember what the user told me 3 weeks ago" — same retrieval mechanics as RAG, applied to the agent's own history |
| **Entity memory** | Structured facts about specific entities (user preferences, project details) kept as key-value/graph data | Personalization, consistent facts across sessions |
| **Episodic vs. semantic memory** (conceptual distinction) | Episodic = specific past events/interactions; semantic = generalized facts/knowledge extracted from those events | Mirrors human memory taxonomy; used in more advanced agent-memory research systems |

### 4.3 Memory vs. checkpointing — distinction worth being precise about

**Checkpointing** (LangGraph `MemorySaver`/DB-backed saver, see `16.langchain_langgraph_basics.md` §3.2) persists **execution state** — where the graph is, what's in `state` — so a *run* can be paused/resumed. **Memory** persists **knowledge/facts learned** for use in *future, separate* runs. They're often implemented on overlapping infrastructure but serve different purposes: checkpointing is about resumability of one interaction, memory is about carrying information forward into new interactions.

## Module 5: Multi-Agent Systems

### 5.1 Why split into multiple agents

- **Separation of concerns** — each sub-agent has a focused system prompt/toolset, easier to prompt-engineer and evaluate than one agent trying to do everything.
- **Context isolation** — a research sub-agent's messy intermediate tool outputs don't pollute the main conversation's context.
- **Parallelism** — independent sub-agents can run concurrently (e.g. multiple research sub-agents on different sub-questions).
- **Specialization** — different agents can use different models (a cheap fast model for simple sub-tasks, an expensive strong model for the orchestrator/hard reasoning).

### 5.2 Topologies

| Topology | Shape | Example |
|---|---|---|
| **Supervisor/orchestrator** | One central agent delegates to workers, synthesizes results | Orchestrator routes "billing question" vs "technical question" to specialist agents |
| **Hierarchical** | Supervisors of supervisors — tree of delegation | Large research agents (manager → team leads → individual researchers) |
| **Peer-to-peer / debate** | Agents converse directly with each other, no central controller | Two agents critique each other's proposed solution to converge on a better one |
| **Pipeline** | Fixed sequence of specialized agents, each transforms the output of the last | Draft agent → fact-check agent → style agent |

### 5.3 Frameworks

| Framework | Model | Notes |
|---|---|---|
| **LangGraph** (multi-agent) | Explicit graph, agents as nodes, shared or partitioned state | Most control/observability, steeper setup, integrates natively with the LangChain ecosystem (retrievers, tools) |
| **AutoGen** (Microsoft) | Conversational agents that message each other | Strong for peer-to-peer/debate patterns, group chat abstraction |
| **CrewAI** | Role-based agents ("Crew" of agents each with a role/goal/backstory) + Tasks | Higher-level, opinionated, fast to prototype role-based teams |
| **OpenAI Agents SDK / Swarm** | Lightweight agent handoff primitive | Minimal, explicit handoffs between agents, close to raw function-calling loop |
| **LlamaIndex agents** | Agent abstractions tied closely to LlamaIndex's data/retrieval layer | Strong when the agent is primarily doing data-heavy RAG-style work |
| **Semantic Kernel** (Microsoft) | Planner + plugin (skill) model | .NET/enterprise-oriented, plugin architecture similar to tools |

### 5.4 Multi-agent failure modes specific to this topology

- **Context/handoff loss** — information one agent had isn't passed to the next, causing repeated work or contradictions.
- **Coordination overhead** — more inter-agent messages = more tokens/latency/cost than a single well-prompted agent would need; multi-agent isn't automatically better.
- **Compounding errors** — a mistake by an early agent in a pipeline propagates and amplifies downstream, since later agents trust earlier outputs as ground truth.
- **Emergent loops** — two agents can get stuck deferring to each other or repeating a negotiation without converging (needs explicit turn/iteration limits).

## Module 6: Planning and Task Decomposition

- **Explicit planning step** — a dedicated LLM call producing a structured plan (list of subtasks) before execution begins, vs. implicit planning where the model just decides the next single action each turn (ReAct-style).
- **Replanning** — trigger a new planning call when execution reveals the original plan was wrong or incomplete (a tool failed, a sub-task revealed a new requirement) — critical for reliability on anything beyond short tasks.
- **Task decomposition granularity** — too coarse (steps still require the executor to improvise significantly) vs. too fine (planning overhead dominates, brittle to real-world deviations) — tuned empirically per task type, same tension as chunk sizing in RAG.

## Module 7: Guardrails and Safety

- **Human-in-the-loop approval gates** — pause before high-stakes/irreversible actions (sending an email, executing a payment, deleting data) for explicit human confirmation. LangGraph's `interrupt` (see `16.langchain_langgraph_basics.md` §3.6) is the mechanism.
- **Tool sandboxing** — code-execution tools run in isolated environments (containers, restricted VMs) with no access to production credentials/network by default.
- **Least-privilege tool scoping** — give an agent only the tools/permissions it needs for its role, not blanket API access — limits blast radius if the agent misuses a tool or is prompt-injected.
- **Input/output validation** — validate tool call arguments against schema before executing (reject malformed/out-of-range args); validate final outputs against expected structure/policy before returning to the user.
- **Prompt injection defense** — treat any content the agent reads (web pages, retrieved docs, tool outputs, emails) as **untrusted data**, never as instructions — same principle as `15.RAG.md` §10.2's "prompt injection via retrieved content." An agent that browses the web or reads user-supplied documents is especially exposed. 
    - solution: 
        - Treat data and instruction seperately
        - use input/output screening: detect malicoius intents/command leakage (use library `Rebuff`)
- **Rate limiting / cost caps** — hard limits on number of tool calls, LLM calls, or spend per task/session to bound runaway behavior.
- **Max iteration limits** — every agentic loop needs an explicit cap on turns/steps, independent of the model's own judgment of when to stop, as a backstop against infinite loops.

## Module 8: Common Agent Failure Modes

| Failure | Cause | Mitigation |
|---|---|---|
| **Infinite/near-infinite loops** | Agent keeps calling the same tool, or ping-pongs between two states without progress | Hard iteration cap; loop/repetition detection (compare consecutive states); reflection step that checks "am I making progress?" |
| **Tool misuse / wrong tool selection** | Ambiguous tool descriptions, overlapping tool responsibilities, too many tools in context | Fewer, more distinct tools; better descriptions; group tools and only expose the relevant subset per state |
| **Hallucinated tool calls** | Model invents a tool/parameter that doesn't exist, or fabricates a plausible-looking but wrong argument | Strict schema validation before execution; reject and re-prompt on validation failure rather than silently coercing |
| **Error compounding** | An early wrong step/tool result is treated as ground truth by later steps | Reflection/self-check steps; validate tool outputs, not just final answers; keep provenance so errors can be traced back |
| **Context window overflow** | Long-running agent accumulates unbounded history/tool outputs | Summarize/compress older turns; retrieve-relevant-history instead of keeping everything; cap tool-output size fed back into context |
| **Cost/latency runaway** | Unbounded tool calls or unnecessarily large sub-agent fan-out | Iteration caps, cost budgets per task, cheaper models for simple sub-steps |
| **Non-determinism / flakiness** | Same input produces different agent trajectories across runs | Lower temperature for decision-making steps; evaluation harness must test trajectories/distributions, not single runs (see next notes file) |

## Module 9: Agent Evaluation (preview — full treatment in `18.observability_evaluation_reliability.md`)

Evaluating an agent is harder than evaluating a single LLM call because there are two things to grade:
1. **Trajectory** — did it take a reasonable sequence of actions (right tools, right order, no wasted/harmful steps)?
2. **Final outcome** — did it actually accomplish the goal?

A model can reach the right final answer via a bad/unsafe trajectory (got lucky, or took a risky shortcut) — production agent eval needs to check both, not just outcome accuracy. See the next notes file for the concrete tooling and metrics.
