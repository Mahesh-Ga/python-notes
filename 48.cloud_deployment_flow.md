# Cloud Deployment Flow (GenAI/API Services)

## The end-to-end flow, in order

1. **Write the app** — FastAPI/Flask service exposing your endpoints (chat, RAG query, ingestion trigger, etc.)
2. **Containerize** — write a `Dockerfile`, build an image, test it locally with `docker run`
3. **Push to a registry** — AWS ECR / Azure Container Registry (ACR) / GCP Artifact Registry. This is just a private Docker Hub your cloud account controls.
4. **Deploy the image to a compute service** — pick one:
   - **Serverless container**: AWS Fargate/ECS, Azure Container Apps, GCP Cloud Run — you don't manage servers, it scales on request volume, good default for GenAI APIs with spiky traffic
   - **Kubernetes**: AWS EKS, Azure AKS, GCP GKE — when you need fine-grained orchestration, multiple services, sidecars
   - **PaaS**: Azure App Service, AWS Elastic Beanstalk — simplest, less control
5. **Wire up secrets** — LLM API keys, DB passwords go into AWS Secrets Manager / Azure Key Vault / GCP Secret Manager, injected as env vars at runtime. Never baked into the image.
6. **Put it behind a gateway/load balancer** — API Gateway (AWS) or Azure API Management, handles auth, rate limiting, routing. LB distributes traffic across container replicas.
7. **Attach logging/monitoring** — CloudWatch (AWS) / Azure Monitor + App Insights / GCP Cloud Logging + Monitoring. This is where you'd hook in your observability notes ([[18.observability_evaluation_reliability]]).
How it fits a RAG pipeline on Azure 

- App Insights on the API or Function app to track request latency, failures, and dependency calls to Azure OpenAI, AI Search and Blob.
- Custom metrics/events for token usage, retrieval latency, number of chunks retrieved, and "no answer found" rate.
- Diagnostic settings on Azure OpenAI and AI Search to capture throttling (429s) and query latency.
- Alerts, for example: P95 latency above 5s, a spike in 429s from OpenAI, or ingestion function failures. Route them through an action group to Teams or email.
- Workbook that shows cost, tokens and latency together in one view.
8. **CI/CD ties it together** — on merge to main: build image → push to registry → trigger deploy (rolling update). GitHub Actions / Azure DevOps / GitLab CI are the common runners.

```
Code → Docker build → Push to registry → Deploy to compute → 
Secrets injected → Behind LB/Gateway → Logs/metrics flowing → 
CI/CD automates all of the above on every merge
```

## Core cloud concepts you should be able to explain plainly

**IAM (Identity and Access Management)**
Who/what can do what. A service gets a *role* with a *policy* attached (e.g., "this container can read from this S3 bucket, nothing else"). Principle of least privilege — don't give a service admin access when it only needs to read one bucket.

**Storage**
- Object storage: S3 (AWS) / Blob Storage (Azure) / GCS (GCP) — for files, documents you're ingesting into a RAG pipeline, model artifacts
- Block/managed DB storage: RDS (AWS) / Azure Database for PostgreSQL / Cloud SQL (GCP) — for your Postgres/MySQL
- Redis: ElastiCache (AWS) / Azure Cache for Redis / Memorystore (GCP)

**Compute spectrum** (know when you'd pick each)
- VM (EC2/Azure VM/Compute Engine) — full control, you patch the OS, rarely the right choice for a new GenAI service
- Container (ECS/Fargate, Container Apps, Cloud Run) — your default for API services, good balance of control and simplicity
- Serverless functions (Lambda/Azure Functions/Cloud Functions) — event-driven, short-lived tasks (e.g., "resize this uploaded doc," "trigger embedding on file upload"), not for long-running LLM streaming responses because of execution time limits

**Networking basics**
- VPC — your private network inside the cloud; resources inside it can talk to each other, outside traffic is blocked unless you allow it
- Security groups / NSGs — firewall rules at the resource level (e.g., "only allow port 443 in") SG is a virtual firewall that controls incoming and outgoing network traffic for cloud resources like virtual server
- Public vs private subnet — your API might sit in a public subnet behind a LB; your DB sits in a private subnet with no direct internet access:
   A subnet (subnetwork) is a smaller network carved out of a bigger one. You take a large block of IP addresses and split it into smaller ranges, and each range is a subnet.
   Why you'd split a network

   - Isolation and security. Keep the database somewhere the internet can't reach, while web servers stay public.
   - Organization. Group resources by role, like web tier, app tier, and data tier.
   - Traffic control. You can attach firewall rules and route tables per subnet.
   - Less broadcast noise. In traditional networks, smaller segments carry less broadcast traffic.

Subnets are written like 10.0.1.0/24.

- The /24 means the first 24 of the 32 bits are the network part, which is fixed.
- The remaining 8 bits are the host part, which gives 2⁸ = 256 addresses.
Rule of thumb: a bigger number after the slash means a smaller subnet

Example: a 3-tier app in the cloud

VNet: 10.0.0.0/16
├── web-subnet   10.0.1.0/24   → load balancer / web servers (public-facing)
├── app-subnet   10.0.2.0/24   → APIs, backend services
└── db-subnet    10.0.3.0/24   → database (private, no internet access)

- A public subnet has a route to the internet (in AWS, through an Internet Gateway).
- A private subnet has no direct inbound route from the internet. Outbound access, for things like package updates, goes through a NAT Gateway.
- In Azure you secure subnets with NSGs (Network Security Groups). In AWS you use Security Groups plus NACLs.
- Private Endpoints let PaaS services like Azure OpenAI, AI Search, or Storage get a private IP inside your subnet, so traffic never goes over the public internet. This comes up a lot with RAG setups.


## Managed GenAI services (the part specific to this JD)

These matter because a lot of "AI engineering" work now is *not* calling OpenAI directly — it's using the cloud's managed LLM layer for enterprise reasons (data residency, no data leaving the VPC, unified billing, access to multiple model providers).

- **AWS Bedrock** — access to Claude, Llama, Titan, etc. through one API, no infra to manage, supports RAG via Knowledge Bases and agents via Bedrock Agents
- **Azure OpenAI Service** — OpenAI models hosted inside Azure's compliance boundary, same OpenAI API shape, common in enterprises already on Azure (your resume already has Azure experience — this is a natural bridge)
- **GCP Vertex AI** — Google's models (Gemini) plus a full ML platform (training, tuning, endpoints, Vertex AI Search for RAG)

Why a company picks managed over calling the LLM API directly: data never leaves their cloud boundary, centralized cost/usage tracking, easier compliance sign-off, sometimes lower latency (same region as the rest of their stack).

## Likely interview questions

1. Walk me through what happens when you push code to main and it ends up running in production.
2. Why containerize instead of just deploying a Python script on a VM?
3. Where do your LLM API keys live in production, and why not just put them in the Dockerfile/env file in the repo?
4. Serverless function vs. container for a chatbot API — which would you pick and why? *(Container — LLM responses can stream and take longer than typical function timeout limits, plus you want a persistent process for connection pooling.)*
5. What's the difference between IAM and a security group / NSG? *(IAM = identity-based, "who can do what to which resource." Security group = network-based, "what traffic can reach this resource.")*
6. Why would a company use Azure OpenAI Service instead of calling OpenAI's API directly? *(Compliance, data residency, single vendor relationship, unified auth via their existing Azure AD.)*
7. How would you scale a RAG API that's getting hammered with traffic? *(Horizontal scaling of stateless API containers behind a LB, cache frequent queries/embeddings, consider a queue in front of ingestion so spikes don't overwhelm the vector DB.)*
