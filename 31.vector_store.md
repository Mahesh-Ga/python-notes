## What is a Vector Store?

A **Vector Store** (or **Vector Database**) is a specialized database designed to store, index, and search **embeddings** — dense numeric vectors — efficiently, so that given a query vector, it can quickly find the **most similar vectors** stored in it.

In simple words: a normal database (SQL/NoSQL) is great at exact lookups (`WHERE id = 42` or `WHERE name = 'Mahesh'`). A vector store is built for a different question: *"which stored items are most similar in meaning to this one?"* — a question exact matching can't answer, but distance/similarity math over embeddings can.

```
Query text → Embed → Query Vector → Vector Store searches for nearest vectors → Top-k similar results
```

Examples: **Pinecone, Weaviate, Milvus, Qdrant, Chroma, FAISS (library, not a full DB), pgvector (Postgres extension).**

---

## Why do we need a Vector Store?

Once data is converted into embeddings (see `30.embeddings.md`), the next problem is **scale**. Comparing a query vector against millions (or billions) of stored vectors **one by one** (brute-force) is accurate but slow — this is called a **linear scan** and doesn't scale in real-time applications.

| Without a Vector Store | With a Vector Store |
|---|---|
| Compare query vector against *every* stored vector (O(n)) | Uses specialized indexes to search in near-logarithmic time |
| Fine for a few thousand vectors | Handles millions/billions of vectors efficiently |
| No built-in metadata filtering, persistence, or scaling | Built-in filtering, persistence, sharding, replication |

A vector store solves this by using **Approximate Nearest Neighbor (ANN)** search algorithms — trading a tiny bit of accuracy for a massive gain in speed.

---

## Real-World Analogy

Think of a vector store like a **librarian who organizes books by topic/meaning instead of alphabetically by title**. If you ask "give me books similar to this one about space travel," a title-sorted library forces you to scan every shelf. A meaning-sorted library (the vector store) has already grouped similar books near each other, so it can point you to the right shelf almost instantly.

## Core Operations of a Vector Store

| Operation | Description |
|---|---|
| **Upsert / Insert** | Add a new vector (plus optional metadata) to the store |
| **Index** | Build a data structure over stored vectors for fast search |
| **Query / Search (kNN / ANN)** | Given a query vector, return the top-k most similar stored vectors |
| **Filter** | Narrow the search using metadata (e.g., `category = "sports"`) alongside vector similarity |
| **Delete / Update** | Remove or modify existing vectors |

```python
# Conceptual example using Chroma
import chromadb

client = chromadb.Client()
collection = client.create_collection("articles")

# Insert
collection.add(
    ids=["1", "2"],
    embeddings=[[0.12, -0.45, 0.88], [0.10, -0.40, 0.91]],
    metadatas=[{"topic": "AI"}, {"topic": "AI"}],
    documents=["Neural networks are powerful", "Deep learning models are trained on data"]
)

# Query
results = collection.query(
    query_embeddings=[[0.11, -0.44, 0.89]],
    n_results=2
)
print(results["documents"])
```

## How Search Works Internally: ANN Indexing

Searching for the *exact* nearest neighbor across millions of high-dimensional vectors is expensive. Vector stores instead use **Approximate Nearest Neighbor (ANN)** algorithms, which return *very close to* the true nearest neighbors, much faster.

| Index Type | Idea | Trade-off |
|---|---|---|
| **Flat / Brute-force** | Compare against every vector | 100% accurate, but slow at scale |
| **IVF (Inverted File Index)** | Cluster vectors into buckets; search only the closest buckets | Faster, small accuracy loss |
| **HNSW (Hierarchical Navigable Small World)** | Builds a multi-layer graph of vectors; hops through the graph toward the query | Very fast + high accuracy; most popular in modern vector DBs |
| **PQ (Product Quantization)** | Compresses vectors into smaller codes to save memory | Saves space, some accuracy loss |

Most production vector databases (Pinecone, Weaviate, Qdrant, Milvus) use **HNSW** or a variant of it as their default index, because it offers the best balance of speed and accuracy.

## Deep Dive: IVF (Inverted File Index)

### The Problem IVF Solves

Comparing a query vector against every single stored vector (Flat/brute-force) is accurate but slow. IVF's idea: **don't search everything — first figure out roughly which "neighborhood" the query belongs to, then only search inside that neighborhood.**

### Intuition: Sorting Books into Sections Before Searching

Imagine a library with a million books dumped in one giant pile. Finding a book about "space travel" means checking every single book. Now imagine the librarian first sorts books into **sections** — Fiction, Science, History, etc. To find a book on space travel, you only need to search the **Science section**, not the whole pile. IVF does exactly this to vectors: it groups them into **clusters ("buckets")** ahead of time, and search only visits the most relevant clusters.

### Step 1: Building the Index (Clustering)

Before any search happens, IVF runs a clustering algorithm (typically **k-means**) over all the stored vectors to split them into `nlist` clusters, each with a **centroid** (the "center point" / average vector of that cluster).

```
All stored vectors  →  k-means clustering (nlist = e.g. 100 clusters)
                     →  Each vector assigned to its nearest centroid
                     →  Each cluster keeps a list ("inverted list") of the vector IDs inside it
```

```
Centroid A ●───────────●  cluster of vectors near A
                 (vectors: v1, v7, v12, v45, ...)

Centroid B ●───────────●  cluster of vectors near B
                 (vectors: v3, v9, v20, v88, ...)

Centroid C ●───────────●  cluster of vectors near C
                 (vectors: v5, v14, v33, ...)
```


**Normal ("forward") index:** `document → list of words it contains`.
doc1 → [cat, dog, run]
doc2 → [dog, jump]
To find "which documents contain 'dog'?" you'd have to scan every document's word list. Slow.

**Inverted index:** flip it — `word → list of documents containing` it.
cat → [doc1]
dog → [doc1, doc2]
run → [doc1]
Now "which documents contain 'dog'?" is a single lookup: dog → [doc1, doc2]. This is literally how search engines answer queries fast — it's "inverted" relative to the natural
document→words direction.

IVF does the same trick, but with clusters instead of words:
centroid A → [v1, v7, v12, v45, ...]
centroid B → [v3, v9, v20, v88, ...]
centroid C → [v5, v14, v33, ...]
Instead of "word → documents containing it," it's "centroid → vectors belome, once you know which centroid(s) the query is closest to, you can jumpstraight to that centroid's list of vectors — you don't scan every vector, just like you don't scan every document once you have the word→docs lookup.  

**In short: a vector ends up in whichever bucket's centroid it is numerically closest to (by the same distance metric used for search), and that closeness is refined over several rounds until the centroids settle into the true "center of mass" of natural groupings in the data.** This is exactly why semantically similar vectors (e.g., many embeddings of "sports" articles) naturally land in the same cluster — they're already close together in vector space *before* clustering even runs; k-means just discovers and formalizes that existing structure into `nlist` groups.

A few practical notes:
- **`nlist` is chosen up front**, not discovered — a common rule of thumb is `nlist ≈ √n` for `n` total vectors, tuned experimentally.
- Because k-means starts from random centroids, results vary slightly run to run — this is fine for ANN search, since we only need *approximately* good clusters, not a perfect partition.
- Once built, the inverted lists are mostly static — new vectors are usually just assigned to their nearest **existing** centroid without re-running full k-means each time (periodic re-training keeps clusters balanced as data grows).

### Step 2: Searching

1. **Compare the query vector only against the cluster centroids** (there are only `nlist` of them — say 100 — not millions).
2. **Pick the `nprobe` closest centroids** to the query (`nprobe` is usually a small number like 1, 8, or 16 — not all clusters).
3. **Search only inside the inverted lists of those chosen clusters**, comparing the query against just those vectors (brute-force, but on a *tiny* subset of the full data).
4. Merge and rank the candidates from all probed clusters to return the final **top-k** nearest vectors.

```
Query vector
     │
     ▼
Compare against all centroids (A, B, C, ... — only nlist of them)
     │
     ▼
Pick nprobe closest centroids, e.g. centroid A and centroid C
     │
     ▼
Brute-force search ONLY inside cluster A's and cluster C's vectors
     │
     ▼
Return top-k nearest among those candidates
```

### Why It's Faster (and Where Accuracy Is Lost)

- **Speed**: instead of comparing against all `n` vectors, you compare against `nlist` centroids + the vectors inside just `nprobe` clusters — a huge reduction when `n` is in the millions.
- **Accuracy loss**: the true nearest neighbor might sit right on the **border** between two clusters and land in a cluster you didn't probe — so IVF is *approximate*, not exact. Increasing `nprobe` (checking more clusters) recovers accuracy at the cost of speed.

### Key Parameters (in practice)

| Parameter | Meaning | Effect |
|---|---|---|
| `nlist` | Number of clusters the data is split into | More clusters → finer partitioning, but centroid comparison itself gets costlier |
| `nprobe` | Number of nearest clusters searched per query | Higher `nprobe` → better accuracy, slower search (closer to brute-force as it approaches `nlist`) |

### IVF vs HNSW at a Glance

| Aspect | IVF | HNSW |
|---|---|---|
| **Approach** | Partition space into clusters, search nearest few | Navigate a multi-layer graph of neighbors |
| **Build cost** | Cheaper (just run k-means once) | Costlier (build a well-connected graph) |
| **Memory** | Lower | Higher (stores graph edges per node) |
| **Speed/accuracy at scale** | Good, tunable via `nprobe` | Usually better recall at same speed, most popular default today |
| **Combines well with** | PQ (compressed vectors) for very large, memory-constrained datasets (IVF+PQ) | Used mostly standalone |

### One-Line Summary

**IVF = cluster all vectors into `nlist` groups using k-means ahead of time, then at query time only compare against the vectors inside the `nprobe` nearest clusters instead of the entire dataset — trading a small, tunable amount of accuracy for a large speedup.**

## Deep Dive: HNSW (Hierarchical Navigable Small World)

### The Problem HNSW Solves

Given a query vector, we want its nearest neighbors among millions of stored vectors — **without** comparing it to every single one (that's the slow "Flat" approach). HNSW builds a **graph structure** ahead of time (at insert time) so that, at search time, we can **navigate** toward the answer instead of scanning everything.

### Intuition: Skip Lists, but for Vectors

HNSW is inspired by a classic data structure called a **Skip List**. A skip list speeds up search in a sorted linked list by adding "express lane" shortcuts on top of the base list:

```
Level 2:  1 ------------------ 9 ------------------ 21
Level 1:  1 ------- 5 -------- 9 ------- 15 -------- 21
Level 0:  1 -- 3 -- 5 -- 7 -- 9 -- 12 -- 15 -- 18 -- 21   (every element)
```

To find `15`, you start at the top (sparse) level, jump as far as you can without overshooting, then drop down a level and repeat — reaching the target in far fewer hops than walking the base list one by one. **HNSW applies this exact idea to a graph of vectors instead of a sorted list**, because vectors don't have a natural "sorted order" — so instead of a line, it uses a **navigable graph** where each vector is a node connected to its approximate nearest neighbors.

### The Structure: Layers of Graphs

HNSW organizes vectors into **multiple stacked layers**, like floors of a building:

```
Layer 2 (fewest points, "highway")        ●-------------------●
                                            \                 /
Layer 1 (more points, "main roads")    ●----●-------●-------●----●
                                        |    |       |       |    |
Layer 0 (ALL points, "local streets")  ●-●--●-●-●-●-●-●-●-●-●-●--●-●
```

### Level assignment

Elements are randomly assigned levels, with fewer elements at higher levels. The level distribution follows an exponentially decaying probability. This randomization ensures a balanced structure that can handle dynamic datasets efficiently.

### Layer construction

The probabilistic tiering in HNSW, where nodes distribute across different layers like skip lists, is governed by a parameter typically denoted as mL. This parameter determines the likelihood of a node appearing in successive layers, with the probability decreasing exponentially as the layers ascend. Each layer is a proximity graph of elements at that level, allowing logarithmic complexity scaling. Higher layers provide a broader overview, while lower layers offer finer details.

### Adding elements
Greedy search
New elements start from the top layer, connecting to the nearest neighbors down through each level. The maximum number of connections per element (M) and the dynamic list size (efConstruction) are key parameters that control the quality and efficiency of the index. These parameters ensure that each element is well-connected, improving the search performance.


Each vector is assigned to a random top layer when it's inserted (higher layers are exponentially less likely), then linked into every layer at or below that level.

### How Search Works (Step by Step)
**Start at the top**
Begin the search from a random, high-level entry point.

**Greedy descent**
Move through layers, always heading toward the closest neighbor to the query vector before descending to the next level. This approach allows the algorithm to quickly narrow down the search space and move in the direction of the query vector, moving to increasingly dense graphs each time a descent occurs.

**Refinement**
As you descend, the search becomes more precise, efficiently finding the nearest neighbors.The lower layers refine the search results, ensuring high accuracy.

HNSW’s hierarchical approach, combined with careful parameter tuning, significantly boosts search efficiency, especially in high-dimensional data.

Each of the trajectories traversed from the top level entry point to the closest vector at the bottom level represents one candidate exploration. The search parameter efSearch, called numCandidates in the $vectorSearch interface, controls the number of entry points/trajectories that are explored. Increasing this increases the likelihood that the top k vectors closest to the query vectors are discovered.

Insertions and deletions in the HNSW graph ensure its dynamic adaptability and robustness in handling high-dimensional datasets based on entry points and distance metrics. When a new node is added for the graph construction,

```
Layer 2:  entry ──► node A  (coarse jump toward the query's rough neighborhood)
                       │ drop down
Layer 1:  node A ──► node B  (refine — smaller jumps)
                       │ drop down
Layer 0:  node B ──► node C ──► node D  (fine-grained search among many nodes)
                       return top-k nearest to query
```

This is exactly like using a highway to get near your destination city, then main roads to get near the neighborhood, then local streets to find the exact house — each layer narrows the search area so you never need to look at most of the graph.

### Why It's Fast AND Accurate

| Property | Why HNSW achieves it |
|---|---|
| **Speed** | Search cost grows roughly **logarithmically** with the number of vectors (`O(log n)`-ish), not linearly, because each layer eliminates most of the search space before dropping down |
| **Accuracy** | The graph is built so nodes connect to their *true* nearest neighbors at insert time; greedy search on a well-connected graph rarely misses the real nearest neighbors |
| **Tunable trade-off** | Parameters like `M` (max neighbors per node) and `ef_search` (candidate list size during search) let you trade speed for accuracy — higher `ef_search` = slower but more accurate |

### Key Parameters (in practice)

| Parameter | Meaning | Effect |
|---|---|---|
| `M` | Max number of connections per node per layer | Higher `M` → better recall, more memory |
| `ef_construction` | Candidate list size while **building** the graph | Higher → better graph quality, slower to build |
| `ef_search` | Candidate list size while **searching** | Higher → more accurate results, slower queries |

### One-Line Summary

**HNSW = a skip-list-style, multi-layer graph of vectors where each layer is sparser and has longer "jumps" than the one below it, letting search start with big coarse hops at the top and end with fine-grained hops at the bottom — finding near-exact nearest neighbors in roughly logarithmic time instead of scanning every vector.**

## Similarity Metrics Used in Search

Same metrics as in `30.embeddings.md`, but here they define **how the index ranks results**:

| Metric | Best For |
|---|---|
| **Cosine Similarity** | Text embeddings (most common default) |
| **Euclidean Distance (L2)** | Image embeddings, general-purpose |
| **Dot Product** | When vector magnitude itself carries meaning (e.g., popularity-weighted embeddings) |

Choosing the wrong metric for the embedding model you used can silently produce poor results — always check what metric the embedding model was **trained/optimized** with.

## Metadata Filtering (Hybrid Search)

Pure vector similarity search sometimes isn't enough — you may want *"documents similar to this query, but only from 2024, and only in category X."* This is called **hybrid search** — combining vector similarity with traditional metadata filters (and sometimes keyword/BM25 search too).

```
Query → Embed → Vector Store
   → Filter: metadata.category == "AI" AND metadata.year >= 2024
   → Rank remaining candidates by vector similarity
   → Return top-k
```

Most modern vector stores (Pinecone, Weaviate, Qdrant) support this natively, so you don't have to post-filter results yourself.

## Vector Store in a RAG Pipeline

The vector store is the **retrieval** half of Retrieval-Augmented Generation (see `15.RAG.md`):

```
1. Documents → Split into chunks → Embed each chunk → Store in Vector Store
2. User Query → Embed query
3. Vector Store → Search (ANN) → Top-k relevant chunks
4. Top-k chunks + User Query → Passed as context to the LLM
5. LLM generates an answer grounded in the retrieved chunks
```

```python
# Conceptual RAG retrieval step
query = "What is self-attention?"
query_vector = embed(query)

results = vector_store.query(query_vector, top_k=3)
context = "\n".join([r["text"] for r in results])

prompt = f"Answer using this context:\n{context}\n\nQuestion: {query}"
```

Without a vector store, the LLM would have no efficient way to find *which* of potentially millions of document chunks are relevant to a given question.

## Popular Vector Store Options

| Vector Store | Type | Notes |
|---|---|---|
| **FAISS** | Library (in-process, not a server) | Built by Meta; extremely fast; no built-in persistence/metadata filtering out of the box |
| **Chroma** | Lightweight, embeddable DB | Easy to start with locally; popular for prototypes |
| **Pinecone** | Fully managed, cloud service | No infra to manage; scales automatically; paid |
| **Weaviate** | Open-source, self-hosted or managed | Built-in hybrid search, GraphQL API |
| **Qdrant** | Open-source, self-hosted or managed | Rust-based, fast, good filtering support |
| **Milvus** | Open-source, distributed | Built for very large scale (billions of vectors) |
| **pgvector** | Postgres extension | Adds vector search to an existing Postgres DB — good if you already use Postgres |

## Vector Store vs Traditional Database

| Aspect | Traditional Database (SQL/NoSQL) | Vector Store |
|---|---|---|
| **Query type** | Exact match / range queries (`WHERE`) | Similarity / "nearest neighbor" queries |
| **Data stored** | Structured rows/documents | High-dimensional vectors (+ metadata) |
| **Index type** | B-Tree, Hash Index | HNSW, IVF, PQ (ANN indexes) |
| **Typical use** | Transactions, structured lookups | Semantic search, RAG, recommendations |

They aren't mutually exclusive — many production systems use **both**: a traditional DB for structured data, and a vector store (or `pgvector` inside the same Postgres DB) for semantic search.

## Quick Recap

- A **vector store** is a database purpose-built to index and search **embeddings** by similarity, not exact match.
- It solves the **scale problem**: brute-force comparison doesn't work for millions of vectors, so vector stores use **ANN indexes** like **HNSW** or **IVF**.
- Core operations: **insert, index, query (kNN/ANN), filter, delete/update**.
- **Metadata filtering (hybrid search)** lets you combine similarity search with traditional filters.
- Vector stores are the **retrieval engine behind RAG** — they find the relevant chunks an LLM uses to ground its answer.
- Popular choices: **FAISS** (library), **Chroma** (lightweight), **Pinecone/Weaviate/Qdrant/Milvus** (production-grade), **pgvector** (if already on Postgres).
