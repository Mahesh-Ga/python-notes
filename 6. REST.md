## 1. Resource-Oriented URLs

A REST URL names a **resource** (a noun), not an action (a verb). The HTTP verb supplies the action.

| Bad (RPC-style) | Good (resource-oriented) |
|---|---|
| `POST /createOrder` | `POST /orders` |
| `GET /getOrderById?id=5` | `GET /orders/5` |
| `POST /updateOrderStatus` | `PATCH /orders/5` |
| `POST /deleteOrder?id=5` | `DELETE /orders/5` |
| `GET /getOrdersForCustomer?customerId=9` | `GET /customers/9/orders` |

Rules of thumb:
- Plural nouns for collections: `/orders`, not `/order`.
- Nesting expresses ownership/hierarchy, but keep it shallow (max ~2 levels): `/customers/9/orders/5` is fine; `/customers/9/orders/5/lines/2/discounts/1` is a sign you should promote a resource to top-level (`/order-lines/2/discounts`) and let clients look it up by ID instead of walking the whole tree.
- Use query params for filtering/sorting/pagination, not for identifying a resource: `/orders?status=pending&sort=-created_at`, never `/orders?id=5`.
- No verbs in the path except for genuine non-CRUD actions that don't map to a resource state change — those become sub-resources: `POST /orders/5/cancel` (a *sub-resource action*, more RESTful than `POST /orders/5?action=cancel`) — used when "cancel" is a meaningful business event you want to log/audit distinctly from a generic PATCH.

**PO→SO example**: `POST /purchase-orders` (create + trigger matching), `GET /purchase-orders/{po_id}/matches` (the computed line-item matches + confidence scores as a sub-resource), `POST /purchase-orders/{po_id}/approve` (an action that promotes it to a Sales Order — this is the "verb-as-sub-resource" exception above, because "approve" is a real domain event, not just a field update).

## 2. Correct HTTP Verbs & Status Codes

### Verbs — semantics matter (safety & idempotency)

| Verb | Safe? (no side effects) | Idempotent? (same result if repeated) | Use for |
|---|---|---|---|
| GET | Yes | Yes | Read a resource/collection |
| POST | No | **No** (by default) | Create a new resource, or a non-idempotent action |
| PUT | No | Yes | Full replace of a resource at a known URL |
| PATCH | No | Not guaranteed (depends on the patch) | Partial update |
| DELETE | No | Yes (deleting twice = still deleted, still 2xx/404) | Remove a resource |

**PUT vs PATCH — a common interview trap**: `PUT /orders/5` with a full order body *replaces* the resource — any field you omit is treated as cleared/defaulted. `PATCH /orders/5` with `{"status": "shipped"}` updates only that field. Sending a partial body to `PUT` is a common bug source (accidentally nulling out fields the client didn't send).

**Why POST is not idempotent by default**: calling `POST /orders` twice creates two orders. This is exactly why unsafe write operations need **idempotency keys** (section 5) — POST's natural semantics don't protect you from network retries.

### Status codes — group by first digit, know the specific ones that get asked about
Informational responses (100 – 199)
Successful responses (200 – 299)
Redirection messages (300 – 399)
Client error responses (400 – 499)
Server error responses (500 – 599)

| Code | Meaning | When |
|---|---|---|
| 200 OK | Success | GET, successful PUT/PATCH returning the resource |
| 201 Created | Resource created | Successful POST — include a `Location` header pointing at the new resource |
| 202 Accepted | Accepted, processing async | POST that enqueues a Celery task (e.g., PO matching runs in the background) |
| 204 No Content | Success, nothing to return | Successful DELETE, or PUT/PATCH where you don't return the body |
| 400 Bad Request | Malformed request / validation failed | Pydantic validation error, bad JSON |
| 401 Unauthorized | Missing/invalid credentials | No token, expired token, bad API key |
| 403 Forbidden | Authenticated but not allowed | Valid token, wrong role/permission |
| 404 Not Found | Resource doesn't exist | `GET /orders/9999` when 9999 doesn't exist |
| 409 Conflict | State conflict | Duplicate resource, idempotency key reused with a *different* payload, optimistic-lock version mismatch |
| 422 Unprocessable Entity | Syntactically valid but semantically invalid | FastAPI's default for Pydantic validation errors — body parses as JSON but fails schema/type rules |
| 429 Too Many Requests | Rate limited | You built this with Redis token-bucket (Topic 10) |
| 500 Internal Server Error | Unhandled exception | Bug — should be rare and always logged/alerted, never a way to communicate "bad input" |
| 503 Service Unavailable | Dependency down / overloaded | Circuit breaker open, DB pool exhausted |
301 Moved Permanently.
308 Permanent Redirect
302 Moved TEmp
307 Temporary Redirect:

**400 vs 422 — asked often**: FastAPI returns 422 automatically when Pydantic validation fails (`RequestValidationError`), because the JSON itself is well-formed but violates the schema (wrong type, missing required field). 400 is the more general "I can't process this request" for cases outside pure schema validation (e.g., a business-rule check before you even get to querying anything).

**401 vs 403 — asked often**: 401 = "I don't know who you are" (no/invalid/expired token → re-authenticate). 403 = "I know who you are, and you're not allowed" (valid token, insufficient role — don't bother retrying with the same identity).

## 3. Request/Response Validation via Pydantic

FastAPI's core value proposition: declare a schema once, get validation + docs + serialization for free.

```python
from pydantic import BaseModel, Field, EmailStr, field_validator
from datetime import datetime
from enum import Enum

class OrderStatus(str, Enum):
    pending = "pending"
    approved = "approved"
    rejected = "rejected"

class OrderLineIn(BaseModel):
    sku: str = Field(..., min_length=1, max_length=64)
    quantity: int = Field(..., gt=0)
    unit_price: float = Field(..., ge=0)

class OrderCreate(BaseModel):
    customer_email: EmailStr
    lines: list[OrderLineIn] = Field(..., min_length=1)

    @field_validator("lines")
    @classmethod
    def no_duplicate_skus(cls, lines):
        skus = [l.sku for l in lines]
        if len(skus) != len(set(skus)):
            raise ValueError("duplicate SKU in order lines")
        return lines

class OrderOut(BaseModel):
    id: int
    status: OrderStatus
    created_at: datetime
    confidence: float

    class Config:
        from_attributes = True  # lets you return an ORM object directly
```

```python
@app.post("/orders", response_model=OrderOut, status_code=201)
async def create_order(payload: OrderCreate):
    ...
```

**Why separate `OrderCreate` (input) from `OrderOut` (output) models** — this is the pattern to name explicitly in an interview:
- there are some field not to show in response (id, internal notes)
- and in the request, there can be mass assignment where user can maliciously add id, status= approved in the input, so create a specific schema for input 
- fastAPI using pydantic we can do ii.

**Validation failure path**: a bad request never reaches your business logic — FastAPI raises `RequestValidationError` before your function body runs, and returns 422 with a field-by-field error list automatically. This is "fail fast at the boundary," same principle as Topic 4 (Pydantic `BaseSettings` failing fast on bad config).

## 4. Pagination for Large Collections

Never return an unbounded list — `GET /orders` on a table with a million rows will eventually take down the DB or the service.

### Offset/limit — simple, but degrades at scale

```
GET /orders?offset=40&limit=20
```
```python
@app.get("/orders")
async def list_orders(offset: int = 0, limit: int = Field(20, le=100)):
    ...
```
- Easy to implement (`OFFSET`/`LIMIT` in SQL), supports "jump to page 5."
- LIMIT = Items Per Page; OFFSET = (Page Number - 1) * Items Per Page
- **Problem at scale**: `OFFSET 1000000` still has the DB scan and discard a million rows before returning the next page — 
    1. gets slower the deeper you paginate. 
    2. if rows are inserted/deleted between page requests (page can skip or repeat a row).
        - in delete case -> skip
        - in insert case -> duplicate

### Cursor-based (keyset) pagination — the production-grade answer

```
GET /orders?cursor=eyJpZCI6IDEwNH0&limit=20
```
- Why it's called cursor=eyJpZCI6IDEwNH0 instead of just ?after_id=104
That string is just {"id": 104} base64-encoded
- Cursor encodes the last seen sort key (e.g., `id` or `created_at`), and the query becomes:
```sql
SELECT * FROM orders WHERE id > :last_id ORDER BY id ASC LIMIT 20;
```
- Uses an index seek instead of scan-and-discard — constant time regardless of how deep you page.
- Stable under concurrent inserts/deletes (no skip/repeat).
- Trade-off: can't jump to an arbitrary page number, only "next"/"previous" — acceptable for API consumers, less so for a UI page-number widget.

### Response envelope

```json
{
  "data": [ { "id": 101, "...": "..." } ],
  "pagination": {
    "next_cursor": "eyJpZCI6IDEyMX0",
    "has_more": true
  }
}
```
Or, for offset-based, include `total_count` so clients can render page numbers — but computing `COUNT(*)` on a huge table is itself expensive; sometimes it's better to return `has_more` (fetch `limit + 1` rows, if you got the extra one, there's a next page) instead of an exact total.

**Interview answer shape**: "I'd default to offset/limit for small admin-facing lists, but for anything user-facing at scale (or anything an agent/automation is going to page through repeatedly, like matching results across thousands of POs) I'd use cursor-based pagination keyed on an indexed column, because offset pagination's cost grows with page depth and it isn't stable under concurrent writes."

## 5. Idempotency Keys for Unsafe Operations

**The problem**: `POST /orders` is not idempotent (section 2). A client's request can time out on the *response* even though the server successfully created the order — the client doesn't know if it worked, so it retries, and now there are two orders. This happens constantly with real networks (mobile clients, load balancer timeouts, transient 5xx from a proxy).

**The fix**: client(js code) generates a unique key (usually a UUID) per logical operation and sends it in a header. Server stores "I've seen this key, here's what happened" and returns the *same result* on retry instead of repeating the side effect.

```
POST /orders
Idempotency-Key: 6c1f7e2a-9b3d-4e11-9c2a-1a2b3c4d5e6f
```

```python
@app.post("/orders", status_code=201)
async def create_order(payload: OrderCreate, idempotency_key: str = Header(...)):
    existing = await redis.get(f"idem:{idempotency_key}")
    if existing:
        cached_response, cached_status = json.loads(existing)
        if cached_response["request_hash"] != hash_payload(payload):
            raise HTTPException(409, "Idempotency key reused with a different payload")
        return JSONResponse(cached_response["body"], status_code=cached_status)

    order = await create_order_in_db(payload)
    result = OrderOut.from_orm(order)
    await redis.set(
        f"idem:{idempotency_key}",
        json.dumps({"body": result.model_dump(), "request_hash": hash_payload(payload)}),
        ex=86400,  # keep the key around long enough to cover realistic retry windows
    )
    return result
```

Design points worth stating out loud in an interview:
- **Store the key with a TTL** (Redis, as you already use for session/caching) — you don't need to remember it forever, just long enough to cover realistic retry windows (e.g., 24h).
- **Key scope**: idempotency keys should be scoped per-client/per-endpoint (e.g., prefix with the API key or customer ID) so two different clients can't collide on the same UUID.
- **409 Conflict** if the same key arrives with a *different* payload — that's a client bug (reusing a key for a genuinely different operation), not something to silently accept.
- **Race condition**: two concurrent requests with the same brand-new key both miss the cache check — guard with a Redis `SETNX`/lock around the "not seen yet" path, or use a DB unique constraint on the idempotency key column as the real source of truth, with Redis as a fast-path cache.
- This is the same idea GET/PUT/DELETE get "for free" from HTTP's idempotency semantics (section 2) — idempotency keys are how you retrofit that safety onto POST.

**Tie to your resume**: "create this order should be safely retryable" is literally the PO→SO Automation use case — a PO ingestion pipeline that could receive the same PO twice (email retry, upstream system re-send) must not raise duplicate Sales Orders.

## 6. Versioning Strategy

Why version at all: you will eventually need to change a response shape or remove a field in a way that breaks existing clients (mobile apps you don't control the release cadence of, other teams' services, external customers). Versioning lets you make a breaking change without breaking everyone currently integrated.

| Strategy | Example | Pros | Cons |
|---|---|---|---|
| URL path | `/v1/orders`, `/v2/orders` | Explicit, visible in logs/browser, easy to route (even at a load-balancer/API-gateway level) | "Not very RESTful" (a resource's identity shouldn't change with its representation version); URL sprawl over time |
| Header-based | `Accept: application/vnd.myapi.v2+json` | Keeps the URL stable — same resource identity across versions | Less discoverable (can't just paste a URL in a browser), harder to test manually, easy to forget to set |
| Query param | `/orders?version=2` | Simple to add | Easy to omit accidentally (silently falls back to a default), not a common convention |

**Practical answer for most interviews**: URL-path versioning (`/v1/...`) is the pragmatic industry default — FastAPI supports this cleanly with `APIRouter(prefix="/v1")`, it's trivially cacheable/routable, and it's what most public APIs (Stripe, GitHub, etc.) actually do, even though header-based is the more "purist" REST answer. Know both, state the trade-off, then pick one.

```python
v1_router = APIRouter(prefix="/v1")
v2_router = APIRouter(prefix="/v2")

@v1_router.get("/orders/{order_id}")
async def get_order_v1(order_id: int):
    ...  # legacy response shape, kept stable for old clients

@v2_router.get("/orders/{order_id}")
async def get_order_v2(order_id: int):
    ...  # new response shape

app.include_router(v1_router)
app.include_router(v2_router)
```

**What actually counts as a breaking change** (know this distinction): removing a field, renaming a field, changing a field's type, changing status codes for existing cases — breaking. **Adding** a new optional field, a new endpoint, or a new optional query param — non-breaking, doesn't need a version bump (clients ignoring unknown fields is the whole point of using JSON + Pydantic's forward-compatible parsing).

## 7. Authentication (JWT, API Keys, OAuth2)

### JWT (JSON Web Token) — what you built in Online Food Ordering

Structure: `header.payload.signature`, base64url-encoded, signed (HMAC or RSA) so the server can verify it wasn't tampered with, without a DB lookup per request.

```python
import jwt
from datetime import datetime, timedelta, timezone

def create_access_token(user_id: int, role: str) -> str:
    payload = {
        "sub": str(user_id),
        "role": role,
        "iat": datetime.now(timezone.utc),
        "exp": datetime.now(timezone.utc) + timedelta(minutes=15),
    }
    return jwt.encode(payload, SECRET_KEY, algorithm="HS256")

def decode_token(token: str) -> dict:
    try:
        return jwt.decode(token, SECRET_KEY, algorithms=["HS256"])
    except jwt.ExpiredSignatureError:
        raise HTTPException(401, "Token expired")
    except jwt.InvalidTokenError:
        raise HTTPException(401, "Invalid token")
```

FastAPI dependency to extract the current user on every protected route:

```python
from fastapi.security import OAuth2PasswordBearer

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/auth/login")

async def get_current_user(token: str = Depends(oauth2_scheme)) -> User:
    payload = decode_token(token)
    user = await get_user(int(payload["sub"]))
    if user is None:
        raise HTTPException(401, "User not found")
    return user

@app.get("/orders/{order_id}")
async def get_order(order_id: int, user: User = Depends(get_current_user)):
    ...
```

**Access token + refresh token pattern** — the detail interviewers probe for:
- **Access token**: short-lived (minutes), sent on every request, stateless (server just verifies the signature — no DB hit).
- **Refresh token**: long-lived (days/weeks), stored server-side (or as an httpOnly cookie), used only to mint a new access token when the old one expires. This bounds the damage of a leaked access token (short window) while not forcing the user to re-login constantly.
- **Revocation problem**: JWTs are stateless by design, so you can't "delete" one early. If you need instant revocation (user logs out, account compromised), you need a server-side denylist (Redis, keyed by `jti` — the token's unique ID — with TTL matching the token's remaining life) — this is exactly the kind of thing Redis session caching (which you built) solves.
- **Never put sensitive data in the payload** — it's base64-encoded, not encrypted; anyone can decode and read it (just not forge a valid signature for a modified one).

### API Keys
Simpler, no expiry/refresh dance — a long-lived static secret sent as a header (`X-API-Key`), typically for service-to-service or third-party integration auth rather than end-user auth. Store a **hash** of the key server-side (like a password), not the raw key, and support revocation/rotation per key. Weaker than JWT/OAuth for user-facing auth (no built-in expiry, no scoping without extra bookkeeping) but simpler to integrate for machine clients.

### OAuth2
A **delegation** protocol — "let app X access resource Y on my behalf without giving X my password." Distinct from JWT: JWT is a *token format*; OAuth2 is a *protocol* for obtaining tokens (which are often, but not necessarily, JWTs). Relevant flows:
- **Authorization Code flow**: standard web-app login (redirect to provider, get a code, exchange for a token) — used for things like "Sign in with Google."
- **Client Credentials flow**: service-to-service, no user involved — the service authenticates itself directly to get a token.
- FastAPI's `OAuth2PasswordBearer` above is actually just the *scheme* for reading a bearer token from the `Authorization` header — it doesn't by itself implement full OAuth2; for real third-party OAuth2 you'd use `authlib` or similar against the provider's endpoints.

## 8. Authorization (Role/Permission Checks)

Authentication answers "who are you." Authorization answers "what are you allowed to do" — a separate step, and mixing them up is a common design/interview mistake.

### Role-based (RBAC) — simplest, good default

```python
def require_role(*allowed_roles: str):
    async def checker(user: User = Depends(get_current_user)):
        if user.role not in allowed_roles:
            raise HTTPException(403, "Insufficient permissions")
        return user
    return checker

@app.post("/purchase-orders/{po_id}/approve")
async def approve_po(po_id: int, user: User = Depends(require_role("manager", "admin"))):
    ...
```

### Permission-based — finer-grained than roles

When "admin can do everything, everyone else can do X" gets too coarse (e.g., "can approve orders under $10k" vs "can approve any amount"), move from roles to explicit permissions attached to a role or user:

```python
class Permission(str, Enum):
    approve_po = "po:approve"
    view_all_orders = "orders:view_all"

async def require_permission(permission: Permission):
    async def checker(user: User = Depends(get_current_user)):
        if permission not in user.permissions:
            raise HTTPException(403, f"Missing permission: {permission}")
        return user
    return checker
```

### Resource-level (object) authorization — the check people forget

Role/permission checks answer "can this role do this *kind* of action" — they don't answer "does *this specific* user own *this specific* resource." A classic vulnerability (IDOR — Insecure Direct Object Reference) is checking only the role and forgetting to check ownership:

```python
@app.get("/orders/{order_id}")
async def get_order(order_id: int, user: User = Depends(get_current_user)):
    order = await get_order_by_id(order_id)
    if order is None:
        raise HTTPException(404)
    if order.customer_id != user.id and user.role not in ("admin", "manager"):
        raise HTTPException(403, "Not your order")  # <-- the check that's easy to forget
    return order
```

**Interview framing**: "Authentication middleware/dependency answers 'who is this,' a role/permission dependency answers 'is this class of user allowed to hit this endpoint at all,' and then inside the handler you still need an object-level check — does *this* user own *this* row — otherwise a valid, authenticated, correctly-permissioned user can still read or modify someone else's data just by changing an ID in the URL."

- Resource-oriented URL: `/v1/purchase-orders` (section 1)
