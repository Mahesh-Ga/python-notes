# LangGraph Tutorial — What is LangGraph, Architecture, and Examples

## What is LangGraph?

**LangGraph** is a Python library, built by the creators of LangChain, that is used to build **stateful, multi-step applications powered by Large Language Models (LLMs)**, especially applications that behave like **agents** — systems that can reason, make decisions, use tools, and loop back to try again if needed.

In simple words: if LangChain helps you build a single "pipeline" where data flows in one direction (input → LLM → output), LangGraph helps you build a **graph** where the flow of data can **branch, loop, and pause**, just like a flowchart with decision points.

LangGraph models an application as a **graph**:
- **Nodes** = steps of work (a function, an LLM call, a tool call)
- **Edges** = the connections that decide which node runs next
- **State** = a shared memory object that flows through the graph and gets updated by each node

This graph-based design is what makes LangGraph well suited for **agentic workflows**, where the LLM might need to call a tool, check the result, decide to try again, ask a human for approval, or take multiple different paths depending on the situation.

## Why do we need LangGraph?

Plain LLM pipelines (like a simple prompt → LLM → output chain) work fine for straightforward tasks, but real-world AI agents often need:

1. **Loops** — e.g., "search the web, check if the answer is good enough, if not, search again."
2. **Conditional branching** — e.g., "if the user asks about billing, go to the billing tool; otherwise go to the general chat flow."
3. **Persistent state** — the application needs to remember information across many steps, not just pass one output to the next input.
4. **Human-in-the-loop** — sometimes the workflow should pause and wait for a human to approve or provide input before continuing.
5. **Reliability and control** — production systems need to control exactly how the agent behaves, instead of relying purely on the LLM to "figure it out" in one big prompt.

Normal linear chains (as used in basic LangChain) cannot easily express loops or complex branching. LangGraph solves this by letting developers **explicitly define the control flow as a graph**, giving much more predictability and control over how the agent behaves.

## Key Features of LangGraph

| Feature | Description |
|---|---|
| **Graph-based control flow** | Define your application as nodes and edges, allowing branches and cycles (loops), unlike simple linear chains. |
| **Shared State** | A central state object is passed between nodes; each node can read from it and update it. |
| **Conditional Edges** | Decide dynamically which node to go to next, based on the current state. |
| **Checkpointing (Persistence)** | The graph's state can be saved after every step, so long-running or paused workflows can resume exactly where they left off. |
| **Human-in-the-loop** | Execution can be paused to wait for human review/approval, then resumed. |
| **Streaming** | Outputs and intermediate steps can be streamed back to the user in real time. |
| **Multi-agent support** | Multiple agents (each modeled as nodes or subgraphs) can be composed together in one larger graph. |

## Core Components of LangGraph

### 1. State

The **State** is like the "memory" of the graph — a data structure (usually a Python `TypedDict`, dataclass, or Pydantic model) that holds all the information the graph needs as it runs. Every node can read the current state and return updates to it.

```python
from typing import TypedDict

class AgentState(TypedDict):
    question: str
    documents: list
    answer: str
```

### 2. Nodes

A **Node** is simply a function that performs one unit of work. It takes the current state as input and returns a dictionary with the fields it wants to update.

```python
def retrieve_node(state: AgentState):
    docs = my_retriever.invoke(state["question"])
    return {"documents": docs}
```

### 3. Edges

An **Edge** connects one node to another, defining what runs next.

- **Normal edge** — always go from Node A to Node B.
- **Conditional edge** — a function looks at the current state and decides which node to go to next (this is how branching and loops are created).

```python
graph.add_edge("retrieve", "generate")               # normal edge

graph.add_conditional_edges(                          # conditional edge
    "retrieve",
    lambda state: "generate" if state["documents"] else "retrieve",
    {"generate": "generate", "retrieve": "retrieve"},
)
```

### 4. START and END

Special markers that tell the graph where execution begins (`START`) and where a path terminates (`END`).

### 5. Checkpointer

A **Checkpointer** saves the state after each node runs. This gives the graph "memory" across multiple calls and lets it recover or pause and resume, which is essential for chatbots (multi-turn memory) and for human-in-the-loop workflows.

## How LangGraph Works — Step by Step

1. **Define the State** — decide what data needs to flow through the application (e.g., `question`, `documents`, `answer`).
2. **Define Nodes** — write functions for each unit of work (retrieve data, call an LLM, call a tool, validate output).
3. **Add Nodes to the Graph** — register each function as a node using `add_node()`.
4. **Connect Nodes with Edges** — use `add_edge()` for fixed paths and `add_conditional_edges()` for decision points.
5. **Set the Entry Point** — tell the graph which node runs first.
6. **Compile the Graph** — call `.compile()`, which turns the graph definition into an executable object.
7. **Run the Graph** — call `.invoke()` (or `.stream()`) with the initial state to execute it.

## Example: Building a Simple RAG Agent with LangGraph

```python
from typing import TypedDict, List
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import MemorySaver

# Step 1: Define the State
class GraphState(TypedDict):
    question: str
    documents: List[str]
    generation: str

# Step 2: Define Nodes
def retrieve(state: GraphState):
    docs = retriever.invoke(state["question"])
    return {"documents": [d.page_content for d in docs]}

def generate(state: GraphState):
    answer = llm.invoke(f"Answer using this context: {state['documents']}\n\nQuestion: {state['question']}")
    return {"generation": answer.content}

# Step 3: Decide the flow
def route(state: GraphState):
    return "generate" if state["documents"] else "retrieve"

# Step 4: Build the Graph
graph = StateGraph(GraphState)
graph.add_node("retrieve", retrieve)
graph.add_node("generate", generate)

graph.add_edge(START, "retrieve")
graph.add_conditional_edges("retrieve", route, {"generate": "generate", "retrieve": "retrieve"})
graph.add_edge("generate", END)

# Step 5: Compile
app = graph.compile(checkpointer=MemorySaver())

# Step 6: Run
result = app.invoke(
    {"question": "What is LangGraph?"},
    config={"configurable": {"thread_id": "user-1"}},
)
print(result["generation"])
```

**Output flow:**
```
START -> retrieve -> (documents found?) -> generate -> END
                   -> (no documents)     -> retrieve (loop again)
```

## Common Design Patterns Built with LangGraph

| Pattern | Description |
|---|---|
| **ReAct Agent** | The LLM alternates between "Reasoning" (thinking about what to do) and "Acting" (calling a tool), looping until it has enough information to answer. |
| **Plan-and-Execute** | The LLM first creates a step-by-step plan, then a separate execution loop carries out each step, replanning if something fails. |
| **Reflection** | After generating an answer, a separate step critiques the answer and sends it back for improvement if it doesn't meet quality criteria — used in Self-RAG / Corrective RAG style workflows. |
| **Multi-Agent Systems** | Several specialized agents (e.g., a "researcher" agent and a "writer" agent) are each modeled as nodes or subgraphs, working together in one bigger graph. |

LangGraph also ships a ready-made helper for the most common pattern:

```python
from langgraph.prebuilt import create_react_agent

agent = create_react_agent(llm, tools=[my_tool])
result = agent.invoke({"messages": [("user", "What's the weather in Paris?")]})
```

## LangGraph vs LangChain (LCEL)

| Aspect | LangChain (LCEL) | LangGraph |
|---|---|---|
| Structure | Linear/branching pipeline (chain) | Graph with nodes and edges |
| Loops | Not supported | Fully supported |
| State | Passed step to step, not persistent | Shared, persistent state object |
| Best for | Simple, one-pass pipelines (prompt → LLM → parser) | Agentic workflows needing loops, retries, multi-step reasoning |
| Human-in-the-loop | Not built in | Built in via `interrupt` |
| Relationship | LangGraph nodes are usually built using LangChain/LCEL components internally | Sits on top of / alongside LangChain, not a replacement |

## Advantages of LangGraph

- Gives **fine-grained control** over how an agent behaves, instead of relying purely on the LLM's judgment.
- Supports **loops and retries**, which are essential for real agentic behavior (e.g., "try again if the answer is not good enough").
- Built-in **state persistence** makes multi-turn conversations and long-running workflows easy to implement.
- Supports **human-in-the-loop**, useful for approval workflows in production systems.
- Works well for **multi-agent orchestration**, since a compiled graph can itself be used as a node inside a bigger graph.
- Because it's built on LangChain's `Runnable` interface, it integrates smoothly with everything else in the LangChain ecosystem (prompts, models, retrievers, tools).

## Disadvantages / Limitations

- **Steeper learning curve** than a simple linear chain — you need to think in terms of state machines and graphs.
- **More boilerplate** for simple use cases where a plain chain would have been enough.
- Debugging a complex graph with many conditional edges can be harder than debugging a linear pipeline.
- Requires careful state design (choosing the right state schema and reducers) to avoid bugs where data gets overwritten unexpectedly.

## Real-World Applications of LangGraph

- **Customer support agents** that can look up information, call APIs, and escalate to a human if unsure.
- **RAG chatbots** that decide whether to retrieve, grade the retrieved documents, and retry with a rewritten query if the documents aren't relevant.
- **Coding agents** that write code, run tests, and loop back to fix errors automatically.
- **Multi-agent research assistants** where one agent searches, another summarizes, and another writes the final report.
- **Workflow automation tools** that need approval steps from a human before taking a sensitive action.

## Conclusion

LangGraph extends LangChain's building blocks with a **graph-based execution model**, adding the two things a simple chain cannot provide: **loops** and **persistent shared state**. This makes it the go-to choice for building **agentic AI applications** — chatbots, autonomous agents, and multi-agent systems — that need to reason over multiple steps, use tools, retry on failure, and optionally involve a human in the loop.
