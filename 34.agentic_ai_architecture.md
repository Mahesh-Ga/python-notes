# Agentic AI & Multi-Agent AI — Architecture

> This note is the "architecture diagram" companion to `17.ai_agents.md` (concepts: ReAct, planning, memory, failure modes), `21.crewai.md` (a concrete multi-agent framework), `29.a2a_protocol.md` (inter-agent protocol), `16.mcp.md` (agent-to-tool protocol), and `20.langgraph.md` (graph-based orchestration runtime). Where those notes explain *what* a component does, this note focuses on *how the pieces are wired together* — single-agent architecture first, then multi-agent topologies, then a full enterprise reference architecture.

---

## 1. Single-Agent (Agentic AI) Architecture

### 1.1 The reference diagram

```
                              ┌─────────────────────────┐
                              │        User / Trigger     │
                              │  (chat, API call, cron,   │
                              │   webhook, another agent)  │
                              └────────────┬───────────────┘
                                           │
                                           ▼
                              ┌─────────────────────────┐
                              │     Interface Layer       │
                              │ (input parsing, auth,     │
                              │  session/thread mgmt)     │
                              └────────────┬───────────────┘
                                           │
                                           ▼
                  ┌───────────────────────────────────────────────┐
                  │              Orchestration Layer                 │
                  │      (the agent loop / control flow engine)      │
                  │                                                   │
                  │   observe → reason → decide → act → observe ...   │
                  └───┬─────────────┬─────────────┬──────────────┬───┘
                      │             │             │              │
                      ▼             ▼             ▼              ▼
              ┌──────────┐  ┌──────────────┐ ┌──────────┐  ┌───────────┐
              │  Reasoning │  │   Memory     │ │  Tools /  │  │ Guardrails │
              │  Engine    │  │   Layer      │ │  Actions  │  │ / Safety   │
              │  (LLM)     │  │ (short+long   │ │  Layer    │  │  Layer     │
              │            │  │  term)        │ │           │  │            │

                                    ┌─────────────────────────────┐

                                    │ (traces, evals, cost/latency, │
```

Everything below is one of these boxes, described as an architectural component rather than a concept.

### 1.2 Layer-by-layer breakdown

| Layer | Responsibility | Typical building blocks |
|---|---|---|
| **Interface** | Turn an external trigger (chat message, API request, scheduled job, inbound webhook, another agent's A2A message) into a normalized task the orchestrator understands. Owns auth, rate limiting, session/thread ID. | REST/gRPC endpoint, WebSocket for streaming, A2A server endpoint (`29.a2a_protocol.md`) |
| **Orchestration** | Runs the actual control loop: given current state, decide the next action (reason, call a tool, ask the user, or finish). This is the architectural home of the patterns in `17.ai_agents.md` §3 (ReAct, Plan-and-Execute, Reflection). | LangGraph `StateGraph` (`20.langgraph.md`), a hand-rolled while-loop, OpenAI Agents SDK runner |
| **Reasoning engine** | The LLM itself — turns (state + tool schemas + memory) into the next decision. Swappable: cheap/fast model for simple routing, strong model for hard reasoning steps. | GPT/Claude/etc. via an LLM gateway |
| **Memory** | Short-term = the working context for *this* run; long-term = facts/history persisted *across* runs. Architecturally these are different stores with different lifecycles — conflating them is a common design mistake (`17.ai_agents.md` §4.3). | In-context history (short-term); vector DB (`31.vector_store.md`) or KV/graph store (`14.neo4j.md`) for long-term |
| **Tools / Actions** | The agent's only way to affect or query the world. Each tool is a declared schema (name, description, JSON-schema args) the LLM can request; the orchestrator executes it. | Function-calling tool registry, or an MCP client pulling tool definitions from one or more MCP servers (`16.mcp.md`) |
| **Environment / Execution** | Where tool calls actually run — the real APIs, databases, code sandboxes, or external agents being invoked. This is *outside* the agent's trust boundary — treat all output from here as untrusted data (`17.ai_agents.md` §7 prompt-injection note). | Sandboxed containers for code exec, scoped API credentials, MCP servers, other agents (via A2A) |
| **Guardrails / Safety** | Cross-cutting, not a single step in the loop — validates tool-call args before execution, screens outputs, enforces iteration/cost caps, and gates high-stakes actions behind human approval. | Schema validation, `Rebuff`-style injection screening, LangGraph `interrupt` for human-in-the-loop, hard max-turn counters |
| **Observability** | Captures every step of the loop (which tool, what args, what the model "thought", latency, cost) for debugging and evaluation — both trajectory and outcome (`17.ai_agents.md` §9). | LangSmith/tracing, structured logs, eval harness (`18.observability_evaluation_reliability.md`) |

### 1.3 The control loop, concretely

The orchestration layer is the one part that's genuinely *agentic* (as opposed to a fixed pipeline) — it's a loop, not a straight line:

```python
state = init_state(user_input)

while not state.is_done and state.steps < MAX_STEPS:
    decision = llm.invoke(state.messages, tools=tool_schemas)   # reasoning engine
    if decision.tool_calls:
        for call in decision.tool_calls:
            validate(call)                                       # guardrails
            result = execute_tool(call)                          # environment
            state.messages.append(tool_result(call, result))     # memory (short-term)
        state.steps += 1
    else:
        state.is_done = True
        final_answer = decision.content
```

This loop *is* the architecture's center of gravity — every other layer exists to feed it, constrain it, or record it. See `17.ai_agents.md` §1.2 for the "how much autonomy" spectrum (fixed chain vs. bounded workflow vs. open-ended agent), which is really a decision about **how much of the control flow lives in this loop vs. is hard-coded around it**.

## 2. Multi-Agent AI Architecture

A multi-agent system replaces the single "Reasoning Engine" box in §1.1 with *multiple* agents, each potentially a full instance of the §1.1 architecture, plus a coordination layer on top. The architectural question is always: **who talks to whom, how, and who holds shared state.**

### 2.1 Topology diagrams

**Supervisor / Orchestrator-Worker** — one controller, no peer communication:

```
                     ┌──────────────┐
                     │  Supervisor   │
                     │  (routes +    │
                     │   synthesizes)│
                     └──┬──┬──┬──┬───┘
             ┌──────────┘  │  │  └──────────┐
             ▼             ▼  ▼             ▼
        ┌─────────┐  ┌─────────┐      ┌─────────┐
        │ Worker A │  │ Worker B │ ...  │ Worker N │
        │(specialist)│(specialist)│      │(specialist)│
        └─────────┘  └─────────┘      └─────────┘
```
Workers never talk to each other; all coordination goes through the supervisor. Simplest to reason about and debug — the default choice unless there's a specific reason to decentralize (`17.ai_agents.md` §5.2).

**Hierarchical** — supervisors of supervisors, for large fan-out:

```
                         ┌──────────────┐
                         │  Top-level    │
                         │  Supervisor   │
                         └───┬───────┬───┘
                    ┌────────┘       └────────┐
                    ▼                          ▼
            ┌──────────────┐          ┌──────────────┐
            │  Team-lead A  │          │  Team-lead B  │
            └──┬────────┬──┘          └──┬────────┬──┘
               ▼        ▼                 ▼        ▼
           Worker A1  Worker A2       Worker B1  Worker B2
```
Same idea as an engineering org chart — used when a flat supervisor would have to manage too many workers or too many unrelated domains at once.

**Peer-to-peer / Debate** — no central controller, agents message each other directly:

```
        ┌──────────┐  <---- messages ---->  ┌──────────┐
        │  Agent A  │ <-------------------->  │  Agent B  │
        └──────────┘                          └──────────┘
              ▲                                     ▲
              └────────────── converge ─────────────┘
                        (shared verdict / vote)
```
Used for critique/debate patterns (two agents propose and challenge each other's answer) — needs an explicit termination condition (max rounds, or a judge) or it can loop indefinitely (`17.ai_agents.md` §5.4 "emergent loops").

**Pipeline** — fixed sequence, each agent transforms the previous agent's output:

```
   ┌───────┐     ┌───────┐     ┌────────┐     ┌────────┐
   │ Draft  │ --> │ Fact-  │ --> │ Style   │ --> │ Final   │
   │ Agent  │     │ Check  │     │ Agent   │     │ Output  │
   └───────┘     │ Agent  │     └────────┘     └────────┘
                  └───────┘
```
Lowest coordination overhead; brittle if an early stage's error compounds downstream (`17.ai_agents.md` §5.4 "compounding errors") — mitigated with a validation/reflection step between stages, not by removing the pipeline structure.

### 2.2 Two architectural axes that cut across all topologies

**(a) State sharing model** — this is often more consequential than the topology diagram itself:

| Model | Description | Trade-off |
|---|---|---|
| **Shared state** | All agents read/write one common state object (e.g. one LangGraph `StateGraph` with multiple agent nodes) | Simple, consistent, but agents can clobber each other's writes if not carefully scoped; tight coupling to one runtime |
| **Message passing** | Agents are separate processes/services with their own private state, exchanging explicit messages (requests/results) | Loose coupling, works across frameworks/vendors/languages (this is what A2A standardizes, `29.a2a_protocol.md`), but requires explicit handoff of *all* needed context — nothing is "just there" in shared memory |

Rule of thumb: shared state for agents built together in one framework (LangGraph multi-agent, CrewAI's `context=[...]` between tasks); message passing (A2A) once agents cross a team/vendor/framework boundary and must stay opaque to each other.

**(b) Communication protocol layer** — where the "who talks to whom" from the diagrams actually gets implemented:

```
   Agent  ──uses tools/data via──▶  MCP  ──▶  Tool / Data source     (agent → tool,   16.mcp.md)
   Agent  ──delegates task to  ──▶  A2A  ──▶  Another agent          (agent → agent,  29.a2a_protocol.md)
```
MCP solves the **M×N tool-integration problem** (every agent framework needing a custom connector per data source); A2A solves the same M×N problem one level up, for **agent-to-agent** collaboration across vendors/frameworks. An enterprise agentic system typically uses *both*: MCP inside each agent to reach its own tools, A2A (or a framework-native equivalent) between agents.

### 2.3 Framework mapping (architecture, not tutorial — see `21.crewai.md` for CrewAI specifics)

| Framework | Where state lives | Coordination mechanism |
|---|---|---|
| **LangGraph multi-agent** | One shared (or partitioned) graph state | Nodes are agents/sub-agents; edges are explicit or conditional routing — supervisor and hierarchical topologies map directly onto graph structure |
| **CrewAI** | Task outputs passed as `context` between tasks | `Process.sequential` (pipeline) or `Process.hierarchical` (supervisor, with an auto-generated or explicit manager agent) |
| **AutoGen** | Each agent keeps its own state; a "group chat" manager mediates | Conversational message-passing — natural fit for peer-to-peer/debate |
| **A2A-based systems** | Fully decentralized — each agent is its own service with its own internal architecture (its own §1.1 diagram) | Task objects + Agent Cards for discovery; no shared runtime at all |

### 2.4 Why split into multiple agents at all — architectural payoffs

(Expands `17.ai_agents.md` §5.1 in architecture terms.)

- **Context isolation** — a research sub-agent's messy tool-call history never enters the main agent's context window; only its final, distilled result crosses the boundary. This is a real architectural firewall, not just an organizing convenience.
- **Independent scaling/model choice** — a cheap model can run the high-volume worker role while an expensive model is reserved for the supervisor's synthesis step — a cost/latency lever that doesn't exist in a single-agent design.
- **Fault isolation** — one worker crashing/looping doesn't take down the orchestrator, provided the supervisor enforces per-worker timeouts/iteration caps.
- **Parallelism** — independent workers (e.g. three research sub-agents on three sub-questions) execute concurrently, then fan back in — same shape as a scatter-gather pattern in classic distributed systems.

The cost side (coordination overhead, handoff loss, compounding errors — `17.ai_agents.md` §5.4) is exactly why "use the least autonomy/decomposition that solves the problem" applies here too: a single well-prompted agent is often both cheaper and more reliable than a multi-agent system for tasks that don't actually need role separation.

## 3. Full Enterprise Reference Architecture

Putting §1 and §2 together into what a production agentic platform typically looks like end-to-end:

```
┌──────────────────────────────────────────────────────────────────────────┐
│                              Client Layer                                 │
│         (Web/chat UI, Slack/Teams bot, API consumers, other agents)       │
└───────────────────────────────┬────────────────────────────────────────────┘
                                 ▼
┌──────────────────────────────────────────────────────────────────────────┐
│                    API Gateway / Interface Layer                          │
│      auth, rate limiting, session routing, streaming (SSE/WebSocket)       │
└───────────────────────────────┬────────────────────────────────────────────┘
                                 ▼
┌──────────────────────────────────────────────────────────────────────────┐
│                      Multi-Agent Orchestration Layer                       │
│   Supervisor agent  ──▶  Worker agent 1 (LangGraph subgraph)                │
│                     ──▶  Worker agent 2 (CrewAI crew)                       │
│                     ──▶  Worker agent 3 (external, via A2A)                 │
└───────┬───────────────────────┬───────────────────────┬────────────────────┘
        ▼                       ▼                       ▼
┌───────────────┐     ┌──────────────────┐     ┌────────────────────┐
│  LLM Gateway    │     │   Memory / RAG     │     │   Tool Layer (MCP)  │
│ (model routing, │     │ - Vector DB         │     │ - Internal APIs     │
│  fallback, cost │     │   (31.vector_store) │     │ - DBs               │
│  tracking)      │     │ - Knowledge graph    │     │ - Code sandbox      │
│                 │     │   (14.neo4j.md)      │     │ - External SaaS     │
└───────────────┘     └──────────────────┘     └────────────────────┘
        │                       │                       │
        └───────────────────────┴───────────────────────┘
                                 ▼
┌──────────────────────────────────────────────────────────────────────────┐
│                    Guardrails & Governance (cross-cutting)                │
│  input/output validation • injection screening • human-in-the-loop        │
│  approval gates • per-tenant cost/rate caps • PII redaction               │
└───────────────────────────────┬────────────────────────────────────────────┘
                                 ▼
┌──────────────────────────────────────────────────────────────────────────┐
│                  Observability & Evaluation Layer                        │
│   distributed tracing across agents • trajectory + outcome evals          │
│   (18.observability_evaluation_reliability.md) • cost/latency dashboards  │
└──────────────────────────────────────────────────────────────────────────┘
```

Key architectural decisions this diagram forces you to make explicitly, roughly in the order they bite in a real build:

1. **Sync vs. async task execution** — a long-running multi-agent task (minutes, not seconds) needs a durable task/job store and a way to stream partial progress back to the client, not a blocking HTTP call.
2. **Where state is durable vs. ephemeral** — checkpointed graph state (resumable mid-run) vs. long-term memory (persists across runs) vs. pure request-scoped context — conflating these is the most common design bug (`17.ai_agents.md` §4.3).
3. **Trust boundaries** — every arrow crossing into "Tool Layer" or coming back from an external agent (via A2A) is untrusted input from the reasoning engine's perspective; guardrails sit on *both* sides of that boundary, not just at the outer edge.
4. **Single point of failure in the orchestration layer** — a supervisor topology concentrates risk in one agent; production systems typically add a fallback/timeout path per worker so one hung specialist doesn't stall the whole task.

## 4. Quick interview-answer summary

- **Single-agent architecture** = an LLM reasoning engine wrapped in a control loop (orchestration layer), with memory, tools, guardrails, and observability as supporting layers around that loop — the loop itself is what makes it "agentic" rather than a fixed pipeline.
- **Multi-agent architecture** = multiple single-agent units connected by a topology (supervisor, hierarchical, peer-to-peer, pipeline) and a state-sharing model (shared graph state vs. message passing).
- **MCP vs. A2A**: MCP is the agent→tool protocol (solves the M×N tool-integration problem inside one agent); A2A is the agent→agent protocol (solves the same M×N problem between independently-built agents). A real platform uses both, at different layers of the same diagram.
- **Framework choice mirrors the state-sharing decision**: LangGraph/CrewAI when agents share one runtime and can share state directly; A2A-style message passing when agents cross a framework/vendor boundary and must stay opaque to each other.
- **Guardrails and observability are cross-cutting layers, not steps in the loop** — they wrap every tool call and every inter-agent handoff, not just the final output.
- **The recurring design principle at every level** (single loop, topology choice, decomposition granularity): use the least autonomy/decentralization that solves the problem — more agents and more open-ended loops buy flexibility at the cost of coordination overhead, compounding errors, and harder debugging.
