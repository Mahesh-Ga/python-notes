# MCP (Model Context Protocol) — Detailed Notes

## 1. What MCP is and why it exists

**MCP (Model Context Protocol)** is an open protocol (introduced by Anthropic, Nov 2024) that standardizes how LLM applications connect to external **tools, data sources, and prompts**. Think of it as **"USB-C for AI applications"** — one standard interface instead of every app writing a bespoke integration for every data source/tool.

**The problem it solves — the M×N integration problem:**

Without a standard, if you have `M` AI applications (Claude Desktop, an IDE, a custom agent, ...) and `N` external systems (GitHub, Slack, a database, a filesystem, ...), you need `M × N` custom integrations — every app reimplements auth, request/response shaping, and error handling for every system.

```
Without MCP:                          With MCP:
App1 ──custom──> GitHub                App1 ─┐
App1 ──custom──> Slack                 App2 ─┼─> MCP Client ──MCP──> MCP Server (GitHub)
App2 ──custom──> GitHub                App3 ─┘                 ──MCP──> MCP Server (Slack)
App2 ──custom──> DB                                             ──MCP──> MCP Server (DB)
   (M×N bespoke integrations)             (each side implements MCP once — M+N integrations)
```

Each app implements the MCP **client** side once; each system implements the MCP **server** side once. Any MCP client can talk to any MCP server.

**Analogy to existing standards:**
- LSP (Language Server Protocol) standardized how editors talk to language tooling (autocomplete, go-to-def) — one language server works with any LSP-compliant editor.
- MCP does the same for LLM apps talking to tools/data — one MCP server works with any MCP-compliant AI app.

## 2. Core architecture

### 2.1 Roles

```
┌─────────────────────────────┐
│         Host                │   e.g. Claude Desktop, an IDE, Claude Code
│  ┌────────────┐              │
│  │ MCP Client │◄────1:1─────┼──── MCP Server (e.g. filesystem server)
│  └────────────┘              │
│  ┌────────────┐              │
│  │ MCP Client │◄────1:1─────┼──── MCP Server (e.g. GitHub server)
│  └────────────┘              │
└─────────────────────────────┘
```

- **Host** — the user-facing AI application (Claude Desktop, an IDE with Claude integration, a custom agent runtime). Manages the LLM, the UI, and owns permissions/consent.
- **Client** — lives inside the host, maintains a **1:1 stateful connection** to a single server. A host with 3 server connections runs 3 client instances.
- **Server** — a lightweight process/service that exposes capabilities (tools, resources, prompts) from one system (a database, an API, the local filesystem, a SaaS product) via the MCP protocol. Servers are typically small, focused, single-purpose programs.

### 2.2 Protocol layer

- **Wire format**: JSON-RPC 2.0 — every message is a `request`/`response`/`notification` with `jsonrpc: "2.0"`.
- **Transports**:
  - **stdio** — server runs as a local subprocess, communicates over stdin/stdout. Used for local tools (filesystem access, local scripts). Simple, no network exposure.
  - **Streamable HTTP** (current spec) — server runs as an HTTP endpoint; client POSTs JSON-RPC requests, server can respond with plain JSON or upgrade to an SSE stream for server-initiated messages/streaming. Used for remote/hosted servers. (Older spec versions used a plain "HTTP+SSE" transport with two separate endpoints — deprecated in favor of the unified Streamable HTTP transport.)
- **Lifecycle**: client and server perform an **initialize handshake** — exchange protocol version + capabilities (which features each side supports: tools, resources, prompts, sampling, roots) — before any real requests flow.

## 3. The three primitives a server exposes

### 3.1 Tools — model-controlled actions

Functions the **LLM decides to call** (like function calling), e.g. `search_issues`, `run_query`, `create_file`. The host lists available tools to the model as part of the system context; the model emits a tool-call request; the client forwards it to the server; the server executes and returns a result.

```json
{
  "name": "get_weather",
  "description": "Get current weather for a location",
  "inputSchema": {
    "type": "object",
    "properties": { "location": { "type": "string" } },
    "required": ["location"]
  }
}
```

- Analogous to OpenAI/Anthropic "function calling" tool definitions, but sourced dynamically from a server instead of hardcoded in the app.
- Because a tool call can have side effects (write a file, send a message), hosts are expected to gate tool execution behind **user consent/approval** — MCP itself doesn't enforce this, it's a host responsibility called out explicitly in the spec's security principles.

### 3.2 Resources — application-controlled data

Read-only(ish) data the **host/app decides to fetch and attach** as context — not something the model calls like a function, more like "files" the app can list and read: a file's contents, a DB schema, a Slack channel's recent messages. Identified by a URI (e.g. `file:///path`, `postgres://db/table`).

```json
{
  "uri": "file:///project/README.md",
  "name": "README.md",
  "mimeType": "text/markdown"
}
```

- `resources/list` — enumerate available resources.
- `resources/read` — fetch a resource's content by URI.
- Servers can also send `resources/updated` notifications so the host knows to re-fetch (subscription model), and `resources/list_changed` when the available set changes.

### 3.3 Prompts — user-controlled templates

Reusable, parameterized prompt templates a server exposes, meant to be **explicitly invoked by the user** (e.g. via a slash-command-like UI in the host) rather than auto-selected by the model — e.g. a `/summarize-pr` prompt template that a GitHub MCP server ships.

```json
{
  "name": "summarize_pr",
  "description": "Summarize a pull request",
  "arguments": [{ "name": "pr_number", "required": true }]
}
```

### 3.4 The fourth piece — Sampling (server-to-client)

**Sampling** inverts the usual direction: a **server** can ask the **client's** LLM to generate a completion (`sampling/createMessage`), e.g. an agentic server that needs an LLM call mid-task without bringing its own API key/model. The host still mediates — typically requiring user approval of the sampled request/response — so servers can't silently spend the user's model budget or exfiltrate data via crafted prompts.

There's also **Roots** — a client can tell a server which directories/URIs it's allowed to operate within (a filesystem server, for instance, is scoped to the workspace root the host grants it).

## 4. Example: a minimal MCP server (Python SDK)

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("weather-server")

@mcp.tool()
def get_weather(location: str) -> str:
    """Get current weather for a location."""
    return f"72F and sunny in {location}"

@mcp.resource("config://settings")
def get_settings() -> str:
    return "theme=dark"

if __name__ == "__main__":
    mcp.run(transport="stdio")   # or transport="streamable-http"
```

Registering it with a host (e.g. Claude Desktop / Claude Code config, `claude_desktop_config.json` or `.mcp.json`):

```json
{
  "mcpServers": {
    "weather": {
      "command": "python",
      "args": ["weather_server.py"]
    }
  }
}
```

For a **remote** server the config instead points at a URL:

```json
{
  "mcpServers": {
    "weather": { "url": "https://weather.example.com/mcp" }
  }
}
```

## 5. A typical request flow

```
1. Host starts client, client<->server "initialize" handshake (protocol version, capabilities)
2. Client calls tools/list -> gets tool schemas
3. Host includes tool schemas in the LLM's context (like function-calling tools)
4. User asks: "what's the weather in Boston?"
5. LLM decides to call get_weather({"location": "Boston"})
6. Host asks user for approval (if configured to) -> client sends tools/call to server
7. Server executes, returns result -> client passes result back to host
8. Host feeds result back to LLM as a tool result -> LLM generates final answer
```

## 6. MCP vs plain function calling vs LangChain tools

| | Plain function calling | LangChain `@tool` | MCP |
|---|---|---|---|
| Tool defined | Hardcoded per app | Hardcoded per app (Python) | Once, in a standalone server process |
| Reusable across apps | No | Only within LangChain apps | Yes — any MCP-compliant host |
| Discovery | Static, compiled into app | Static, compiled into app | Dynamic (`tools/list` at runtime) |
| Process boundary | In-process | In-process | Separate process/service — language-agnostic (server can be Python, TS, Go, ...; host can be a different language entirely) |
| Data access primitive | Ad hoc | Ad hoc / retriever objects | Standardized `resources` |
| Server-initiated LLM calls | N/A | N/A | `sampling` |

MCP and LangChain aren't mutually exclusive — LangChain has an `langchain-mcp-adapters` package that turns MCP server tools into LangChain-compatible tool objects, so you can plug an MCP server into a LangGraph agent.

```python
from langchain_mcp_adapters.client import MultiServerMCPClient

client = MultiServerMCPClient({
    "weather": {"command": "python", "args": ["weather_server.py"], "transport": "stdio"},
    "github": {"url": "https://github-mcp.example.com/mcp", "transport": "streamable_http"},
})
tools = await client.get_tools()   # LangChain-compatible tool objects, usable in create_react_agent etc.
```

## 7. Security considerations

MCP's own spec calls these out as host/client responsibilities, since the protocol itself doesn't enforce them:

- **User consent for tool execution** — a tool call can have real side effects (delete a file, send an email); hosts should surface what's about to run and get explicit approval, not auto-execute silently.
- **Consent for data access** — resources can expose sensitive data; hosts should let users control what a server can read.
- **Consent for sampling** — since sampling lets a server trigger LLM calls (and spend tokens/budget) through the client, hosts should gate this too.
- **Prompt injection via tool/resource content** — a malicious or compromised server (or content it returns, e.g. a poisoned webpage a "fetch" tool retrieves) can embed instructions aimed at hijacking the model ("ignore previous instructions and..."). Treat tool/resource output as **data, not instructions**, same discipline as RAG-retrieved content.
- **Server trust boundary** — installing an MCP server is effectively installing arbitrary code with the permissions you grant it (filesystem/network access, credentials it holds); only add servers from sources you trust, same caution as installing any dependency/package.
- **Tool description spoofing** — since tool descriptions are supplied by the server and fed into the model's context, a malicious server could write a deceptive tool description to manipulate model behavior even without ever being "called" maliciously — another reason server provenance matters.

## 8. Where MCP fits in an agentic-RAG / LangGraph system

MCP is a natural fit for the "RAG as a tool for an agent" pattern (see RAG notes, Module 8): instead of a single hardcoded retriever tool, expose retrieval — and any other action (DB query, API call, filesystem access) — as MCP servers, and let a LangGraph agent's tool-calling node dynamically discover and invoke them. This decouples "what tools exist" from "what agent framework is running the loop," so the same MCP server (e.g. a company knowledge-base search server) can be reused by Claude Desktop, Claude Code, and a custom LangGraph agent without rewriting the integration three times.
