# Model Context Protocol (MCP) Tutorial

**Model Context Protocol (MCP)** is an open protocol, introduced by Anthropic in November 2024, that standardizes how AI applications (like chatbots, IDE assistants, and autonomous agents) connect with external tools, data sources, and prompt templates. It is often described as **"USB-C for AI applications"** — instead of every application writing a custom, one-off integration for every external system it wants to use, both sides implement one common protocol, and any MCP-compatible application can talk to any MCP-compatible tool.

In this tutorial, we will learn what MCP is, why it was introduced, its architecture, how it works internally, how to build a simple MCP server, and how to secure an MCP deployment.

## 1. What is MCP and Why Do We Need It?

Before MCP, every AI application that wanted to use external tools (a GitHub search, a Slack message, a database query) had to write its own custom integration for every single tool. If there were **M** AI applications and **N** external systems, this required building and maintaining **M × N** bespoke integrations — each one reimplementing authentication, request/response formatting, and error handling on its own. This is known as the **M×N integration problem**.

```
Without MCP (M x N problem):          With MCP (M + N solution):

App1 --custom--> GitHub                App1 --\
App1 --custom--> Slack                 App2 ---+--> MCP Client --MCP--> MCP Server (GitHub)
App2 --custom--> GitHub                App3 --/                --MCP--> MCP Server (Slack)
App2 --custom--> Database                                       --MCP--> MCP Server (Database)
```

MCP solves this the same way earlier standards solved similar problems:

| Protocol | Problem it solved |
|---|---|
| **LSP** (Language Server Protocol) | One language server works with any LSP-compliant code editor, instead of every editor writing its own support for every language. |
| **MCP** (Model Context Protocol) | One MCP server works with any MCP-compliant AI application, instead of every AI app writing its own support for every tool/data source. |

**In short:** each AI application implements the MCP *client* side once, and each external system implements the MCP *server* side once. This reduces the integration effort from M×N to M+N.

## 2. Architecture of MCP

MCP follows a **Host → Client → Server** architecture.

```
+-------------------------------+
|            Host               |   e.g. Claude Desktop, an IDE, Claude Code
|   +------------+               |
|   | MCP Client |<----1:1------+---- MCP Server A (e.g. filesystem)
|   +------------+               |
|   +------------+               |
|   | MCP Client |<----1:1------+---- MCP Server B (e.g. GitHub)
|   +------------+               |
+-------------------------------+
```

- **Host** — the user-facing AI application, such as Claude Desktop, an IDE plugin, or a custom agent runtime. It manages the LLM, the user interface, and owns permission/consent decisions.
- **Client** — a component that lives *inside* the host and maintains a **one-to-one, stateful connection** with exactly one server. If a host connects to 3 servers, it runs 3 separate client instances internally.
- **Server** — a lightweight, focused process that exposes capabilities (tools, data, or prompts) belonging to one external system — for example, a filesystem, a database, or a SaaS product's API.

### Protocol Layer

- **Wire format**: [JSON-RPC 2.0](https://www.jsonrpc.org/specification) — every message is a request, response, or notification carrying `"jsonrpc": "2.0"`.
- **Transports**:
  - **stdio** — the server runs as a local subprocess and communicates over standard input/output. Used for local tools (filesystem access, local scripts). Simple, and not exposed to the network.
  - **Streamable HTTP** — the server runs as an HTTP endpoint; the client sends JSON-RPC requests via POST, and the server can respond with plain JSON or upgrade to a Server-Sent Events (SSE) stream for server-initiated messages. Used for remote/hosted servers.
- **Lifecycle**: the client and server first perform an **initialize handshake**, exchanging the protocol version and the capabilities each side supports (tools, resources, prompts, sampling, roots), before any real requests are exchanged.

## 3. Core Primitives Exposed by an MCP Server

An MCP server can expose up to four kinds of capabilities:

### 3.1 Tools (Model-Controlled)

Functions that the **LLM itself decides to call**, similar to function calling — for example `search_issues`, `run_query`, or `create_file`.

```json
{
  "name": "get_weather",
  "description": "Get current weather for a location",
  "inputSchema": {
    "type": "object",
    "properties": { "location": { "type": "string" } },
    "required": ["location"]
  }
}
```

Because a tool call can have real side effects (writing a file, sending a message), the host is expected to ask the user for approval before executing it. MCP itself does not enforce this — it is a documented host responsibility.

### 3.2 Resources (Application-Controlled)

Read-only data that the **host application** decides to fetch and attach as context — think of these as "files" the app can list and read, such as a file's contents, a database schema, or recent Slack messages. Each resource is identified by a URI.

```json
{
  "uri": "file:///project/README.md",
  "name": "README.md",
  "mimeType": "text/markdown"
}
```

- `resources/list` — enumerate available resources.
- `resources/read` — fetch a resource's content by URI.
- Servers can also emit `resources/updated` and `resources/list_changed` notifications so the host knows when to re-fetch.

### 3.3 Prompts (User-Controlled)

Reusable, parameterized prompt templates meant to be **explicitly triggered by the user** — for example, a `/summarize-pr` slash command exposed by a GitHub MCP server.

```json
{
  "name": "summarize_pr",
  "description": "Summarize a pull request",
  "arguments": [{ "name": "pr_number", "required": true }]
}
```

### 3.4 Sampling (Server-to-Client)

**Sampling** reverses the usual flow: a **server** can ask the **client's** LLM to generate a completion (`sampling/createMessage`). This lets an agentic server request an LLM call mid-task without needing its own API key. The host still mediates this, typically requiring user approval, so a server cannot silently spend the user's model budget.

There is also a related concept called **Roots** — the client tells the server which directories/URIs it is allowed to operate within (for instance, scoping a filesystem server to a specific project folder).

## 4. How MCP Works — Step by Step

1. The host starts an MCP client; the client and server perform the `initialize` handshake (protocol version + capabilities).
2. The client calls `tools/list` to fetch the available tool schemas.
3. The host includes these tool schemas in the LLM's context, just like function-calling tool definitions.
4. The user asks a question, e.g. *"What's the weather in Boston?"*
5. The LLM decides to call `get_weather({"location": "Boston"})`.
6. The host asks the user for approval (if configured to); once approved, the client sends a `tools/call` request to the server.
7. The server executes the request and returns a result; the client passes it back to the host.
8. The host feeds the result back to the LLM as a tool result, and the LLM generates the final answer for the user.

## 5. Example: Building a Simple MCP Server

Below is a minimal MCP server built using Anthropic's Python SDK. It exposes one **tool** and one **resource**.

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("weather-server")

@mcp.tool()
def get_weather(location: str) -> str:
    """Get current weather for a location."""
    return f"72F and sunny in {location}"

@mcp.resource("config://settings")
def get_settings() -> str:
    return "theme=dark"

if __name__ == "__main__":
    mcp.run(transport="stdio")   # or transport="streamable-http"
```

To register this server with a host (e.g. Claude Desktop or Claude Code), add it to the host's MCP config file (`claude_desktop_config.json` or `.mcp.json`):

```json
{
  "mcpServers": {
    "weather": {
      "command": "python",
      "args": ["weather_server.py"]
    }
  }
}
```

For a **remote** server, the config points at a URL instead of a local command:

```json
{
  "mcpServers": {
    "weather": { "url": "https://weather.example.com/mcp" }
  }
}
```

## 6. MCP vs Function Calling vs LangChain Tools

| Feature | Plain Function Calling | LangChain `@tool` | MCP |
|---|---|---|---|
| Where the tool is defined | Hardcoded per app | Hardcoded per app (Python) | Once, in a standalone server process |
| Reusable across apps | No | Only within LangChain apps | Yes — any MCP-compliant host |
| Discovery | Static, compiled into the app | Static, compiled into the app | Dynamic, via `tools/list` at runtime |
| Process boundary | In-process | In-process | Separate process/service; language-agnostic |
| Data access primitive | Ad hoc | Ad hoc / retriever objects | Standardized `resources` |
| Server-initiated LLM calls | Not supported | Not supported | Supported via `sampling` |

MCP and LangChain are not mutually exclusive. The `langchain-mcp-adapters` package converts MCP server tools into LangChain-compatible tool objects, so an MCP server can be plugged directly into a LangGraph agent:

```python
from langchain_mcp_adapters.client import MultiServerMCPClient

client = MultiServerMCPClient({
    "weather": {"command": "python", "args": ["weather_server.py"], "transport": "stdio"},
    "github": {"url": "https://github-mcp.example.com/mcp", "transport": "streamable_http"},
})
tools = await client.get_tools()   # usable directly in create_react_agent, etc.
```

## 7. Security in MCP

Because an MCP server can execute code, touch the filesystem, and hold real credentials, security is a first-class concern. This section covers what the protocol expects of implementers, the specific attack vectors documented in the official [MCP Security Best Practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices) guide, and a practical checklist for day-to-day use.

### 7.1 General Security Principles

The MCP specification calls these out as **host/client responsibilities** — the protocol itself does not enforce them:

- **User consent for tool execution** — a tool call can have real side effects (deleting a file, sending an email). The host must surface what is about to run and get explicit approval rather than auto-executing silently.
- **Consent for data access** — resources can expose sensitive data, so the host should let the user control what a server is allowed to read.
- **Consent for sampling** — since sampling lets a server trigger LLM calls (and spend tokens) through the client, this should also require user approval.
- **Prompt injection via tool/resource content** — a malicious or compromised server (or content it returns, e.g. a poisoned webpage fetched by a "fetch" tool) can embed instructions aimed at hijacking the model, such as *"ignore previous instructions and..."*. Tool and resource output should always be treated as **data, not instructions** — the same discipline used for RAG-retrieved content.
- **Server trust boundary** — installing an MCP server is effectively installing arbitrary code with whatever permissions you grant it (filesystem access, network access, stored credentials). Only add servers from sources you trust, the same way you would vet any third-party dependency.
- **Tool description spoofing** — tool descriptions are supplied by the server and fed directly into the model's context. A malicious server could write a deceptive description to manipulate model behavior even without the tool ever being maliciously "called".

### 7.2 Common Attack Vectors and Their Mitigations

| # | Attack Vector | What Happens | How to Mitigate |
|---|---|---|---|
| 1 | **Confused Deputy Problem** | An MCP *proxy* server using a static client ID with a third-party auth server, combined with dynamic client registration and a consent cookie, lets an attacker register a malicious redirect URI and ride the victim's existing cookie to steal an authorization code. | The proxy **must** show its own per-client consent screen before forwarding to the third party; secure the consent cookie (`__Host-` prefix, `Secure`/`HttpOnly`/`SameSite=Lax`, signed, bound to `client_id`); validate `redirect_uri` with exact match; use a cryptographically random, short-lived, single-use `state` parameter. |
| 2 | **Token Passthrough** | A server accepts a token that was not issued specifically for it (no audience check) and forwards it unmodified downstream, breaking the OAuth trust boundary and the audit trail. | Servers **must not** accept any token not explicitly issued *for* them — always validate the audience claim ([RFC 9068](https://www.rfc-editor.org/rfc/rfc9068.html)). |
| 3 | **Server-Side Request Forgery (SSRF)** | A malicious server supplies OAuth discovery URLs (`resource_metadata`, `token_endpoint`, etc.) pointing at internal IPs or cloud metadata endpoints (`169.254.169.254`), tricking the client into leaking credentials. | Enforce HTTPS (except loopback in dev); block private/reserved IP ranges ([RFC 9728 §7.7](https://datatracker.ietf.org/doc/html/rfc9728#section-7.7)); validate redirect targets the same way; route discovery requests through an egress proxy instead of hand-rolled IP checks. |
| 4 | **State Handle Hijacking** | A server mints a stateful handle (e.g. a cart ID) and treats mere *possession* of that handle as proof of identity, letting an attacker who guesses it act as another user. | Never treat a handle as authentication. Use non-deterministic, securely random, expiring handles, bound server-side to the authenticated user (e.g. keyed as `<user_id>:<handle>`). |
| 5 | **Local MCP Server Compromise** | A locally installed server is arbitrary code running with the client's privileges — a malicious startup command, a poisoned package, or an insecure localhost listener reachable via DNS rebinding. | Clients must show the exact, untruncated command before running it and flag dangerous patterns (`sudo`, `rm -rf`, network calls). Prefer `stdio` transport over an open HTTP port; sandbox spawned processes with least privilege. |
| 6 | **OAuth Authorization URL Validation (XSS/RCE)** | A malicious server hands the client a `javascript:` URL as the "authorization URL." Passing it to `window.open()` causes XSS; shelling out to open it causes command injection. | Allowlist only `http(s)://` schemes; reject `javascript:`, `data:`, `file:`, `vbscript:`; never shell out to open URLs; apply CSP (`script-src 'self'`) on web-based clients. |
| 7 | **Mix-Up Attacks / Localhost Redirect Impersonation** | A malicious auth server tries to get a client to hand it a code/token meant for a different, honest server; separately, an attacker can bind to a free `localhost` port to impersonate a legitimate native client. | Bind the authorization response to the auth server recorded before redirect (PKCE alone is not sufficient); clearly surface the redirect URI's hostname and warn on `localhost`-only redirects. |
| 8 | **Scope Over-Granting** | Requesting/granting broad, omnibus scopes (`files:*`, `admin:*`) up front means one leaked token has a huge blast radius and is hard to revoke without breaking every workflow. | Start with a minimal scope set; step up incrementally via `WWW-Authenticate: scope="..."` challenges only when a privileged operation is actually attempted. |

### 7.3 Practical Security Checklist

**If you only *use* MCP servers** (e.g. through Claude Desktop or Claude Code):

- Only add servers from sources you trust — an MCP server is arbitrary code running with whatever permissions you grant it.
- Review the exact command and arguments before approving a new local server; don't blindly accept one-click configs from a link or a README.
- Treat all tool/resource output as **untrusted data**, never as instructions — the same discipline used for RAG.
- Grant the narrowest possible access (don't hand a filesystem server your entire home directory if a project folder would do).
- In Claude Code, the list of allowed MCP servers lives in checked-in settings — review it in code review like any other dependency; new servers require trust verification on first use.

**If you are *building* an MCP server:**

- Never accept a token that was not issued specifically for your server — validate the audience claim.
- If your server proxies a third-party API, implement your own per-client consent screen rather than relying on the third party's cookie.
- Bind any stateful handle you mint to the authenticated user server-side; never treat possession as identity.
- Prefer `stdio` for anything meant to run locally; if exposing HTTP, require authentication.
- Request and advertise the narrowest OAuth scopes that work.

**If you are *building* an MCP client or host:**

- Require explicit, visible user consent before executing a tool call, reading a resource, or honoring a sampling request.
- Validate every URL a server hands you: allowlist `http(s)` only, block private/reserved IP ranges and cloud metadata addresses, never shell out to open a URL.
- Don't blindly follow redirects — re-validate each hop.
- If running a local `stdio`-spawning proxy alongside a web-based client, sandbox it so a web-layer XSS cannot reach arbitrary process spawning.

## 8. Advantages of MCP

- **Reduces integration effort** from M×N custom integrations down to M+N standardized ones.
- **Reusability** — one MCP server works across every MCP-compliant host (Claude Desktop, an IDE, a custom agent) without rewriting the integration.
- **Dynamic discovery** — clients discover available tools/resources at runtime via `tools/list` and `resources/list`, instead of them being hardcoded into the app.
- **Language-agnostic** — a server can be written in Python, TypeScript, Go, or any other language, and any host can still talk to it.
- **Clear separation of concerns** — tools (model-controlled), resources (app-controlled), and prompts (user-controlled) give each actor in the system a well-defined role.

## 9. Disadvantages / Limitations of MCP

- **Security is largely a host/client responsibility** — the protocol does not itself enforce consent, sandboxing, or trust; a careless implementation can expose real risk.
- **Trust-boundary risk** — installing a server means running its code with the permissions you grant it, similar to installing any third-party package.
- **Prompt injection surface** — any tool/resource output the model reads can carry adversarial instructions if not treated as untrusted data.
- **Operational overhead** — running many local servers as separate processes adds resource and process-management overhead compared to in-process function calling.
- **Still a young ecosystem** — tooling, server quality, and security maturity vary widely across community-built servers.

## 10. Applications of MCP

- Connecting an AI coding assistant to a **filesystem**, **Git**, or a **database** for read/write operations.
- Letting an AI agent **search and summarize** issues/PRs from **GitHub**, or send messages via **Slack**.
- Exposing **retrieval (RAG)** as a tool for an agent, instead of hardcoding a single retriever — see the "RAG as a tool" pattern.
- Building **multi-agent systems** (e.g. with LangGraph) where the same MCP server (say, a company knowledge-base search server) is reused across multiple different agent frameworks and hosts without re-implementing the integration for each.

---

## 11. Conclusion

MCP standardizes how AI applications connect to external tools, data, and prompts, solving the M×N integration problem the same way LSP standardized editor-to-language-tooling communication. It defines a clean **Host → Client → Server** architecture and four primitives — **tools**, **resources**, **prompts**, and **sampling** — each with a clearly assigned controller (model, app, user, and server respectively). Because an MCP server is effectively arbitrary code running with real permissions, security is not automatic: user consent, input validation, trust boundaries, and the specific attack vectors covered in Section 7 must be deliberately engineered by whoever builds the client, host, or server. Used carefully, MCP lets the same tool integration be written once and reused across every compliant AI application.
