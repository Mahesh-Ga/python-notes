## 1. What is vLLM?

An open-source **inference and serving engine** for LLMs (originated at UC Berkeley, now a community project). It is not a model — it loads a model (Llama, Mistral, Qwen, etc. from Hugging Face) and serves it efficiently on GPUs.

**Headline claim:** 2–24× higher throughput than naive Hugging Face Transformers serving, mainly by wasting less GPU memory and keeping the GPU busy.

**Key features**
- **PagedAttention** — paged KV-cache memory management
- **Continuous batching** — requests join/leave the batch every step
- **OpenAI-compatible HTTP server** (`/v1/chat/completions`, `/v1/completions`, `/v1/embeddings`)
- Streaming (SSE), prefix caching, speculative decoding, chunked prefill
- Quantization support (AWQ, GPTQ, FP8, INT8, bitsandbytes, GGUF)
- Tensor / pipeline parallelism for multi-GPU
- LoRA adapter serving (many adapters on one base model)
- Multimodal models, structured/guided decoding (JSON schema, regex)
- Hardware: NVIDIA, AMD, Intel, TPU, CPU (support varies)

## 2. The problem it solves

LLM generation has two phases:

| Phase | What happens | Bound by |
|---|---|---|
| **Prefill** | Process the whole prompt in parallel, build the KV cache | Compute |
| **Decode** | Generate one token at a time, reading all weights + KV cache each step | **Memory bandwidth** |

The **KV cache** (keys/values of all previous tokens, per layer) grows with sequence length and with every concurrent request. It is the main memory consumer besides the weights.

```
KV cache per token ≈ 2 × layers × kv_heads × head_dim × bytes
e.g. Llama-2-13B ≈ ~0.8 MB/token (fp16)  →  a 2K-token sequence ≈ 1.6 GB
```

### Naive serving wastes memory
- Pre-allocates a **contiguous max-length** KV buffer per request (e.g. 2048 tokens) even if the request uses 100 → **internal fragmentation**.
- Different-sized buffers → **external fragmentation**.
- Reported waste: **60–80%** of KV memory → few concurrent requests → low throughput.
- **Static batching:** batch waits for the slowest request; finished sequences leave idle GPU slots.

---

## 3. PagedAttention (the core idea)

Borrowed from OS virtual memory paging.

- Split each sequence's KV cache into fixed-size **blocks** (e.g. 16 tokens).
- Blocks are **non-contiguous** in GPU memory; a per-request **block table** maps logical blocks → physical blocks (like a page table).
- Allocate blocks **on demand** as tokens are generated; free them on completion.

```
Logical (seq A):  [B0][B1][B2]            Block table A: 0→7, 1→2, 2→9
Physical GPU mem: [ ][ ][A1][ ][ ][ ][ ][A0][ ][A2]...
```

**Benefits**
- Near-zero fragmentation (waste < ~4%, only the last partially filled block) → **more concurrent sequences per GPU**.
- **Memory sharing:** parallel sampling (`n>1`), beam search, and shared prompts point to the *same physical blocks* with **copy-on-write**.
- Enables **prefix caching** — requests with the same prompt prefix reuse blocks (hash of block contents).
- Enables **preemption** — evict (swap to CPU or recompute) low-priority sequences when memory runs out.

---

## 4. Continuous (iteration-level) batching

| Static batching | Continuous batching |
|---|---|
| Fixed batch; waits for all to finish | Scheduler runs **each decode step**; finished requests exit and new ones enter immediately |
| GPU idle on short sequences | GPU stays saturated |
| High tail latency for new requests | New request starts at next iteration |

The **scheduler** keeps waiting / running / swapped queues, admits requests while KV blocks are available, and may preempt when blocks run out.

**Chunked prefill:** splits long prompts into chunks mixed with decode tokens in the same step → prevents a huge prompt from stalling everyone else's token generation (better inter-token latency).

## 5. Architecture (high level)

```
Clients (OpenAI SDK / curl)
        │  HTTP (FastAPI/uvicorn, SSE streaming)
        ▼
 API server ──► AsyncLLMEngine ──► Scheduler (continuous batching, block manager)
                                        │
                                        ▼
                              Workers (1 per GPU)  ── model executor + PagedAttention kernels
                                        │
                              KV cache blocks in GPU memory (+ CPU swap)
```

- Tokenization/detokenization and sampling are handled by the engine; the API layer is async ([[5. WSGI vs ASGI.md]]).
- Multi-GPU uses Ray or multiprocessing for workers.
- The V1 engine rewrote the core loop (separate process for engine core, better prefix caching, lower CPU overhead) — details change by version, so check the docs.

## 6. Using vLLM

### Start an OpenAI-compatible server
```bash
pip install vllm
vllm serve meta-llama/Llama-3.1-8B-Instruct \
    --dtype bfloat16 \
    --max-model-len 8192 \
    --gpu-memory-utilization 0.90 \
    --enable-prefix-caching \
    --port 8000
```

### Call it with the OpenAI SDK (drop-in)
```python
from openai import OpenAI
client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")

stream = client.chat.completions.create(
    model="meta-llama/Llama-3.1-8B-Instruct",
    messages=[{"role": "user", "content": "Explain PagedAttention"}],
    max_tokens=256,
    stream=True,
)
for chunk in stream:
    print(chunk.choices[0].delta.content or "", end="")
```

### Offline batch inference (Python)
```python
from vllm import LLM, SamplingParams

llm = LLM(model="meta-llama/Llama-3.1-8B-Instruct", gpu_memory_utilization=0.9)
params = SamplingParams(temperature=0.2, top_p=0.9, max_tokens=200)
outputs = llm.generate(["Prompt 1", "Prompt 2", "Prompt 3"], params)
for o in outputs:
    print(o.outputs[0].text)
```

### Multi-GPU / quantized
```bash
# 70B across 4 GPUs
vllm serve meta-llama/Llama-3.1-70B-Instruct --tensor-parallel-size 4

# AWQ 4-bit model on 1 GPU
vllm serve TheBloke/Llama-2-13B-AWQ --quantization awq
```

## 7. Important knobs

| Flag | Meaning / tuning tip |
|---|---|
| `--gpu-memory-utilization` | Fraction of GPU memory vLLM may use (weights + KV cache). Default ~0.9. Higher → bigger KV cache → more concurrency; too high → OOM |
| `--max-model-len` | Max context (prompt + output). Lower it to free KV memory if you don't need the full window |
| `--max-num-seqs` | Max concurrent sequences in a batch |
| `--max-num-batched-tokens` | Token budget per step; trades throughput vs latency (and chunked prefill behaviour) |
| `--tensor-parallel-size` | Shard each layer across N GPUs (needed when model doesn't fit on one) |
| `--pipeline-parallel-size` | Split layers across GPUs/nodes |
| `--quantization` | `awq`, `gptq`, `fp8`, `bitsandbytes`, etc. |
| `--kv-cache-dtype fp8` | Quantize KV cache → ~2× more cache capacity |
| `--enable-prefix-caching` | Reuse KV blocks for shared prefixes (system prompts, RAG docs) |
| `--enable-chunked-prefill` | Mix prefill chunks with decodes |
| `--speculative-config` | Speculative decoding (draft model / n-gram / EAGLE) |
| `--enable-lora` | Serve LoRA adapters on a shared base |
| `--swap-space` | CPU memory for swapped KV blocks |

**Sizing a deployment (rule of thumb)**
```
GPU memory = weights + KV cache + activations/overhead
weights    ≈ params × bytes/param           (8B @ bf16 ≈ 16 GB)
KV budget  = GPU mem × utilization − weights − overhead
max concurrent tokens ≈ KV budget / KV bytes-per-token
```

## 8. Performance metrics to know

| Metric | Meaning |
|---|---|
| **TTFT** (time to first token) | Dominated by queueing + prefill |
| **ITL / TPOT** (inter-token latency / time per output token) | Decode speed per user |
| **Throughput** (tokens/s) | Total across all users — drives cost per token |
| **Goodput** | Throughput that meets latency SLOs |
| **KV cache usage %** | If pinned at ~100%, requests queue/preempt → add GPUs, shrink `max-model-len`, or quantize |

vLLM exposes Prometheus metrics at `/metrics` (running/waiting requests, cache usage, TTFT, etc.) — wire into Grafana ([[18.observability_evaluation_reliability.md]]).

Benchmark with `vllm bench serve` (or `benchmarks/benchmark_serving.py`) using realistic prompt/output length distributions.

## 9. Production deployment

- **Container:** official `vllm/vllm-openai` Docker image; mount HF cache; `--gpus all`.
- **Kubernetes** ([[11.kubernetes.md]]): one pod per model replica (or per TP group), GPU node pool, readiness probe on `/health`, HPA/KEDA on queue depth (`num_requests_waiting`) rather than CPU. vLLM **production-stack** / KServe / Ray Serve / KubeAI provide routing and autoscaling.
- **Routing:** prefix-aware / session-affinity routing improves prefix-cache hit rate across replicas.
- **Auth/rate limits:** put an API gateway in front (vLLM's `--api-key` is basic).
- **Model load time is slow** (GBs of weights) → keep warm replicas, use fast storage/model caching; cold-start autoscaling is painful.
- **Disaggregated prefill/decode:** separate prefill and decode pools to tune TTFT and ITL independently (newer/advanced).

## 10. vLLM vs alternatives

| Engine | Notes |
|---|---|
| **HF Transformers `generate`** | Simple, flexible, low throughput; fine for prototyping |
| **HF TGI** | Production server, continuous batching; ecosystem tied to HF |
| **TensorRT-LLM (NVIDIA)** | Often highest NVIDIA performance, but compile/engine-build step, more complex |
| **SGLang** | Strong at prefix reuse (RadixAttention) & structured/agent workloads; very competitive |
| **llama.cpp / Ollama** | CPU/edge/local, GGUF quantization, great for laptops, not for high-concurrency GPU serving |
| **Triton Inference Server** | General serving framework; can host vLLM/TensorRT-LLM backends |

**Pick vLLM when:** self-hosting open models, many concurrent users, want OpenAI-compatible API and quick setup. **Don't bother** for a single-user local app (Ollama/llama.cpp) or when using closed APIs.

## 11. Limitations / gotchas

- Needs GPUs with enough memory; model must fit (weights + KV) — else TP/quantization.
- First request after start is slow (CUDA graph capture / warmup).
- Throughput vs latency trade-off: bigger batches raise throughput but increase per-user latency.
- Quantized models can lose quality — evaluate ([[38.AI evaluation.md]]).
- Version churn: flags and defaults change quickly; pin versions.
- Long contexts reduce concurrency since KV cache scales with tokens.
- Sampling nondeterminism across batch composition (not bit-exact reproducible).

## 12. Quick interview-answer summary

> "vLLM is an open-source LLM serving engine that maximizes GPU throughput. Decoding is memory-bound and the KV cache dominates memory; naive servers reserve contiguous max-length buffers per request and waste 60–80% of it. vLLM's **PagedAttention** stores the KV cache in fixed-size non-contiguous blocks with a block table, like OS paging, so waste is near zero, and blocks can be shared with copy-on-write for parallel sampling and **prefix caching**. Combined with **continuous batching** — scheduling at every decode step so finished requests free slots immediately — it fits more concurrent requests per GPU, giving multiples of the throughput of static-batched Transformers serving. It exposes an OpenAI-compatible API with streaming, supports quantization (AWQ/GPTQ/FP8), tensor parallelism, speculative decoding and LoRA. I'd tune `gpu-memory-utilization`, `max-model-len` and `max-num-seqs`, monitor KV-cache usage and TTFT/ITL via Prometheus, and autoscale on queue depth. It lowers cost per token when self-hosting open models at scale."

### Common follow-up Q&A

| Question | Short answer |
|---|---|
| What is PagedAttention? | KV cache split into fixed blocks mapped via a block table; removes fragmentation and enables sharing. |
| Continuous vs static batching? | Continuous schedules per iteration so finished sequences free slots at once; static waits for the whole batch. |
| Why is decode memory-bound? | Each token reads all weights + KV cache but does little compute per byte. |
| How do you serve a model too big for one GPU? | Tensor parallelism (`--tensor-parallel-size`), pipeline parallelism, and/or quantization. |
| How to improve TTFT? | Prefix caching, chunked prefill, fewer queued requests (more replicas), smaller prompts. |
| How to improve throughput/cost? | Raise memory utilization, quantize weights/KV (FP8/AWQ), larger batch, speculative decoding. |
| KV cache full — what happens? | Requests wait or get preempted (swap/recompute); fix with more GPUs, lower `max-model-len`, KV quantization. |
| What to autoscale on? | Waiting-request queue depth / KV cache usage, not CPU. |
