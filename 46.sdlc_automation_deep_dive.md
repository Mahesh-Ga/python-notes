# SDLC Automation — Production Deep Dive

Companion to Option B in `45.resume_based.md`. That file has the interview-ready summary (situation/contribution/outcome); this one is for when the interviewer starts pulling on threads — "how would this actually run in prod," "what's in your database," "walk me through one agent's tool calls." Treating the product as if it shipped: multi-tenant, one pipeline run per feature request, five agents handing work off in sequence, human approval gates between the risky steps.

Pipeline: **Requirements Analyst (RA) → Architect → Dev → Tester → Deployment**, each a Semantic Kernel agent with its own plugins, each step logged, evaluated, and gated.

---

## 1. System context

| Actor / system | Interaction |
|---|---|
| Product manager / requester | Submits a feature spec (text, Jira ticket link, or template form) that kicks off a pipeline run |
| RA agent | Turns the spec into a structured requirements doc, flags ambiguity back to the requester |
| Architect agent | Reads the requirements doc + existing dependency graph, proposes component design and tech choices |
| Dev agent | Scaffolds code modules against the architecture doc, opens a draft PR |
| Tester agent | Generates and runs tests against the scaffolded code, reports coverage and failures |
| Deployment agent | Generates CI/CD manifests, builds the image, deploys to a target environment |
| Human reviewer | Approves/rejects at the two gated steps (architecture sign-off, pre-prod deploy) |
| Eval pipeline | Replays golden sets after every release, flags quality regressions per agent |

Runtime: every agent role is its own containerized deployment on AKS, so a slow Tester run (spinning up a sandbox pod to execute generated tests) doesn't starve the RA/Architect steps of capacity. The orchestrator itself is a lightweight coordinator process — it holds the Semantic Kernel `AgentGroupChat`/sequential-orchestration state per run in Redis so a pod restart doesn't lose an in-flight pipeline.

## 3. Agents

| Agent | Role | Reads | Produces | Key plugin functions | Human gate after? |
|---|---|---|---|---|---|
| **RA** (Requirements Analyst) | Turns a raw feature spec into a structured, testable requirements doc | Feature spec, prior requirement docs (vector search) | `requirements_docs` row + ambiguity score | `draft_requirements()`, `score_ambiguity()`, `request_clarification()` | No — auto-advances unless ambiguity score is high |
| **Architect** | Designs components, picks tech, checks for conflicts with existing modules | Requirements doc, Neo4j dependency graph | `architecture_docs` row (design + ADRs + tech stack) | `query_dependency_graph()`, `propose_components()`, `select_tech_stack()`, `generate_diagram()` | **Yes** — reviewer signs off before scaffolding starts |
| **Dev** | Scaffolds code modules per the architecture doc | Architecture doc, repo template library | `code_artifacts` rows, draft PR | `scaffold_module()`, `write_file()`, `run_linter()`, `open_pull_request()` | No |
| **Tester** | Generates and executes tests against scaffolded code | Code artifacts | `test_results` row (pass/fail, coverage) | `generate_unit_tests()`, `run_test_suite()`, `compute_coverage()`, `run_sast_scan()` | No — but a failing gate blocks Deployment |
| **Deployment** | Generates CI/CD manifests and deploys to target environment | Code artifacts, test results | `deployment_records` row, live pipeline in CI system | `generate_ci_pipeline()`, `build_image()`, `push_registry()`, `deploy_k8s()`, `run_smoke_test()` | **Yes** — second approval before prod, auto-deploy to staging |

Each agent is a `ChatCompletionAgent` wrapping its own `Kernel` instance (own plugin set, own instructions/persona). They don't share a kernel — that keeps a bad tool call in one agent's plugin from ever being callable by another agent, and keeps the function-calling schema handed to each LLM small and role-scoped.

---

## 4. Why Semantic Kernel here

| Requirement | How SK covers it |
|---|---|
| Five distinct roles, each with its own toolset | One `Kernel` + plugin set per agent — plugins are role-scoped by construction, not by convention |
| Deterministic handoff order with conditional branches/retries | `SequentialOrchestration`/handoff orchestration pattern drives the RA→Architect→Dev→Tester→Deployment chain; branch conditions read the previous step's structured output (ambiguity score, test pass rate) |
| Native functions + prompts treated uniformly | Plugin functions (`write_file`, `run_test_suite`, `deploy_k8s`) and prompt-based functions (`draft_requirements`) are both `KernelFunction`s, so the LLM's function-calling schema looks the same regardless of what's behind it |
| Enterprise/Azure integration | First-class `AzureChatCompletion` connector, App Insights/OpenTelemetry hooks, Azure Key Vault for secrets used by plugins |
| Auditable tool calls | Every plugin invocation is a function call the kernel can log with full arguments/result before it goes back to the LLM — no hidden string-parsing of tool output |

This is presented as the production target design; if asked "did you personally build the SK orchestration," be straight about what part you actually touched (tracing/eval, per the resume note) versus what's the surrounding system.

### 5.2 Neo4j (dependency/knowledge graph)

| Node label | Key properties |
|---|---|
| `Requirement` | id, run_id, summary |
| `Module` | id, name, language, repo_path |
| `Component` | id, name, layer (api/service/data) |
| `Pipeline` | id, run_id |
| `Release` | id, version, deployed_at |
| `Agent` | role, version |

| Relationship | Meaning |
|---|---|
| `(Requirement)-[:IMPLEMENTED_BY]->(Module)` | Traces a requirement to the code that fulfills it |
| `(Module)-[:DEPENDS_ON]->(Module)` | Dependency edges the Architect agent walks before proposing a design, so it doesn't recommend something that breaks an existing consumer |
| `(Module)-[:GENERATED_BY]->(Agent)` | Which agent/version produced it |
| `(Module)-[:TESTED_BY]->(Pipeline)` | Links to the run that validated it |
| `(Release)-[:INCLUDES]->(Module)` | What shipped in a given release |
| `(Requirement)-[:DERIVED_FROM]->(Requirement)` | Follow-up/amendment chains |

The Architect agent's `query_dependency_graph()` plugin function is what actually queries this — it's the mechanism that lets the design step reason about "what else touches this module" instead of hallucinating a clean-slate design every time.

## 6. Production tech stack

| Layer | Technology | Why |
|---|---|---|
| Agent orchestration | Semantic Kernel (Python), Sequential/Handoff Orchestration | Role-scoped plugins per agent, native+prompt functions treated uniformly, Azure-native |
| LLM serving | Azure OpenAI (GPT-4o class models), per-agent deployment/version pinning | Version pinning per agent lets you roll one agent to a new model without touching the others |
| API layer | FastAPI | Async, same stack as the PO/SO project, easy OpenAPI contracts |
| AuthN/AuthZ | OIDC (Azure AD/Entra ID), RBAC at the tenant/project level | Multi-tenant SaaS requirement |
| API gateway | Azure API Management / Kong | Rate limiting, tenant routing, auth enforcement at the edge |
| Event bus | Azure Service Bus (or Kafka) | Decouples run-creation from orchestration, replay on consumer failure |
| Primary DB | PostgreSQL (managed, e.g. Azure Flexible Server) | Run/step metadata, docs, test results, deployment records |
| Graph DB | Neo4j | Module/requirement/pipeline dependency lineage |
| Cache / session state | Redis | Kernel/orchestration session state per run, hot-path caching |
| Vector store | pgvector or Azure AI Search | RA/Architect context retrieval over past requirement & architecture docs |
| Object storage | Azure Blob Storage | Large artifacts: generated code bundles, diagrams, test reports |
| Containers | Docker | One image per agent role |
| Orchestration | Kubernetes (AKS) | Independent scaling per agent role; Tester pods run generated code in a sandboxed, network-restricted namespace |
| Autoscaling | KEDA (scale on queue depth) | Tester/Dev steps are bursty and CPU-heavier than RA/Architect |
| CI/CD | GitHub Actions / Azure DevOps Pipelines | Generated by the Deployment agent, executed by the real CI system — the agent writes the pipeline, it doesn't become the pipeline |
| IaC | Terraform | Environments provisioned identically per tenant tier |
| Secrets | Azure Key Vault | Plugin credentials (registry push, cluster deploy) never touch app config |
| Observability | OpenTelemetry → Grafana Tempo (traces), Prometheus + Grafana (metrics), structured logs to Log Analytics | Per-step spans roll up into a per-run trace tree |
| Eval store | Postgres tables above + scheduled job (Azure Container Apps Jobs / K8s CronJob) | Golden-set replay and regression diffing run independent of live traffic |

## 7. Tracing detail (unchanged from the resume summary, expanded)

Each `agent_steps` row is one span: run id, step id, agent role, model name/version, input/output artifact refs, token count, latency, status. Spans roll up into a per-run trace tree, so "the pipeline got worse" becomes "step 3 (Dev), release v14, coverage-relevant test generation regressed" — that's the isolation this schema is built to give you, and it's the piece closest to what's actually described as your contribution in the resume summary.

## 8. Key design decisions

- **Per-agent kernel, not a shared one** — keeps plugin surfaces role-scoped; a Dev-agent plugin bug can't be invoked by the Tester agent by accident.
- **Two human gates, not five** — architecture sign-off and pre-prod deploy are the two steps where a bad agent decision is expensive/hard to reverse; RA and Dev auto-advance because their output is cheap to correct downstream (Tester catches bad code, a low ambiguity-score threshold catches bad requirements).
- **Retry policy distinguishes tool failure from bad LLM output** — a transient plugin/API failure retries with backoff; a plugin that succeeds but produces a low-confidence or gate-failing result goes to `review_queue` instead of blind-retrying the LLM.
- **Structured per-step tracing over end-to-end logs** — same rationale as the original summary: isolate regressions to a specific agent/step/release, not just "quality dropped."
- **Sandbox execution for the Tester agent** — generated tests run in a network-restricted pod, never in the same execution context as the orchestrator, since the code under test was itself LLM-generated.
