## 23. Message Queues & Event-Driven Architecture

### 23.0 Quick framing (your own notes, kept)
- Celery is a task queue — you say "do this work later". Message queues like RabbitMQ and Kafka are about decoupling. Services don't call each other, they emit facts.
- Celery pattern: Service A -> "Hey worker, send this email". It's a direct command. If the worker is down, task retries. It's coupled to *who* should do the work.
- Event-driven pattern: Service A -> "OrderPlaced event happened". Service A doesn't care who listens. Email service, Inventory service, Analytics service can all react independently. **You can add a new consumer tomorrow without touching Service A.**
  - This is what RabbitMQ and Kafka give you.

---

### 23.1 Why message queues exist at all
Two services that call each other directly (HTTP/RPC) are **temporally coupled** — both must be up, at the same time, or the call fails. A queue sits between producer and consumer so:
- The producer can publish and move on even if the consumer is down, slow, or scaling up.
- Traffic bursts get absorbed (buffered) instead of falling over downstream services.
- You can add new consumers later without changing the producer (fan-out).
- Failures are isolated — a crashing consumer doesn't take down the producer.

This is the same idea as Celery's broker (§11.2), just generalized: broker = queue, worker = consumer. The difference is *intent*. Celery is "run this specific job." A message queue / event bus is "this fact happened, react if you care."

### 23.2 RabbitMQ vs Kafka — different tools for different jobs

| | RabbitMQ | Kafka |
|---|---|---|
| Model | Smart broker, dumb consumer. Broker tracks per-message state (delivered/acked) | Dumb broker, smart consumer. Broker just appends to a log; consumers track their own read position (offset) |
| Message lifecycle | Message is **removed** from the queue once acked | Message **stays** on the log for a retention period (e.g. 7 days), even after being read |
| Ordering | Per-queue ordering, but multiple consumers on one queue = ordering not guaranteed across consumers | Strict ordering **within a partition**; global order not guaranteed across partitions |
| Replay | Not really — once consumed+acked, it's gone (unless you redeliver) | Yes — any consumer can rewind and re-read from an earlier offset. Great for replay/backfill/debugging |
| Fan-out | Exchanges + multiple queues (each queue gets a copy) | Multiple consumer groups can each read the same topic independently, at their own pace |
| Routing | Rich routing: direct, topic, fanout, headers exchanges | No routing logic — you just pick a topic (and optionally a partition key) |
| Throughput / use case | Great for task/work queues, RPC-style patterns, complex routing, lower absolute throughput | Built for very high throughput event streaming, log aggregation, event sourcing, stream processing |
| Delivery guarantee knobs | ack/nack, publisher confirms, DLX | acks=0/1/all, idempotent producer, transactions |

**Rule of thumb for interviews:** RabbitMQ when you need "do this task, once, with complex routing" (closer to Celery's broker role). Kafka when you need "many consumers independently replaying a durable stream of business events" (event sourcing, analytics pipelines, audit logs).

```
RabbitMQ:                                   Kafka:
 Producer -> Exchange -> Queue -> Consumer   Producer -> Topic (partitioned log) -> Consumer Group A (offset=120)
                                                                                  -> Consumer Group B (offset=45)
 message deleted after ack                   message stays on disk until retention expires;
                                              each group tracks its own offset independently
```

### 23.3 Delivery semantics: at-most-once, at-least-once, "exactly-once"

Three theoretical guarantees a broker can offer for a single message:

1. **At-most-once** — message is delivered 0 or 1 times. Fire-and-forget, no retry. If it's lost, it's gone. Fast, but data loss on any failure. Rarely what you want for anything that matters (fine for metrics/telemetry where losing a sample is fine).
2. **At-least-once** — message is delivered 1 or more times. The broker keeps redelivering until it gets an ack. This is the **default and dominant pattern** in real systems (Celery, RabbitMQ, Kafka with `acks=all` + consumer commits after processing). Guarantees you never silently lose a message, but means **duplicates will happen**: a consumer can process a message, crash before acking, and receive it again.
3. **Exactly-once** — message delivered and processed exactly one time, no more, no less.

**Exactly-once delivery across a network is mostly a myth.** This is the important interview point: you cannot have a producer, a network, a broker, and a consumer that all agree a message was processed exactly once, because acknowledgment itself can be lost (the classic "two generals problem" / the ack for a successfully processed message can die in transit, so the sender retries, hence duplicate). Kafka's "exactly-once semantics" (idempotent producer + transactional writes) is real, but it is scoped to **Kafka-to-Kafka** pipelines (producer → topic → consume-transform-produce → another topic) — it does not extend exactly-once out to an arbitrary external side effect like "charge a credit card" or "send an email." The moment your consumer talks to something outside Kafka's transaction boundary, you're back to at-least-once for that side effect.

**The practical answer, always: design for at-least-once delivery + idempotent consumers**, so that processing the same message N times has the same effect as processing it once. This is exactly §11.4 (Celery idempotency) applied at the message-queue level:
- Dedup key / natural key check before the side effect (`WHERE order_id = ?`).
- Unique DB constraints + treat `IntegrityError` on duplicate as a no-op success.
- Upsert (`INSERT ... ON CONFLICT DO UPDATE`) instead of blind insert.
- Store a "processed message IDs" set (Redis, with TTL) and skip if the message ID was already seen — classic dedup table pattern.
- Make the side effect itself idempotent: "set status = SHIPPED" is safe to repeat; "increment inventory by 1" is not — prefer absolute-state updates over relative deltas wherever the domain allows it.

```python
# Idempotent consumer pattern (works for RabbitMQ or Kafka)
def handle_order_placed(event):
    if ProcessedEvent.objects.filter(event_id=event.id).exists():
        return  # already handled, ack and move on — no duplicate side effect

    with transaction.atomic():
        ProcessedEvent.objects.create(event_id=event.id)
        fulfill_order(event.order_id)   # the actual side effect
```

### 23.4 Ack/nack and when duplicates actually happen
The redelivery (and thus duplication) window is the gap between "consumer received the message" and "consumer acked it":

```
Consumer receives msg --> [ do work ] --> ack sent to broker
                              ^
                    if consumer crashes HERE,
                    broker never sees the ack,
                    and redelivers the message
                    to another (or the same) consumer
                    => duplicate processing
```

- **Manual ack, ack-after-processing** (not auto-ack-on-receive) is the correct pattern for at-least-once — you only tell the broker "done" after the side effect actually succeeded (e.g. Celery's `acks_late=True`, RabbitMQ manual ack, Kafka manual offset commit after processing). Auto-ack-on-receive is closer to at-most-once (you ack, then crash before finishing the work → message is lost, not redelivered).
- **Nack / reject** — explicitly tell the broker "I couldn't process this, redeliver it" (optionally to a different consumer, or back onto the queue with a delay).

### 23.5 Dead-letter queues (DLQ) — generalizing §11.5
Same idea as Celery's DLQ (§11.5), but now at the broker layer instead of the application layer:
- **RabbitMQ**: configure `x-dead-letter-exchange` on a queue. A message that is `nack`ed without requeue, or that expires (TTL), or exceeds `x-max-length`, is automatically re-routed to the DLX, which typically routes into a dedicated `*.dlq` queue for manual inspection/replay.
- **Kafka**: no built-in DLQ concept (it's just an append-only log) — you implement it yourself: on repeated processing failure, the consumer explicitly produces the failed message onto a separate `*.dlt` (dead-letter topic), then commits its own offset past the poison message so the rest of the partition isn't blocked.
- **Why it matters**: without a DLQ, a single malformed/"poison" message can block an entire queue/partition forever (consumer keeps failing → nack → redeliver → fail → loop), or get silently dropped after max retries. A DLQ makes failures visible and replayable instead of either silently disappearing or wedging the pipeline.
- Always alert on DLQ depth — a growing DLQ is a production incident, not a place messages go to be forgotten.

### 23.6 Backpressure — what happens when producers outpace consumers
If producers publish faster than consumers can drain the queue, the queue grows without bound unless something pushes back. Options, roughly from "let it buffer" to "actively reject":

1. **Let the queue absorb the burst** — fine for short spikes if you have room (Kafka's disk-backed log is built for this; RabbitMQ queues can grow but memory/disk becomes a real constraint).
2. **Bound the queue and reject/block when full** — RabbitMQ `x-max-length` on a queue: once full, either the oldest message is dropped or new publishes are rejected/blocked, depending on config. Forces the *producer* to feel the pressure instead of silently piling up unbounded work.
3. **Scale consumers horizontally** — add more worker processes / add more Kafka partitions + consumers in the group (partition count is the hard ceiling on Kafka consumer parallelism for a topic — you cannot have more active consumers in a group than partitions).
4. **Slow the producer down (flow control)** — RabbitMQ can send a `channel.flow` / TCP-level backpressure signal to publishers when it's overwhelmed, which naturally slows them. In application code: rate-limit or apply a semaphore around publish calls once queue depth crosses a threshold.
5. **Shed load deliberately** — for non-critical data (metrics, low-priority notifications), it's fine to drop or sample rather than let backpressure cascade upstream. Not every message deserves at-least-once treatment — decide per use case.
6. **Autoscale consumers on queue depth** — e.g. KEDA/HPA scaling worker pod count on RabbitMQ queue length or Kafka consumer lag as the metric, rather than CPU.

**Consumer lag** (Kafka term: how far behind the latest offset a consumer group is) and **queue depth** (RabbitMQ: messages ready/unacked) are the two numbers to watch/alert on — a growing trend means consumers can't keep up and you need to scale out or shed load before the backlog becomes an outage.

### 23.7 Quick interview-answer shape
- "Exactly-once delivery doesn't really exist across a network boundary — the ack itself can be lost. So the answer is always at-least-once delivery + idempotent consumers (dedup key, unique constraint, or upsert), the same pattern used for Celery task idempotency."
- "RabbitMQ is a smart broker/dumb consumer, good for routing and task-queue-style workloads; Kafka is a dumb broker/smart consumer built around a durable, replayable log, good for high-throughput event streaming and multiple independent consumer groups reading the same data."
- "A dead-letter queue exists so a poison message doesn't either loop forever or vanish silently — it gets isolated for inspection/replay, and DLQ depth should be an alert."
- "Backpressure is handled by bounding queues, scaling consumers (partition count is the ceiling in Kafka), or explicitly shedding low-priority load — the goal is to make the pressure visible and controlled rather than letting it cascade into an outage."
