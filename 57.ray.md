## 1. What is Ray?

**Ray** is an open-source framework for running Python code in parallel across many CPU cores and many machines. It was created at UC Berkeley (RISELab) and is maintained by Anyscale.

You write normal Python functions and classes, add a decorator, and Ray runs them on a cluster, handles scheduling, data transfer and failures.

In simple words:

> Ray turns a cluster of machines into one big computer that you program with ordinary Python.

It is widely used for machine learning: distributed training, hyperparameter search, batch inference, reinforcement learning and online model serving. OpenAI, Uber, Shopify and many others use it.

---

## 2. Why Ray Exists

Python has a limit: because of the GIL (Global Interpreter Lock), normal threads do not run Python code in parallel. `multiprocessing` works on one machine only. Moving to many machines usually meant learning Spark, MPI or writing your own queue and worker system.

ML workloads make this harder:
- They need **GPUs**, not just CPUs.
- They need **stateful workers** (a model loaded once in GPU memory, reused for many requests).
- They need **fine-grained tasks** with low latency (thousands of small jobs, not one huge batch).
- Different stages need different resources (CPU preprocessing, then GPU inference).

Ray was designed for exactly this: simple API, GPU-aware scheduling, stateful actors, and a shared object store.

---

Where they live: A Ray cluster has one or more nodes (machines). Each node runs several worker processes, typically about one per CPU core. On your laptop with `ray.init()`, workers are just extra Python processes on the same machine.

## 3. Core Concepts

### 3.1 Tasks (stateless remote functions)

A **task** is a Python function that runs on some worker in the cluster, asynchronously.

```python
import ray
ray.init()

@ray.remote
def square(x):
    return x * x

futures = [square.remote(i) for i in range(4)]   # returns immediately with ObjectRefs
print(ray.get(futures))                          # blocks until done -> [0, 1, 4, 9]
```

- `.remote()` does not run the function in your process. It submits it and returns an **ObjectRef** (a future / promise).
- `ray.get(ref)` waits for and fetches the actual result.
- Tasks can call other tasks, so you can build task graphs.

### 3.2 Actors (stateful remote classes)

An **actor** is a Python class that lives in its own worker process and **keeps its state** between calls.

```python
@ray.remote(num_gpus=1)
class ModelWorker:
    def __init__(self):
        self.model = load_model()        # loaded once, stays in GPU memory

    def predict(self, x):
        return self.model(x)

worker = ModelWorker.remote()            # starts the actor on a GPU node
result = ray.get(worker.predict.remote("hello"))
```

Use an actor when you need to **hold something expensive** (a model, a DB connection, a counter) and reuse it. Method calls on one actor run one at a time by default (or concurrently for async actors).

### 3.3 Objects and the object store
- In Ray, an object is any value that Ray stores for you in the cluster: a task's return value.  It can be a NumPy array, a dict, a tensor, or a string.
- Each object lives in the object store, a shared-memory region on every node. You never hold the object directly. You hold an `ObjectRef`, a small handle that works like a claim ticket. This is the same `ObjectRef` that `.remote()` returns.
-  `.remote()` returns, the task may not have run yet, so the object may not exist.
- The `ObjectRef` is a promise that it will exist.

When a task returns a value, it is placed in Ray's **distributed object store** (shared memory on each node). Other tasks can use it without you copying it around manually.

```python
data_ref = ray.put(big_numpy_array)        # put once into the object store
refs = [process.remote(data_ref, i) for i in range(10)]   # all tasks share it
```

- Objects on the same node are shared through shared memory
- Objects on other nodes are transferred when needed.
- `ray.put` avoids sending the same big object again for every task.

### 3.4 Comparison

| | Task | Actor |
|---|---|---|
| State | None | Keeps state between calls |
| Created by | Decorated function | Decorated class |
| Lifetime | Short | Until killed or out of scope |
| Typical use | Parallel map, preprocessing | Model server, counters, workers holding GPU memory |

## 4. Ray Architecture

```
                 +----------------------------+
                 |        Head node           |
                 |  GCS (Global Control Store)|
                 |  Autoscaler, Dashboard     |
                 +-------------+--------------+
                               |
          +--------------------+--------------------+
          |                                         |
  +-------+--------+                        +-------+--------+
  |  Worker node 1 |                        |  Worker node 2 |
  |  Raylet        |                        |  Raylet        |
  |  Object store  |  <---- transfer --->   |  Object store  |
  |  Worker procs  |                        |  Worker procs  |
  +----------------+                        +----------------+
```

| Component | Role |
|---|---|
| **Head node** | Runs the cluster-wide services. Also can run tasks. |
| **GCS (Global Control Service)** | Stores cluster metadata: nodes, actors, placement groups. |
| **Raylet** | Per-node daemon. Schedules tasks locally, manages the object store, talks to other raylets. |
| **Worker processes** | Execute tasks and host actors. |
| **Object store** | Shared-memory store for task inputs/outputs on each node. |
| **Autoscaler** | Adds or removes nodes based on the resource demand. |
| **Dashboard** | Web UI for jobs, actors, logs, metrics. |

Ray uses a **distributed scheduler**: a task is first scheduled by the local raylet and only goes to others if the local node is busy, which keeps latency low.

## 5. Resources and Scheduling

Every task or actor can say what it needs:

```python
@ray.remote(num_cpus=2, num_gpus=1, memory=8 * 1024**3)
def heavy(): ...

@ray.remote(num_gpus=0.5)       # fractional GPUs: two actors can share one GPU
class SmallModel: ...
```

Ray places the work only on nodes that have those resources free. You can also define **custom resources** (for example `{"A100": 1}`) to pick a type of machine.

### GPU-aware scheduling

Ray treats GPUs as a logical resource, just like CPUs. Each node reports how many GPUs it has when it joins the cluster, and the scheduler only places a task or actor on a node that has enough free GPUs.

- **Logical, not physical.** `num_gpus=1` is a reservation in Ray's books. Ray does not enforce it, it just won't schedule more work than the node has GPUs for.
- **Device isolation.** Ray sets `CUDA_VISIBLE_DEVICES` for each worker, so a task asking for 1 GPU only sees its own GPU, not the whole machine. `ray.get_gpu_ids()` shows which ones it got.
- **Fractional GPUs.** `num_gpus=0.5` lets two actors share one GPU. Ray does not split memory, so each process must keep within its share, otherwise you get OOM.
- **Multiple GPUs per worker.** `num_gpus=4` gives one worker four GPUs on the same node. That is how a tensor-parallel model replica is usually placed.
- **GPU type.** Use `accelerator_type="A100"` (or a custom resource) to pick a kind of GPU instead of any GPU.
- **Waiting and autoscaling.** If no node has free GPUs, the task waits as pending. On a cluster with an autoscaler (or KubeRay), those pending requests trigger new GPU nodes to be added, and idle ones are removed later.
- **Gang placement.** For multi-GPU or multi-node jobs, use placement groups so all the GPU bundles are reserved together, otherwise you can end up with half the workers running and the rest stuck waiting.

```python
@ray.remote(num_gpus=1, accelerator_type="A100")
class Worker:
    def gpus(self):
        return ray.get_gpu_ids()      # e.g. [0]
```

Gotcha: GPU actors hold their GPU for as long as they live, even when idle. A task that asks for 1 GPU will not run while all GPUs are held by idle actors, so size actors carefully.

### Placement groups

A **placement group** reserves a set of resource "bundles" together, so related workers are placed in a certain way:

| Strategy | Meaning |
|---|---|
| `PACK` | Put bundles on as few nodes as possible |
| `SPREAD` | Spread bundles over different nodes |
| `STRICT_PACK` | Everything must be on the same node |
| `STRICT_SPREAD` | Every bundle on a different node |

This is important for LLM serving. For tensor parallelism, all GPU workers should be on the **same node** (fast NVLink), so `STRICT_PACK`. For pipeline parallelism across nodes, bundles are spread out.

### Fault tolerance

- A failed **task** is retried automatically (`max_retries`).
- A failed **actor** can be restarted (`max_restarts`).
- Lost objects can be recomputed from their lineage.
- Head node failure needs a GCS fault-tolerance setup (for example using external Redis).

## 6. Ray Libraries

Ray core is the base. On top of it sit libraries ("Ray AI Libraries"):

| Library | Used for | Example |
|---|---|---|
| **Ray Data** | Scalable data loading and transformation, **offline batch inference** | Run an LLM over 10 million documents |
| **Ray Train** | Distributed training (PyTorch, TensorFlow, XGBoost, Hugging Face) | Fine-tune a model on 16 GPUs |

| **Ray RLlib** | Reinforcement learning | Train agents in simulation |

## 7. Ray and LLM Inference

### 7.1 vLLM uses Ray for distributed execution

When a model is too large for one GPU, vLLM splits it with **tensor parallelism** (inside a node) and **pipeline parallelism** (across nodes). vLLM needs to start and coordinate one worker per GPU. For multi-node setups it uses Ray for this.

```bash
# On a single node, vLLM can use Python multiprocessing (no Ray needed)
vllm serve meta-llama/Llama-3.1-70B-Instruct --tensor-parallel-size 4

# Multi-node: start a Ray cluster first, then tell vLLM to use it
ray start --head                       # on node 1
ray start --address=<head-ip>:6379     # on node 2

vllm serve meta-llama/Llama-3.1-405B-Instruct \
  --tensor-parallel-size 8 \
  --pipeline-parallel-size 2 \
  --distributed-executor-backend ray
```

Here TP = 8 inside each node and PP = 2 across the two nodes, 16 GPUs in total.

### 7.2 Ray Serve in front of vLLM

Ray Serve manages multiple vLLM replicas, routes requests, autoscales them, and can serve several models behind one API.

### 7.3 Ray Data for offline batch inference

For jobs that are not latency sensitive (labelling, summarizing, embedding a whole corpus), Ray Data streams the data through a pool of vLLM actors on GPUs:

```
Read data -> CPU preprocess (tokenize) -> GPU stage (vLLM actors) -> CPU postprocess -> Write
```

Each stage scales independently, so GPUs stay busy while CPUs prepare the next batch.

### 7.4 Other uses in LLM systems

- **Distributed training and fine-tuning** (Ray Train with DeepSpeed / FSDP).
- **RLHF / RL post-training** frameworks (for example OpenRLHF, veRL) use Ray to coordinate actor, critic, reward and generation workers.
- **Disaggregated prefill/decode** and large serving platforms use Ray-style actors for orchestration.
- **Embedding generation** at scale for RAG ([[31.vector_store.md]]).

## 8. Ray Serve in Detail

**Ray Serve** is a scalable model-serving library. It is framework-agnostic and Python-first.

### Main ideas

| Concept | Meaning |
|---|---|
| **Deployment** | A Python class or function that handles requests. Can have many **replicas** (each replica is a Ray actor). |
| **Replica** | One running copy of the deployment. |
| **Application** | One or more deployments wired together (a graph). |
| **Router / proxy** | Receives HTTP/gRPC requests and sends them to replicas. |
| **Controller** | Manages deployments, replicas and autoscaling. |

### Features

- **Autoscaling** replicas based on the number of ongoing requests.
- **Dynamic request batching** (`@serve.batch`) that groups requests for GPU efficiency.
- **Model composition**: call several models in a pipeline (retriever -> reranker -> LLM) with each part scaled separately.
- **Fractional GPUs** and multi-model serving on one cluster.
- **Zero-downtime updates** and canary rollouts.
- **Streaming responses**, FastAPI integration, OpenAI-compatible LLM serving (`ray.serve.llm`).

### Ray Serve vs just running vLLM

| | Plain `vllm serve` | Ray Serve + vLLM |
|---|---|---|
| Setup | One command | More setup |
| Replicas and autoscaling | Do it yourself (Kubernetes etc.) | Built in |
| Multi-model / pipelines | Separate servers | One application graph |
| Best for | One model, simple deployment | Many models, scaling, complex flows |

## 9. Deploying Ray

| Option | Notes |
|---|---|
| **Local** (`ray.init()`) | Starts a mini cluster on your machine. Good for development. |
| **Manual cluster** | `ray start --head` on one node, `ray start --address=...` on others. |
| **Cluster launcher** | `ray up cluster.yaml` for AWS/GCP/Azure with autoscaling. |
| **KubeRay (Kubernetes)** | Operator with CRDs `RayCluster`, `RayJob` and `RayService`. The usual production choice. |
| **Anyscale** | Managed Ray platform from the creators. |

**KubeRay CRDs**

| CRD | Purpose |
|---|---|
| `RayCluster` | A long-running Ray cluster |
| `RayJob` | Runs a job on a (temporary) cluster, then cleans up |
| `RayService` | Runs Ray Serve apps with upgrades and high availability |

Useful commands: `ray status`, `ray job submit`, the dashboard on port `8265`.

## 10. Ray vs Celery, Dask, Spark, Kubernetes

| Tool | What it is | Difference from Ray |
|---|---|---|
| **Celery** | Task queue with a broker (Redis/RabbitMQ) for background jobs | Great for web app background tasks and retries. Not built for GPUs, shared state or very low-latency fine-grained parallel compute. |
| **Dask** | Parallel computing for NumPy/pandas-style data | Strong for dataframes and arrays. Ray is more general, with actors and a stronger ML ecosystem. |
| **Spark** | Big-data batch processing (JVM) | Best for large ETL and SQL. Ray is better for ML, GPUs and Python-native workloads. |
| **Kubernetes** | Container orchestration | Schedules containers and pods. Ray schedules tasks and actors **inside** an app. They are used together (KubeRay). |
| **multiprocessing** | Parallelism on one machine | Ray scales to many machines with the same style of code. |

## 11. Limitations and Gotchas

- **Overhead:** each remote call has a cost (about a millisecond). Do not make tasks too tiny; batch small work into bigger tasks.
- **Serialization:** arguments and results are pickled. Large objects should go in the object store with `ray.put`, not be passed again and again.
- **Blocking `ray.get` in loops** kills parallelism. Submit everything first, then call `ray.get` on the list.
- **Object store memory** can fill up. Ray spills to disk, which is slower.
- **Version matching:** Python and Ray versions must match across all nodes.
- **Debugging** distributed code is harder than local code. Use the dashboard and logs.
- **Operational complexity:** a Ray cluster is another system to run. For one model on one node, plain vLLM is simpler.
- **Head node** is a single point of failure unless GCS fault tolerance is configured.

## 12. Code Examples

### 12.1 Parallel tasks (wrong way vs right way)

```python
import ray, time
ray.init()

@ray.remote
def slow(x):
    time.sleep(1)
    return x * 2

# Wrong: waits for each result, so it runs one by one (~4 s)
results = [ray.get(slow.remote(i)) for i in range(4)]

# Right: submit all, then wait together (~1 s)
refs = [slow.remote(i) for i in range(4)]
results = ray.get(refs)
```

### 12.2 Actor holding a model

```python
@ray.remote(num_gpus=1)
class Embedder:
    def __init__(self):
        from sentence_transformers import SentenceTransformer
        self.model = SentenceTransformer("all-MiniLM-L6-v2", device="`cuda`")

    def embed(self, texts):
        return self.model.encode(texts)

embedders = [Embedder.remote() for _ in range(2)]      # needs 2 GPUs
chunks = [["a", "b"], ["c", "d"]]
out = ray.get([e.embed.remote(c) for e, c in zip(embedders, chunks)])
```

### 12.3 Ray Serve deployment with autoscaling and batching

```python
from ray import serve
from starlette.requests import Request

@serve.deployment(
    ray_actor_options={"num_gpus": 1},
    autoscaling_config={"min_replicas": 1, "max_replicas": 4, "target_ongoing_requests": 8},
)
class Classifier:
    def __init__(self):
        self.model = load_model()

    @serve.batch(max_batch_size=16, batch_wait_timeout_s=0.05)
    async def predict(self, texts: list[str]):
        return self.model(texts)          # one GPU call for the whole batch

    async def __call__(self, request: Request):
        text = (await request.json())["text"]
        return await self.predict(text)

app = Classifier.bind()
serve.run(app)         # then POST to http://localhost:8000/
```

### 12.4 Offline batch LLM inference with Ray Data + vLLM

```python
import ray
from vllm import LLM, SamplingParams

class LLMPredictor:
    def __init__(self):
        self.llm = LLM(model="meta-llama/Meta-Llama-3-8B-Instruct")
        self.params = SamplingParams(temperature=0.0, max_tokens=128)

    def __call__(self, batch):
        outputs = self.llm.generate(list(batch["prompt"]), self.params)
        batch["answer"] = [o.outputs[0].text for o in outputs]
        return batch

ds = ray.data.read_json("prompts.jsonl")
ds = ds.map_batches(LLMPredictor, concurrency=2, num_gpus=1, batch_size=64)
ds.write_json("answers/")
```

## 13. Interview Questions

**Q1. What is Ray?**
An open-source framework for scaling Python across cores and machines. It provides tasks (stateless remote functions), actors (stateful remote classes) and a distributed object store, plus libraries for data processing, training, tuning, serving and RL.

**Q2. Task vs actor?**
A task is a stateless function call that runs somewhere in the cluster. An actor is a remote class instance that keeps state, so it suits things like a loaded model. Use actors when initialization is expensive and should be reused.

**Q3. What is an ObjectRef and what does `ray.get` do?**
`.remote()` returns an ObjectRef, which is a future for a result stored in the object store. `ray.get` blocks until the value is ready and fetches it. Call `ray.get` on a list of refs after submitting all the work, so tasks run in parallel.

**Q4. How does Ray schedule GPU work?**
Tasks and actors declare resources such as `num_gpus`. The scheduler places them on nodes with free resources. Fractional GPUs are allowed, and placement groups control how groups of workers are packed or spread.

GPU-aware scheduling: GPUs are a logical resource. Ray tracks free GPUs per node, places work only where enough are free, sets `CUDA_VISIBLE_DEVICES` so each worker sees only its own GPU, and queues work as pending (which can trigger the autoscaler) when none are free. It does not enforce GPU memory limits.

**Q5. Where does Ray fit with vLLM?**
For single-node serving, vLLM does not need Ray. For multi-node tensor/pipeline parallelism, vLLM uses Ray to start and coordinate workers (`--distributed-executor-backend ray`). Ray Serve can sit in front of vLLM replicas for autoscaling and routing, and Ray Data can feed vLLM actors for large offline jobs.

**Q6. What is Ray Serve and why use it?**
A serving library built on Ray. It gives deployments with replicas, autoscaling, dynamic batching, model composition and rolling updates, all in Python. It is useful when you have several models or a pipeline (retriever, reranker, LLM) to scale independently.

**Q7. Ray vs Celery?**
Celery is a broker-based task queue for background jobs in web apps. Ray is a distributed compute framework with GPU-aware scheduling, stateful actors and shared memory, aimed at ML workloads and low-latency parallel work. Different problem.

**Q8. Ray vs Kubernetes?**
Kubernetes schedules containers. Ray schedules tasks and actors inside an application. In production, Ray usually runs on Kubernetes through KubeRay, with Kubernetes providing the machines and Ray providing the app-level parallelism.

**Q9. How does Ray handle failures?**
Failed tasks are retried, actors can be restarted, and lost objects can be rebuilt from lineage. The head node needs extra setup (external Redis for the GCS) to survive a failure.

**Q10. What are placement groups and why do they matter for LLM serving?**
They reserve bundles of resources with a chosen placement strategy. For tensor parallelism, the GPU workers should sit on the same node with a fast interconnect, so `STRICT_PACK`. For pipeline parallelism across nodes, bundles are spread.

**Q11. Common mistakes when using Ray?**
Calling `ray.get` inside a loop (kills parallelism), making tasks too small so overhead dominates, passing large objects repeatedly instead of using `ray.put`, and using Ray when a single node and plain vLLM would do.

---

## Conclusion

Ray lets you scale Python code from a laptop to a GPU cluster with tasks, actors and a shared object store. For LLM work, it matters in three places: running vLLM across multiple nodes, serving many replicas and models with Ray Serve, and running large offline inference jobs with Ray Data. For one model on one node, you probably do not need it.
