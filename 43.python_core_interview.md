## 1. Data Model & Mutability

- **Everything is an object** — even `int`, `function`, `class` are objects with a type, identity (`id()`), and reference count.
- **Mutable vs immutable types**:

  | Mutable | Immutable |
  |---|---|
  | `list`, `dict`, `set`, custom objects (by default) | `int`, `float`, `str`, `tuple`, `frozenset`, `bytes` |

- **Variables are names bound to objects**, not boxes holding values — `a = b` makes `a` point to the same object `b` points to; it does not copy.
- **Pass-by-object-reference** (often mis-called "pass by reference" or "pass by value" — it's neither exactly): a function receives the same object reference as the caller. Mutating a mutable object inside the function affects the caller's object; *rebinding* the parameter name to a new object does not.

  ```python
  def append_one(lst):
      lst.append(1)          # mutates the same list object the caller sees

  def reassign(lst):
      lst = [99]              # only rebinds the local name; caller's list is untouched

  nums = [1, 2]
  append_one(nums)   # nums == [1, 2, 1]
  reassign(nums)      # nums == [1, 2, 1]  (unchanged)
  ```

- **`==` vs `is`** — `==` compares value (calls `__eq__`); `is` compares identity (same object in memory, same `id()`). Small integers (-5 to 256) and interned strings are cached by CPython, so `is` can appear to work for equality by accident — never rely on this.
- **`copy` vs `deepcopy`** — `copy.copy()` makes a shallow copy (new outer container, same nested object references); `copy.deepcopy()` recursively copies nested objects too. A shallow copy of a list of lists still shares the inner lists.

### Are strings mutable or immutable?

**Strings are immutable in Python.** Once created, a `str` object's contents can never be changed in place — every operation that looks like it "modifies" a string actually creates and returns a **new** string object.

```python
s = "hello"
s[0] = "H"          # TypeError: 'str' object does not support item assignment

s = "hello"
s2 = s.upper()       # creates a brand-new string "HELLO"
print(s)             # "hello" — original is untouched
print(s is s2)       # False — different objects

s += " world"        # rebinds `s` to a NEW string "hello world"; the old "hello" object is unchanged (and gets garbage collected if unreferenced)
```

- **Why it matters**: immutability is what makes strings **hashable** (usable as dict keys/set members) and safe to share freely between functions/threads without defensive copying — no caller ever has to worry about a string changing underneath it.
- **Performance implication**: repeatedly building a string with `+=` in a loop is O(n²) overall, since each `+=` allocates a new string and copies the old contents (see §14 gotchas). Prefer accumulating pieces in a list and `"".join(parts)` once at the end.
- If you need an actually-mutable sequence of characters, use a `list` of characters (or `bytearray` for bytes) and build/mutate that, converting to a string only at the end via `"".join(...)`.

## 2. Memory Management & Garbage Collection

- CPython uses **reference counting** as the primary mechanism: every object tracks how many references point to it; when the count hits zero, it's deallocated immediately.
- A **cyclic garbage collector** (the `gc` module) supplements this to catch **reference cycles** (e.g., two objects referencing each other) that reference counting alone can't free, since neither ever hits zero on its own.
- `gc.collect()` can be called manually; generational GC (3 generations) makes cycle detection cheaper by scanning young objects more often than old, long-lived ones.
- **Memory leaks in Python** usually come from: unbounded caches/global lists that keep growing, closures/callbacks holding references longer than expected, or C-extension objects not releasing memory properly — not from "forgetting to free" like in C.
- `__del__` (finalizer) is unreliable for critical cleanup (timing isn't guaranteed, especially with cycles) — prefer explicit context managers (`with`) for deterministic resource release.

## 3. The GIL

The **Global Interpreter Lock** ensures only one thread executes Python bytecode at a time in a single CPython process, even on a multi-core machine.

- **Why it exists**: simplifies CPython's memory management (reference counting isn't thread-safe without it) at the cost of true parallel execution of Python code.
- **Effect on concurrency models**:

  | Model | Helps with | Why |
  |---|---|---|
  | `threading` | I/O-bound work (network, disk, sleeping) | The GIL is released during blocking I/O, so threads overlap waiting time |
  | `threading` | **not** CPU-bound work | Only one thread runs Python bytecode at a time — no real parallel speedup |
  | `multiprocessing` | CPU-bound work | Separate processes, each with its own interpreter + GIL, giving true parallelism across cores |
  | `asyncio` | High-concurrency I/O without OS threads | Single-threaded event loop cooperatively switches between coroutines at `await` points |

- Interview trap: "Does Python support multithreading?" — yes, but the GIL means it doesn't give CPU-bound speedup; it's still useful for I/O concurrency.
- Note: newer CPython work (PEP 703, "free-threaded" builds from 3.13+) allows building CPython *without* the GIL — worth mentioning as the direction the language is heading, though it's not yet the default in most production environments.

## 4. Variables, Scope, and Closures

- **LEGB rule** for name resolution: **L**ocal → **E**nclosing → **G**lobal → **B**uilt-in.
- `global` keyword lets a function rebind a module-level variable; `nonlocal` lets a nested function rebind a variable in an enclosing (but non-global) scope.
- **Closures** — a nested function that captures variables from its enclosing scope, keeping them alive even after the outer function returns.

  ```python
  def make_counter():
      count = 0
      def increment():
          nonlocal count
          count += 1
          return count
      return increment

  counter = make_counter()
  counter()  # 1
  counter()  # 2
  ```

- **Late-binding closure gotcha** — closures capture the *variable*, not its value at definition time. A classic loop bug:

  ```python
  funcs = [lambda: i for i in range(3)]
  [f() for f in funcs]   # [2, 2, 2], not [0, 1, 2] — all lambdas share the same `i`

  # fix: bind the value as a default argument
  funcs = [lambda i=i: i for i in range(3)]   # [0, 1, 2]
  ```

## 5. Functions — Arguments, `*args`/`**kwargs`, Defaults

- **Positional vs keyword arguments**, `*args` (extra positional args as a tuple), `**kwargs` (extra keyword args as a dict).

  ```python
  def describe(name, age, *args, **kwargs):
      print(f"name={name}, age={age}")
      print("extra positional args:", args)     # tuple
      print("extra keyword args:", kwargs)       # dict

  describe("Mahesh", 30)
  # name=Mahesh, age=30
  # extra positional args: ()
  # extra keyword args: {}

  describe("Mahesh", 30, "engineer", "Bangalore", team="AI", years_exp=5)
  # name=Mahesh, age=30
  # extra positional args: ('engineer', 'Bangalore')
  # extra keyword args: {'team': 'AI', 'years_exp': 5}

  describe(age=30, name="Mahesh")   # keyword args can be passed in any order
  # name=Mahesh, age=30
  ```

  - **Positional argument** — matched to a parameter by position/order (`"Mahesh"` → `name`, `30` → `age`).
  - **Keyword argument** — matched to a parameter by name, regardless of order (`age=30, name="Mahesh"` still works correctly).
  - `*args` collects any additional positional arguments beyond the named ones into a **tuple**.
  - `**kwargs` collects any additional keyword arguments beyond the named ones into a **dict**.
  - The **unpacking** direction also works: `*`/`**` can spread an existing list/dict into a function call instead of collecting extras.

  ```python
  args = ["Mahesh", 30]
  kwargs = {"team": "AI", "years_exp": 5}

  describe(*args, **kwargs)
  # equivalent to: describe("Mahesh", 30, team="AI", years_exp=5)
  # name=Mahesh, age=30
  # extra positional args: ()
  # extra keyword args: {'team': 'AI', 'years_exp': 5}
  ```

  Unpacking also works outside function calls, to merge/expand sequences and mappings:

  ```python
  a, *rest = [1, 2, 3, 4]        # a = 1, rest = [2, 3, 4]
  first, *middle, last = [1, 2, 3, 4]   # first = 1, middle = [2, 3], last = 4

  combined_list = [*[1, 2], *[3, 4]]           # [1, 2, 3, 4]
  combined_dict = {**{"a": 1}, **{"b": 2}}      # {'a': 1, 'b': 2}
  ```
- **Argument order** in a signature: positional-only, positional-or-keyword, `*args`, keyword-only, `**kwargs`. Python 3.8+ supports explicit `/` (positional-only marker) and `*` (keyword-only marker):

  ```python
  def f(a, b, /, c, *, d):
      ...
  # a, b: positional-only | c: positional-or-keyword | d: keyword-only
  ```

- **Mutable default argument bug** — a classic interview question:

  ```python
  def add_item(item, bucket=[]):    # BUG: default list is created ONCE at def time, shared across calls
      bucket.append(item)
      return bucket

  add_item(1)   # [1]
  add_item(2)   # [1, 2]  <- unexpected, same list reused!

  # fix:
  def add_item(item, bucket=None):
      if bucket is None:
          bucket = []
      bucket.append(item)
      return bucket
  ```

- **First-class functions** — functions are objects: can be assigned to variables, passed as arguments, returned from other functions, stored in data structures. This is the foundation of decorators, callbacks, and functional-style code (`map`/`filter`/`sorted(key=...)`).

## 6. Iterators, Generators, and `yield`

- **Iterable** — implements `__iter__` (returns an iterator). **Iterator** — implements both `__iter__` and `__next__`, raising `StopIteration` when exhausted.
- **Generator function** — any function containing `yield`; calling it returns a generator object without running the body immediately. Each `next()` resumes execution until the next `yield`, preserving local state between calls.

  ```python
  def count_up_to(n):
      i = 1
      while i <= n:
          yield i
          i += 1

  gen = count_up_to(3)
  next(gen)  # 1
  next(gen)  # 2
  ```

- **Why generators matter in production**: lazy evaluation — process huge/infinite sequences (file lines, DB cursors, API pagination) without loading everything into memory at once.
- **Generator expression** vs list comprehension — `(x*x for x in range(1000000))` is lazy/memory-efficient; `[x*x for x in range(1000000)]` builds the whole list in memory immediately.
- `yield from` delegates to a sub-generator, flattening nested generator composition.

## 7. Comprehensions

```python
squares = [x*x for x in range(10) if x % 2 == 0]      # list
squares_set = {x*x for x in range(10)}                 # set
squares_map = {x: x*x for x in range(10)}               # dict
squares_gen = (x*x for x in range(10))                  # generator (lazy)
```

- Comprehensions are generally faster than an equivalent `for` loop with `.append()` because the loop is implemented in C internally.
- Nested comprehensions are legal but hurt readability fast — interviewers often ask you to rewrite a nested comprehension as an explicit loop to check you understand the underlying iteration order.
- A comprehension has its **own scope** in Python 3 (unlike Python 2) — the loop variable doesn't leak into the enclosing scope.

## 8. OOP — Classes, Inheritance, MRO, Dunder Methods

### Is Python purely object-oriented?

**No — Python is multi-paradigm, not purely OO.** It supports object-oriented programming fully, but doesn't *force* it the way a purely OO language does.

- **What "everything is an object" actually means**: at the implementation level, every value in Python — `int`s, `str`ings, functions, modules, even classes themselves — is an instance of some class and has attributes/methods (`(5).bit_length()`, `print.__name__`). This is true and often cited as evidence Python is "pure OO."
- **Why it isn't purely OO anyway**: you are never *required* to define a class to write a working program. You can write an entire script as free functions and module-level code — plain procedural style — with zero classes, and it runs fine. A purely OO language (Java, or more strictly Smalltalk) requires everything to live inside a class, and in Smalltalk's case even control flow (`if`, loops) is expressed as message sends between objects.
- **Python is genuinely multi-paradigm**:

  | Paradigm | Example in Python |
  |---|---|
  | Procedural | Plain top-level functions and scripts, no classes at all |
  | Object-oriented | Classes, inheritance, encapsulation, polymorphism (§8 below) |
  | Functional | `map`/`filter`/`reduce`, list comprehensions, first-class functions, `lambda`, immutability-friendly idioms |

- **Interview framing**: say "Python supports OOP as one of several paradigms, and its data model happens to implement everything as an object under the hood — but it's not purely OO like Java (class required) or Smalltalk (message-passing all the way down), because you can write idiomatic, fully functional Python code without ever touching a class."

### Classes, Inheritance, MRO, and Dunder Methods

- **`self`** is just a convention — the instance is always passed as the first argument to instance methods; Python doesn't have an implicit `this`.
- **Class variables vs instance variables** — a class variable is shared across all instances until an instance shadows it by assignment; a common gotcha with mutable class-level defaults (same root cause as the mutable-default-argument bug).

  ```python
  class Dog:
      tricks = []          # class variable — shared! same bug pattern as mutable defaults
      def __init__(self, name):
          self.name = name  # instance variable
  ```

- **Method Resolution Order (MRO)** — with multiple inheritance, Python uses the **C3 linearization** algorithm to decide which parent's method runs; inspect it with `ClassName.__mro__` or `ClassName.mro()`.
- **`super()`** — calls the next method in the MRO chain, not necessarily the "immediate parent" in a diamond-inheritance hierarchy — important for cooperative multiple inheritance.
- **Common dunder (magic) methods**:

  | Method | Purpose |
  |---|---|
  | `__init__` | Constructor/initializer (object already exists; `__new__` actually creates it) |
  | `__repr__` / `__str__` | Developer-facing vs user-facing string representation |
  | `__eq__`, `__lt__`, etc. | Operator overloading for comparisons |
  | `__len__`, `__getitem__`, `__iter__` | Make an object behave like a sequence/collection |
  | `__enter__`, `__exit__` | Context manager protocol (`with` statement) |
  | `__call__` | Makes an instance callable like a function |

- **`@classmethod` vs `@staticmethod` vs instance method**:

  | | First arg | Use case |
  |---|---|---|
  | Instance method | `self` | Needs instance state |
  | `@classmethod` | `cls` | Needs the class itself (e.g., alternate constructors: `from_json(cls, data)`) |
  | `@staticmethod` | none | Logically grouped with the class but needs neither `self` nor `cls` |

- **Abstract Base Classes (`abc` module)** — `@abstractmethod` on an `ABC` subclass forces subclasses to implement a method, catching incomplete implementations at instantiation time rather than at first call.

### Does Python have interfaces?

**Not as a dedicated keyword** (no `interface` like Java/C#/TypeScript), but Python achieves the same goal — "guarantee an object exposes certain methods" — through a few idiomatic mechanisms:

**1. Duck typing (the default Python way)** — no explicit interface at all; if an object has the right methods, it just works, checked only at call time.

```python
class Duck:
    def make_sound(self):
        return "Quack!"

class Dog:
    def make_sound(self):
        return "Woof!"

def announce(animal):
    print(animal.make_sound())   # works with ANY object that has make_sound(), no shared base class needed

announce(Duck())   # Quack!
announce(Dog())    # Woof!
```
> "If it walks like a duck and quacks like a duck, it's a duck" — no type check happens until `make_sound()` is actually called; if it's missing, you get an `AttributeError` at runtime rather than a compile-time error.

**2. Abstract Base Classes (`abc` module)** — the closest thing to a "real" enforced interface: declares required methods and makes it **impossible to instantiate** a subclass that doesn't implement them all.

```python
from abc import ABC, abstractmethod

class PaymentGateway(ABC):
    @abstractmethod
    def charge(self, amount: float) -> str: ...

    @abstractmethod
    def refund(self, transaction_id: str) -> str: ...

class StripeGateway(PaymentGateway):
    def charge(self, amount):
        return f"Charged ${amount} via Stripe"
    def refund(self, transaction_id):
        return f"Refunded {transaction_id} via Stripe"

class BrokenGateway(PaymentGateway):
    def charge(self, amount):
        return "..."
    # missing refund()

StripeGateway(10.0).charge(10.0)   # works fine
BrokenGateway()                     # TypeError: Can't instantiate abstract class BrokenGateway
                                     # with abstract method refund
```
- This is **nominal typing** — a class must explicitly inherit from `PaymentGateway` to count as one, and the check happens at **instantiation time**, not just when a method is called.

**3. `typing.Protocol` (PEP 544, Python 3.8+)** — **structural typing**: define the shape an object must have, without requiring it to inherit from anything. This is the closest match to how interfaces work in Go or TypeScript.

```python
from typing import Protocol

class SupportsArea(Protocol):
    def area(self) -> float: ...

class Circle:
    def __init__(self, r): self.r = r
    def area(self) -> float: return 3.14159 * self.r ** 2

class Square:
    def __init__(self, side): self.side = side
    def area(self) -> float: return self.side ** 2

def total_area(shapes: list[SupportsArea]) -> float:
    return sum(shape.area() for shape in shapes)

total_area([Circle(2), Square(3)])   # works — neither class inherits from SupportsArea at all
```
- `Circle` and `Square` never subclass `SupportsArea` — they satisfy it purely because they have a matching `area()` method. A type checker (`mypy`/`pyright`) verifies this statically; at runtime it's still ordinary duck typing (no enforcement unless you also apply `@runtime_checkable` and use `isinstance()`).

**Comparison:**

| Mechanism | Typing style | Enforced at | Requires inheritance? |
|---|---|---|---|
| Duck typing | Structural, implicit | Method call time (if missing → `AttributeError`) | No |
| `abc.ABC` + `@abstractmethod` | Nominal | Instantiation time | Yes |
| `typing.Protocol` | Structural, explicit | Static type-check time (mypy/pyright); optionally `isinstance()` with `@runtime_checkable` | No |

**Interview framing**: "Python has no `interface` keyword, but achieves the same contract-enforcement goal via `ABC`s (nominal, like Java interfaces) or `Protocol`s (structural, like Go interfaces or TypeScript) — and in idiomatic Python, plain duck typing is often enough and an explicit interface is only introduced once a contract needs to be enforced or documented explicitly."

## 9. `@property`, Descriptors, and `__slots__`

- **`@property`** turns a method into an attribute-like accessor, enabling computed attributes and validation without changing the public API from a plain attribute to a method call (important for backwards compatibility when you later need to add validation).

  ```python
  class Circle:
      def __init__(self, radius):
          self._radius = radius

      @property
      def area(self):
          return 3.14159 * self._radius ** 2

      @radius.setter
      def radius(self, value):
          if value < 0:
              raise ValueError("radius must be non-negative")
          self._radius = value
  ```

- **Descriptors** — the general protocol (`__get__`/`__set__`/`__delete__`) that `@property` is built on top of; understanding this explains how ORMs (e.g., SQLAlchemy columns) implement attribute-like fields with custom behavior.
- **`__slots__`** — declaring a fixed set of attribute names on a class prevents the creation of a per-instance `__dict__`, reducing memory footprint significantly for classes with millions of instances, at the cost of losing dynamic attribute assignment.

## 10. Exceptions

- **Exception hierarchy** — all exceptions inherit from `BaseException`; user code should generally catch/raise subclasses of `Exception` (not `BaseException`, which also covers `SystemExit`/`KeyboardInterrupt`).
- **`try` / `except` / `else` / `finally`**:

  ```python
  try:
      risky()
  except ValueError as e:
      handle(e)
  else:
      # runs only if no exception was raised
      ...
  finally:
      # always runs — cleanup goes here
      ...
  ```

- **Never use bare `except:`** — it catches everything including `KeyboardInterrupt`/`SystemExit`, masking bugs and making Ctrl+C not work. Catch specific exception types.
- **Custom exceptions** — define a domain-specific hierarchy (`AppError` → `ValidationError`, `NotFoundError`) so calling code can catch broadly or narrowly as needed (see `production_engineering_python_notes.md` §5).
- **`raise ... from err`** — chains exceptions, preserving the original traceback context (`__cause__`) when re-raising as a different exception type, instead of losing the root cause.
- **Exceptions vs return codes** — Python favors exceptions ("easier to ask forgiveness than permission" / EAFP) over checking preconditions first ("look before you leap" / LBYL) — e.g., `try: d[key] except KeyError` is often more idiomatic than `if key in d`.

## 11. Context Managers (`with`)

- Implements the **`__enter__`/`__exit__`** protocol to guarantee setup/teardown (closing files, releasing locks, closing DB connections) even if an exception occurs inside the block.

  ```python
  class Timer:
      def __enter__(self):
          self.start = time.time()
          return self
      def __exit__(self, exc_type, exc_val, exc_tb):
          print(f"Elapsed: {time.time() - self.start:.2f}s")
          return False   # False = don't suppress exceptions

  with Timer():
      do_work()
  ```

- **`contextlib.contextmanager`** — write a context manager as a generator function instead of a class, splitting it at `yield` (setup before, teardown after, wrapped in `try/finally` internally):

  ```python
  from contextlib import contextmanager

  @contextmanager
  def timer():
      start = time.time()
      try:
          yield
      finally:
          print(f"Elapsed: {time.time() - start:.2f}s")
  ```

- Returning `True` from `__exit__` **suppresses** the exception — a subtle footgun if done unintentionally.

## 12. `async`/`await` Basics

- `async def` defines a **coroutine function**; calling it returns a coroutine object that does nothing until it's awaited or scheduled on an event loop.
- `await` suspends the current coroutine at an I/O point, letting the event loop run other coroutines in the meantime — this is cooperative multitasking, not preemptive (a coroutine that never awaits blocks the whole loop).
- `asyncio.gather(*coros)` runs multiple coroutines concurrently and waits for all to finish.
- A **blocking call inside async code** (e.g., a synchronous `requests.get()` instead of an async HTTP client) stalls the entire event loop — one of the most common production bugs in async services; use `asyncio.to_thread()`/a thread pool to offload blocking calls if an async alternative isn't available.
- Async and threads/multiprocessing solve different problems and can be combined: asyncio for I/O concurrency within a process, multiprocessing for CPU parallelism across cores (see §3 table).

## 13. Typing / Type Hints

- Type hints (`def f(x: int) -> str:`) are **not enforced at runtime** by the interpreter — they're for static analysis (`mypy`, `pyright`) and readability/IDE support. Passing a wrong type at runtime will not raise a `TypeError` on its own.
- **Pydantic** and similar libraries *do* enforce types at runtime (validation), which is why they're the standard for API request/response models and config (see `production_engineering_python_notes.md` §4).
- Useful typing constructs: `Optional[X]` (== `X | None`), `Union[X, Y]` (== `X | Y` in 3.10+), `list[int]`/`dict[str, int]` (generic containers, no need for `List`/`Dict` from `typing` since 3.9+), `TypedDict` (typed dict shape), `Protocol` (structural typing / duck-typing contracts without inheritance).

## 14. Common "Gotchas" Interviewers Probe

| Gotcha | Why it happens |
|---|---|
| Mutable default arguments (§5) | Default value is evaluated once, at function definition time |
| Late-binding closures in loops (§4) | Closures capture the variable, not a snapshot of its value |
| `is` vs `==` misuse | Small-int/string interning makes `is` *appear* to work for equality by coincidence |
| Modifying a list while iterating over it | Iterator indices shift as elements are removed, silently skipping items |
| Shallow copy of nested structures | `copy.copy()` doesn't recurse — inner mutable objects are still shared |
| Class-level mutable attributes (§8) | Same root cause as mutable default arguments — one object shared across all instances |
| Circular imports | Two modules importing each other at module load time before either has finished defining its names |
| Floating-point comparison (`0.1 + 0.2 == 0.3` is `False`) | Binary floating-point can't represent all decimals exactly — compare with a tolerance (`math.isclose`) instead |

## 15. Is Python Interpreted or Compiled? How Code Actually Executes

**Short answer: Python is both — it's compiled to an intermediate bytecode, and that bytecode is then interpreted.** It's not "purely interpreted" (re-parsing source line by line every run) nor "compiled to native machine code" (like C/Rust) — it sits in between, similar in spirit to how Java compiles to JVM bytecode.

```
your_script.py
      │  (compile step — automatic, happens on every run unless a cached .pyc exists)
      ▼
  Bytecode (.pyc)              ← a low-level, platform-independent instruction set
      │  (interpret step)
      ▼
  Python Virtual Machine (PVM) ← the CPython runtime loop that executes bytecode instructions
      │
      ▼
   Program output
```

**Step by step (CPython, the reference implementation most people mean by "Python"):**

1. **Lexing/parsing** — the source `.py` file is tokenized and parsed into an Abstract Syntax Tree (AST).
2. **Compilation to bytecode** — the AST is compiled into **bytecode**, a compact set of instructions for the Python Virtual Machine (not machine code the CPU can run directly). You can inspect it yourself:

   ```python
   import dis
   def add(a, b):
       return a + b

   dis.dis(add)
   # LOAD_FAST a
   # LOAD_FAST b
   # BINARY_OP +
   # RETURN_VALUE
   ```

3. **Caching the bytecode** — for imported modules, CPython writes this bytecode to disk as `.pyc` files under a `__pycache__/` directory, so future runs can skip re-parsing/re-compiling the source if it hasn't changed (checked via a hash/timestamp). Note: the script you run directly (`python main.py`) is compiled fresh each run and not cached this way — only *imported* modules get `.pyc` caching.
4. **Execution by the PVM** — the **Python Virtual Machine**, a big interpreter loop inside the CPython executable, reads bytecode instructions one at a time and executes them (this is the "interpreted" part — no separate machine-code compilation step happens here, unlike a JIT).
5. **(Optional) JIT compilation** — alternative implementations add a Just-In-Time compiler that translates hot bytecode paths into actual machine code at runtime for speed: **PyPy** does this generally; CPython itself gained an experimental JIT starting in 3.13 (off by default in most environments). Standard CPython in most production deployments today still just interprets bytecode — no JIT.

**Why this distinction comes up in interviews:**

- "Interpreted" languages are often said to trade raw execution speed for development speed (no separate build step, run the source directly) and portability (the same `.pyc` bytecode/AST logic doesn't depend on target CPU architecture the way compiled machine code does) — Python fits this description overall even though there IS a compile step, because that step is automatic, fast, and produces portable bytecode rather than architecture-specific machine code.
- It also explains **why Python only catches some errors at "compile" time and others at runtime**: syntax errors are caught during the parse/compile step before any code runs at all; things like `NameError`/`TypeError` on a rarely-hit branch are only caught when the interpreter actually executes that line — Python does very little static type/semantic checking compared to a language like Java or Rust.
- Other implementations exist with different execution strategies: **PyPy** (JIT-compiled, often much faster for long-running CPU-bound code), **Jython** (compiles to JVM bytecode), **IronPython** (targets .NET's CLR), **MicroPython** (embedded/microcontrollers) — "Python" is a language spec, CPython is just the most common implementation.

## 16. Quick-Fire Q&A

**Q: What's the difference between a list and a tuple, beyond mutability?**
Tuples can be used as dict keys/set elements (hashable, if their contents are hashable); lists cannot. Tuples also signal "fixed-shape record" semantically (e.g., a coordinate pair), while lists signal "homogeneous, variable-length collection."

> **How exactly can a tuple be a dict key?** A dict key must be **hashable** — it needs a `__hash__()` that returns a fixed integer for its contents and never changes for the object's lifetime, plus a consistent `__eq__()`. Tuples are **immutable**, so CPython gives them a working `__hash__()` that combines the hashes of their elements — hashable as long as every element inside is itself hashable. Lists are **mutable**, so Python deliberately sets `list.__hash__ = None`: if lists were hashable and you mutated one after using it as a key, its hash would change and the dict could never find it again (silently broken lookups) — so lists are barred from being keys by design, not by oversight.
>
> ```python
> d = {}
> d[(1, 2)] = "point A"          # tuple as dict key — works, ints are hashable
> print(d[(1, 2)])                # "point A"
>
> d[[1, 2]] = "oops"
> # TypeError: unhashable type: 'list'
>
> d[(1, [2, 3])] = "fails"
> # TypeError: unhashable type: 'list'
> # the outer tuple is immutable, but it CONTAINS a mutable list,
> # so Python still can't compute a stable hash for it
> ```
>
> So it isn't that tuples are special-cased for dict keys — any object satisfying the hashable contract can be a key; tuples just naturally qualify because they're immutable and delegate hashing to their contents, while lists are explicitly excluded.

**Q: What happens when you call `len()` on an object?**
Python calls the object's `__len__` dunder method — `len()` is a thin wrapper, not special-cased per type internally.

**Q: Why does `a_tuple = (1)` not create a tuple?**
Parentheses alone don't make a tuple — it's the comma: `a_tuple = (1,)`. `(1)` is just the int `1` in parentheses.

**Q: What's the difference between `__new__` and `__init__`?**
`__new__` actually creates and returns the new instance (rarely overridden, mainly for immutable types or metaclasses/singletons); `__init__` initializes an already-created instance and returns `None`.

**Q: How do you make an object hashable?**
Implement `__hash__` (and typically `__eq__` consistently with it) — required to use an instance as a dict key or set member. If you override `__eq__` without `__hash__`, Python makes the object unhashable by default.

**Q: What's a metaclass, briefly?**
A class whose instances are classes themselves (`type` is the default metaclass). Overriding `__new__`/`__init__` on a custom metaclass lets you control how *classes* are created (e.g., auto-registering subclasses, enforcing interface rules) — rarely needed day-to-day, but a known "advanced Python" interview signal question.

**Q: Why is string concatenation in a loop discouraged (`s += chunk`)?**
Strings are immutable, so each `+=` creates a new string object and copies the old contents — O(n²) total for n concatenations. Prefer collecting parts in a list and `"".join(parts)` at the end.

**Q: What does `if __name__ == "__main__":` do?**
`__name__` is `"__main__"` only when the file is run directly (not when imported as a module) — this guard lets a file be both an importable module and a runnable script without the script logic firing on import.
