## 1. Why Inference Needs Optimization

Training happens once, but inference happens for **every single request**. A model that is used by millions of people spends far more GPU hours on inference than it ever did on training. So even a 20% improvement in inference efficiency saves a lot of money.

**Inference optimization** means making a trained model respond **faster**, **cheaper** and to **more users at the same time**, ideally without hurting the quality of the output.

There are three things we usually want:

| Goal | What it means |
|---|---|
| Lower latency | The user sees the first token sooner and the full answer sooner |
| Higher throughput | The same GPU serves more tokens (and users) per second |
| Lower cost | Fewer / cheaper GPUs for the same traffic |

These goals often pull against each other. For example, a bigger batch gives better throughput but each user waits slightly longer. Most of the techniques in this note are about getting **one of these without paying too much on the others**.

Optimization can be done at four levels:

```
Level 1: Model            -> quantization, distillation, pruning, MoE
Level 2: Algorithm/kernel -> FlashAttention, GQA, speculative decoding, fused kernels
Level 3: Serving system   -> continuous batching, PagedAttention, prefix caching, parallelism
Level 4: Application      -> shorter prompts, caching, routing, streaming
```

## 2. Where the Time Goes: Compute-bound vs Memory-bound

Before using any technique we must know **what is actually slow**. A GPU has two limits:

1. **Compute limit** – how many floating point operations per second (FLOPs) it can do.
2. **Memory bandwidth limit** – how many bytes per second it can read from its memory (HBM).

An operation is:
- **Compute-bound** if the GPU spends most time calculating.
- **Memory-bound** if the GPU spends most time waiting for data to arrive from memory.

### Arithmetic intensity

```
Arithmetic intensity = FLOPs performed / Bytes moved from memory
```

Every GPU has a "ridge point". If an operation's arithmetic intensity is below it, the operation is memory-bound; above it, compute-bound.

Example (A100 80GB): ~312 TFLOPs (BF16) and ~2 TB/s bandwidth, so ridge point ≈ 312 / 2 = **~150 FLOPs per byte**.

### Prefill vs decode

| | Prefill | Decode |
|---|---|---|
| Tokens processed at once | Whole prompt (hundreds to thousands) | 1 token per request per step |
| Weight reuse | Each weight is used for many tokens | Each weight is used for just 1 token |
| Arithmetic intensity | High (hundreds of FLOPs/byte) | ~1 FLOP/byte at batch size 1 |
| Bottleneck | **Compute-bound** | **Memory-bandwidth-bound** |
| Affects | TTFT | Inter-token latency (ITL/TPOT) |

For decode at batch size 1, each parameter is read once (2 bytes in FP16) and used for 1 multiply-add (2 FLOPs). So intensity is about 1 FLOP/byte, which is way below 150. The GPU's compute units are mostly idle while it waits for weights.

### A simple speed limit for decode

```
Time per token  ≈  Model size in bytes / Memory bandwidth
```

Example: Llama-3-8B in FP16 = ~16 GB. On a GPU with 2 TB/s:

```
16 GB / 2000 GB/s = 8 ms per token  ->  at most ~125 tokens/s for one user
```

If we quantize the same model to INT4 (~4 GB):

```
4 GB / 2000 GB/s = 2 ms per token   ->  at most ~500 tokens/s for one user
```

This one formula explains why **quantization, batching, speculative decoding and better hardware** all help decode. They either read fewer bytes, or use each byte for more tokens, or read bytes faster.

### Three types of memory pressure

1. **Memory bandwidth** – how fast weights and KV cache can be read (decides decode speed).
2. **Memory capacity** – whether weights + KV cache even fit in GPU memory (decides how many users and how long a context).
3. **Compute** – decides prefill speed and the maximum useful batch size.

Almost every optimization attacks one of these three.

## 3. Goals and Metrics

| Metric | Meaning | Mostly improved by |
|---|---|---|
| **TTFT** | Time to first token | Prefix caching, chunked prefill, faster prefill (TP, FlashAttention), less queueing |
| **ITL / TPOT** | Time between output tokens | Quantization, speculative decoding, smaller batch, faster GPU |
| **E2E latency** | TTFT + output tokens × TPOT | All of the above, plus shorter outputs |
| **Throughput** | Tokens/s of the whole server | Continuous batching, PagedAttention, quantization |
| **Goodput** | Throughput of requests that meet the SLO | Good scheduling, disaggregation |
| **Cost / 1M tokens** | GPU $/hour ÷ tokens/hour | Throughput up, GPU count down |
| **Quality** | Accuracy of output | Must be checked after every lossy change |

**Lossless vs lossy:** Some optimizations give exactly the same output (FlashAttention, PagedAttention, continuous batching, prefix caching, speculative decoding). Others change the output a bit (quantization, pruning, distillation, KV cache eviction). Lossy ones always need an evaluation on your own task.

## 4. Quantization

### 4.1 What is quantization?

Quantization stores numbers using **fewer bits**. A weight that was kept in 16 bits (FP16/BF16) is stored in 8 bits or 4 bits instead.

```
FP16 -> 2 bytes per weight
INT8 -> 1 byte per weight
INT4 -> 0.5 byte per weight
```

### 4.2 Why does it help?

1. **Smaller model** – a 70B model is 140 GB in FP16, 70 GB in INT8, 35 GB in INT4. It may now fit on fewer GPUs.
2. **Faster decode** – decode is memory-bound, so reading fewer bytes directly cuts the time per token.
3. **More room for KV cache** – the memory saved lets us serve more concurrent users.
4. **Faster math (sometimes)** – GPUs have INT8 and FP8 tensor cores with higher throughput than FP16.

### 4.3 How does it work? (the math)

The idea is to map a range of real numbers onto a small set of integers.

**Symmetric (absmax) quantization to INT8**

```
scale = max(|x|) / 127
q     = round(x / scale)            # stored as int8
x'    = q * scale                   # dequantized value used in computation
```

Example: weights are in the range [-2.54, 2.54].

```
scale = 2.54 / 127 = 0.02
x = 1.00   -> q = round(1.00 / 0.02) = 50   -> x' = 50 * 0.02 = 1.00   (no error)
x = 0.013  -> q = round(0.65)        = 1    -> x' = 0.02              (error 0.007)
```

The difference between x and x' is the **quantization error**. Fewer bits means bigger steps, hence more error.

**Asymmetric quantization** uses a scale and a **zero-point** so the integer range can be shifted to match data that is not centred on zero:

```
scale      = (max - min) / (2^bits - 1)
zero_point = round(-min / scale)
q          = round(x / scale) + zero_point
x'         = (q - zero_point) * scale
```

### 4.4 Granularity: how many numbers share one scale?

| Granularity | Meaning | Accuracy | Overhead |
|---|---|---|---|
| Per-tensor | One scale for the whole weight matrix | Lowest | Lowest |
| Per-channel | One scale per output row/column | Better | Small |
| Per-group (group size 64/128) | One scale per group of 64 or 128 weights | Best for INT4 | Small extra storage |

Most 4-bit methods use **group-wise** quantization (for example group size 128) because a single outlier weight would otherwise ruin the precision of everything that shares its scale.

### 4.5 What can be quantized?

| Target | Notes |
|---|---|
| **Weights** | Biggest memory saving, most common |
| **Activations** | Harder, because activations have large outliers |
| **KV cache** | Reduces cache memory, helps long context and big batches |

Notation: **W8A8** = 8-bit weights and 8-bit activations. **W4A16** = 4-bit weights, 16-bit activations (weight-only quantization). Weights are stored in 4 bits, but are dequantized to 16 bits on the fly inside the kernel before the matrix multiplication.

> Weight-only quantization (W4A16) speeds up **decode** (less memory read) but does not speed up the matrix multiply itself. W8A8 / FP8 speeds up compute too, so it helps **prefill and large batches** as well.

### 4.6 Post-Training Quantization (PTQ) vs Quantization-Aware Training (QAT)

| | PTQ | QAT |
|---|---|---|
| When | After training, no (or little) retraining | During training / fine-tuning with fake quantization |
| Cost | Minutes to hours, small calibration set | Expensive, needs training infrastructure |
| Quality at 8-bit | Almost lossless | Almost lossless |
| Quality at 4-bit or less | Usually small drop | Better |
| Used for | Most LLM deployments | When PTQ quality is not enough |

### 4.7 Popular LLM quantization methods

| Method | Type | Idea |
|---|---|---|
| **LLM.int8() / bitsandbytes** | INT8 / NF4 | Keeps outlier features in FP16 and the rest in INT8. NF4 (used by QLoRA) is a 4-bit format designed for normally distributed weights. Easy to use, not the fastest. |
| **GPTQ** | W4/W3, PTQ | Quantizes layer by layer and uses second-order (Hessian) information to adjust the remaining weights and compensate for the error already made. Needs a small calibration dataset. |
| **AWQ** (Activation-aware Weight Quantization) | W4A16, PTQ | Only ~1% of weights are "salient" (they see large activations). AWQ scales those channels before quantizing to protect them. Fast and accurate. |
| **SmoothQuant** | W8A8, PTQ | Activations have outliers, weights do not. It moves the difficulty from activations to weights by dividing activations and multiplying weights by a per-channel factor. Mathematically equivalent, easier to quantize. |
| **FP8 (E4M3 / E5M2)** | W8A8 | Supported natively on H100/H200/Blackwell. Floating-point keeps a wider dynamic range than INT8, so it is simple and close to lossless. |
| **GGUF (llama.cpp)** | Q2–Q8, K-quants | File format for CPU / Apple / consumer GPU inference, with many mixed-precision options (Q4_K_M, Q5_K_M, ...). |
| **MXFP4 / NVFP4** | 4-bit float with block scaling | New hardware-supported 4-bit formats on latest GPUs. |

### 4.8 Why do outliers matter?

In large LLMs, a few activation channels have values 10 to 100 times bigger than the others. If one scale covers everything, the small values all collapse to 0 or 1 after rounding. Methods like LLM.int8(), SmoothQuant and AWQ are basically different ways of handling these outliers.

### 4.9 KV cache quantization

The KV cache can be stored in FP8 or INT8 instead of FP16, which halves its size. This doubles the number of tokens (or users) that fit in memory. The quality drop is usually small at FP8 and larger at INT4.

### 4.10 Rule of thumb

| Precision | Memory vs FP16 | Typical quality |
|---|---|---|
| BF16 / FP16 | 1× | Baseline |
| FP8 / INT8 | 0.5× | Nearly the same |
| INT4 (AWQ/GPTQ) | 0.25× | Small drop, check on your task |
| INT3 / INT2 | <0.2× | Noticeable drop, only for very constrained devices |

A **larger model quantized to 4-bit often beats a smaller model at 16-bit** with the same memory budget (for example a 13B INT4 vs a 7B FP16).

### 4.11 Trade-offs

- Quality can drop, especially for math, code, and reasoning tasks, and for small models.
- Not every GPU has fast kernels for every format. Pick a format your serving engine and hardware support (e.g. FP8 needs H100 or newer).
- Dequantization adds a small overhead, so a 4× smaller model is not 4× faster. Typical gains are 1.5× to 3×.

## 5. Attention Optimizations

Attention is expensive because for a sequence of length N it needs an N × N score matrix. Compute and memory both grow with N².

### 5.1 FlashAttention

**Problem.** Standard attention does three steps and writes the large N × N matrix to GPU main memory (HBM) in between:

```
S = Q × Kᵀ        -> write S to HBM
P = softmax(S)    -> read S, write P to HBM
O = P × V         -> read P
```

This is slow because HBM is slow compared to the small on-chip SRAM (shared memory), and attention is memory-bound.

**Idea.** FlashAttention splits Q, K, V into small **tiles** that fit in SRAM, and computes the output tile by tile **without ever writing the full N × N matrix to HBM**. To do softmax in pieces it uses the **online softmax** trick: it keeps a running maximum and running sum, and rescales the earlier partial results when a new tile has a bigger maximum.

**Result.**
- Exactly the same output as standard attention (it is not an approximation).
- Memory for attention goes from O(N²) to O(N).
- 2× to 4× faster in practice, and gives much bigger gains for long sequences.

| Version | Notes |
|---|---|
| FlashAttention-1 | Tiling + online softmax |
| FlashAttention-2 | Better work partitioning across GPU thread blocks, ~2× faster than v1 |
| FlashAttention-3 | Uses Hopper (H100) features: asynchrony and FP8 |
| FlashDecoding / Flash-Decoding | Splits work along the KV length so that decode with a long context and a small batch also uses the whole GPU |

### 5.2 Multi-Query and Grouped-Query Attention (MQA, GQA)

These change the model architecture so that the **KV cache is smaller**.

| Type | Query heads | KV heads | KV cache size |
|---|---|---|---|
| MHA (Multi-Head) | H | H | 1× |
| GQA (Grouped-Query) | H | G (1 < G < H) | G/H |
| MQA (Multi-Query) | H | 1 | 1/H |

Example, Llama-3-8B: 32 query heads and only 8 KV heads, so the KV cache is 4× smaller than if it used MHA. Each KV head is shared by a group of 4 query heads.

```
KV cache per token = 2 (K and V) × layers × KV_heads × head_dim × bytes

Llama-2-7B  (MHA, 32 KV heads): 2 × 32 × 32 × 128 × 2 B = 512 KB per token
Llama-3-8B  (GQA,  8 KV heads): 2 × 32 ×  8 × 128 × 2 B = 128 KB per token
```

So an 8K context costs ~4 GB with MHA and ~1 GB with GQA. GQA gives almost the quality of MHA with the memory benefit of MQA, which is why nearly all modern open models use it.

> Note: this is decided at **training time**. You cannot switch a model to GQA at serving time (although some methods can "uptrain" an MHA model into GQA).

### 5.3 Multi-head Latent Attention (MLA)

Used in DeepSeek models. Instead of storing full K and V for each head, it stores a small **compressed latent vector** per token and reconstructs K and V from it when needed. The KV cache can be many times smaller than MHA or even GQA, while keeping better quality.

### 5.4 Sliding Window and Local Attention

Each token attends only to the last W tokens (for example W = 4096) instead of the whole history.
- The KV cache per layer is capped at W tokens, so memory stops growing with the context length.
- Used in Mistral-7B and in some layers of Gemma and others.
- Often combined with a few **global attention layers** so that far-away information can still flow.

### 5.5 Other ideas (just know the names)

- **Sparse attention** – attend to only a selected subset of tokens.
- **Linear attention / state space models (Mamba)** – replace attention with a recurrent state of fixed size, so there is no growing KV cache. Hybrid models mix both.
- **Attention sinks (StreamingLLM)** – keep the first few tokens plus a recent window, which lets a model stream over very long text.

## 6. KV Cache Optimizations

Recap from [[55.llm_inference_fundamentals.md]]: during generation, the K and V vectors of every previous token are stored so they are not recomputed. The cache grows with **sequence length × number of concurrent requests**, and for long contexts it can become larger than the model weights.

### 6.1 The problem with naive KV cache allocation

Older systems reserved one contiguous block of memory for each request, sized for the **maximum possible length**. This wasted memory in three ways:

| Waste | Meaning |
|---|---|
| Internal fragmentation | Reserved for 2048 tokens, request only uses 200 |
| Reservation | Space for future tokens is held but not yet used |
| External fragmentation | Free memory exists but is in pieces that are too small to use |

Studies reported that only ~20 to 40% of the KV memory was actually used for tokens. So the batch size was much smaller than what the GPU could really handle.

### 6.2 PagedAttention

PagedAttention (the core of [[54.vllm.md]]) borrows the idea of **virtual memory and paging** from operating systems.

- KV cache memory is divided into small fixed-size **blocks** (for example 16 tokens each).
- A request's blocks do **not** have to be next to each other. A **block table** maps the request's logical blocks to physical blocks, just like a page table.
- Blocks are allocated **on demand** as the sequence grows.
- The attention kernel is written to read K and V through the block table.

```
Request A logical blocks:  [0] [1] [2]
Block table:               0 -> physical 7,  1 -> physical 2,  2 -> physical 9
Physical GPU memory:       [ ][ ][A1][ ][ ][ ][ ][A0][ ][A2] ...
```

Benefits:
- Waste is limited to the last partially filled block (under 4% in the paper).
- Much bigger batches fit in the same memory, so **2× to 4× higher throughput** than older systems.
- **Sharing:** if several outputs share the same prompt (parallel sampling, beam search), they point to the same physical blocks. When one of them writes a new token into a shared block, it is copied first (**copy-on-write**).

### 6.3 Prefix caching (automatic prefix caching)

If many requests start with the same text (system prompt, few-shot examples, tool definitions, a long document), their prefill output (the KV cache of that prefix) is identical. So we compute it once and **reuse** it.

How it works with blocks: each full block is identified by a hash of its tokens and everything before it. When a new request arrives, the engine looks for matching blocks, reuses them, and only prefills the remaining tokens.

```
Request 1:  [system prompt 2000 tokens][user question A]
Request 2:  [system prompt 2000 tokens][user question B]
                 ^ KV for these 2000 tokens computed once, reused by Request 2
```

Benefits:
- TTFT drops a lot (no recompute of the shared part).
- Saves GPU compute and money. API providers charge a lower price for cached input tokens.

Rules:
- Only an exact **prefix** matches. Put the static text (system prompt, instructions, documents) **first** and the changing text (user question, timestamps) **last**. A single changed token early in the prompt breaks the cache for everything after it.
- Cached blocks occupy memory, so old ones are evicted (usually LRU).
- **RadixAttention** (SGLang) stores prefixes in a radix tree, so many branching prefixes can share parts automatically. It is very effective for agents, multi-turn chat and few-shot prompts.

### 6.4 KV cache quantization

Covered in 4.9. FP8 KV cache halves the memory. In vLLM: `--kv-cache-dtype fp8`.

### 6.5 KV cache eviction and compression (for very long contexts)

When even a quantized cache is too big, we can throw some of it away. These methods are **lossy**.

| Method | Idea |
|---|---|
| Sliding window | Keep only the last W tokens |
| StreamingLLM / attention sinks | Keep the first few tokens (they receive lots of attention) + recent window |
| H2O, SnapKV, Scissorhands | Keep tokens that received the highest attention scores ("heavy hitters") |
| Token merging / low-rank compression | Compress many KV entries into fewer |

### 6.6 KV cache offloading

Move less-used KV blocks from GPU memory to CPU RAM or SSD, and bring them back when needed (LMCache, vLLM CPU offload, Mooncake). It trades some latency for much higher capacity, and is useful for multi-turn chats where the user returns after some time.

### 6.7 Memory budget example

80 GB GPU, Llama-3-8B in FP16, 90% memory utilisation:

```
Usable memory      = 80 × 0.9 = 72 GB
Weights            = 16 GB
Left for KV cache  ≈ 72 − 16 − ~4 (activations/overhead) = ~52 GB
KV per token       = 128 KB
Total tokens in KV = 52 GB / 128 KB      ≈ 400,000 tokens
Users at 4K context ≈ 100 concurrent requests
```

With an FP8 KV cache this becomes ≈ 200 concurrent requests. With INT4 weights (4 GB instead of 16 GB) even more. This is how quantization and KV optimization translate to **users per GPU**.

## 7. Batching and Scheduling

(Basic idea already in [[55.llm_inference_fundamentals.md]]. Here is the deeper part.)

### 7.1 Why batching is so effective

Decode is memory-bound: reading the weights takes the same time whether they are used for 1 token or for 32 tokens. So with batch size B you get nearly B times the tokens for almost the same step time. Throughput goes up and cost per token goes down, until the GPU becomes compute-bound (the ridge point), after which time per step starts to grow with B.

```
Time per step
   |             ______/   <- compute-bound, step time grows with batch
   |____________/
   |  memory-bound, step time almost flat
   +----------------------------> Batch size
```

### 7.2 Static vs dynamic vs continuous batching

| Type | How it works | Problem |
|---|---|---|
| Static | Fixed group, runs until the longest request finishes | Short requests wait, GPU slots are idle |
| Dynamic (request-level) | Wait a short window to collect requests, then run them as a static batch | Same problem within the batch |
| **Continuous / in-flight / iteration-level** | Scheduler works at each token step. Finished requests leave, waiting requests join | Needs a smart engine (vLLM, TGI, TensorRT-LLM, SGLang) |

Continuous batching (from the Orca paper) gives **up to an order of magnitude higher throughput** than naive static batching because no slot is wasted.

### 7.3 Chunked prefill

A long prompt (say 32K tokens) takes a long time to prefill. If it runs as one big step, everyone else's decode is stalled, and their ITL spikes.

Chunked prefill splits the prompt into chunks (for example 512 or 2048 tokens), and each step mixes **one prefill chunk + the decode tokens of all running requests**.

```
Step 1: [prefill chunk 1 of long prompt] + [decode tokens of 20 users]
Step 2: [prefill chunk 2 of long prompt] + [decode tokens of 20 users]
...
```

Benefits: smooth ITL for existing users, better GPU utilisation (compute-bound prefill is mixed with memory-bound decode so both resources are used). Cost: the long prompt's own TTFT gets a bit longer.

### 7.4 Scheduling policies

| Policy | Notes |
|---|---|
| FCFS (first come first served) | Simple, but one long request can delay many short ones (head-of-line blocking) |
| Priority / SLO-aware | Interactive requests are served before batch jobs |
| Shortest job first (approx.) | Predict output length to reduce average waiting time |
| Preemption | If KV memory runs out, pause a request, either **swap** its KV blocks to CPU or **recompute** them later |
| Admission control / rate limits | Reject or queue when overloaded, rather than letting all requests become slow |

### 7.5 Tuning knobs (vLLM names)

| Knob | Effect |
|---|---|
| `--max-num-seqs` | Max concurrent requests in the batch |
| `--max-num-batched-tokens` | Max tokens processed per step (controls chunk size). Higher = better throughput, worse ITL |
| `--gpu-memory-utilization` | Fraction of GPU memory the engine can use (rest is a safety margin) |
| `--max-model-len` | Max context length. Lower value = more room for batch size |
| `--enable-chunked-prefill` | Turns on chunked prefill |
| `--enable-prefix-caching` | Turns on automatic prefix caching |

## 8. Speculative Decoding

### 8.1 The idea

Decode produces one token per forward pass, and each pass is memory-bound, so the GPU has spare compute. Speculative decoding uses that spare compute.

1. A cheap **draft** mechanism guesses the next **k** tokens.
2. The big **target** model checks all k guesses **in a single forward pass** (processing k tokens in parallel costs about the same as 1 token when memory-bound).
3. Tokens are accepted from left to right while they match what the target model would have produced. At the first mismatch, the target's own token is used and the rest of the guesses are discarded.

```
Draft model guesses:      "The" "capital" "of" "France" "is"
Target verifies (1 pass):  ok    ok       ok   ok       ok  + 1 bonus token "Paris"
-> 6 tokens produced in 1 target pass instead of 6
```

The target model always gets the last word, so the output has **exactly the same distribution** as normal decoding. It is lossless. (With greedy decoding the output is identical; with sampling, a rejection sampling rule keeps the distribution correct.)

### 8.2 Expected speed-up

If each draft token is accepted with probability **α** (assumed independent) and we draft **k** tokens, the expected number of tokens produced per target pass is:

```
E[tokens] = (1 − α^(k+1)) / (1 − α)
```

Example: α = 0.8, k = 4 → (1 − 0.8⁵) / 0.2 = (1 − 0.328) / 0.2 ≈ **3.36 tokens per target pass**.

Real speed-up is lower because the draft also takes time. Typical practical gains are **1.5× to 3×**.

### 8.3 Variants

| Variant | Draft source | Notes |
|---|---|---|
| Draft model | A small model of the same family (e.g. 1B drafting for 70B) | Must share the tokenizer. Extra memory for the draft. |
| **Prompt lookup / n-gram** | Copy matching text from the prompt itself | No extra model. Great for summarization, code editing, RAG, where the output repeats the input. |
| **Medusa** | Extra "heads" on the target model predict several future tokens | No separate model, but needs a small fine-tune. Uses tree-based verification. |
| **EAGLE / EAGLE-2/3** | A small autoregressive head works on the target's hidden features | Higher acceptance rate than Medusa. |
| **Multi-token prediction (MTP)** | The model is trained to predict several tokens ahead (e.g. DeepSeek-V3) | Built into the model. |
| Self-speculative / layer skip | Use early layers of the same model as the draft | No extra weights. |

### 8.4 When it helps and when it doesn't

- Helps most at **low to moderate batch sizes** (when the GPU has spare compute) and when the draft usually agrees with the target (predictable text like code, JSON, repeated phrases).
- Gives little or even negative gain at **very high batch sizes** (the GPU is already compute-bound, so verification of extra tokens costs real time), and for high-temperature creative sampling (low acceptance).
- Uses extra memory (draft model weights and its KV cache).

## 9. Parallelism

When a model doesn't fit on one GPU, or we want lower latency, we split the work over several GPUs.

### 9.1 Tensor parallelism (TP)

Each weight matrix is **split across GPUs**. Every GPU computes its part of each layer, and then they combine results with an **all-reduce** (usually 2 per transformer layer).

```
Layer weight W = [W1 | W2]          (split column-wise over 2 GPUs)
GPU 0: Y1 = X × W1        GPU 1: Y2 = X × W2      then combine
```

- Reduces latency (each GPU reads only 1/TP of the weights, so decode is faster) and splits memory.
- Needs very fast links (NVLink / NVSwitch) because of the all-reduce on every layer. Normally kept **within one node** (TP = 2, 4 or 8).
- Over slow links (PCIe, network) the communication cost can kill the gain.

### 9.2 Pipeline parallelism (PP)

Different **layers** are placed on different GPUs (GPU 0 has layers 1–20, GPU 1 has 21–40 ...). The activations are passed from one GPU to the next.

- Needs little communication, so it works across nodes.
- Does not reduce latency of a single request (the token still passes through all stages one after another). Throughput improves when micro-batches keep all stages busy, but "pipeline bubbles" (idle time) appear.

### 9.3 Expert parallelism (EP)

For MoE models, different experts live on different GPUs. Tokens are sent (all-to-all communication) to the GPUs holding their selected experts and the results come back. Needs good load balancing, because popular experts can overload one GPU.

### 9.4 Sequence / context parallelism

For very long prompts, the sequence is split across GPUs (Ring Attention and similar), so that no single GPU holds the whole KV cache or the whole N × N computation.

### 9.5 Data parallelism / replicas

Run several identical copies of the model and send different requests to each. This is the simplest way to scale throughput. Combine with TP inside each replica, for example 8 GPUs = 2 replicas × TP 4.

### 9.6 Comparison

| | Splits | Communication | Best for |
|---|---|---|---|
| Tensor | Within each layer | Very high (all-reduce per layer) | Latency, fitting a big model inside a node |
| Pipeline | Between layers | Low (only activations between stages) | Multi-node, very large models |
| Expert | MoE experts | All-to-all | MoE models |
| Sequence | Tokens of a sequence | Moderate | Very long contexts |
| Data/replica | Requests | None between replicas | Scaling throughput |

## 10. Disaggregated Prefill and Decode

Prefill is compute-bound and decode is memory-bound. When both run on the same GPU they **interfere**: a big prefill delays decode steps (high ITL) and decode requests occupy GPU capacity that prefill needs (high TTFT). Chunked prefill reduces the problem but does not remove it.

**Disaggregation** runs them on **separate GPU pools**:

```
Request -> [Prefill pool] --(transfer KV cache over fast network)--> [Decode pool] -> tokens
```

- Prefill GPUs can be chosen for compute (and use higher TP for low TTFT).
- Decode GPUs can be chosen for memory bandwidth and capacity (and use big batches).
- Each pool is scaled independently based on its own bottleneck.
- Cost: the KV cache must be moved from prefill GPU to decode GPU, which needs a fast interconnect (NVLink, InfiniBand/RDMA), and the system is more complex.

Examples: DistServe, Splitwise, Mooncake, NVIDIA Dynamo, vLLM disaggregated prefill. It pays off mostly at large scale with strict TTFT and ITL targets.

## 11. Mixture of Experts (MoE)

In an MoE model, the feed-forward block of each layer is replaced by many parallel "expert" networks plus a small **router** that picks the top-k experts for each token.

- Mixtral 8x7B: ~47B total parameters, 2 of 8 experts active per token, so ~13B active parameters.
- DeepSeek-V3: 671B total, ~37B active per token.

Effect on inference:

| | Dense model | MoE model |
|---|---|---|
| Compute per token | All parameters | Only active parameters (cheaper) |
| Memory for weights | All parameters | **All** parameters (expensive) |
| Decode bandwidth at batch 1 | Read all weights | Read only the chosen experts |
| At large batch | Reads all weights once | Different tokens pick different experts, so almost every expert gets read |

So MoE gives the quality of a large model at the compute cost of a smaller one, but it needs a lot of memory and good expert parallelism. It is a great fit for high-throughput serving on multi-GPU setups, and less attractive for a single small GPU.

## 12. Model Compression

### 12.1 Knowledge distillation

Train a small **student** model to imitate a large **teacher** model. The student learns from the teacher's output probabilities (soft labels), not just from the correct answers, so it picks up more information per example.

- Result: a smaller, faster, cheaper model with much of the teacher's quality on the target task.
- Examples: DistilBERT, many "mini" and "flash" size models, DeepSeek-R1 distilled models.
- Cost: needs training and data; the student rarely beats the teacher in general ability.

### 12.2 Pruning

Remove parameters that matter little.

| Type | What is removed | Speed-up |
|---|---|---|
| Unstructured | Individual weights anywhere | Hard to speed up on GPU (irregular pattern) |
| **Structured** | Whole neurons, heads, or layers | Real speed-up, directly smaller matrices |
| **2:4 semi-structured sparsity** | In every 4 weights, 2 are zero | Supported by NVIDIA sparse tensor cores, up to ~2× matrix speed |

Methods: SparseGPT, Wanda (one-shot, no retraining), and structured approaches like Sheared-LLaMA / Minitron (prune then distil to recover quality).

### 12.3 Low-rank factorization

Replace a big weight matrix W (d × d) with two thin matrices A (d × r) and B (r × d), with r much smaller than d. Used more in fine-tuning (LoRA) than for speeding up inference, but merged LoRA adapters add no inference cost.

### 12.4 Serving many LoRA adapters

Instead of keeping 100 full fine-tuned models, keep one base model plus 100 small adapters and swap or batch them per request (vLLM multi-LoRA, S-LoRA, LoRAX). Saves a huge amount of memory for multi-tenant products.

## 13. Kernel, Compiler and Runtime Optimizations

### 13.1 Why these matter

Each decode step launches many small GPU operations (kernels). With a small batch, the time spent launching kernels and moving data between them can be as large as the useful math.

### 13.2 Kernel fusion

Combine several operations (e.g. add bias + activation + layer norm) into **one kernel**, so the intermediate result stays in fast registers/SRAM and is not written to and read from HBM. FlashAttention is the most famous example of fusion.

### 13.3 CUDA graphs

Record a sequence of GPU launches once and replay it as a single unit. This removes the CPU overhead of launching hundreds of kernels at each decode step, which matters when each step is only a few milliseconds.

### 13.4 Compilers and optimized runtimes

| Tool | What it does |
|---|---|
| `torch.compile` | Traces the PyTorch model and generates fused, optimized kernels |
| **TensorRT-LLM** | NVIDIA's engine: fused kernels, in-flight batching, paged KV, FP8/INT4, speculative decoding. Fastest on NVIDIA, but needs a model-specific build step. |
| **vLLM** | Python/CUDA engine with PagedAttention and continuous batching, easiest to use and very broad model support |
| **SGLang** | RadixAttention, structured-output speedups, strong for agentic workloads |
| **TGI** (Hugging Face) | Production server with continuous batching and quantization |
| **llama.cpp / Ollama** | CPU, Apple Silicon and consumer GPUs with GGUF |
| ONNX Runtime, OpenVINO, MLC-LLM | Cross-platform and edge deployment |

### 13.5 Other low-level tricks

- Using **Tensor Cores** with the right data types and shapes (multiples of 8/16/64).
- **Overlapping** communication with computation in multi-GPU setups.
- **Asynchronous scheduling** so the CPU prepares the next step while the GPU runs the current one.
- Fast tokenizers and avoiding Python overhead in the hot path.

## 14. Prompt and Application Level Optimizations

Many of the cheapest wins have nothing to do with GPUs.

| Technique | Why it helps |
|---|---|
| **Shorter prompts** | Prefill cost and TTFT are proportional to prompt length. Remove unused instructions and examples. |
| **Limit output length** (`max_tokens`, "answer in 3 bullet points") | Every output token costs one sequential decode step. Output tokens are the slowest and most expensive part. |
| **Static content first** | Makes prefix caching work. |
| **Retrieve less, retrieve better (RAG)** | Fewer, more relevant chunks = shorter prompts and better answers. Re-rank and cut. |
| **Streaming** | Doesn't reduce total time but improves *perceived* latency, since the user starts reading at TTFT. |
| **Response caching / semantic caching** | A cache hit costs no GPU time at all ([[39.llm_response_caching.md]]). |
| **Model routing / cascades** | Send easy queries to a small model, hard ones to a large model. |
| **Structured outputs / constrained decoding** | Short, valid JSON without retries. |
| **Parallel tool calls and parallel sub-tasks** | Reduce the total wall-clock time of agent flows. |
| **Batch API for offline work** | Non-urgent jobs can use cheaper batch pricing and fill idle GPU time. |
| **Prompt compression** (e.g. LLMLingua) | Drops low-information tokens from long prompts. |
| **Avoid unnecessary reasoning tokens** | Reasoning/"thinking" models generate many hidden tokens. Use a lower reasoning budget for simple tasks. |

## 15. Choosing Hardware

Because decode is bandwidth-bound and capacity decides batch size, GPU specs that matter most are **memory bandwidth** and **memory size**, then compute.

| GPU (approx.) | Memory | Bandwidth | Notes |
|---|---|---|---|
| NVIDIA L4 | 24 GB | ~300 GB/s | Cheap, low power, good for small / quantized models |
| NVIDIA A10G | 24 GB | ~600 GB/s | Common for 7B–13B models |
| NVIDIA A100 | 40 / 80 GB | 1.5–2.0 TB/s | Previous generation workhorse |
| NVIDIA H100 | 80 GB | ~3.35 TB/s | FP8 support, NVLink |
| NVIDIA H200 | 141 GB | ~4.8 TB/s | Same compute as H100 but more memory and bandwidth, so it is better for big models and long context |
| AMD MI300X | 192 GB | ~5.3 TB/s | Large memory |
| Google TPU, AWS Inferentia/Trainium, Groq | – | – | Specialised inference hardware |

Sizing a deployment, quick method:
1. Weights size = parameters × bytes per parameter.
2. Add KV cache = users × context length × KV bytes per token.
3. Add ~10–20% for activations and overhead.
4. Pick GPUs (and TP degree) so the total fits; then benchmark for latency and throughput.

## 16. How to Optimize in Practice (Workflow)

1. **Define targets (SLOs).** For example: TTFT p95 < 500 ms, ITL p95 < 50 ms, 200 concurrent users.
2. **Measure a baseline** with realistic traffic (real prompt and output length distribution). Tools: vLLM `benchmark_serving`, GenAI-Perf, Locust, k6.
3. **Find the bottleneck** with metrics: GPU utilisation, memory bandwidth, KV cache usage, queue time, TTFT vs ITL.
4. **Apply the technique that matches the symptom** (table below).
5. **Re-measure** and also **re-evaluate quality** on your own test set for any lossy change.
6. Change **one thing at a time** so you know what helped.

### Symptom → fix

| Symptom | Likely cause | What to try |
|---|---|---|
| High TTFT, GPU compute busy | Long prompts, prefill bottleneck | Prefix caching, shorter prompts, higher TP, FP8, chunked prefill, disaggregation |
| High TTFT, requests waiting in queue | Not enough capacity | More replicas, bigger batch, quantization, autoscaling |
| High ITL (slow streaming) | Memory-bandwidth-bound decode | Quantization, speculative decoding, smaller batch, higher TP, faster GPU |
| ITL spikes when long prompts arrive | Prefill interfering with decode | Chunked prefill, disaggregation |
| Out-of-memory / small batch size | Weights + KV cache too big | Quantize weights and KV, GQA/MLA model, reduce `max-model-len`, PagedAttention, more GPUs |
| Low throughput, GPU underused | Batch too small, poor scheduling | Continuous batching, raise `max-num-seqs`, route more traffic per replica |
| Cost too high | Over-provisioned or wasteful | Quantize, smaller model, cache, routing, batch API, spot instances |
| Quality dropped after optimization | Lossy technique | Use higher precision (INT4 → INT8/FP8), better method (AWQ/GPTQ), calibrate with domain data |

## 17. Optimization Cheat Sheet

| Technique | Level | Lossless? | Helps | Cost / Trade-off |
|---|---|---|---|---|
| Quantization (INT8/FP8/INT4) | Model | No | Memory, decode speed, cost | Possible quality drop |
| FlashAttention | Kernel | Yes | Prefill speed, memory | None |
| GQA / MQA / MLA | Architecture | n/a (training time) | KV cache size | Must be built into the model |
| Sliding window attention | Architecture | No (changes model) | KV size for long context | Loses far context unless mixed with global layers |
| PagedAttention | System | Yes | Batch size, throughput | Needs supporting engine |
| Prefix caching | System | Yes | TTFT, cost | Only exact shared prefixes |
| KV cache quantization | System | No (small loss) | Memory, batch size | Small quality drop |
| KV eviction / offload | System | Eviction no, offload yes | Long context capacity | Quality loss / latency |
| Continuous batching | System | Yes | Throughput | Small latency increase at load |
| Chunked prefill | System | Yes | Stable ITL | Slightly higher TTFT for the long prompt |
| Speculative decoding | Algorithm | Yes | Decode latency | Extra memory, weak at high batch |
| Tensor parallelism | System | Yes | Latency, fit big models | Needs fast interconnect |
| Pipeline parallelism | System | Yes | Fit huge models across nodes | Pipeline bubbles |
| Disaggregated prefill/decode | System | Yes | TTFT and ITL at scale | KV transfer, complexity |
| MoE | Architecture | n/a | Compute per token | High memory |
| Distillation | Model | No | Everything (smaller model) | Training cost, lower capability |
| Pruning / sparsity | Model | No | Compute, memory | Quality drop, hardware dependent |
| Kernel fusion, CUDA graphs, TensorRT | Runtime | Yes | Per-step overhead | Build / engineering effort |
| Caching, routing, shorter prompts | Application | Mostly | Cost, latency | Design effort |

### 18.1 Load a model in 4-bit (bitsandbytes, NF4)

```python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig

model_id = "meta-llama/Meta-Llama-3-8B-Instruct"

bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=torch.bfloat16,
    bnb_4bit_use_double_quant=True,   # also quantizes the scales
)

tokenizer = AutoTokenizer.from_pretrained(model_id)
model = AutoModelForCausalLM.from_pretrained(
    model_id, quantization_config=bnb_config, device_map="auto"
)

inputs = tokenizer("Explain KV cache in one line.", return_tensors="pt").to(model.device)
out = model.generate(**inputs, max_new_tokens=50)
print(tokenizer.decode(out[0], skip_special_tokens=True))
```

### 18.2 Manual symmetric INT8 quantization (to understand the math)

```python
import numpy as np

w = np.random.randn(4, 4).astype(np.float32)

scale = np.abs(w).max() / 127
q = np.round(w / scale).astype(np.int8)       # quantize
w_hat = q.astype(np.float32) * scale          # dequantize

print("max error:", np.abs(w - w_hat).max())  # at most ~scale/2
```

### 18.5 Quick benchmark (tokens per second and TTFT)

```python
import time
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="x")

start = time.perf_counter()
first = None
n = 0
stream = client.chat.completions.create(
    model="meta-llama/Meta-Llama-3-8B-Instruct",
    messages=[{"role": "user", "content": "Write a 200 word note on GPUs."}],
    stream=True, max_tokens=300,
)
for chunk in stream:
    if chunk.choices and chunk.choices[0].delta.content:
        if first is None:
            first = time.perf_counter() - start     # TTFT
        n += 1

total = time.perf_counter() - start
print(f"TTFT: {first*1000:.0f} ms")
print(f"Decode speed: {n / (total - first):.1f} tokens/s")
```

## 19. Interview Questions

**Q1. Why is LLM decode memory-bound and what does that mean for optimization?**
At batch size 1, each generated token needs every weight to be read from GPU memory but each weight is used for only one multiply-add. So the GPU waits on memory, not on math. The speed limit is roughly model size ÷ memory bandwidth. Anything that reads fewer bytes (quantization), reuses each byte for more tokens (batching, speculative decoding) or reads bytes faster (better GPU, tensor parallelism) will speed up decode.

**Q2. What is quantization and what are its types?**
Storing weights/activations/KV cache in fewer bits. Types: weight-only (W4A16 like AWQ, GPTQ), weight+activation (W8A8 like SmoothQuant, FP8), and KV cache quantization. Done post-training (PTQ) or with quantization-aware training (QAT). It reduces memory and speeds up decode at a possible small quality cost.

**Q3. AWQ vs GPTQ?**
Both are 4-bit weight-only PTQ methods. GPTQ quantizes layer by layer and uses Hessian information to update the remaining weights and compensate for the error. AWQ finds the small set of salient weight channels (based on activation magnitude) and scales them to protect them before quantizing. AWQ is usually faster to run and generalizes well; both work with vLLM.

**Q4. How does FlashAttention work and does it change the output?**
It computes attention in tiles inside on-chip SRAM, using online softmax, and never materialises the full N×N matrix in HBM. This cuts memory traffic, so it is faster and uses O(N) memory. The result is mathematically exact, so output does not change.

**Q5. What are MQA and GQA and why do they matter?**
They share key/value heads across several query heads. MQA uses one KV head, GQA uses a group count between 1 and the number of query heads. This shrinks the KV cache by H/G times, allowing longer contexts and bigger batches with little quality loss. Llama-3-8B has 32 query heads and 8 KV heads.

**Q6. Explain PagedAttention.**
The KV cache is split into fixed-size blocks that don't need to be contiguous. A block table maps each request's logical blocks to physical ones, like OS paging. Blocks are allocated as needed, so fragmentation and over-reservation are nearly eliminated, and sequences can share blocks with copy-on-write. This allows much larger batches and 2–4× throughput.

**Q7. What is continuous batching and why is it better than static batching?**
Scheduling happens every decode step. Finished requests leave and new ones join immediately, so no slot waits for the longest request in the batch. This keeps GPU utilisation high and improves throughput by a large factor.

**Q8. What is chunked prefill?**
Splitting a long prompt into chunks and mixing each chunk with the decode tokens of other users in the same step. It prevents a long prompt from freezing everyone else's streaming and balances compute-bound and memory-bound work in one step.

**Q9. How does speculative decoding work, and is it lossless?**
A cheap draft proposes k tokens; the target model verifies all of them in one pass and accepts the matching prefix, plus one extra token of its own. Because the target decides, the output distribution is unchanged (lossless). Speed-up comes from producing several tokens per expensive pass. It works best with high acceptance rates and low-to-medium batch sizes.

**Q10. Prefix caching: how does it work and how do you make it effective?**
KV blocks are keyed by a hash of their tokens and all previous tokens, so identical prefixes reuse stored KV and skip prefill. To benefit, put static content (system prompt, tools, documents) at the beginning and variable content at the end, and keep the prefix byte-identical.

**Q11. Tensor parallelism vs pipeline parallelism?**
Tensor splits each layer's matrices across GPUs; it lowers latency but needs an all-reduce each layer, so it needs NVLink and is used inside a node. Pipeline puts different layers on different GPUs; it needs little communication and works across nodes, but doesn't reduce single-request latency and has pipeline bubbles.

**Q12. What is disaggregated prefill/decode and when is it worth it?**
Prefill (compute-bound) and decode (memory-bound) run on separate GPU pools, with the KV cache transferred between them. It removes interference between the phases and lets you scale and tune each independently. Worth it at large scale with strict TTFT and ITL targets and fast interconnects.

**Q13. Why does a MoE model need a lot of memory even though it is "cheap" per token?**
Only the selected experts do compute for each token, so FLOPs per token follow the active parameters. But any expert might be selected, so all experts' weights must stay in memory.

**Q14. Your service has high TTFT. What do you check?**
First separate queueing delay from actual prefill time. If it's queueing, add capacity or increase throughput (batching, quantization, replicas). If prefill is slow, shorten prompts, add prefix caching, use chunked prefill, FP8, higher tensor parallelism, or disaggregation. Check whether prompts in RAG are larger than they need to be.

**Q15. Your streaming is slow (high inter-token latency). What do you check?**
That's decode. Check the batch size and KV usage (too big a batch slows each step), try quantization, speculative decoding, higher TP, or a faster GPU. Also check if long prefills are stalling decode and, if so, use chunked prefill.

**Q16. You run out of GPU memory when load increases. Options?**
Quantize weights (AWQ/FP8), quantize the KV cache, lower `max-model-len`, use a GQA/MLA model, make sure PagedAttention is on, offload KV to CPU, or add GPUs / use tensor parallelism. Remember KV cache grows with users × context length, not only the weights.

**Q17. How would you reduce LLM inference cost by 50% without changing the model quality noticeably?**
Prefix and response caching, prompt trimming and `max_tokens` limits, routing easy requests to a smaller model, FP8 or AWQ quantization (after evaluation), continuous batching with a tuned engine such as vLLM, autoscaling and spot instances, and the batch API for non-urgent work.

**Q18. Which optimizations are lossless and which are lossy?**
Lossless: FlashAttention, PagedAttention, continuous batching, chunked prefill, prefix caching, speculative decoding, parallelism, kernel fusion. Lossy: quantization, pruning, distillation, KV cache eviction/quantization, smaller models. Lossy ones need evaluation on your own task.

**Q19. How do you decide between quantizing a bigger model and using a smaller model at full precision?**
Compare on your own evaluation set at the same memory/latency budget. In general, a larger model at 4-bit tends to beat a smaller model at 16-bit with the same memory, but reasoning, math and code tasks are more sensitive to quantization, so test them.

**Q20. How would you load test and tune a vLLM deployment?**
Replay realistic prompt and output length distributions, ramp concurrency, and watch TTFT, ITL, throughput, GPU KV cache usage, queue length and preemptions. Tune `max-num-seqs`, `max-num-batched-tokens`, `gpu-memory-utilization` and `max-model-len`, and turn on prefix caching and chunked prefill. Pick the configuration with the highest throughput that still meets the p95 latency SLO.

---

## Conclusion

Inference optimization comes down to a few ideas repeated at different levels: decode is memory-bound, so read fewer bytes (quantization, GQA/MLA, compressed KV), reuse every byte for more tokens (batching, speculative decoding), avoid wasting memory (PagedAttention), avoid redoing work (prefix and response caching), split work sensibly across GPUs (TP, PP, EP, disaggregation), and cut overhead (fused kernels, CUDA graphs). Always measure first, change one thing at a time, and re-check quality after any lossy change.
