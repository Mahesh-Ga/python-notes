# Inference & Cost Reduction at High Traffic
---

> **Interview question:** *"How do you reduce high-traffic inference costs?"*
> Expect follow-ups on **response caching, streaming, quantization, and small vs large model selection**.

Related notes: [[39.llm_response_caching.md]] (cache internals), [[40.llm_parameters_tokens_and_cost.md]] (cost formula, pricing), [[28.llm_architecture.md]] (why generation is sequential), [[8. redis.md]].

---

## 1. Mental model: where does the money go?

```
cost ≈ (input tokens × in-price) + (output tokens × out-price)      # API models
cost ≈ GPU-hours × $/GPU-hour ÷ throughput (tokens/sec)             # self-hosted
```

So there are only **four levers**:

| Lever | Idea | Techniques |
|---|---|---|
| **Don't call the model** | Avoid the request entirely | Exact cache, semantic cache, rules/FAQ routing, dedupe in-flight requests |
| **Call a cheaper model** | Pay less per token | Small model, routing/cascade, distillation, fine-tuned small model |
| **Send/produce fewer tokens** | Shrink input and output | Prompt trimming, prompt caching, RAG top-k tuning, `max_tokens`, stop sequences, concise output instructions |
| **Make each GPU-second do more** | Higher throughput (self-hosted) | Quantization, continuous batching, KV-cache, speculative decoding, vLLM/TensorRT-LLM |

**Order of attack (best ROI first):** cache → route to smaller model → trim tokens → quantize/optimize serving → batch non-urgent work.

> Streaming is **not** a cost lever — it is a **latency/UX lever**. Say this explicitly in interviews (see §4).

## 2. Response caching

Detailed design lives in [[39.llm_response_caching.md]]; here is the interview-level summary.

### Three kinds of caching (don't confuse them)

| Type | What is cached | Hit condition | Saves |
|---|---|---|---|
| **Exact-match response cache** | Full final answer, keyed by hash of (model, system prompt, messages, params) | Byte-identical request | 100% of that call |
| **Semantic cache** | Full answer, keyed by *embedding* of the query | Cosine similarity ≥ threshold (e.g. 0.92–0.95) | 100% of that call, with false-positive risk |
| **Provider prompt/prefix cache** | The *KV state of the prompt prefix* (system prompt, docs, tools) | Same prefix at start of prompt | ~90% off cached **input** tokens (Anthropic cache reads ≈ 0.1× base); output still generated |

### Rules of thumb

- **Exact cache first** (cheap, zero risk), semantic second, prompt cache always for long static prefixes.
- Only cache when `temperature` is low / deterministic; otherwise the "same question" legitimately has different answers.
- **Key design:** include model name, prompt version, tool set, and params — otherwise a prompt change serves stale answers.
- **Don't cache:** user-specific/PII answers (or key them per-user/tenant), time-sensitive data, tool-call results that mutate state.
- **Invalidate** on knowledge-base update (RAG) — tag keys with a corpus/version id; short TTL for volatile topics.
- **Cache stampede:** many identical misses at once → use request coalescing (single-flight lock) so only one hits the LLM.
- **Prompt-cache layout:** put static content (system prompt, tool defs, big docs) **first**, dynamic user input **last**, or the prefix never matches.
- Track **hit rate**, **$ saved**, and **false-positive rate** (semantic) as metrics.

```python
# Cache-aside with single-flight (sketch)
def answer(req):
    key = sha256(json.dumps([MODEL, PROMPT_V, req.messages, req.params], sort_keys=True))
    if (hit := redis.get(key)): return hit
    with redis.lock(f"lock:{key}", timeout=30):          # coalesce identical misses
        if (hit := redis.get(key)): return hit
        out = llm.generate(req)
        redis.setex(key, TTL, out)
        return out
```

## 3. Small vs large model selection

**Principle:** use the *smallest model that meets the quality bar*, measured on **your** eval set — not on public benchmarks ([[38.AI evaluation.md]]).

### Price/latency gap (order of magnitude)

Within one vendor family, the small tier is typically **~5–20× cheaper** and noticeably faster than the flagship (e.g. Haiku vs Opus class). At millions of requests/day this dominates every other optimization.

### Which tasks go where

| Small / cheap model is usually enough | Large / expensive model earns its cost |
|---|---|
| Classification, intent detection, routing | Multi-step reasoning, planning |
| Extraction to a fixed JSON schema | Ambiguous or open-ended analysis |
| Summarising short text, rewriting, tagging | Complex code generation / debugging |
| FAQ / RAG answers where context is provided | Agentic tool use with many steps |
| Guardrail/moderation checks ([[52.Guardrails.md]]) | Final high-stakes answers (legal, medical, financial) |

### Patterns

1. **Routing** – a cheap classifier (or rules) sends easy queries to the small model and hard ones to the large model.
2. **Cascade / fallback** – try small first; if confidence is low (logprobs, self-check, validator fails, "I'm not sure") → escalate to large. Cost = small always + large only on the hard tail.
3. **Distillation / fine-tuning** – use the large model to generate labelled data, fine-tune a small model for one narrow task. Small fine-tuned models often match large ones on that task.
4. **Split the pipeline** – small model for retrieval/query rewrite/rerank/classification, large model only for final synthesis.
5. **Draft + verify** – small model drafts, large model reviews (cheaper than large generating everything because verification is mostly input tokens).

**Trade-offs to mention:** routing adds latency and its own error rate (a wrong route to the small model = quality drop); maintain an eval set per route and monitor escalation rate.

**Worked intuition:** 1M requests/day, 80% easy. Large-only = 1M × C_large. Routed = 1M × C_router + 0.8M × C_small + 0.2M × C_large → typically **60–75% cheaper** with near-equal quality.

## 4. Streaming responses

### What it is

Server sends tokens **as they are generated** (Server-Sent Events / chunked HTTP / WebSocket) instead of waiting for the full completion. Autoregressive models generate one token at a time anyway ([[28.llm_architecture.md]]), so streaming just exposes that.

```python
# Anthropic SDK
with client.messages.stream(model=MODEL, max_tokens=1024, messages=msgs) as s:
    for text in s.text_stream:
        yield f"data: {text}\n\n"          # SSE to the browser
```

```
Client ──POST──> API gateway ──> app (ASGI, see [[5. WSGI vs ASGI.md]]) ──stream──> LLM
   ◄── data: tok1 ... data: tok2 ... data: [DONE] ──
```

### What it buys you

| Benefit | Explanation |
|---|---|
| **Low time-to-first-token (TTFT)** | User sees output in ~0.3–1 s instead of waiting 10–30 s → feels fast |
| **Avoids timeouts** | Long generations don't hit gateway/load-balancer idle timeouts (required for large `max_tokens`) |
| **Early cancel = real savings** | If the user navigates away / hits "stop", abort the upstream request → you stop paying for unread tokens |
| **Pipeline overlap** | Start TTS, UI rendering, or downstream parsing before generation ends |

### Honest framing for interviews

- Streaming **does not reduce tokens or per-token price** → it does not cut the bill by itself.
- It cuts **perceived latency** and enables **cancellation** (indirect savings) and lets you use **slower/cheaper** model configs while staying UX-acceptable.
- Cost-adjacent: cap with `max_tokens` and `stop_sequences`, since output tokens cost ~3–5× input tokens.

### Gotchas

- **Caching + streaming:** cache the *assembled* final text; on a cache hit, *replay* it as a fake stream (chunk it) so the client code path is identical.
- **Guardrails/validation** need the full text — stream only after a cheap pre-check, or buffer + moderate by sentence/chunk ([[52.Guardrails.md]]).
- **Structured output (JSON)** can't be parsed until complete — use incremental JSON parsing or don't stream those.
- Proxies (nginx) buffer by default → disable (`proxy_buffering off`, `X-Accel-Buffering: no`).
- Handle client disconnect → propagate cancellation to the LLM call.
- Mid-stream errors can't change the HTTP status already sent — send an error event.
- Retries are harder (partial output already shown).

## 5. Quantization (self-hosted models)

### Definition

Store/compute weights (and optionally activations / KV cache) in **lower precision** — FP16/BF16 → INT8 → INT4 (or FP8) — shrinking memory and speeding up inference.

### Why it reduces cost

LLM decoding is **memory-bandwidth bound**: each token requires reading all weights from GPU memory. Fewer bytes per weight → faster tokens, and the model fits on **fewer / cheaper GPUs**.

| Precision | Bytes/param | 70B model weights | Typical impact |
|---|---|---|---|
| FP16 / BF16 | 2 | ~140 GB (2× 80GB GPUs+) | Baseline |
| INT8 / FP8 | 1 | ~70 GB (1× 80GB GPU) | Usually <1% quality loss |
| INT4 | 0.5 | ~35 GB (1× 48GB GPU) | Small-moderate loss, task-dependent |

### Types

| Kind | Notes |
|---|---|
| **PTQ** (post-training quantization) | Quantize an already-trained model with a small calibration set. Cheap, most common. Methods: **GPTQ**, **AWQ** (activation-aware, protects salient weights), **SmoothQuant**, **bitsandbytes** (LLM.int8 / NF4), **GGUF** (llama.cpp, CPU/edge) |
| **QAT** (quantization-aware training) | Simulate quantization during training/fine-tuning → better quality at very low bits, but costs training compute |
| **QLoRA** | 4-bit frozen base model + LoRA adapters → cheap *fine-tuning* |
| **Weight-only vs weight+activation** | W4A16 (weights int4, activations fp16) is common for decoding speed; W8A8 / FP8 gives compute speedups on modern GPUs |
| **KV-cache quantization** | Shrinks cache memory → longer context / more concurrent users per GPU |

### Trade-offs

- **Quality drop**, worst on math, code, long-context reasoning, and low-resource languages → **always re-run your eval set** on the quantized model.
- Outlier weights/activations are the hard part (why AWQ/SmoothQuant exist).
- INT4 gains depend on kernel support; naive quantization can even be *slower* without optimized kernels.
- Not applicable to closed APIs (you can't quantize Claude/GPT) — there the equivalent levers are model tier choice and caching.

### Related serving optimizations (mention as a bundle)

| Technique | What it does |
|---|---|
| **Continuous (in-flight) batching** | Add/remove requests per decoding step → much higher GPU utilisation (vLLM, TGI, TensorRT-LLM) |
| **PagedAttention** | Paged KV-cache memory → less fragmentation, more concurrent sequences |
| **Prefix / KV caching** | Reuse computation for shared prompts (self-hosted analogue of provider prompt caching) |
| **Speculative decoding** | Small draft model proposes tokens, big model verifies in parallel → 2–3× faster, identical output |
| **FlashAttention** | Faster, memory-efficient attention kernels |
| **Tensor/pipeline parallelism** | Split big models across GPUs (only if the model doesn't fit) |
| **Autoscaling + spot GPUs** | Scale to traffic; use cheaper interruptible capacity for batch work |

## 6. Token & request-level reductions (cheap wins)

- **Trim prompts:** shorter system prompt, drop unused few-shot examples, compress/summarise chat history (sliding window + summary).
- **RAG tuning:** retrieve fewer, better chunks (top-k 3–5 + rerank) rather than dumping 20 chunks.
- **Cap output:** `max_tokens`, `stop_sequences`, "answer in ≤ 3 sentences", structured/terse formats.
- **Batch API for offline work:** async batch endpoints are ~50% cheaper (evals, backfills, nightly classification).
- **Rate-limit & quota per user/tenant**, dedupe retries, add circuit breakers ([[18.observability_evaluation_reliability.md]]).
- **Cheap pre-filters:** regex/rules/FAQ lookup/intent classifier before the LLM; reject spam/abuse early.
- **Avoid unnecessary reasoning:** disable/lower extended-thinking budgets on simple tasks.
- **Prompt caching** for long static context (see §2).

## 7. Putting it together — reference architecture

```
Request
  │
  ├─► Rate limit / auth / dedupe
  ├─► Exact cache ──hit──► return (replay as stream)
  ├─► Semantic cache ─hit─► return
  ├─► Router (rules / small classifier)
  │      ├─ easy ─► small model (quantized, self-hosted or cheap tier) ──┐
  │      └─ hard ─► large model (prompt-cached prefix, streamed) ────────┤
  │                                                  low confidence ─────┘ (escalate)
  ├─► Guardrails / validation
  └─► Write to cache + log tokens, cost, latency, hit-rate  (observability)
```

**Monitor:** cost per request/user/feature, cache hit rate, % routed to each tier, escalation rate, TTFT, p95 latency, quality eval score. Optimise only against measured cost *and* quality — never cost alone.

## 8. Quick interview-answer summary

> "I'd attack it in order of ROI. First **don't call the model**: exact-match cache and a semantic cache with a tuned threshold, plus provider prompt caching for long static prefixes, and request coalescing to avoid stampedes. Second, **right-size the model**: route easy tasks — classification, extraction, FAQ — to a small, cheap model and escalate to the large model only when confidence is low; distil or fine-tune a small model for high-volume narrow tasks. Third, **cut tokens**: trim prompts and history, tune RAG top-k, cap `max_tokens`, and use the batch API for offline work. If we self-host, **quantize** (INT8/FP8, or INT4 with AWQ/GPTQ) so the model fits on fewer GPUs and decodes faster, and serve with continuous batching and PagedAttention via vLLM — validating quality on our eval set after each change. **Streaming** doesn't lower the token bill, but it slashes time-to-first-token, avoids timeouts, and lets us cancel generation when users leave, which saves tokens. Finally I'd track cost per request alongside quality so optimisations don't silently degrade answers."

### Common follow-up Q&A

| Question | Short answer |
|---|---|
| Does streaming reduce cost? | Not directly; improves perceived latency, avoids timeouts, enables cancellation (indirect savings). |
| Exact vs semantic cache? | Exact = safe, low hit rate; semantic = higher hit rate but false-positive risk → tune threshold, add guard checks, scope per tenant. |
| Prompt cache vs response cache? | Prompt cache saves *input* compute for shared prefixes (output still generated); response cache skips the call entirely. |
| When NOT to quantize? | Quality-critical reasoning/code tasks without an eval showing parity; no kernel support; when using closed APIs. |
| How to choose small vs large? | Build an eval set, find the cheapest model above the quality bar per task; route by difficulty; monitor escalations. |
| What breaks caching hit-rate? | Dynamic content early in the prompt (timestamps, user IDs), high temperature, unnormalised queries, prompt-version churn. |
| Biggest hidden cost? | Output tokens (priced higher) and long conversation history re-sent every turn. |
