## Module 1: RAG Fundamentals and Architecture

### 1.1 What RAG is, and the problems it solves

**RAG (Retrieval-Augmented Generation)** = instead of relying only on what an LLM memorized during training, you fetch relevant external documents at query time and feed them into the prompt as context, so generation is grounded in retrieved text.

```
User query → Retriever finds relevant chunks → Chunks + query stuffed into prompt → LLM generates answer
```

Problems it solves:

- **Knowledge cutoff** — LLM training data has a fixed cutoff; RAG lets it answer about things after that date, or about private data it never saw.
- **Hallucination** — LLMs confidently invent facts when they don't know something. Giving the model real source text to ground on reduces (doesn't eliminate) this.
- **Private/proprietary data** — you can't put internal docs/customer data into a public model's training set. RAG reasons over it without retraining.
- **Editability** — update the doc store and the very next query sees new info; no retraining cycle.
- **Attribution/citations** — because you know which chunks were retrieved, you can show "this came from doc X, page Y."

### 1.2 Core components and data flow

```
Knowledge Base (raw docs) → Loader/Chunker/Embedder → Vector Store (Retriever's index)
                                                              │
User Query ───────────────────────────────► Retriever ───────┘
                                                  │ top-k chunks
                                                  ▼
                                    Prompt = query + retrieved context
                                                  │
                                                  ▼
                                              Generator (LLM) → Answer
```

Two phases:

- **Indexing (offline)**: Load → Clean → Chunk → Embed → Store (with metadata).
- **Query (online)**: Embed query → Similarity search → (optional rerank/compress) → Build prompt → Generate.

### 1.3 RAG vs Fine-Tuning vs Prompt Engineering

| | Prompt Engineering | RAG | Fine-Tuning |
|---|---|---|---|
| Adds new **facts** | No (only what fits in-context, manually) | Yes, well suited | Poor — models don't reliably memorize new facts from a few examples |
| Adds new **behavior/style/format** | Limited (few-shot) | No | Yes, well suited |
| Update latency | Immediate (edit prompt) | Immediate (re-index doc) | Requires retraining run |
| Cost | Lowest | Medium (embedding + storage + retrieval compute) | Highest (GPU training) |
| Explainability | High | High — see source chunks | Low — black box |
| Typical combo | Used inside RAG (system prompt) | Facts | Domain tone/format, fine-tune + RAG together is common |

## Module 2: Document Processing and Chunking

### 2.1 Document Loaders in LangChain

Loaders normalize heterogeneous sources into `Document` objects (`page_content` + `metadata`).

```python
from langchain_community.document_loaders import (
    PyPDFLoader, UnstructuredPDFLoader,      # PDFs
    WebBaseLoader,                            # web pages
    CSVLoader, JSONLoader,                    # structured data
    DirectoryLoader, TextLoader,
    NotionDirectoryLoader, ConfluenceLoader,  # SaaS knowledge bases
    SQLDatabaseLoader,
)

pdf_docs = PyPDFLoader("report.pdf").load()             # 1 Document per page
web_docs = WebBaseLoader("https://example.com").load()
csv_docs = CSVLoader("data.csv").load()                  # 1 Document per row
```

- **PDFs**: `PyPDFLoader` is fast but layout-naive; scanned/complex-layout PDFs need OCR (`UnstructuredPDFLoader` with `strategy="hi_res"`) or table-aware extraction — tables don't linearize into plain text well.
- **Web**: `WebBaseLoader` (requests+bs4) for static pages; needs a headless-browser loader for JS-rendered pages.
- **Structured data**: CSV/JSON/SQL loaders usually map one row/record → one `Document`; you decide what becomes `page_content` vs `metadata`.
- **Cleaning** — strip boilerplate (nav/footers), fix encoding, normalize whitespace. Garbage in the index = garbage retrieved = garbage generated.

### 2.2 Text Splitting Strategies

| Splitter | How it works | When to use |
|---|---|---|
| `CharacterTextSplitter` | Fixed-size split on one separator (e.g. `\n\n`) | Simple baseline |
| `RecursiveCharacterTextSplitter` | Tries a separator list `["\n\n", "\n", " ", ""]` recursively — respects paragraph/sentence boundaries while hitting a size target | **Default choice** for generic text |
| Semantic chunking (`SemanticChunker`, langchain-experimental) | Embed sentences, split where embedding similarity between consecutive sentences drops (topic shift) | Higher quality, more compute-expensive |
| `MarkdownHeaderTextSplitter` | Splits on `#`/`##`/`###` headers, keeps header path in metadata | Docs sites, README-style content |
| Code splitters (`RecursiveCharacterTextSplitter.from_language`) | Splits on language-aware boundaries (function/class defs) for Python, JS, Go, etc. | Codebases |
| Parent-child / small-to-big (`ParentDocumentRetriever`) | Embed small chunks for precise retrieval, but return the larger parent chunk to the LLM | Best of both — precise match + full context, very common in production |

```python
from langchain_text_splitters import (
    RecursiveCharacterTextSplitter, MarkdownHeaderTextSplitter, Language,
)

splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000, chunk_overlap=150,
    separators=["\n\n", "\n", ". ", " ", ""],
)
chunks = splitter.split_documents(pdf_docs)

md_splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=[("#", "h1"), ("##", "h2")]
)

code_splitter = RecursiveCharacterTextSplitter.from_language(
    language=Language.PYTHON, chunk_size=800, chunk_overlap=100
)
```

### 2.3 Chunking Best Practices

**Core tension:** too small → loses surrounding context, ambiguous fragments; too large → embedding becomes a diluted average that matches queries poorly, and wastes context-window budget with irrelevant text.

- **Chunk size**: 300–800 tokens is a common starting range for prose; tune per corpus (dense technical text wants smaller chunks, narrative text can go larger).
- **Overlap**: ~10–20% of chunk size, so a fact split across a boundary still appears intact in at least one chunk.
- Chunk size interacts with everything downstream: embedding model's effective input limit, vector DB storage cost, retrieval precision, and generation prompt budget (`top_k × chunk_size` must fit).
- **Chunking is usually the highest-leverage fix** for RAG quality problems — debug retrieval before blaming the LLM's generation.

### 2.4 Metadata Management and Filtering

Attach at chunking/indexing time: source path/URL, page/section number, doc type, author, last-modified date, access-control tags (`tenant_id`, `permission_level`).

```python
for chunk in chunks:
    chunk.metadata.update({"source": "report.pdf", "dept": "finance"})
```

Used later for:
- **Metadata filtering** at query time (`vectorstore.similarity_search(query, filter={"dept": "finance"})`) — real production retrieval is almost never pure vector search, it's vector search **combined with** filters.
- **Citations** in the final answer.
- **Access control** — enforce tenant/permission filters at the retrieval layer, not just the UI, or a user's query could surface chunks from documents they shouldn't see.

## Module 3: Embeddings and Vector Representations

### 3.1 How Embeddings Work

An embedding model maps text → a fixed-length dense vector (e.g. 384/768/1536/3072-d) such that semantically similar text lands close together in vector space.

- **Training intuition**: contrastive learning — pairs of related text (question↔correct answer, paraphrases) are pulled together; unrelated pairs pushed apart.
- **Distance metrics**:(How similar vectors come close together)
  - **Cosine similarity** — measures the angle between two vectors, not their length; most common for text. (cosine_sim = (A · B) / (|A| * |B|))
  - **Dot product** — sensitive to magnitude; equivalent to cosine (cheaper) when vectors are pre-normalized.
  - **Euclidean (L2)** — straight-line distance; less common for text. useful in image embedding. (sqrt(sum((A - B)^2)))
- **Symmetric vs asymmetric** — some models are trained specifically for query↔passage matching (short question vs long passage), a different geometry than sentence-similarity models. `e5`/`bge` families use explicit prefixes: `"query: ..."` vs `"passage: ..."`.

### 3.2 Embedding Models Overview

| Model family | Type | Notes |
|---|---|---|
| OpenAI `text-embedding-3-small/large` | Closed, API | Strong general quality, cheap, 1536/3072-d (truncatable via Matryoshka) |
| Cohere `embed-v3` | Closed, API | Strong multilingual, has input-type param (`search_query` vs `search_document`) |
| `BAAI/bge-*` | Open-source | Top of MTEB leaderboard tiers, self-hostable |
| `intfloat/e5-*` | Open-source | Query/passage prefix convention |
| `sentence-transformers/all-MiniLM-L6-v2` | Open-source | Small/fast, lower quality, good for prototyping |

### 3.3 Choosing the Right Embedding Model (cost vs quality)

- **Closed API models**: no infra to run, high quality, ongoing per-token cost, data leaves your network (compliance concern).
- **Open-source self-hosted**: fixed infra cost (GPU/CPU), full data control, need to manage serving/scaling.
- **Dimensionality tradeoff**: higher dims capture more nuance but cost more storage/compute per comparison; Matryoshka-trained models let you truncate dims with graceful quality loss.
- **Must match indexing and query time** — vectors from different models live in incompatible spaces; changing embedding models means re-indexing everything.

### 3.4 LangChain Embeddings Implementation

```python
from langchain_openai import OpenAIEmbeddings
from langchain_community.embeddings import HuggingFaceEmbeddings

openai_emb = OpenAIEmbeddings(model="text-embedding-3-small")
```

## Module 4: Vector Stores

### 4.1 Indexing Strategies (IVF, HNSW)

Exact brute-force search is O(n) per query — fine for small collections, too slow at millions of vectors. Production uses **Approximate Nearest Neighbor (ANN)** indexes:

- **HNSW (Hierarchical Navigable Small World)** — graph-based, layered "express lane to local street" structure; very fast, high recall. Default in Pinecone, Weaviate, Qdrant, pgvector's HNSW mode. Tuned via `M` (graph connectivity) and `ef_search` (search breadth vs speed).
- **IVF (Inverted File Index)** — clusters vectors (k-means-like), searches only the `nprobe` nearest clusters instead of everything. Faster to build than HNSW, slightly lower recall.
- **PQ (Product Quantization)** — compresses vectors into compact codes to cut memory; often combined as **IVF-PQ** for billion-scale corpora at some recall cost.
- Classic **speed vs recall vs memory** tradeoff — tune `ef_search`/`nprobe` per system and measure recall@k on a held-out set.

### 4.2 Vector Store Operations (CRUD) in LangChain

```python
from langchain_chroma import Chroma
from langchain_community.vectorstores import FAISS, Pinecone as LC_Pinecone

# Create (index)
vs = Chroma.from_documents(chunks, embedding=openai_emb, persist_directory="./chroma_db")

# Read
results = vs.similarity_search("what is chunking?", k=4)
results_with_scores = vs.similarity_search_with_score("what is chunking?", k=4)

# Update — most stores: delete + re-add, some support in-place upsert
vs.add_documents([new_chunk])
vs.delete(ids=["chunk_123"])

# As a retriever (LCEL-composable)
retriever = vs.as_retriever(search_kwargs={"k": 5})
```

**Options**: dedicated vector DBs (Pinecone, Weaviate, Qdrant, Milvus, Chroma) vs vector-search bolted onto existing infra (`pgvector` for Postgres, OpenSearch/Elasticsearch `dense_vector`, Redis). Choice depends on scale, need for hybrid metadata filtering, existing infra, ops overhead tolerance.

## Module 5: Basic Retrieval Techniques

### 5.1 Similarity Search Fundamentals

```python
retriever = vs.as_retriever(search_type="similarity", search_kwargs={"k": 5})
docs = retriever.invoke("explain vector indexing")
```
Straight top-k nearest neighbor by cosine/dot/L2.

### 5.2 Similarity Score Thresholds

Avoid returning irrelevant chunks just to fill `k` when nothing in the corpus is actually relevant:

```python
retriever = vs.as_retriever(
    search_type="similarity_score_threshold",
    search_kwargs={"score_threshold": 0.75, "k": 5},
)
```
If no chunk clears the threshold, return nothing → lets the app say "I don't know" instead of grounding on noise.

### 5.3 Maximal Marginal Relevance (MMR)

Balances **relevance** to the query with **diversity** among results — avoids returning 5 near-duplicate chunks that all say the same thing.
helps in the diversity in the chunks
```python
retriever = vs.as_retriever(
    search_type="mmr", search_kwargs={"k": 5, "fetch_k": 20, "lambda_mult": 0.5}
)
```
`fetch_k` candidates are pulled first, then MMR greedily re-selects `k` of them trading off `lambda_mult` (1 = pure relevance, 0 = pure diversity).

### 5.4 Hybrid Search (dense + sparse/BM25)

- **Dense retrieval** — semantic matches ("car" ~ "automobile") even without shared keywords.
- **Sparse retrieval (BM25/TF-IDF)** — exact term-overlap weighted by rarity; good at IDs, error codes, acronyms, rare proper nouns that dense embeddings blur.
- **Hybrid** = run both, merge — typically via **Reciprocal Rank Fusion (RRF)**, which combines ranked lists without needing score normalization across systems. Current production best-practice default because dense/sparse fail on different query types.

```python
from langchain_community.retrievers import BM25Retriever
from langchain.retrievers import EnsembleRetriever

bm25 = BM25Retriever.from_documents(chunks)
bm25.k = 5
dense = vs.as_retriever(search_kwargs={"k": 5})

hybrid = EnsembleRetriever(retrievers=[bm25, dense], weights=[0.4, 0.6])  # RRF-based merge
```

### 5.5 Ensemble Retriever

Generalization of hybrid search — combine **any** number of retrievers (dense from different stores, sparse, metadata-filtered) with weights; LangChain's `EnsembleRetriever` fuses ranked lists via RRF under the hood.

## Module 6: Advanced Retrieval Techniques

### 6.1 Contextual Compression
(Uses the  LLM)
Initial retrieval optimizes recall (wide net); a compressor then strips each retrieved chunk down to just the sentences relevant to the query, or discards irrelevant chunks entirely — saves context budget, reduces noise fed to the generator.

```python
from langchain.retrievers import ContextualCompressionRetriever
from langchain.retrievers.document_compressors import LLMChainExtractor

compressor = LLMChainExtractor.from_llm(llm)
compression_retriever = ContextualCompressionRetriever(
    base_compressor=compressor, base_retriever=vs.as_retriever()
)
```

### 6.2 Parent Document Retriever

Index **small child chunks** for precise embedding matches, but store/return the **larger parent document** (or section) to the LLM — precise retrieval, full context at generation time.

```python
from langchain.retrievers import ParentDocumentRetriever
from langchain.storage import InMemoryStore

parent_splitter = RecursiveCharacterTextSplitter(chunk_size=2000)
child_splitter = RecursiveCharacterTextSplitter(chunk_size=400)

retriever = ParentDocumentRetriever(
    vectorstore=vs, docstore=InMemoryStore(),
    child_splitter=child_splitter, parent_splitter=parent_splitter,
)
retriever.add_documents(raw_docs)
```

### 6.3 Self-Query Retriever

The LLM parses the natural-language query into a **structured filter + a residual semantic query** (e.g. "papers about transformers published after 2020" → filter `year > 2020` + semantic search "transformers"). Requires declaring the metadata schema up front.

```python
from langchain.retrievers.self_query.base import SelfQueryRetriever
from langchain.chains.query_constructor.base import AttributeInfo

metadata_field_info = [
    AttributeInfo(name="year", description="publication year", type="integer"),
    AttributeInfo(name="dept", description="department", type="string"),
]
self_query_retriever = SelfQueryRetriever.from_llm(
    llm, vs, document_content_description="research papers", metadata_field_info=metadata_field_info
)
```

### 6.4 Multi-Query Retriever

LLM generates several rephrasings of the user's query, retrieves for each, unions/dedupes results — helps when the user's literal wording doesn't match document wording.

```python
from langchain.retrievers.multi_query import MultiQueryRetriever

mq_retriever = MultiQueryRetriever.from_llm(retriever=vs.as_retriever(), llm=llm)
```

## Module 7: Advanced RAG Patterns

### 7.1 RAG-Fusion and RRF

A specific popularized combo of Module 6's multi-query idea + RRF fusion: generate N query variants → retrieve for each → fuse ranked lists with **Reciprocal Rank Fusion** (`score = Σ 1/(rank_i + k)`)  simple and powerful algorithm used to combine multiple ranked lists of search results into a single, unified ranking9

9

### 7.2 HyDE (Hypothetical Document Embeddings)

Instead of embedding the raw (often short/underspecified) query, ask the LLM to first generate a **hypothetical answer**, then embed *that* and search with it. Works because a hypothetical answer is closer in vector space to a real answer passage than a short question is — questions and answers have different "shapes" in embedding space.

```python
from langchain.chains import HypotheticalDocumentEmbedder

hyde_embeddings = HypotheticalDocumentEmbedder.from_llm(llm, openai_emb, prompt_key="web_search")
hyde_vs = Chroma(embedding_function=hyde_embeddings, persist_directory="./chroma_db")
```

### 7.3 Corrective RAG (CRAG)

After retrieval, an evaluator (LLM or lightweight classifier) grades each chunk's relevance:
- **Correct** → use as-is, maybe strip noise.
- **Ambiguous** → refine (e.g. decompose/recompose knowledge strips) before use.
- **Incorrect** → discard, fall back to an external source (e.g. web search) instead of feeding bad context to the generator.

### 7.4 Self-RAG

The model is trained/prompted to emit special reflection tokens as it works: whether retrieval is needed at all, whether each retrieved passage is relevant, and whether its own generated sentence is actually supported by the passage — self-critique baked into the generation loop rather than a separate offline eval step.

### 7.5 Graph RAG

Build a knowledge graph (entities + relationships) from the corpus (see Neo4j notes) and retrieve via **graph traversal / community summaries** instead of pure vector similarity. Better for multi-hop relational questions or corpus-wide synthesis ("what are the main themes across all documents") that chunk retrieval handles poorly, since no single chunk contains the "global" answer.

### 7.6 Multimodal RAG

Extend retrieval beyond text: embed images (CLIP-style joint text-image embedding space) or use a multimodal LLM to caption images/tables into text at indexing time so they become retrievable alongside text chunks. Retrieved images can also be passed directly to a multimodal generator model.

## Module 8: Agentic RAG with LangGraph

### 8.1 Introduction to Agentic RAG

Plain RAG is one fixed retrieve-then-generate pass. **Agentic RAG** lets an LLM agent decide *whether* to retrieve, *what* to query for, issue multiple retrieval rounds, call different tools/indexes, and reflect on whether retrieved info actually answers the question before responding. Handles multi-hop questions a single pass can't (e.g. "compare X's revenue in 2023 vs 2024" needs two lookups).

### 8.2 RAG as a Tool for Agents

Wrap the retriever as a callable tool; the agent decides when to invoke it (vs answering directly, vs calling another tool).

```python
from langchain_core.tools import tool

@tool
def search_knowledge_base(query: str) -> str:
    """Search internal docs for information relevant to the query."""
    docs = retriever.invoke(query)
    return "\n\n".join(d.page_content for d in docs)

tools = [search_knowledge_base]
```

### 8.3 LangGraph Fundamentals for RAG

- **State** — a typed dict/`TypedDict`/Pydantic model threaded through the graph, e.g. `{question, documents, generation, retry_count}`.
- **Nodes** — plain functions `state -> partial_state_update` (retrieve, grade_documents, generate, rewrite_query).
- **Edges** — normal (`A -> B`) or **conditional** (route based on state, e.g. "if no relevant docs, go to rewrite_query, else go to generate").
- **Checkpointing** — persist state after each node (e.g. `MemorySaver`, or a DB-backed saver) so runs are resumable, support human-in-the-loop interrupts, and enable multi-turn memory keyed by `thread_id`.

```python
from typing import TypedDict, List
from langgraph.graph import StateGraph, END
from langgraph.checkpoint.memory import MemorySaver

class RAGState(TypedDict):
    question: str
    documents: List[str]
    generation: str

def retrieve(state: RAGState):
    docs = retriever.invoke(state["question"])
    return {"documents": [d.page_content for d in docs]}

def grade_documents(state: RAGState):
    relevant = [d for d in state["documents"] if is_relevant(state["question"], d)]  # LLM-graded
    return {"documents": relevant}

def generate(state: RAGState):
    answer = llm.invoke(build_prompt(state["question"], state["documents"]))
    return {"generation": answer.content}

def route(state: RAGState):
    return "generate" if state["documents"] else "rewrite_query"

graph = StateGraph(RAGState)
graph.add_node("retrieve", retrieve)
graph.add_node("grade_documents", grade_documents)
graph.add_node("generate", generate)
graph.set_entry_point("retrieve")
graph.add_edge("retrieve", "grade_documents")
graph.add_conditional_edges("grade_documents", route, {"generate": "generate", "rewrite_query": "retrieve"})
graph.add_edge("generate", END)

app = graph.compile(checkpointer=MemorySaver())
result = app.invoke({"question": "what is HNSW?"}, config={"configurable": {"thread_id": "session-1"}})
```

### 8.4 Agentic RAG Design Patterns

- **ReAct (Reason + Act)** — agent alternates thought → tool call → observation → thought, looping until it decides it has enough to answer. LangGraph ships a prebuilt `create_react_agent`.
- **Plan-and-execute** — a planner LLM first decomposes the task into an explicit multi-step plan (e.g. "1. retrieve X, 2. retrieve Y, 3. compare"), then an executor works through the steps, replanning if a step fails — more token-efficient and predictable than pure ReAct for multi-hop tasks, at the cost of upfront planning latency.
- **Reflection** — after generating an answer, a critique step (self or separate LLM call) checks it against the retrieved context/grading criteria and triggers a retry/refinement loop if it fails — this is the mechanism behind Self-RAG/CRAG-style correction implemented as an explicit graph loop.

## Module 9: RAG Evaluation through RAGAS

### 9.1 What RAGAS is

An open-source framework for **reference-free, LLM-judged evaluation** of RAG pipelines — instead of exact-string-match against a fixed answer, an LLM judge scores qualities like faithfulness and relevance, since there's rarely one "correct" answer string for open-ended generation.

### 9.2 Parts of the RAG pipeline to evaluate

RAG has two failure surfaces — evaluate them **separately** to know what to fix:

1. **Retrieval** — did the retriever surface the right (and only the right) chunks?
2. **Generation** — given those chunks, did the LLM produce a faithful, relevant answer?

### 9.3 RAG metrics in detail

| Metric | Surface | Question it answers | Needs ground-truth? |
|---|---|---|---|
| **Context Precision** | Retrieval | Of the retrieved chunks, how many were actually relevant (and ranked high)? | Optional (reference-free variant exists) |
| **Context Recall** | Retrieval | Of the chunks needed to answer, how many were retrieved? | Yes (reference answer) |
| **Context Entity Recall** | Retrieval | Did retrieved context cover the key entities in the reference answer? | Yes |
| **Faithfulness** | Generation | Is every claim in the generated answer supported by the retrieved context (groundedness / hallucination check)? | No |
| **Answer Relevancy** | Generation | Does the answer actually address the question asked (penalizes faithful-but-off-topic)? | No |
| **Answer Correctness** | Generation | Semantic + factual match of the answer vs a reference answer | Yes |
| **Answer Similarity** | Generation | Embedding similarity between generated and reference answer | Yes |

### 9.4 Code implementation of individual metrics

```python
from ragas.metrics import faithfulness, answer_relevancy, context_precision, context_recall
from ragas.dataset_schema import SingleTurnSample
import asyncio

sample = SingleTurnSample(
    user_input="What indexing strategy does Pinecone default to?",
    response="Pinecone defaults to HNSW for approximate nearest neighbor search.",
    retrieved_contexts=["Pinecone uses HNSW as its default ANN index for fast, high-recall vector search."],
    reference="Pinecone's default ANN index is HNSW.",
)

score = asyncio.run(faithfulness.single_turn_ascore(sample))
```

### 9.5 Code implementation of the RAG pipeline using `evaluate()` API

```python
from datasets import Dataset
from ragas import evaluate
from ragas.metrics import (
    faithfulness, answer_relevancy, context_precision, context_recall,
)

eval_dataset = Dataset.from_dict({
    "question": ["What is HNSW?", "What does BM25 optimize for?"],
    "answer": [rag_answer_1, rag_answer_2],                # generated by your pipeline
    "contexts": [retrieved_chunks_1, retrieved_chunks_2],   # list[list[str]]
    "ground_truth": [ref_answer_1, ref_answer_2],
})

results = evaluate(
    eval_dataset,
    metrics=[faithfulness, answer_relevancy, context_precision, context_recall],
)
print(results.to_pandas())
```

Run this over a golden Q&A set on every pipeline change (chunking, retriever, prompt) to catch regressions — treat it like a test suite, not a one-off report.

## Module 10: Capstone Project with Deployment

### 10.1 Project shape: production-ready RAG system

- **Multi-document ingestion** — pipeline that loads/chunks/embeds heterogeneous sources (PDF, web, structured), keeps the index in sync with source-of-truth (scheduled re-index or event-driven on write).
- **Hybrid retrieval with re-ranking** — dense + BM25 (`EnsembleRetriever`) as first-stage recall, cross-encoder reranker (Cohere Rerank / `bge-reranker`) as second-stage precision, so you can cast a wide net cheaply then re-score accurately.
- **Agentic workflow with LangGraph** — retrieve → grade → (rewrite/retry loop) → generate → (reflect) graph, with checkpointing for resumability and multi-turn memory.
- **Evaluation suite (RAGAS) + Monitoring (LangSmith)** — RAGAS on a golden set for pipeline-level regression testing; LangSmith for tracing individual runs in production (see which chunks were retrieved, latency per node, token cost per call).
- **System deployment** — package retriever + generator behind an API (FastAPI is the natural fit given LangChain's Python-first ecosystem), vector store as a managed service or self-hosted with persistence, async ingestion workers for indexing.

### 10.2 Production RAG concerns

- **Pipeline optimization** — parallelize independent steps (embed query while doing keyword search; batch-embed at index time); cache aggressively (below).
- **Caching strategies**:
  - **Exact-match cache** — same query string → cached answer (cheap, low hit rate for varied phrasing).
  - **Semantic cache** — cache keyed by embedding similarity to prior queries (e.g. GPTCache) — higher hit rate, needs a similarity threshold tuned to avoid stale/wrong cache hits.
  - **Embedding cache** — avoid re-embedding identical/unchanged chunks on re-index.
- **Cost optimization** — smaller/open embedding models where quality allows, retrieve fewer but higher-precision chunks (rerank hard), cache generation for repeated queries, truncate/compress context before generation.
- **Monitoring and debugging** — trace retrieval (what was retrieved, at what score) separately from generation (what was said, was it faithful) — LangSmith or custom tracing; track retrieval-quality and faithfulness metrics over time in production, not just at eval time, to catch corpus/query drift.
- **Common pitfalls and solutions**:
  - Bad chunking → most quality issues trace here first; debug retrieval before blaming generation.
  - Stale index → define a sync strategy (real-time vs scheduled batch) based on freshness requirements.
  - "Lost in the middle" → don't just cram in more chunks with big context windows; order/rerank still matters — put the most relevant chunk first/last, not buried.
  - Over-retrieval → more chunks ≠ better answer if they dilute relevant signal; tune `top_k` against eval metrics, not intuition.
  - No refusal path → a well-built system should say "I don't know" when retrieval is empty/irrelevant (score-threshold retrieval + explicit prompt instruction), rather than fabricate.
- **Security and compliance**:
  - **Access control at the retrieval layer** — enforce tenant/permission metadata filters in the vector search itself, not just at the UI, or a query can surface chunks a user shouldn't see.
  - **PII handling** — redact/mask sensitive fields before indexing, or tag and filter them at retrieval time.
  - **Data residency** — matters when choosing API-based vs self-hosted embedding/generation models, since API calls send data off-network.
  - **Prompt injection via retrieved content** — untrusted documents in the knowledge base could contain instructions aimed at hijacking the generator; treat retrieved context as data, not instructions, and constrain the system prompt accordingly.
