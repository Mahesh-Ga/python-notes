Option A: PO → SO Automation (recommend if they want business impact)

Situation: CSRs(Customer Service Representatives) were manually matching incoming Purchase Orders against catalog/pricing data to raise Sales Orders — slow and error-prone at volume.

My contribution: I built the service end-to-end — ingestion of incoming POs, a matching engine that validates and scores line items against catalog/pricing data, and a confidence-scoring layer. Orders above a tuned threshold auto-promote to Sales Orders; below-threshold ones route to a human for review.

Tech stack: Python, FastAPI (API layer), Celery (async matching/scoring jobs), PostgreSQL (catalog/pricing/order data), Redis (job state/caching), Docker + Azure (deployment).

Data model (Postgres): `purchase_orders`, `po_line_items`, `catalog_items`, `pricing_rules`, `match_results` (per-line + aggregate score, matched catalog id, reasons), `sales_orders`, `review_queue` — the audit trail (raw PO → match result → final SO) is kept end-to-end so any auto-promoted order can be traced back to the scoring decision that produced it.

Deployment: containerized FastAPI + Celery worker services on Azure (e.g., AKS or App Service + Container Apps), horizontally scaled workers to absorb PO volume spikes independent of the API tier; Redis and Postgres as managed Azure services.

Key design decisions to mention:

- Celery for async processing so PO ingestion doesn't block on matching latency.
