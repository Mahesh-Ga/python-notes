# Worked System Design Example — URL Shortener (bit.ly)

> Applies the Part 4 framework from `22.system_design.md` (§1.13): requirements → estimation → API → high-level design → deep dive → tradeoffs. This example is read-dominant and single-entity, which makes it the classic "warm-up" system design question — the interesting parts are the encoding scheme, the redirect hot path, and cache design, not distributed transactions.

---

## 1. Requirements

**Functional:**
- Given a long URL, generate a short URL (e.g. `https://bit.ly/abc123`).
- Given a short URL, redirect the client to the original long URL.
- Optionally: user-chosen custom aliases, expiration dates, click analytics.

**Non-functional (drives every later decision):**
- **Read-heavy**: redirects vastly outnumber creations — realistically 100:1 or higher (a link is created once, clicked many times).
- **Low latency on redirect** — this is on the critical path of someone's click; every extra millisecond is felt directly.
- **High availability** — a broken redirect service breaks every link shared anywhere; availability matters more than strong consistency here.
- **Uniqueness** — two different long URLs must never collide on the same short code.
- **Short codes should not be easily guessable/enumerable** (avoid leaking how many links exist or letting someone scan sequential IDs).

## 2. Back-of-envelope estimation

- 100M new URLs/month → ~40 writes/sec average.
- Read:write ratio 100:1 → ~4,000 redirects/sec average, design for 10x peak ≈ 40,000/sec.
- Storage: 100M URLs/month × 5 years × ~500 bytes/record (short code + long URL + metadata) ≈ 6B records × 500B ≈ 3TB — large but a single well-indexed key-value store handles this fine; no need to over-shard on day one.
- Short code space: with a 7-character code over a 62-character alphabet (`[a-zA-Z0-9]`), `62^7` ≈ 3.5 trillion combinations — comfortably covers the 6B-record estimate with huge headroom.

**Conclusion from the math**: this is a **read-heavy key lookup problem**, not a complex-relationship problem — the right shape is a key-value store with a cache in front, not a relational schema with joins. The interesting engineering is entirely in (a) how the short code is generated without collision and (b) making the redirect path as fast as possible.

## 3. API design

```
POST /api/v1/shorten
  body: { "long_url": "https://example.com/very/long/path", "custom_alias": "optional", "expires_at": "optional" }
  → { "short_url": "https://bit.ly/abc123" }

GET /{short_code}
  → 301/302 redirect to the long URL
```

**301 (permanent) vs 302 (temporary) redirect**: 302 is usually preferred despite being "less correct" for a permanent-looking link — a 301 gets cached by the browser, so subsequent clicks never hit the server again, which kills click-analytics visibility. 302 keeps every click observable server-side, at a small latency cost.

## 4. High-Level Architecture

```
Client ──HTTPS──► Load Balancer (L7) ──► API Gateway (rate limiting, auth) ──┐
                                                                                │
                                    ┌───────────────────────────────────────────┼───────────────────┐
                                    ▼                                                                 ▼
                          ┌──────────────────┐                                            ┌──────────────────┐
                          │  Shorten Service  │                                            │  Redirect Service │
                          │  (write path)     │                                            │  (read/hot path)  │
                          └─────────┬─────────┘                                            └─────────┬─────────┘
                                    │                                                                 │
                          ┌─────────▼─────────┐                                            ┌──────────▼─────────┐
                          │  ID Generator      │                                            │  Redis Cache        │
                          │  (unique code gen) │                                            │  (short_code → URL) │
                          └─────────┬─────────┘                                            └──────────┬──────────┘
                                    │                                                                  │

                          ┌────────────────────────────────────────────────────────────────────────────┐
                          │              Key-Value Store (short_code → long_url, metadata)                │
                          │              e.g. DynamoDB / Cassandra, replicated                             │
                          └────────────────────────────────────────────────────────────────────────────┘
                                                          │
                                                          ▼
                                              ┌──────────────────────┐
                                              │  Analytics pipeline   │
                                              │  (async, Kafka →      │

```

Two logically separate services (Shorten vs Redirect) because they have **completely different scaling and latency profiles** (§3.3 of the architecture notes — split along real boundaries): Redirect must be blazing fast and horizontally scaled way out; Shorten is low-volume and can afford slightly more work per request (uniqueness checks, custom alias validation).

## 5. Deep Dive: Generating the Short Code

This is the one genuinely hard part of the problem — three real approaches, with real tradeoffs.

**Option A — Hash the long URL (e.g. MD5/SHA-256), take the first 7 characters (base62-encoded)**
- Simple, and deterministic (same long URL → same short code, which can be a feature: dedupes reshortening the same link).
- **Collision risk**: truncating a hash to 7 chars means two different URLs can produce the same code. Must check the KV store for that code on write and, on collision, retry with a different slice/salt.
- Downside: collision-check-and-retry adds latency and complexity to every write, and gets worse as the table fills up.

**Option B — Auto-incrementing counter, base62-encode the counter value**
- A global counter (e.g. a dedicated counter service, or a range of IDs pre-allocated to each app server to avoid a single contended counter) is incremented on each new URL; the resulting integer is base62-encoded into a short code.
- **No collisions possible by construction** — huge simplification vs Option A.
- Downside: sequential codes are guessable/enumerable (someone could scan `1, 2, 3...` and discover every link ever created) — mitigate by pre-shuffling the ID space (e.g. XOR/permute the counter through a reversible bijective function before encoding) so codes look random without needing a uniqueness check.
- This is the approach real systems (e.g. the classic Bitly/TinyURL designs) most commonly converge on, specifically because it eliminates collision handling from the hot write path.

**Option C — Pre-generated random code pool**
- A background worker continuously generates random unused 7-character codes and pushes them into a queue/pool; the Shorten Service simply pops a ready-to-use code off the pool instead of computing anything at request time.
- Fastest possible write path (no compute, no collision check at request time — that work happened earlier, offline).
- Downside: extra moving part (the generator + a queue/store for the pool) and needs monitoring so the pool never runs dry under a write burst.

**Chosen approach: Option B (counter + base62 + bijective shuffle)** — it has the best latency/complexity tradeoff: zero collision risk by construction, no extra background service to run, and the enumeration risk is fully solved by the reversible-permutation trick rather than by adding a runtime uniqueness check.

```
counter (int64, globally unique) → permute(counter) → base62_encode(permuted) → "abc123Z"
```

- **Base62** (`0-9a-zA-Z`) is chosen over base64 to keep short codes URL-safe without needing to escape `+`/`/`.
- Counter uniqueness at scale: don't use one single DB row as the counter (that's a write bottleneck/hot key, §1.12 of the notes) — instead, pre-allocate ID ranges to each app server (e.g. server claims IDs 1,000,000–1,000,999 from a coordination service, then hands them out locally without a network round trip per request) — the same "range allocation" trick used by Snowflake-style ID generators.

## 6. Deep Dive: The Redirect Path (the hot path)

This is the path that must be fast at 40,000+ req/sec peak, so every layer is optimized for reads:

1. Request hits the Redirect Service for `GET /abc123`.
2. **Check Redis cache first** (cache-aside, §1.4) — key `short_code`, value `long_url`. Cache hit → immediate 302, done in low single-digit milliseconds.
3. On a cache miss, read from the KV store, populate the cache (TTL, e.g. 24h), then redirect.
4. **Click event** is NOT recorded synchronously in the request path — it's fired asynchronously onto a Kafka topic (`fire-and-forget` from the caller's perspective) and processed by a separate analytics pipeline. Recording clicks synchronously in the DB would put a write on the critical path of every single redirect, which defeats the entire purpose of optimizing this path for reads.

**Why Redis over an in-process cache**: the Redirect Service is horizontally scaled across many stateless instances behind the load balancer — a shared Redis cache means a URL that becomes viral gets cached once and benefits every instance, instead of each instance independently paying the cache-miss cost.

**Cold URLs / long tail**: most of the 3TB of stored links are rarely clicked (long tail) — Redis doesn't need to (and can't affordably) hold all 6B records, only the working set of recently/frequently accessed codes. This is exactly what an LRU eviction policy (§1.4) is for — hot links stay cached, the long tail falls out naturally.

## 7. Data Model

**Key-value store** (DynamoDB / Cassandra) chosen over a relational DB because the access pattern is a pure key lookup with no joins or relational queries needed — this is precisely the case NoSQL key-value modeling is built for (§2.7: model around the access pattern, not the data's inherent structure).

```
short_code (partition key) → {
  long_url: string,
  created_at: timestamp,
  expires_at: timestamp | null,
  user_id: string | null,
  click_count: int   -- denormalized, eventually-consistent, updated async from the analytics pipeline
}
```

- `click_count` is a deliberately denormalized, eventually-consistent field (same pattern as `stock_hint` in the e-commerce example, `23.system_design_case_study_ecommerce.md` §5) — exact real-time accuracy isn't needed; a dashboard that's a few seconds behind is completely fine.
- Partitioning by `short_code` itself (hash-based, §1.6) distributes load evenly across the cluster since short codes are already effectively random (thanks to the permutation step in §5) — no hot-partition risk from a viral link, since one code always maps to exactly one partition regardless of its popularity (the **cache**, not the partition layout, is what absorbs a hot link's read volume).

## 8. Consistency & CAP Tradeoffs

| Component | Chosen model | Why |
|---|---|---|
| URL creation (write) | Strong consistency | A just-created short link must resolve correctly immediately — the creator will likely test it right away. |
| Redirect (read) | Eventual consistency acceptable | Serving a cached long_url that's a few seconds stale (e.g. after an admin edits a custom alias) is a fine tradeoff for redirect speed. |
| Click analytics | Eventual consistency (AP) | Async pipeline, dashboard lag of seconds/minutes is completely acceptable. |

Per §1.7/§9-style reasoning from the e-commerce example: this system leans **AP** overall (availability over consistency) because the cost of a stale-but-working redirect is near-zero, while the cost of the redirect service being *unavailable* is that every shared link everywhere breaks — a much worse failure mode to optimize against.

## 9. Scaling & Failure Handling

- **Redirect Service**: stateless, scales horizontally behind the load balancer trivially — this is the layer to over-provision, since it's the highest-QPS, most latency-sensitive component.
- **Rate limiting** (§1.11, token bucket) on the Shorten endpoint specifically — prevents abuse (spam link generation, scraping the ID space).
- **CDN/edge redirect** (optional, at very large scale): for extremely popular short links, the redirect mapping itself could be pushed to edge locations so the redirect happens before the request ever reaches the origin — the same principle as CDN-cached static assets in the e-commerce example, applied to a dynamic-but-effectively-static mapping.
- **SPOF avoidance** (§1.12): Redis runs as a replicated cluster (a cache-layer outage should degrade to "slower redirects via KV store," not "site down"); the KV store itself runs multi-node/multi-AZ by construction (DynamoDB/Cassandra are built for this).
- **Custom alias collisions**: unlike the counter-generated path, a user-requested custom alias *does* need an explicit uniqueness check against the KV store at write time (unavoidable — the whole point is the user picks the value) — but this only affects the low-volume write path, not the hot redirect path.

## 10. What changes at 10x / 100x scale

- **10x**: current design mostly holds — add Redis cluster capacity and Redirect Service instances; the KV store's built-in horizontal scaling absorbs the extra data volume.
- **100x**: ID-range pre-allocation (§5) needs larger, more frequently replenished ranges per server to avoid coordination-service contention; the analytics pipeline's Kafka partition count needs revisiting so click-event processing doesn't lag; a CDN-edge-redirect layer (§9) likely graduates from "optional" to "necessary" for the small set of extremely viral links that would otherwise concentrate huge read volume on a handful of cache keys.

---

**How to use this in an interview**: this question is often used as a filter for whether a candidate defaults to over-engineering (jumping straight to sharding/microservices for what is fundamentally a single-table key-value lookup) — the strongest answers keep the core system simple and put all the depth into the ID-generation scheme (§5) and the read-path optimization (§6), since that's where the actual design decisions live.
