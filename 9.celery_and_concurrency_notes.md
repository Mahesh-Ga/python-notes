# Detailed Notes: Background Jobs (Celery) & Concurrency Models / GIL

---

Celery is a task queue that helps manage and execute background tasks in a distributed environment.

## 11. Background Jobs & Task Queues (Celery)

### 11.1 Why background jobs exist
A web request should return fast. Anything slow, unreliable, or bursty (sending email, calling an LLM, generating a PDF, calling a flaky third-party API, running a matching algorithm over thousands of rows) gets pulled out of the request/response cycle and handed to a worker running elsewhere. The API just needs to enqueue the job and return a `202 Accepted` (or a task ID the client can poll).

### 11.2 Architecture: Producer → Broker → Worker → Result Backend

```
[FastAPI/Flask app]  --publish task-->  [Broker (Redis/RabbitMQ)]  --pull-->  [Celery Worker pool]
      (producer)                                (queue)                          (consumer)
                                                                                       |
                                                                                       v
                                                                          [Result Backend (Redis/DB)]
```

- **Producer**: your web app (or another service) calls `task.delay(...)` / `task.apply_async(...)`. This serializes the task name + args and pushes a message onto a queue in the broker. The producer does NOT execute the task.
- **Broker**: a message queue (Redis or RabbitMQ most commonly). Its only job is to hold messages until a worker is ready to consume them. RabbitMQ gives you proper AMQP semantics (ack/nack, exchanges, routing keys, priority queues). Redis is simpler and often already in your stack, but weaker delivery guarantees.
- **Worker**: a separate process (or pool of processes/threads) running `celery -A app worker`, polling the broker, executing the task function, and optionally writing the result somewhere.
- **Result backend**: where the return value / status of a task is stored (Redis, a DB, RPC). Optional — if you never call `.get()` or check `.status`, you don't need one, and skipping it reduces load.

Key mental model: **the producer and worker do not share memory or process space.** Everything that crosses the boundary must be serialized (JSON/pickle) — so task args must be simple, serializable values (IDs, primitives), never live objects/DB sessions/open file handles.

### 11.3 Retry policies with exponential backoff
Naive retries hammer a failing dependency and can cause a "retry storm" that takes down an already-struggling service. The fix: exponential backoff, ideally with jitter.

```python
from celery import Task
from celery.utils.log import get_task_logger

logger = get_task_logger(__name__)

@app.task(
    bind=True,
    autoretry_for=(ConnectionError, TimeoutError),
    retry_backoff=True,       # exponential: 1s, 2s, 4s, 8s...
    retry_backoff_max=600,    # cap the wait
    retry_jitter=True,        # randomize to desynchronize retries across tasks
    max_retries=5,
)
def call_external_api(self, payload_id: str):
    try:
        result = external_client.call(payload_id)
    except (ConnectionError, TimeoutError) as exc:
        raise self.retry(exc=exc)
    return result
```

- `retry_backoff=True` → Celery add waiting period `2^retry_count` seconds before retrying after task fails.
- `retry_jitter=True` → adds randomness so 1000 failed tasks don't all retry at the exact same second (the "thundering herd").
- Only retry on **transient** errors (network, timeout, 5xx). Never retry on **permanent** errors (validation failure, 4xx, malformed input) — that just wastes worker cycles and delays failure visibility.

### 11.4 Task idempotency — the most important interview topic here
**A task may run more than once.** This isn't a hypothetical — it's a guarantee you must design for,

**Idempotency = running the task N times has the same effect as running it once.**

Techniques used in practice (this maps directly to the PO→SO and Document Classification services mentioned in the main notes):

- **Idempotency key / natural key check**: before doing the side effect, check if a record for this operation already exists (e.g., `SELECT ... WHERE po_id = ? AND so_id = ?`) and short-circuit if so.
  ```python
  @app.task(bind=True)
  def match_po_to_so(self, po_id: str):
      if MatchResult.objects.filter(po_id=po_id, status="completed").exists():
          logger.info("Match already completed for %s, skipping", po_id)
          return
      # ... do the matching work, write result with a unique constraint on po_id
  ```
- **Unique DB constraints**: let the database reject the duplicate insert (`UNIQUE(po_id)`), and catch the `IntegrityError` as a no-op rather than a failure.
- **Upserts instead of inserts**: `INSERT ... ON CONFLICT DO UPDATE` (Postgres) so re-running converges to the same state instead of creating duplicates.
- **Idempotency keys passed by the caller**: for API-triggered tasks, the caller supplies a UUID; the task uses it as a dedup key stored in Redis/DB with a TTL — if seen before, skip.
- **Make side effects idempotent themselves**: e.g., "set status to CLASSIFIED" is idempotent; "append to a list" or "increment a counter" is NOT — prefer the former pattern.
- **Avoid non-idempotent external calls without a dedup key**: e.g., sending an email — pass a client-generated idempotency key to the email provider if it supports one, or check a "sent" flag first.

### 11.5 Dead-letter handling
When a task fails repeatedly (exhausts `max_retries`), you don't want it silently disappearing or endlessly clogging the queue. Standard pattern: route it to a **dead-letter queue (DLQ)**.

- In RabbitMQ: configure `x-dead-letter-exchange` on the queue so rejected/expired messages are automatically routed to a DLQ.
- In Celery generically (broker-agnostic): catch the final failure in an `on_failure` handler and persist it somewhere durable (a `failed_tasks` table, or a dedicated Celery queue) for manual inspection/replay.

```python
class BaseTaskWithDLQ(Task):
    def on_failure(self, exc, task_id, args, kwargs, einfo):
        FailedTask.objects.create(
            task_name=self.name,
            task_id=task_id,
            args=args,
            kwargs=kwargs,
            error=str(exc),
            traceback=str(einfo),
        )

@app.task(base=BaseTaskWithDLQ, bind=True, max_retries=3)
def classify_document(self, doc_id: str):
    ...
```

A DLQ gives you: visibility (alert when it grows), and replay-ability (fix the bug, then reprocess the dead-lettered tasks instead of having lost them).

### 11.6 Avoiding long-running tasks blocking the worker pool
Celery workers typically run a fixed-size pool (prefork = N processes, or threads/gevent for I/O-bound work). If a task blocks for a long time:

- **Head-of-line blocking**: with `prefork` and `-c 4` (4 worker processes), one task that takes 10 minutes ties up one of only 4 slots — throughput for everything else drops.
- **Mitigations**:
  - **Separate queues by task type/duration** and route long tasks to a dedicated worker pool so they don't starve fast tasks. `task_routes` in Celery config lets you send `slow.*` tasks to a `slow` queue with its own workers.
  - **Set `task_time_limit` / `task_soft_time_limit`** so a runaway task is killed (soft limit raises a catchable exception first; hard limit kills the process) instead of hanging forever.
  - **Break large tasks into smaller chained/chunked tasks** (Celery `chain`, `chord`, `group`) so no single task monopolizes a worker for too long, and partial progress isn't lost on failure.
  - **Use `acks_late` + `prefetch_multiplier=1`** for long/critical tasks so a worker doesn't grab a big batch of tasks upfront and sit on them (this also improves fairness across workers) — but note `acks_late` interacts with idempotency: if the worker dies mid-task, the task gets redelivered, which is exactly why idempotency (11.4) matters here.
  - For CPU-bound long tasks, consider whether they even belong in the same worker pool as I/O-bound tasks — see the GIL section below for why.

### 11.7 Other practical failure modes worth knowing
- **Broker connection loss**: workers should reconnect automatically (`broker_connection_retry_on_startup`); tasks queued while the broker is down are simply not accepted (producer needs its own retry/backoff on `.delay()`).
- **Result backend growth**: if you don't set `result_expires`, results accumulate forever in Redis/DB — set a TTL.
- **Late binding of task state**: don't rely on a task "knowing" data that could have changed since it was enqueued — always re-fetch fresh state (e.g., re-read the PO row) rather than trusting stale data passed at enqueue time, since the task might run seconds or hours later.
- **Poison messages**: a malformed task payload that always throws (e.g., bad serialization) will retry forever unless retries are capped — always cap `max_retries` and route to DLQ.

## 12. Concurrency Models & the GIL

### 12.1 What the GIL actually is
- GIL = Global Interpreter Loc.  It's inside CPython.
- CPython is the default Python you install from python.org. Inside it, every Python object has a counter: reference count. When count goes to 0, Python frees the memory
- If two threads updated the same counter at the exact same time, you'd corrupt memory and crash Python.
-  proper fix would be to put a tiny lock on every object. That would be slow and complex.
- The cheap fix the CPython creators chose in 1990: Put ONE big lock around the whole interpreter.
- Only one thread can execute Python bytecode at a time.
- This is ONLY a CPython problem. Jython, PyPy, and Python 3.13t [free-threaded / no-GIL build] don't have it.

### 12.2 When threads still help: I/O-bound work
- The GIL is released when a thread is doing nothing.
- The GIL is released during blocking I/O (network calls, disk reads, `time.sleep`, most DB driver calls). So while one thread is waiting, another thread can acquire the GIL and run.

This is why threads (or a thread pool, `concurrent.futures.ThreadPoolExecutor`) are a perfectly good tool for **I/O-bound** work: many concurrent HTTP calls, DB queries, file reads. Wall-clock time drops close to the slowest single call, not the sum of all calls.

### 12.3 When threads don't help: CPU-bound work
```python
def cpu_heavy(n):
    total = 0
    for i in range(n):
        total += i * i
    return total
```
Running this in multiple threads doesn't speed it up — they fight over the single GIL and you get roughly the same (or worse, due to context-switch overhead) wall-clock time as running it sequentially. This is the classic interview trap: "why doesn't adding threads speed up my number-crunching function?"

Context switching means the CPU pauses one thread/process and starts running another, while saving enough information to later continue the first one.
context switching is not possible in multiprocessing
### 12.4 `multiprocessing` — sidestepping the GIL
Each process gets its own Python interpreter and its own GIL, so processes genuinely run in parallel across cores.

```python
from multiprocessing import Pool

def cpu_heavy(n):
    return sum(i * i for i in range(n))

if __name__ == "__main__":
    with Pool(processes=4) as pool:
        results = pool.map(cpu_heavy, [10_000_000] * 4)
```

Tradeoffs vs. threads:
- **No shared memory by default** — data passed between processes is pickled and copied (or you use `multiprocessing.shared_memory`, `Value`/`Array` for explicit shared state). This has real serialization overhead, so it's only worth it when the CPU work per task outweighs the copy cost.
- **Higher memory footprint** — each process has its own full Python interpreter + imported modules.
- **Slower startup** — spawning a process is much heavier than spawning a thread.
- This is exactly the model Celery's `prefork` pool uses under the hood: separate worker *processes*, so CPU-bound Celery tasks actually get parallelism, and one task crashing doesn't take down other tasks' memory space.

### 12.5 `asyncio` — high concurrency without threads at all
- `asyncio` runs a **single-threaded event loop** 
- "Don't wait. While this one request is waiting for the internet, let me run other work."
- It does this with one thread and one event loop. No OS threads, no processes.
- **The critical failure mode**: a single blocking/synchronous call inside an async function (e.g., calling `requests.get()` instead of an async HTTP client, or doing heavy CPU work, or a blocking DB driver call) **stalls the entire event loop** — every other coroutine(Coroutines components that can be suspended and resumed ) waiting on that loop freezes until the blocking call returns. This is a very common real-world FastAPI bug: someone calls a sync DB library inside an `async def` route and the whole service's throughput collapses under load, even though it looks fine in local testing with one request at a time.
  - Fix: use async-native libraries (`asyncpg`, `httpx.AsyncClient`, `aioredis`), or if you must call blocking code, offload it via `await loop.run_in_executor(None, blocking_fn)` (which runs it in a thread pool) or a background worker/queue.


### 12.6 Decision table (the interview-ready summary)

| Workload type | Best tool | Why |
|---|---|---|
| Many concurrent network/DB calls, simple app | `asyncio` | Lowest overhead, single thread, huge concurrency |
| I/O-bound work in a codebase that's mostly sync (e.g., Blocking I/O library) | `threading` / `ThreadPoolExecutor` | GIL releases during I/O wait; simpler to retrofit than full async |
| CPU-bound work (parsing, ML inference, image processing, heavy computation) | `multiprocessing` (or a process pool, or hand off to Celery workers running `prefork`) | Only way to get true parallel execution across cores in CPython |
| Mixed: async web server that occasionally needs CPU-heavy work | `asyncio` + `run_in_executor` (thread) for light blocking calls, or delegate to a separate process/worker (Celery) for genuinely heavy CPU work | Keep the event loop unblocked; don't let one slow request stall all others |

### 12.7 Related fact worth knowing
- **PyPy / alternative interpreters** and **`multiprocessing`-based frameworks** exist partly *because* of the GIL's limits.
- Recent CPython work (PEP 703, "free-threaded" / no-GIL builds, experimental from 3.13 onward) is trying to remove the GIL, but as of now (mid-2026) it's still opt-in/experimental and not the production default — worth mentioning if asked "is the GIL going away," but don't claim it's already gone in mainline CPython.
- C-extension libraries (NumPy, pandas core ops) release the GIL internally during heavy native computation, which is why NumPy vectorized operations can still benefit somewhat from being called across threads even though "Python threads don't help CPU-bound work" — the actual crunching happens outside the GIL in C.

## Quick interview answers (rehearsed one-liners)

- **"How do you make a Celery task idempotent?"** → Check for existing state before acting (natural key lookup or unique DB constraint), or use upserts, so re-running the task converges to the same end state instead of duplicating side effects.
- **"What happens if a Celery worker crashes mid-task?"** → With `acks_late`, the broker redelivers the task to another worker once the visibility/heartbeat times out — meaning the task can run twice, which is exactly why idempotency isn't optional, it's a design requirement.
- **"Why doesn't adding threads speed up my CPU-bound function?"** → The GIL means only one thread executes Python bytecode at a time; threads only help when they spend time waiting on I/O (GIL released), not computing. Use `multiprocessing` for real parallelism on CPU-bound work.
- **"What breaks if you block the event loop in FastAPI?"** → Every other concurrent request on that worker process stalls until the blocking call returns, since asyncio is single-threaded cooperative multitasking — one bad synchronous call can degrade the whole service's latency under load.
