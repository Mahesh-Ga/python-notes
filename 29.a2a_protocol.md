# Agent2Agent (A2A) Protocol Tutorial

**Agent2Agent (A2A)** is an open protocol, originally introduced by Google in April 2025 and later contributed to the **Linux Foundation**, that standardizes how independent AI agents — often built by different vendors, on different frameworks, running as separate services — discover each other and communicate to complete tasks together. While **MCP (Model Context Protocol)** standardizes how a single agent talks to *tools and data*, A2A standardizes how one agent talks to *another agent*.

In this tutorial, we will learn what A2A is, why it was introduced, its architecture, core concepts, how it works internally, a step-by-step example, how it compares to MCP, security considerations, and its advantages, limitations, and applications.

## 1. What is A2A and Why Do We Need It?

As organizations build more AI agents, a new problem appears that MCP does not solve: **agent-to-agent collaboration**. Suppose a "travel planning" agent needs help from a separate "flight booking" agent and a separate "hotel booking" agent, each built by a different team, in a different framework (LangGraph, CrewAI, a custom stack), possibly running in a different company entirely. Without a shared protocol, every pair of agents needs its own custom integration — the same **M×N integration problem** that MCP solved for tools, except this time it's happening between *agents*.

```
Without A2A (custom, per-pair integrations):     With A2A (common protocol):

Agent A --custom--> Agent B                       Agent A --\
Agent A --custom--> Agent C                       Agent B ---+--> A2A (shared protocol)
Agent B --custom--> Agent C                       Agent C --/
```

**A2A solves this by giving agents a common language to:**
1. **Discover** what another agent can do (its skills, without needing to know its internal implementation).
2. **Negotiate** how to interact (what input/output formats, what modalities — text, files, structured data — are supported).
3. **Collaborate** on a task, including long-running tasks, back-and-forth clarification, and streaming updates.
4. **Exchange results**, including rich content like documents, images, or structured forms — not just plain text.

The key design principle behind A2A is that agents remain **opaque** to each other — Agent A never needs to see Agent B's internal prompts, memory, tools, or reasoning steps. It only sees Agent B's *declared capabilities* and the *messages* exchanged. This preserves each vendor's IP and lets agents built on completely different stacks interoperate.

## 2. Core Concepts of A2A

| Concept | Meaning |
|---|---|
| **Client agent** | The agent that initiates a request — it wants a task done. |
| **Remote agent** | The agent that receives the request and performs (or partially performs) the task. |
| **Agent Card** | A JSON document a remote agent publishes describing its identity, skills, and how to reach it — the discovery mechanism. |
| **Task** | The central unit of work in A2A. Every request creates a task, identified by a unique ID, which moves through a defined lifecycle. |
| **Message** | A single turn of communication (from the client or the agent) within a task, made up of one or more Parts. |
| **Part** | The smallest unit of content inside a message — text, a file, or structured JSON data. This is what allows A2A to carry more than plain text. |
| **Artifact** | A tangible output produced by the remote agent as a result of the task (e.g., a generated report, an image, a booking confirmation). |

## 3. Architecture of A2A

A2A follows a **client–remote agent** model over standard web technology, so it can reuse existing enterprise auth, gateways, and observability tooling instead of inventing new infrastructure.

```
+----------------+                              +----------------+
|  Client Agent  |----- HTTP(S) + JSON-RPC ---->|  Remote Agent   |
|  (A2A Client)  |<---- Task / Message / -------|  (A2A Server)   |
+----------------+       Artifact / SSE stream  +----------------+
        |                                                |
        |  1. GET /.well-known/agent.json (Agent Card)   |
        |------------------------------------------------>
        |                                                |
        |  2. send task / message (JSON-RPC over HTTPS)  |
        |------------------------------------------------>
        |  3. task status updates (sync, polling, or SSE)|
        |<------------------------------------------------
```

- **Wire format**: JSON-RPC 2.0 over HTTP(S), the same battle-tested wire format used by MCP.
- **Transport modes**:
  - **Synchronous request/response** — for quick tasks.
  - **Polling** — the client periodically checks task status for longer-running work.
  - **Server-Sent Events (SSE) streaming** — the remote agent can push incremental updates (status changes, partial artifacts) as the task progresses, useful for long-running or multi-step agent work.
  - **Push notifications (webhooks)** — for very long-running, disconnected tasks, the remote agent can notify the client asynchronously once done.
- **Transport-agnostic content**: because content is broken into typed Parts (text, file, structured data), the same protocol can carry a plain chat reply or a rich multi-modal result.

## 4. The Agent Card — Discovery Mechanism

Before a client agent can use a remote agent, it needs to know what that agent can do. A2A standardizes this via an **Agent Card** — a JSON document typically published at a well-known URL:

```
https://<remote-agent-domain>/.well-known/agent.json
```

A simplified Agent Card looks like:

```json
{
  "name": "Hotel Booking Agent",
  "description": "Finds and books hotel rooms based on dates, location, and budget.",
  "url": "https://hotels.example.com/a2a",
  "capabilities": {
    "streaming": true,
    "pushNotifications": true
  },
  "skills": [
    {
      "id": "search-hotels",
      "name": "Search Hotels",
      "description": "Search available hotels for a given city and date range.",
      "inputModes": ["text", "data"],
      "outputModes": ["text", "data"]
    }
  ],
  "authentication": {
    "schemes": ["bearer"]
  }
}
```

This is conceptually similar to a **service's OpenAPI/Swagger spec**, but tailored for agent capabilities rather than plain REST endpoints — it tells another agent (or the LLM orchestrating it) *what* it can ask for and *how* to authenticate, without exposing *how* the remote agent internally does its reasoning.

## 5. How A2A Works — Step by Step

1. **Discovery** — the client agent fetches the remote agent's Agent Card to learn its skills, supported content types, and auth requirements.
2. **Task initiation** — the client sends a message describing the task (e.g., "book a hotel in Paris, Dec 10–12, budget $200/night"). A2A creates a **Task** object with a unique ID to track it.
3. **Task lifecycle** — the task moves through defined states as work progresses:

   ```
   submitted → working → input-required → completed
                              |
                              └──> failed / canceled
   ```

   - `submitted` — task received.
   - `working` — the remote agent is actively processing.
   - `input-required` — the remote agent needs clarification from the client (e.g., "Which of these 3 hotels do you prefer?") — this is what makes A2A support genuine **multi-turn, stateful collaboration** rather than one-shot request/response.
   - `completed` — the task finished successfully, with resulting Artifacts attached.
   - `failed` / `canceled` — terminal error/cancellation states.
4. **Streaming updates (optional)** — for long-running tasks, the client can subscribe via SSE to receive incremental status and partial artifacts instead of blocking until completion.
5. **Artifact delivery** — once complete, the remote agent returns one or more Artifacts (structured data, files, or text) that the client agent consumes and folds back into its own reasoning/workflow.

## 6. Example: A Minimal A2A Interaction

A client agent sends a task via JSON-RPC to a remote agent's A2A endpoint:

```json
POST /a2a HTTP/1.1
Host: hotels.example.com
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": "req-1",
  "method": "tasks/send",
  "params": {
    "id": "task-123",
    "message": {
      "role": "user",
      "parts": [
        { "type": "text", "text": "Find a hotel in Paris, Dec 10-12, under $200/night." }
      ]
    }
  }
}
```

The remote agent responds once the task completes:

```json
{
  "jsonrpc": "2.0",
  "id": "req-1",
  "result": {
    "id": "task-123",
    "status": { "state": "completed" },
    "artifacts": [
      {
        "name": "hotel-results",
        "parts": [
          { "type": "data", "data": { "hotel": "Hotel Lumière", "price": 180, "nights": 2 } }
        ]
      }
    ]
  }
}
```

Note how the **Part** abstraction (`text` vs `data` here) lets the same protocol carry a natural-language explanation and machine-readable structured data side by side in one message.

## 7. A2A vs MCP

A2A and MCP are **complementary, not competing** protocols — they solve different layers of the same overall problem and are commonly used together in the same system.

| | MCP (Model Context Protocol) | A2A (Agent2Agent Protocol) |
|---|---|---|
| **Solves** | Agent ↔ Tool/Data integration | Agent ↔ Agent collaboration |
| **Relationship** | Vertical — an agent calls a tool it controls/orchestrates | Horizontal (peer-to-peer) — two independent agents collaborate |
| **What's exposed** | Tools, resources, prompts (fine-grained, structured functions) | Skills, tasks, messages, artifacts (coarser, capability-level) |
| **Opacity** | The tool is typically simple/stateless; internals matter less | The remote agent is deliberately a "black box" — only capabilities are exposed |
| **Statefulness** | Mostly stateless tool calls | First-class stateful **Task** lifecycle, supports multi-turn clarification |
| **Analogy** | A function call | A conversation/negotiation between two colleagues |

**In practice**: an orchestrator agent might use **MCP** to call its own tools (a database, a search API) *and* use **A2A** to delegate a sub-problem to a completely separate specialized agent owned by another team — both inside the same overall workflow.

## 8. Security in A2A

- **Transport security**: A2A runs over HTTPS, inheriting standard TLS guarantees.
- **Authentication**: handled the same way as standard enterprise APIs — the Agent Card declares supported schemes (API keys, OAuth 2.0 bearer tokens, etc.), so A2A does not reinvent auth; it reuses existing identity infrastructure.
- **Authorization/opacity**: because a remote agent never exposes its internal reasoning, prompts, or tool access to the client agent, the blast radius of a compromised or malicious client is limited to what the remote agent's own API explicitly allows.
- **Least-privilege delegation**: production deployments typically scope each remote agent's credentials narrowly (e.g., the hotel-booking agent can only search/book hotels, nothing else), so a compromised client agent can't pivot into unrelated systems through it.
- **Input validation still matters**: since Artifacts and Parts can carry structured data and files, a remote agent must validate/sanitize inbound content just as any API would, rather than trusting it implicitly because it came from "another agent."

## 9. Advantages of A2A

- **Vendor/framework agnostic** — a LangGraph agent, a CrewAI agent, and a custom agent can all interoperate as long as each speaks A2A.
- **Preserves opacity/IP** — agents collaborate without exposing internal prompts, tools, or memory to each other.
- **Supports long-running, stateful tasks** — the Task lifecycle (including `input-required`) enables real back-and-forth collaboration, not just one-shot calls.
- **Rich content, not just text** — Parts can carry files and structured data alongside natural language.
- **Builds on existing web infrastructure** — HTTP(S), JSON-RPC, SSE — so it plugs into existing auth, gateways, load balancers, and observability tools with minimal new plumbing.

---

## 10. Disadvantages / Limitations of A2A

- **Still an emerging standard** — tooling, SDKs, and ecosystem support are younger and less mature than REST/gRPC.
- **Discovery trust** — a client must trust that a fetched Agent Card genuinely represents the remote agent's real capabilities; malicious or stale Agent Cards are a real operational risk.
- **Added latency/complexity** — going through Agent Card discovery + task lifecycle management is heavier than a direct function call, so it's overkill for simple, tightly-coupled agent interactions within one team's own stack.
- **Overlaps conceptually with MCP** for teams unfamiliar with both — deciding "is this an MCP tool or an A2A remote agent" requires understanding the distinction described in Section 7.

---

## 11. Applications of A2A

- **Multi-agent enterprise workflows** — an orchestrator agent delegating sub-tasks (HR, IT, finance) to specialized agents owned by different internal teams.
- **Cross-company agent collaboration** — e.g., a travel-planning agent from one company calling a flight-booking agent and hotel-booking agent from other companies, each exposing only an Agent Card.
- **Marketplaces of agents** — platforms where third-party agents publish Agent Cards so other agents can discover and use their specialized skills on demand.
- **Long-running agentic pipelines** — research, document generation, or approval workflows that need to pause for human/agent input mid-task (`input-required` state) and resume later.

---

## 12. Conclusion

A2A fills the gap that MCP intentionally leaves open: **collaboration between independent, opaque agents**, as opposed to a single agent's use of tools and data. Together, MCP (agent ↔ tool) and A2A (agent ↔ agent) form two complementary layers of the emerging "agentic web" stack — MCP handles what an agent can *do*, and A2A handles who an agent can *work with*.
