    ## 1. Property graph model — the core mental shift from relational

A graph DB stores **nodes** (entities) and **relationships** (edges) directly, instead of rows joined via foreign keys.

- **Node** — has one or more **labels** (like a table name, but a node can have multiple) and a set of key-value **properties**.
- **Relationship** — always **directed**, has exactly one **type**, connects exactly two nodes, and can also hold properties (e.g. `since`, `weight`).
- No JOINs at query time — a relationship is a physical pointer stored on disk (**index-free adjacency**). Traversing an edge is a pointer dereference, not a lookup.

```
(:Person {name: "Mahesh"}) -[:WORKS_AT {since: 2023}]-> (:Company {name: "Saxon AI"})
```

**Why this matters vs relational:** in Postgres, "find all colleagues of colleagues of colleagues" (3-hop) means 3 self-joins — cost grows with table size at each hop. In Neo4j, cost grows with the **number of relationships actually traversed**, regardless of total graph size. This is the whole pitch of a graph DB: relational JOINs get more expensive as data grows and as hop-count grows; graph traversal doesn't, because there's no join being computed — just edges being followed.

## 2. When to reach for a graph DB vs relational

| Use graph when... | Use relational when... |
|---|---|
| Query pattern is variable-depth traversal (friend-of-friend, dependency chains, org hierarchies) | Query pattern is set-based (aggregate, filter, group over flat tables) |
| Relationships themselves carry meaning/weight and are queried directly | Data is naturally tabular with fixed shape |
| Schema is relationship-heavy and evolving (many-to-many exploding into many-to-many-to-many) | Strong need for standard SQL tooling, reporting, BI |

Concrete tie-in: building a **knowledge graph over a codebase** (files → functions → calls → imports → tests) is exactly a graph-shaped problem — "what breaks if I change this function" is a multi-hop traversal query, painful as recursive SQL, natural as Cypher.

## 3. Cypher fundamentals

```cypher
// Create
CREATE (p:Person {name: "Mahesh", role: "SWE"})

// Match + return (SELECT + WHERE ) 
MATCH (p:Person {name: "Mahesh"}) RETURN p.name

// Relationship pattern
MATCH (p:Person)-[:WORKS_AT]->(c:Company)
RETURN p.name, c.name

// MERGE = "create if not exists" (idempotent upsert — critical for pipelines that re-run)
MERGE (p:Person {email: "m@x.com"})
ON CREATE SET p.created_at = timestamp()
ON MATCH SET p.last_seen = timestamp()

// Variable-length path — the thing SQL can't do cleanly
MATCH (a:Person {name: "Mahesh"})-[:KNOWS*1..3]->(b:Person)
RETURN DISTINCT b.name
```

- `MATCH` = pattern to find (like `SELECT ... FROM ... WHERE` combined)
- `MERGE` = match-or-create, always use for idempotent writes (pipelines/ETL that may re-run over the same data)
- `WHERE` filters after pattern match, same semantics as SQL
- `WITH` chains query parts together, like a CTE — lets you aggregate mid-query then continue matching
- `*1..3` = variable-length relationship traversal (1 to 3 hops) — this single operator replaces what would be a recursive CTE in SQL

```cypher
// Delete
MATCH (p:Person {name: "Mahesh"}) DETACH DELETE p
-- DETACH DELETE removes the node AND all its relationships.
-- Plain DELETE on a node with relationships throws an error (Neo4j won't silently orphan edges).
```

## 4. Indexes & constraints

```cypher
CREATE INDEX person_name_idx FOR (p:Person) ON (p.name);
CREATE CONSTRAINT person_email_unique FOR (p:Person) REQUIRE p.email IS UNIQUE;
```

- Without an index, `MATCH (p:Person {name: "X"})` is a **label scan** — O(all nodes with that label). Same failure mode as a missing index causing a Postgres seq scan.
- A uniqueness constraint auto-creates a backing index — use it for any property you `MERGE` on, since `MERGE` needs fast lookup to check existence.
- Composite indexes exist too, same idea as multi-column indexes in Postgres.

## 5. Query performance — PROFILE / EXPLAIN

```cypher
PROFILE
MATCH (p:Person {name: "Mahesh"})-[:WORKS_AT]->(c:Company)
RETURN c.name
```

- `EXPLAIN` shows the planned execution without running it; `PROFILE` runs it and shows actual rows processed per step — this is Neo4j's `EXPLAIN ANALYZE`.
- Watch for `NodeByLabelScan` in the plan where you expected `NodeIndexSeek` — same red flag as a Postgres seq scan on an indexed column.
- **Cartesian products**: a query with two disconnected `MATCH` patterns (no shared variable) silently produces a cross join. This is the single most common Cypher performance bug.

```cypher
-- BAD: two disconnected patterns -> cartesian product
MATCH (p:Person), (c:Company)
WHERE p.company_id = c.id
RETURN p, c

-- GOOD: express the relationship directly
MATCH (p:Person)-[:WORKS_AT]->(c:Company)
RETURN p, c
```

## 6. Graph algorithms (Graph Data Science library)

Beyond simple traversal, Neo4j GDS provides built-in graph algorithms — the equivalent of "things you'd otherwise hand-roll in Python over query results":

- **Shortest path** — Dijkstra/A* between two nodes (e.g. dependency chain length, degrees of separation)
- **PageRank** — importance/centrality scoring (e.g. "most-called function," "most-referenced doc")
- **Community detection** (Louvain, Label Propagation) — clustering densely-connected subgraphs (e.g. detecting module boundaries in an unstructured codebase graph)
- **Similarity** (Jaccard, cosine over node neighborhoods) — "find nodes with similar connection patterns"

```cypher
CALL gds.pageRank.stream('myGraph')
YIELD nodeId, score
RETURN gds.util.asNode(nodeId).name, score
ORDER BY score DESC LIMIT 10
```

GDS algorithms run on an in-memory **projected graph** (a subset of the full graph loaded for the algorithm), not directly on the stored graph — this keeps algorithm runs fast but means you explicitly project the nodes/relationships you need first.

## 7. APOC — the standard-library gap-filler

APOC (`Awesome Procedures On Cypher`) is a plugin so commonly used it's treated as near-core: JSON/CSV import-export, dynamic property access, batching large writes (`apoc.periodic.iterate` — chunk a huge write into transactions so you don't blow a single transaction's memory), path-finding helpers, trigger-like functionality. Worth knowing it exists and roughly what class of problem it solves, even without memorizing procedure names.

## 8. Python driver usage patterns

```python
from neo4j import GraphDatabase

driver = GraphDatabase.driver("bolt://localhost:7687", auth=("neo4j", "password"))

def get_colleagues(tx, name):
    result = tx.run(
        "MATCH (p:Person {name: $name})-[:WORKS_AT]->(:Company)<-[:WORKS_AT]-(colleague) "
        "RETURN colleague.name AS name",
        name=name,
    )
    return [record["name"] for record in result]

with driver.session() as session:
    colleagues = session.execute_read(get_colleagues, "Mahesh")
```

- Always use **parameterized queries** (`$name`) — same injection risk as raw SQL string interpolation, and it lets Neo4j cache the query plan.
- `session.execute_write` / `execute_read` wrap the call in a managed transaction with automatic retry on transient cluster errors — prefer these over manually calling `tx.run` outside a transaction function.
- For bulk writes (loading a generated knowledge graph from a pipeline), batch via `UNWIND` instead of one query per node:

```cypher
UNWIND $rows AS row
MERGE (p:Person {id: row.id})
SET p.name = row.name
```
-- one round trip for many rows, instead of one query per node

## 9. ACID & transactions

- Neo4j is fully ACID for single-instance writes — same guarantees you'd expect from Postgres, just scoped to graph operations.
- A transaction can span multiple `MATCH`/`MERGE`/`CREATE` statements; nothing commits until the transaction function returns successfully.
- Deadlocks can happen with concurrent writes touching overlapping nodes — same class of problem as row-lock contention in Postgres, same fix (keep transactions short, consistent lock ordering).

## 10. Scaling & HA

- **Causal Cluster**: one or more **Core** servers (hold full graph, participate in Raft consensus for writes) plus optional **Read Replica** servers (async-replicated copies, read-only, horizontally scalable for read throughput).
- Writes always go to Core servers and require majority consensus (Raft) — same tradeoff shape as Postgres synchronous replication: durability vs write latency.
- Bookmarks (`causal consistency`) let a client that just wrote data guarantee its next read (even against a replica) sees that write — solves the classic "read-your-own-write" replication lag problem explicitly, rather than leaving it to chance.

## 11. Where this fits a RAG / knowledge-graph pipeline

Directly relevant if the graph is being built from source code or documents for retrieval:

- **Construction**: parse source (AST, imports, call graph) → nodes (`File`, `Function`, `Class`) + relationships (`CALLS`, `IMPORTS`, `DEFINED_IN`) → `MERGE` them in so re-running the pipeline over an updated repo doesn't duplicate nodes.
- **Retrieval**: instead of pure vector similarity, traverse from a semantically-matched node outward N hops to pull in *structurally relevant* context (e.g. "also include every function this one calls") — this is the standard way graph-augmented RAG beats plain vector search for code, because relevance in code is structural, not just semantic.
- **Debugging retrieval quality**: check whether the graph construction step actually created the relationships you expect (`MATCH (f:Function)-[:CALLS]->(g:Function) RETURN count(*)`) before assuming the retrieval/ranking logic is at fault — a common root cause of "bad RAG answers" is an incomplete graph, not a bad query.

## 12. Quick interview-answer summary

- **What is Neo4j / graph DB, one line**: stores entities as nodes and relationships as first-class edges with index-free adjacency, so multi-hop traversal cost depends on relationships walked, not table size.
- **When to use over relational**: variable-depth traversal queries, relationship-heavy/evolving schemas, "N-hop from X" style questions.
- **Cypher core**: `MATCH` to find patterns, `MERGE` for idempotent upsert, `*1..N` for variable-length paths, `DETACH DELETE` to remove a node with its edges.
- **Performance red flag**: two disconnected `MATCH` patterns → cartesian product; always connect patterns or use `PROFILE` to catch it.
- **Indexes**: same purpose as relational — without one, a label match degrades to a full label scan.
- **HA model**: Core servers (Raft consensus, writes) + Read Replicas (async, read scaling) — same durability/latency tradeoff shape as Postgres replication.
- **RAG tie-in**: graph traversal adds *structural* relevance on top of vector *semantic* relevance — the two are complementary, not competing.
