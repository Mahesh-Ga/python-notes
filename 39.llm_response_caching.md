# LLM Response Caching (Exact + Semantic)

> Companion to [[8. redis.md]] (caching patterns/TTL/invalidation) and [[30.embeddings.md]] / [[31.vector_store.md]] (embeddings, similarity search). This topic is specifically about caching **LLM call results**, not general API caching — the interesting part is that "the same question" can be phrased a hundred different ways, so a plain key-value cache misses almost everything unless you also cache *semantically*.

---

## 1. Why bother caching LLM responses

- **Cost** — every uncached call pays for input + output tokens; a chatbot FAQ, RAG system, or eval harness re-asks the same or near-same question constantly.
- **Latency** — a cache hit is single-digit milliseconds; a real LLM call is hundreds of ms to several seconds, more for long generations.
- **Rate limits** — providers cap requests/tokens per minute; caching reduces pressure on that ceiling during traffic spikes.
- **Determinism for evals/tests** — replaying a cached response makes CI and regression tests fast and stable instead of hitting a live, non-deterministic API each run.

The tradeoff is the same one as any cache: staleness risk and the chance of serving a *wrong* answer for a *similar but not identical* question. That risk is exactly why LLM caching splits into two tiers.

---

## 2. Two tiers: exact-match vs semantic

| | Exact-match cache | Semantic cache |
|---|---|---|
| **Key** | Hash of the literal request (prompt + params) | Embedding vector of the prompt |
| **Lookup** | Dict/hash lookup, O(1) | Nearest-neighbor / similarity search |
| **Hits on** | Byte-identical requests only | Paraphrases, reordered words, different phrasing, same intent |
| **Risk of wrong hit** | None (identical input → cached output is valid by definition) | False positive — a "close enough" question that actually needed a different answer |
| **Storage** | Redis string/hash | Vector store (or Redis with a vector index) + the stored response |
| **Typical hit rate** | Low unless traffic is genuinely repetitive (FAQ bots, batch dedup) | Much higher — catches the long tail of rephrasings |

In practice you run **both**, in order: check exact-match first (cheap, zero risk), fall back to semantic (more expensive, small risk), then fall back to the real LLM call on a miss.

## 3. Exact-match cache

### Cache key design — the part people get wrong

The key must encode *everything that can change the output*, not just the user's message:

```python
import hashlib, json

def cache_key(model: str, messages: list[dict], temperature: float,
              system_prompt: str, tools: list[dict] | None = None) -> str:
    payload = {
        "model": model,
        "system": system_prompt,
        "messages": messages,
        "temperature": temperature,
        "tools": tools,
    }
    blob = json.dumps(payload, sort_keys=True)          # sort_keys → stable hash regardless of dict order
    return "llmcache:" + hashlib.sha256(blob.encode()).hexdigest()
```

Common bugs:
- Forgetting `temperature`/`top_p` in the key → caching a response as if it were deterministic when it wasn't, or conversely never hitting cache because a default value differs subtly between call sites.
- Forgetting the **system prompt** or **prompt template version** → a prompt-engineering change silently keeps serving the old cached answer.
- Caching when `temperature > 0` at all — if the caller *wants* varied outputs (creative generation), exact-match caching defeats the purpose. Only cache deterministic-intent calls (temperature 0, classification, extraction, RAG Q&A) by default; make it opt-in otherwise.

### Storage (Redis, same pattern as [[8. redis.md]] cache-aside)

```python
import redis
r = redis.Redis(decode_responses=True)

def get_or_call(model, messages, temperature, system_prompt) -> str:
    key = cache_key(model, messages, temperature, system_prompt)
    cached = r.get(key)
    if cached:
        return cached                      # cache hit — no LLM call

    response = call_llm(model, messages, temperature, system_prompt)
    r.set(key, response, ex=3600 + random.randint(0, 300))   # jittered TTL, per Topic 8 §3
    return response
```

### TTL / invalidation for LLM caches specifically

- **Prompt template changes** → bump a version string into the cache key (`system_prompt_v3`) rather than trying to invalidate by pattern; old keys just age out via TTL.
- **Model upgrades** (e.g., provider deprecates a model version) → include the exact model string/version in the key so a silent model swap doesn't serve pre-upgrade cached text under the new model's name.
- **RAG context changes** → if retrieved documents are part of the prompt, the key naturally changes when retrieval changes (different docs → different `messages` → different hash) — this is actually *correct* behavior, not a bug to work around.
- Short TTLs (minutes-hours) for anything touching time-sensitive or personalized data; longer TTLs are fine for static-knowledge Q&A.

## 4. Semantic cache

### Core idea

1. Embed the incoming query (same embedding model used consistently — Topic 30).
2. Search a vector store for the nearest previously-cached query.
3. If similarity ≥ threshold → return that cached response (cache hit).
4. Else → call the LLM, then store `(embedding, query, response)` for future hits.

```python
from dataclasses import dataclass

@dataclass
class CacheEntry:
    query: str
    embedding: list[float]
    response: str

class SemanticCache:
    def __init__(self, embed_fn, vector_store, threshold: float = 0.92):
        self.embed_fn = embed_fn
        self.store = vector_store          # e.g. a Qdrant/FAISS collection (Topic 31)
        self.threshold = threshold

    def get(self, query: str) -> str | None:
        vec = self.embed_fn(query)
        hit = self.store.search(vec, top_k=1)
        if hit and hit[0].score >= self.threshold:
            return hit[0].payload["response"]
        return None

    def set(self, query: str, response: str):
        vec = self.embed_fn(query)
        self.store.upsert(vector=vec, payload={"query": query, "response": response})

def answer(query: str, cache: SemanticCache) -> str:
    cached = cache.get(query)
    if cached is not None:
        return cached
    response = call_llm(query)
    cache.set(query, response)
    return response
```

This is the same architecture as **GPTCache** and LangChain's `SemanticCache` integrations — a thin wrapper around an embedding call + a vector index (HNSW under the hood, Topic 32), scoped either globally or per-namespace.

### The threshold is the whole game

- **Too low (permissive)** → false positives: "How do I cancel my subscription?" incorrectly matches "How do I cancel my order?" and returns the wrong cached answer. This is worse than a cache miss — it's silently wrong output.
- **Too high (strict)** → cache degenerates toward exact-match, losing most of the benefit.
- There's no universal number — tune against a labeled set of "should match" / "should not match" query pairs for your domain, the same way you'd tune `efSearch`/recall in [[32.hnsw.md]]. Cosine similarity ≈0.90–0.97 is a common starting range for sentence-embedding models, but it's domain-dependent (short factual Q&A tolerates a tighter threshold; open-ended chat needs it looser or shouldn't be semantically cached at all).

### Mitigating false-positive risk

- **Cache only for low-stakes / idempotent-intent queries** (FAQ, RAG lookups, classification) — never semantically cache anything with side effects, personalized data, or safety-critical content.
- **Verify before serving**: some implementations do a cheap secondary check (e.g., re-rank the candidate against the query with a cross-encoder, or require both high cosine similarity *and* matching extracted entities/intent) before trusting a semantic hit.
- **Scope by tenant/user** when responses are personalized — a semantic hit across two different users' contexts can leak one user's cached answer to another; namespace the vector store by tenant ID the same way you'd namespace Redis keys (`tenant:{id}:...`).
- **Track and log hit sources** — record whether a served response came from exact cache, semantic cache, or a live call, so you can audit false-positive complaints after the fact.

## 5. Combining both tiers in one lookup path

```python
def get_llm_response(query: str, exact_cache: redis.Redis,
                      semantic_cache: SemanticCache, **params) -> str:
    key = cache_key(**params, messages=[{"role": "user", "content": query}])

    if hit := exact_cache.get(key):
        return hit                              # tier 1: exact — cheapest, zero risk

    if hit := semantic_cache.get(query):
        exact_cache.set(key, hit, ex=3600)       # promote to exact cache for next identical ask
        return hit                               # tier 2: semantic

    response = call_llm(query, **params)          # tier 3: miss — real call
    exact_cache.set(key, response, ex=3600)
    semantic_cache.set(query, response)
    return response
```

Promoting a semantic hit into the exact-match tier means the *next* byte-identical repeat of that exact phrasing skips the (more expensive) vector search entirely.

## 6. Sample key/value examples

### Exact-match cache (Redis) — concrete example

Request:
```python
model = "gpt-4o-mini"
system_prompt = "system_prompt_v3: You are a helpful support agent."
messages = [{"role": "user", "content": "How do I reset my password?"}]
temperature = 0
```

**Key** (sha256 of the sorted-key JSON payload from `cache_key()`):
```
llmcache:8f1a2c7e0e6b4a9d3f0d2c1b5a8e7f6c1d4b3a2f9e8d7c6b5a4f3e2d1c0b9a8f
```

**Value stored** — usually the raw response string, or a small JSON envelope if you also want to cache metadata (token usage, latency) alongside it:
```json
{
  "response": "To reset your password: go to Settings → Security → Reset Password, then check your email for the reset link.",
  "model": "gpt-4o-mini",
  "prompt_tokens": 42,
  "completion_tokens": 28,
  "cached_at": "2026-09-13T10:15:00Z"
}
```
Redis commands:
```
SET llmcache:8f1a2c7e... '{"response": "...", "model": "gpt-4o-mini", ...}' EX 3900
```
A byte-identical repeat of this exact `(model, system_prompt, messages, temperature)` tuple hashes to the same key and hits instantly. Change *anything* — even `temperature=0.1` instead of `0`, or add a trailing space to the user message — and you get a completely different hash → guaranteed miss (this is exact-match's whole limitation, and exactly what the semantic tier exists to catch).

### Semantic cache (vector store) — concrete example

Stored entries are `(embedding, payload)` pairs, not string keys — lookup is nearest-neighbor search, not exact match.

**Entry stored after the first time someone asks:**
```json
{
  "id": "sc_0007f3",
  "embedding": [0.0123, -0.0891, 0.0456, "... 1536 dims total ..."],
  "payload": {
    "query": "How do I reset my password?",
    "response": "To reset your password: go to Settings → Security → Reset Password, then check your email for the reset link.",
    "tenant_id": "acme_corp",
    "created_at": "2026-09-13T10:15:00Z"
  }
}
```

**A later, differently-phrased query that hits this entry:**
```
"I forgot my password, how can I set a new one?"
```
Its embedding lands at, say, cosine similarity `0.94` against `sc_0007f3` — above the `0.92` threshold → semantic cache hit, same `response` returned even though not a single word matches the original query.

**A query that should NOT hit it (near-miss you'd catch during threshold tuning):**
```
"How do I reset my payment method?"
```
Superficially similar wording ("reset my ___"), but the embedding similarity comes out lower (say `0.81`) because the semantic content (payment vs. password) differs — falls below threshold → correctly treated as a cache miss, goes to a real LLM call.

Qdrant-style pseudo-call for the lookup:
```python
store.search(
    collection="semantic_cache:acme_corp",
    vector=embed("I forgot my password, how can I set a new one?"),
    top_k=1,
)
# → [{"id": "sc_0007f3", "score": 0.94, "payload": {...}}]
```

## 7. Streaming responses

LLM APIs often stream tokens. Two options:
- **Cache the fully assembled response**, and on a cache hit, re-stream it chunk-by-chunk to the client so the UX stays consistent (looks like a live generation, but no LLM cost/latency).
- Never cache mid-stream partial state — only cache once the full response is known-good (e.g., didn't error out, wasn't cut off by a length limit).

---

## 8. What NOT to cache

- Anything with **non-idempotent side effects** embedded in the prompt/response (tool calls that mutate state, agent actions).
- **Personalized or time-sensitive** content (today's date, "what's my order status") unless the cache key/namespace fully captures that context.
- Outputs from **high-temperature creative generation** where varied output is the point.
- Anything containing **PII/secrets** in the prompt, unless the cache store has the same access controls and encryption as the primary data store — a cache is still a place data lives.

---

## 9. Quick interview-answer summary

- **"Why can't you just cache LLM calls like any API response?"** — because the same intent can be phrased infinitely many ways; a plain key-value cache only catches byte-identical repeats, so LLM caching layers in a *semantic* tier (embedding similarity) on top of exact-match to catch paraphrases.
- **"What goes into the cache key?"** — everything that affects the output: model name/version, full message list, system prompt (versioned), temperature/top_p, tool definitions. Missing any of these causes either false cache hits (stale/wrong answer) or false misses (works but wastes the cache).
- **"How do you pick a semantic similarity threshold?"** — tune it against a labeled set of query pairs that should/shouldn't match; too low risks confidently wrong answers (false positive), too high collapses toward exact-match. There's no universal number.
- **"What's the architecture?"** — exact-match tier (hash → Redis) checked first, semantic tier (embed query → vector store nearest-neighbor, e.g. HNSW-backed) checked second, real LLM call as the fallback; a semantic hit gets promoted into the exact-match tier.
- **"What would you never cache?"** — high-temperature creative output, personalized/time-sensitive answers, anything with side-effecting tool calls, and PII-bearing prompts without cache-level access controls.
