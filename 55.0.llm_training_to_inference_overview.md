## 1. Training in short (learning the weights)

**Goal:** make the transformer good at one task — *predict the next token*.

```
Text: "The cat sat on the mat"
Input  : The  cat  sat  on  the
Target : cat  sat  on   the mat      (shifted by one; every position is a training example)
```

**One training step**
1. Take a batch of text → tokenize → embed.
2. **Forward pass** through the transformer layers (causal attention, so each position only sees earlier tokens) → logits over the vocabulary at every position.
3. **Loss** = cross-entropy between predicted distribution and the true next token (high loss when the model gave the correct token low probability).
4. **Backward pass** (backpropagation) → gradient of the loss w.r.t. every weight.
5. **Optimizer** (AdamW) nudges weights slightly to reduce loss.
6. Repeat over trillions of tokens on thousands of GPUs (data/tensor/pipeline parallelism).

What gets learned: the embedding matrix, Q/K/V/output projections in attention, FFN weights — i.e. all the "parameters". Grammar, facts, reasoning patterns and code are encoded implicitly in those numbers because predicting text well requires them.

**Stages**

| Stage | Data | Result |
|---|---|---|
| **Pre-training** | Web, books, code (trillions of tokens), next-token prediction | Base model: knows language and world knowledge, but just continues text |
| **SFT** (supervised fine-tuning) | Curated instruction → response pairs | Follows instructions, answers in chat format |
| **RLHF / preference tuning** | Human/AI preference rankings | Helpful, harmless, better-styled answers ([[37.RLHF.md]]) |

After training, the weights are **saved and frozen** (a file of billions of numbers, e.g. 16 GB for an 8B model in FP16). The training data itself is *not* stored or looked up.

## 2. KV cache (needed to understand the next section)

### Why it exists
In self-attention, every token produces three vectors: a **Query (Q)**, a **Key (K)** and a **Value (V)** (see [[28.llm_architecture.md]]). To generate a new token, its **Q** is compared with the **K** of *all earlier tokens* to decide who to attend to, then the matching **V**s are blended.

The important observation: **K and V of earlier tokens never change** once computed (causal attention — past tokens can't see the future). Only the newest token needs a fresh Q, K, V.

### Without a cache (wasteful)
```
Step 1: process  [The cat sat]            → predict "on"
Step 2: process  [The cat sat on]         → recompute K,V for The/cat/sat again → predict "the"
Step 3: process  [The cat sat on the]     → recompute everything again → ...
```
Work per step grows with the whole sequence, so generating n tokens costs ~O(n²) of repeated work.

### With a KV cache
Store each token's K and V (per layer, per attention head) in GPU memory the first time they're computed.
```
Prefill : process [The cat sat] once → cache K,V for these 3 tokens
Step 1  : new token "on"  → compute only its Q,K,V; reuse cached K,V of 3 old tokens → append "on" to cache
Step 2  : new token "the" → compute only its Q,K,V; reuse cache of 4 tokens → append
```
Each step now processes **one token** instead of the whole sequence. Output is identical; it is purely a speed optimisation.

### The trade-off: memory
The cache grows with every token and every concurrent user:
```
KV bytes per token = 2 (K and V) × layers × kv_heads × head_dim × bytes_per_value
Llama-3-8B (32 layers, 8 KV heads, 128 dim, FP16) ≈ 128 KB/token
→ an 8K-token conversation ≈ 1 GB;  100 simultaneous users ≈ 100 GB
```
So on a busy server the KV cache, not the model weights, often limits how many users fit on a GPU. Memory-saving tricks (GQA, KV quantization, PagedAttention, prefix caching) are covered in [[55.llm_inference_fundamentals.md]] and [[54.vllm.md]].

### Things worth remembering
- The cache is **per request/conversation**; it's temporary working memory, not learned knowledge and not shared between users (except identical prompt prefixes with prefix caching).
- It is why the first token is slow (**prefill** builds the cache for the whole prompt) and later tokens are fast (**decode** only extends it).
- Long chat history = bigger cache = more memory and slower decoding; this is part of why context windows are limited.
- It is also what provider **prompt caching** reuses: a repeated prompt prefix skips recomputing its K/V and is billed cheaper.

## 3. What happens when a user asks a question the model has never seen?

**Key idea: the model does not search its training data and does not learn from your question.** It runs the frozen weights as a function: `text in → probability of next token out`. A "new" question works because the model learned general patterns, not memorised exact sentences.

```
User: "Why would a 12-year-old Python script suddenly leak memory?"   ← never seen verbatim
```
 Your question is not treated as a question.
The chat template wraps it into one long text sequence, roughly like this:
<system> You are a helpful assistant
<user> What is the capital of France?
<assistant>
The model's only job is to predict what token comes next after <assistant>. Everything it writes is a continuation of that tex


Step by step:

1. **Build the prompt:** system prompt + chat history + the new question, wrapped in the chat template, then **tokenized** into IDs.
2. **Prefill:** the whole prompt goes through all layers once. Attention lets every token mix information from the others, so the model builds a contextual representation of *this specific question*. K/V for each token are stored in the **KV cache**.
3. **Predict the next token:** the last position's vector → output layer → probabilities over the vocabulary (e.g. "A": 31%, "Memory": 22%, "There": 9%…).
4. **Sample** a token (temperature / top-p / greedy).
5. **Append** it to the sequence and run just that one token through the model (using the cached K/V) → next-token probabilities → sample again.
6. **Loop** until an end-of-sequence token, a stop sequence, or `max_tokens`. Stream tokens to the user as they appear.

The answer is built token by token; each token is conditioned on the question *plus everything generated so far*, which is how a coherent, never-before-written answer emerges.

### Why it can answer something new (generalisation)
- Training compressed regularities (concepts, syntax, facts, reasoning styles) into the weights, so unseen combinations of known concepts still map to sensible continuations.
- **In-context learning:** information placed in the prompt (instructions, examples, retrieved documents) steers the output **without changing any weights**. Weights are fixed; only the activations differ per prompt.

### What it can't do on its own
| Limitation | Why | Fix |
|---|---|---|
| Doesn't know events after its **training cutoff** | Weights frozen at training time | RAG / web search / tools, put fresh data in the prompt ([[15.A.RAG.md]]) |
| Doesn't know your private data | Never in training set | RAG, fine-tuning, long-context prompt |
| May **hallucinate** | It generates *plausible* tokens, not verified facts | Grounding, citations, guardrails ([[52.Guardrails.md]]) |
| Doesn't remember across chats | No weight update; context window is its only memory | Re-send history, memory stores ([[35.Agent Memory.md]]) |
| Answers vary run to run | Sampling is probabilistic | `temperature=0`, seed |

## 4. Training vs inference at a glance

| | Training | Inference (user asks a question) |
|---|---|---|
| Input | Huge corpus, known next tokens | One prompt, next tokens unknown |
| Passes | Forward + backward | Forward only |
| Weights | Updated | **Frozen** |
| Output | Better weights | Generated text |
| Frequency / cost | Once, enormous | Every request, recurring |

## 5. Quick interview-answer summary

> "An LLM is trained by next-token prediction: the transformer reads text, predicts each next token, we compute cross-entropy loss against the real token, backpropagate and update the weights with AdamW over trillions of tokens — that's pre-training — then SFT and RLHF make it follow instructions and behave well. The result is a frozen set of weights, not a database of text. When a user asks a new question, nothing is looked up or learned: the prompt is tokenized, run through the frozen network once (prefill), the model outputs a probability distribution for the next token, one is sampled, appended, and the process repeats until the end token. It handles unseen questions because it learned general patterns and uses in-context information from the prompt. For fresh or private knowledge you add it to the prompt via RAG or tools, since the weights themselves don't change at inference time."

### Follow-ups

| Question | Short answer |
|---|---|
| Does the model learn from my chat? | No; weights are frozen. It only uses the context window. Providers may use data for future training separately. |
| Does it look up answers from training data? | No; knowledge is stored implicitly in weights, and retrieval needs RAG. |
| Why can it answer unseen questions? | Generalisation from learned patterns + in-context information. |
| Why do outputs differ between runs? | Token sampling is random unless temperature is 0. |
| Where do knowledge cutoffs come from? | Training data ends at a date; weights don't update afterwards. |
| What is the KV cache? | Stored Keys/Values of previous tokens so each new token only computes its own Q/K/V instead of reprocessing the whole sequence. |
| Why is it needed? | Past K/V never change; recomputing them makes generation O(n²) wasteful. |
| What is its downside? | Memory grows with sequence length × concurrent users, often limiting GPU concurrency more than the weights do. |
