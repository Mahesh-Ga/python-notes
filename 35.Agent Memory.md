### Why AI Agents Need Memory? 

- **No continuity.** The agent cannot remember what the user said 30 seconds ago once the current call ends - the next call starts fresh, with nothing carried over unless we explicitly pass it in.
- **No personalization.** The agent cannot remember that the user prefers short answers, writes in Python, or lives in Bangalore. It treats every user the same.
- **No learning.** The agent cannot remember what worked and what did not. It will make the same mistakes again and again.
- **No long tasks**. Multi-step tasks that take hours or days become impossible. The agent forgets the plan halfway through and has to start over. Designing the agent's repeating cycle so this does not happen is Loop Engineering.


### The Memory Stack
```
+--------------------------------------------+
|              AI Agent Memory               |
|                                            |
|  Layer 1: Context Window (in the prompt)   |
|     - In the current prompt                |
|     - Lost when context overflows          |
|                                            |
|  Layer 2: Short-Term Memory (session)      |
|     - Scratchpad, current task state       |
|     - Lost when the session ends           |
|                                            |
|  Layer 3: Long-Term Memory (persistent)    |
|     - Facts about the user                 |
|     - Past conversations                   |
|     - Learned preferences                  |
|                                            |
|  Layer 4: External Knowledge (tools/RAG)   |
|     - Documents, databases, APIs           |
|     - Queried, not maintained by agent     |
+--------------------------------------------+
```

Layer 1 - Context Window. This is the text the LLM sees in a single call. It is the fastest memory because the LLM reads it directly. But it is also the smallest. Once it is full, older messages have to be dropped or summarized. For tasks where the input itself is too large to fit, we have a detailed blog on `Recursive Language Models (RLMs)` that keeps the main context small by recursively splitting the input across sub-model calls.

Layer 2 - Short-Term Memory. This is the scratchpad the agent uses during one task or session. It holds the plan, the current step, and the intermediate results. When the session ends, this memory is usually gone.

Layer 3 - Long-Term Memory. This is the persistent memory that survives across conversations and sessions. It stores user facts, preferences, past conversation summaries, and learned behaviors. This is what makes the agent feel like it "knows" the user.

Layer 4 - External Knowledge. This is everything the agent can query but does not maintain - documents, databases, APIs, the web. The agent reads from these sources but does not write back to them as its own memory, even when the sources belong to the same company. Some frameworks classify this as a type of long-term memory; others keep it separate. From the agent's point of view, it looks the same either way - the agent asks, and information comes back.

### PROBLEMS 
1. Context window overflow. The prompt becomes too long and either fails or gets truncated. The agent loses the oldest (and sometimes most important) information.

How to fix: Summarize old turns into a compact summary. Drop tool outputs that are no longer needed. Put only the most relevant retrieved memories in the prompt, not everything.

2. Retrieval misses the important memory. The agent has the memory stored, but the retrieval step does not find it, so the LLM answers as if it never knew.

How to fix: Use semantic search (embeddings) instead of keyword match. Store memories with good titles and descriptions. Retrieve more candidates than we need and let the LLM pick. At scale, that similarity search is powered by Approximate Nearest Neighbor (ANN) search, which finds the closest memory vectors fast without scanning every one.

3. Outdated memories. The agent keeps acting on old facts. The user's job changed, but the agent still thinks they are a student.

How to fix: On every write, check if an existing memory contradicts it. If yes, update or replace it. Do not just append.


### How Agent Memory Is Implemented

**Short-term memory.** In its rawest form this is just the message/state buffer fed into the LLM on every call - system prompt, tool calls , and their outputs, appended as the agent works. It grows fast , so it needs a management strategy:
- Sliding window / truncation - drop the oldest messages once a token budget is hit. Crude, but fine when old tool outputs are no longer relevant.
- Summarization / compaction - periodically have the LLM compress older parts of the transcript into a short summary and replace the raw messages with it.
- Scratchpad / working state object - instead of one long message list, keep an explicit state dict that gets updated as structured fields. More reliable than making the model re-parse a wall of text for one fact.
```json
// for single agent 
state = {
    "user_query": "Summarize the Q3 sales report.",
    "intent": None,
    "messages": [
        {"role": "user", "content": "Summarize the Q3 sales report."}
    ],
    "retrieved_docs": [],
    "tool_results": {},
    "current_step": "classify_intent",
    "final_answer": None
}

// for multiple agents 
state = {
    "user_query": "Find the top 5 selling products from the sales database and explain the trend.",
    "messages": [{"role": "user", "content": "..."}],
    "plan": [],
    "current_task": None,
    "retrieved_docs": [],
    "completed_tasks": [],
    "next_agent": "planner",
    "final_answer": None
}
```
by default it's just in-memory (RAM), living as a variable/object in the running process for the duration of the session (the message list, or a state dict like LangGraph's). It's not written to disk at all unless you deliberately checkpoint it.

That said, in production systems it's common to back it with a cache like Redis (with a TTL), especially when:
- the agent runs across multiple server instances (so any instance can pick up the session), or
- you want the session to survive a process restart, or
- the task is long-running (hours) and you don't want to lose progress if the server crashes.

For the SDLC agent, short-term memory is scoped to one ticket/PR lifecycle and torn down when it closes - unless something is deliberately promoted out of it.

**Long-term memory.** External storage plus retrieval, usually a few pieces working together:
1. Vector store + embeddings (semantic memory) - the workhorse. Each time something worth remembering happens (a bug fix, a postmortem, a stated convention), embed the text and store the vector plus metadata (repo, module, date, ticket ID) in a vector DB (Pinecone, Weaviate, pgvector, Chroma). On a new ticket, embed its description, run a similarity search, pull back the top-k relevant memories, inject them into the prompt. This is RAG applied to the agent's own history.
2. Structured key-value / database memory (episodic/procedural) - not everything should be fuzzy search. Known flaky tests, team conventions, a service dependency graph are better as exact lookups (a Postgres table, a JSON file) than embeddings, because you want the exact fact, not the closest match.
3. Memory write policy - the part most implementations get wrong. There needs to be an explicit decision point for what gets promoted to long-term: either rule-based triggers (on PR merge, extract "lessons learned"; on reviewer comment, store as a preference) or an LLM-as-judge step at the end of a task ("was there anything here worth remembering?"). Without this, you either store everything (noisy, pollutes retrieval) or nothing (agent never improves).
4. Retrieval at inference time - before starting a new ticket, embed it, hit the vector store, query structured stores for relevant facts, and inject only the top handful (e.g. top-5, above a relevance threshold) into the prompt - not everything that matches.
5. Consolidation / forgetting - duplicate or stale memories build up over time ("test X is flaky" stored five times, or a memory about an architecture that's since changed). A consolidation job periodically clusters and dedupes similar memories and expires ones that are stale or contradicted. Most frameworks still lean on relevance scoring rather than real pruning here - it's an open problem.

**End-to-end for the SDLC agent:** ticket comes in -> embed it, query vector memory for similar past tickets/postmortems and structured memory for known facts about the affected service -> inject results into the short-term working context -> do the work, accumulating tool outputs in that same short-term buffer, compacting as it grows -> on completion, a write step decides what's worth extracting (new flaky test, a reviewer's stated preference, a learned convention) and pushes it into long-term storage -> short-term state gets discarded.

> Short-term memory is a context-window management problem (truncation, summarization, structured state). Long-term memory is a retrieval-systems problem (embeddings, indexing, similarity search, write/consolidation policy) - it looks a lot like building a search engine over the agent's own experience.
