# Observability, Logging, Tracing, Evaluation Pipelines, and Agent Reliability — Prep Notes

> Builds on `15.RAG.md` (Module 9: RAGAS) and `17.ai_agents.md` (Module 9: agent evaluation preview). This is the "how do you know it's actually working in production, and keep it working" layer.

---

## Module 1: Why This Matters for LLM/Agent Systems Specifically

Traditional software observability assumes deterministic code — same input, same output, and a stack trace pinpoints the failure. LLM/agent systems break that assumption:

- **Non-determinism** — same prompt can yield different outputs across calls (temperature > 0, model updates), so a single failed run doesn't prove a bug and a single passed run doesn't prove correctness.
- **No stack trace for "wrong"** — a hallucinated fact or a bad tool choice doesn't throw an exception; the system "succeeds" while being wrong. You need semantic evaluation, not just error-rate monitoring.
- **Multi-step, branching execution** — an agent's actual path (which tools, in what order, with what intermediate reasoning) is itself the thing you need visibility into, not just the final input/output pair.
- **Cost and latency are first-class metrics** — unlike typical backend calls, every step can cost real money (tokens) and add seconds of latency, and both are load-bearing for the eval/reliability story.

This is why LLM observability tooling (LangSmith, Langfuse, etc.) is a distinct category from general APM (Datadog, New Relic) — though the two increasingly integrate, since the underlying infra (requests, latency, errors) is still normal distributed-systems observability with an LLM-specific layer on top.

## Module 2: Logging

### 2.1 What to log for every LLM/agent call

- **Full prompt** (system + user + injected context/retrieved docs) — needed to reproduce and debug bad outputs.
- **Full completion**, including any tool calls requested.
- **Model + parameters** — model name/version, temperature, max_tokens, stop sequences (model updates silently change behavior; you need to know which version produced which output).
- **Token usage** (prompt tokens, completion tokens) — the basis for cost tracking.
- **Latency** — time-to-first-token (TTFT) and total completion time separately (matters a lot for streaming UX).
- **Request metadata** — user/session id, trace/run id, timestamp, environment (prod/staging).
- **Tool call inputs/outputs** — for agents, log what was actually executed and what came back, not just that "a tool was called."
- **Errors** — API errors, timeouts, rate limits, validation failures (e.g. structured-output parse failure) — these are often silently retried and lost if not explicitly logged.

### 2.2 Structured logging

Log as structured JSON (not free-text log lines) keyed by the fields above — makes logs queryable/filterable in whatever log aggregation system you use (ELK/OpenSearch, Datadog logs, CloudWatch, BigQuery sink), and is the substrate tracing tools build on.

### 2.3 PII and sensitive-data handling in logs

Prompts and completions routinely contain user PII, so logging pipelines need the same treatment as any other system handling sensitive data:
- Redact/mask known-sensitive fields before they hit long-term log storage, or tag them for restricted-access storage.
- Apply data-retention limits — don't keep full prompt/completion logs indefinitely by default.
- This is the same concern as `15.RAG.md` §10.2's "PII handling" for retrieved content, applied to the logging layer instead of the index.

## Module 3: Tracing

### 3.1 What a "trace" is for an LLM/agent system

A **trace** = the full execution tree of one user-facing request, broken into **spans** — one span per meaningful step (an LLM call, a tool call, a retrieval, a sub-agent invocation). Directly analogous to distributed tracing in microservices (OpenTelemetry spans/trace-id/parent-span-id), just applied to LLM pipeline steps instead of network calls.

```
Trace: "answer user question"
├── Span: retrieve (vector search)         120ms
├── Span: grade_documents (LLM call)       340ms
├── Span: generate (LLM call)              890ms
│     └── Span: tool_call: search_web      410ms
└── Span: final output                     
Total: 1.76s, 2,340 tokens, $0.004
```

This is what lets you answer "why was this response slow/wrong/expensive" by drilling into exactly which step caused it, instead of treating the whole pipeline as a black box.

### 3.2 Why tracing matters more for agents than single LLM calls

An agent's trace can branch, loop, and fan out (parallel tool calls, sub-agents) — the trace tree **is** the debugging artifact for "why did the agent do that." Without it you can only see the final answer and have to guess at the path that produced it.

### 3.3 Tracing/observability tools

| Tool | Type | Notes |
|---|---|---|
| **LangSmith** | Hosted, LangChain-native | Deepest integration with LangChain/LangGraph (auto-traces Runnables/graphs with zero/minimal instrumentation), also supports eval datasets, prompt playground, and monitoring dashboards. Referenced directly in `15.RAG.md` §10.1/10.2. |
| **Langfuse** | Open-source (self-hostable) + hosted | Framework-agnostic (works with or without LangChain), traces + prompt management + eval scoring + cost tracking; popular open-source default. |
| **Arize Phoenix** | Open-source | Strong on embedding/retrieval visualization (drift, clustering) alongside tracing — useful specifically for RAG pipelines. |
| **W&B Weave** | Hosted (Weights & Biases) | Extends W&B's ML-experiment-tracking lineage into LLM tracing/eval. |
| **Helicone** | Proxy-based | Sits as an API proxy in front of your LLM calls — near-zero code change to add logging/cost tracking, less deep structural tracing than SDK-based tools. |
| **OpenTelemetry GenAI semantic conventions / OpenLLMetry (Traceloop)** | Open standard | Emits LLM traces as standard OTel spans with agreed-upon attribute names, so they flow into whatever general APM backend you already run (Datadog, Grafana Tempo, etc.) instead of a dedicated LLM tool. |

### 3.4 What good tracing enables operationally

- **Root-causing a bad response** — inspect the exact retrieved chunks / tool outputs / intermediate reasoning that led to it, rather than re-running and guessing.
- **Latency/cost breakdown per step** — find the actual bottleneck (often a specific tool call or an oversized prompt) instead of optimizing blindly.
- **Regression comparison** — diff traces of the same input across two versions of a prompt/pipeline to see exactly what changed in behavior.

## Module 4: Evaluation Pipelines

### 4.1 Offline vs. online evaluation

| | Offline eval | Online eval |
|---|---|---|
| When | Before deploy, on a fixed golden dataset (CI-style) | Continuously, on live production traffic |
| Purpose | Catch regressions from a prompt/model/pipeline change before shipping | Catch drift, real-world edge cases the golden set didn't anticipate |
| Ground truth | Often has reference answers | Rarely has reference answers — relies on reference-free metrics, LLM-judge, or user feedback signals |

Both are necessary — offline eval alone misses real-world distribution shift; online eval alone gives no pre-deploy regression gate.

### 4.2 Golden datasets

A curated, versioned set of representative (input, expected-behavior) examples — the eval equivalent of a test suite. Should be:
- **Representative** of real usage (built from real production queries/logs where possible, not just hand-invented edge cases).
- **Versioned** alongside the pipeline code, so eval runs are reproducible and comparable across commits.
- **Regularly expanded** with real production failures once found ("regression test" discipline — every bug that reaches production becomes a new golden-set case).

### 4.3 LLM-as-judge

Using an LLM to score another LLM's output against criteria (faithfulness, relevance, correctness, safety) — necessary because most open-ended generation has no single correct string to exact-match against. This is exactly the mechanism behind RAGAS (`15.RAG.md` Module 9).

- **Strengths**: scales far better than human eval, can apply nuanced rubrics, cheap/fast relative to human review.
- **Weaknesses/biases to know**: judge models have their own biases — **position bias** (favor whichever answer is shown first), **verbosity bias** (favor longer answers), **self-preference bias** (a model favors outputs from its own family). Mitigations: randomize answer order, use a different/stronger model as judge than the one being evaluated, calibrate the judge against a human-labeled sample before trusting it.

### 4.4 Human evaluation

Still the ground truth for subjective quality (tone, helpfulness, nuanced correctness) and for calibrating LLM-judges. Typically sampled (not exhaustive) due to cost — common patterns: periodic human review of a random production sample, expert review for high-stakes domains (medical/legal/financial), and structured annotation rubrics so different reviewers score consistently (inter-rater agreement is itself worth tracking).

### 4.5 User feedback signals

Implicit and explicit signals collected from real usage, useful as a cheap continuous online-eval proxy:
- **Explicit** — thumbs up/down, star ratings, "was this helpful."
- **Implicit** — did the user rephrase and re-ask (signals the first answer failed), abandonment rate, follow-up question patterns, whether a suggested action was accepted (e.g. a code suggestion actually applied/kept).

### 4.6 A/B testing and shadow deployments

- **A/B testing** — route a fraction of live traffic to a new prompt/model/pipeline version, compare metrics (task success, user feedback, cost, latency) against the control before full rollout.
- **Shadow deployment** — run the new version in parallel on real traffic **without** serving its output to users, just logging/comparing it against the current production output — lets you validate a risky change with zero user-facing risk before an A/B test.
- **Canary release** — roll out to a small percentage first, watch key metrics, expand gradually — standard progressive-delivery practice applied to model/prompt changes.

### 4.7 Eval-driven development

Treat the golden-set eval suite like a CI test suite: run it on every pipeline change (prompt edit, chunking change, retriever swap, model upgrade) and require it to pass/not regress before merging — exactly the discipline `15.RAG.md` §9.5 recommends ("run this over a golden Q&A set on every pipeline change... treat it like a test suite, not a one-off report"). This is what turns evaluation from a one-time report into a reliability mechanism.

## Module 5: Key Metrics to Track

| Category | Metric | Why it matters |
|---|---|---|
| **Quality** | Task success rate, faithfulness/groundedness, answer relevancy, context precision/recall (see `15.RAG.md` §9.3 for RAG-specific versions) | The actual "is it working" signal |
| **Latency** | Time-to-first-token, total completion time, per-span latency in traces | UX-critical, and pinpoints bottlenecks |
| **Cost** | Tokens per request, $ per request, $ per session, cost trend over time | LLM costs scale with usage in a way traditional compute often doesn't; easy to blow budget unnoticed |
| **Reliability** | Error rate, timeout rate, retry rate, tool-call failure rate | Operational health, distinct from output quality |
| **Agent-specific** | Trajectory correctness (right tools/order), iteration count per task, loop/repetition rate, escalation-to-human rate | Agent loops fail in ways single calls can't (Module 8 of `17.ai_agents.md`) |
| **Drift** | Query distribution shift, embedding-space drift of incoming queries vs. golden set, degradation of a previously-passing eval over time | Production data drifts away from what your golden set/index was built against; needs to be caught, not assumed static |

## Module 6: Agent / Pipeline Reliability Engineering

### 6.1 Resilience mechanisms (mostly LCEL/infra-level)

- **Retries with backoff** — `.with_retry()` (see `16.langchain_langgraph_basics.md` §2.7) for transient failures (rate limits, timeouts); use exponential backoff, not tight retry loops, to avoid hammering a struggling upstream.
- **Fallback models** — `.with_fallbacks([...])` to a backup model/provider if the primary fails or times out — improves availability at the cost of potential quality/behavior differences you should also be evaluating.
- **Timeouts** — every external call (LLM, tool, retrieval) needs an explicit timeout; without one, a hung dependency can hang the whole request/agent loop indefinitely.
- **Circuit breakers** — stop calling a dependency that's consistently failing (rather than retrying every request into a known-down service), fail fast, and periodically probe for recovery.
- **Idempotency** — especially for agent tool calls with side effects (sending an email, charging a payment) — ensure a retried action doesn't double-execute; use idempotency keys where the underlying API supports them.

### 6.2 Deterministic guards around non-deterministic components

- **Schema/structured-output validation** (`with_structured_output`, `instructor`, Pydantic) — reject and re-prompt rather than silently accept malformed output; this is the single highest-leverage reliability lever for anything downstream that parses LLM output programmatically.
- **Max iteration/step limits** — hard cap on agent loop turns, independent of the model's own judgment (see `17.ai_agents.md` §8) — the backstop against infinite loops.
- **Checkpointing/resumability** — LangGraph's checkpointer (`16.langchain_langgraph_basics.md` §3.2) lets a failed multi-step run resume from its last good state instead of restarting (and re-paying for) the whole pipeline.
- **Human escalation path** — a defined fallback ("hand off to a human," "return 'I don't know'") when confidence is low or iteration/error limits are hit, rather than the agent guessing indefinitely or returning a low-confidence answer as if certain.

### 6.3 Testing beyond golden-set eval

- **Adversarial/red-team testing** — deliberately probe for prompt injection, jailbreaks, and harmful-output edge cases as part of the reliability suite, not just correctness.
- **Chaos testing** — inject failures (simulate a tool timing out, a retrieval returning empty, a malformed LLM response) and verify the system degrades gracefully (falls back, escalates) instead of crashing or producing silently wrong output.
- **Load/concurrency testing** — verify behavior under realistic concurrent request volume, since rate limits and shared-resource contention (vector DB, embedding service) behave differently under load than in single-request testing.

### 6.4 Monitoring and alerting in production

- Dashboard the Module 5 metrics over time (not just point-in-time), segmented by version/model/prompt so regressions are attributable to a specific change.
- Alert on threshold breaches: error-rate spike, latency P95/P99 regression, cost-per-request spike, eval-score drop on a continuously-sampled online eval, sudden drop in user-feedback positivity.
- **Separate quality monitoring from infra monitoring** — an agent can be "up" (200 OK, normal latency) while silently producing wrong/unfaithful answers; infra health metrics alone won't catch this, which is exactly why the quality metrics in Module 5 need their own dashboards/alerts, not just standard APM.

### 6.5 Putting it together — the reliability loop

```
Production traffic → Tracing (every call/span logged)
        │
        ├── Online eval / user feedback → detect regressions & drift
        │
        ▼
   New golden-set case added from real failure
        │
        ▼
   Offline eval (CI) gates every pipeline change ──► Shadow / canary / A/B rollout
        │                                                      │
        └──────────────── feeds back into ─────────────────────┘
```
The point of this loop: production observability isn't just for debugging incidents after the fact — it's the mechanism that continuously feeds the evaluation pipeline, which is what actually keeps quality from silently degrading as the model, data, and usage patterns drift over time.
