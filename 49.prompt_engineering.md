# Prompt Engineering

## What it actually is

Prompt engineering is designing the input to an LLM so it reliably produces the output you want — without retraining the model. For a junior AI engineer, this shows up less as "clever wording" and more as: structuring prompts consistently, testing them against real cases, and catching when a prompt silently breaks after a model or data change.

## Core techniques

**Zero-shot** — just ask, no examples. Works fine for simple, well-known tasks ("summarize this email").

**Few-shot** — give 2-5 examples of input→output pairs in the prompt before the real task. Use when the output format is specific or unusual (e.g., "classify this ticket into exactly one of these 5 categories, here's what each looks like"). Few-shot examples anchor the model's output format and tone far more reliably than describing the format in words.

**Chain-of-thought (CoT)** — ask the model to reason step by step before giving the final answer ("think through this step by step, then give your answer"). Improves accuracy on multi-step reasoning, math, and logic tasks. Costs more tokens and latency, so you don't use it for simple lookups.

**ReAct (Reason + Act)** — the pattern behind most agents: the model alternates between *reasoning* ("I need to check the order status") and *acting* (calling a tool), observing the result, then reasoning again. This is what your [[17.ai_agents]] notes already cover at the architecture level — prompt engineering here means writing the system prompt that tells the model *when* to reason vs. act vs. stop.

**Self-consistency** — run the same prompt multiple times (with some temperature) and take the majority answer. Used when you need higher reliability on a hard reasoning task and can afford the extra calls.

**Role / system prompting** — set persona and constraints in the system message ("You are a support agent for X. Only answer questions about Y. Never make up prices."). This is your primary lever for controlling tone and boundaries, and it's cheaper than re-explaining rules in every user turn.

## Structuring a prompt well

A good production prompt usually has, in this order:
1. **Role/system instructions** — who the model is, what it can/can't do
2. **Context** — retrieved chunks (in a RAG system), conversation history, relevant data
3. **Task instruction** — what to do with the context, explicit and unambiguous
4. **Output format constraint** — "respond only in JSON matching this schema" / "answer in under 3 sentences"
5. **The actual user input**

Use clear delimiters (`"""`, XML-style tags like `<context>...</context>`, or markdown headers) to separate these sections — models handle structured prompts more reliably than one undifferentiated block of text, especially when context is long.

**Structured output**: for anything downstream code will parse, don't just ask nicely for JSON — use the provider's actual structured-output/function-calling feature (OpenAI's `response_format`, tool/function calling) so the model is constrained to valid JSON instead of you regex-parsing free text and hoping.

## Prompt testing and evaluation

This is the part the JD specifically calls out ("participate in prompt engineering, testing, and evaluation activities") and it's the part people skip.

- **Golden test set** — a fixed set of representative inputs with expected outputs (or expected properties, like "must mention X," "must not hallucinate a price"). Every prompt change gets run against this set before shipping.
- **Regression testing** — when you change the prompt *or* swap the underlying model, rerun the golden set. A prompt tuned for one model can silently degrade on another.
- **LLM-as-judge** — use a second LLM call to score outputs against a rubric (helpfulness, correctness, format compliance) when you have too many cases for manual review. Ties into [[18.observability_evaluation_reliability]] and [[38.AI evaluation]].
- **A/B testing prompts** — run two prompt versions against real or held-out traffic, compare on your actual metrics (task success rate, user correction rate), not just vibes.
- **Version your prompts like code** — store them in the repo (not hardcoded inline scattered across files), track changes in git, so a regression is diffable and revertible.

## Guardrails and failure modes

- **Prompt injection** — user input (or retrieved RAG content!) contains instructions trying to override your system prompt ("ignore previous instructions and..."). Mitigate by: never blindly trusting retrieved/user content as instructions, clearly delimiting untrusted content, validating/filtering output, keeping sensitive actions behind explicit confirmation rather than letting a prompt alone trigger them.
- **Output validation** — always validate structured output against a schema before using it downstream; don't trust the model followed the format even when asked nicely.
- **Parameter tuning connects here too** — temperature, top_p, max_tokens all shape how the prompt's instructions get followed. Low temperature for deterministic/format-sensitive tasks, higher for creative generation. Full detail in [[40.llm_parameters_tokens_and_cost]].

## Likely interview questions

1. What's the difference between zero-shot and few-shot prompting, and when would you use each?
2. How do you make sure an LLM returns valid JSON every time, not just most of the time?
3. You changed a prompt and it works better in your manual testing — how do you know it didn't break something else? *(Golden test set / regression suite, not just eyeballing a few examples.)*
4. What's prompt injection, and how would you defend a RAG system against it if the injected instruction is hiding inside a retrieved document rather than the user's message?
5. When would you reach for chain-of-thought vs. just asking directly? *(Multi-step reasoning tasks where the model benefits from "thinking out loud"; skip it for simple lookups — it adds latency/cost for no gain.)*
6. How would you evaluate a chatbot's prompt quality at scale, when you have thousands of conversations and can't read them all manually? *(LLM-as-judge against a rubric, sampled human review to validate the judge, track task success rate over time.)*
7. If you swap from one model to another (e.g., different provider), does your existing prompt just work? *(Not guaranteed — different models respond differently to the same phrasing/formatting; always rerun the golden set before treating the swap as done.)*
