> Your QA system always generates an answer even when no answer exists in the context. How do you detect unanswerable questions?
I prevent hallucinations by adding an answerability detection step before returning the response. First, I retrieve the top-k documents and check retrieval confidence using similarity or reranker scores. Then I use an LLM-based classifier or groundedness verifier to determine whether the retrieved context actually supports the answer. If the confidence is below a threshold or the verifier cannot find supporting evidence, the system returns 'I don't know' or 'The provided context doesn't contain the answer' instead of generating unsupported information. This is the same idea used in systems inspired by SQuAD 2.0's no-answer detection.

> What is jailbreaking in LLMs, and what are common jailbreak techniques?
Jailbreaking is an adversarial prompting technique that attempts to bypass an LLM's safety alignment using carefully crafted inputs.
Common Jailbreak Technique Families
1. Role-play or Persona Attacks: The attacker asks the model to behave as a fictional character, unrestricted assistant, or simulated system.
2. Hypothetical or Fictional Framing: Instead of asking directly, the request is framed as fiction, research, or a thought experiment.
3. Encoding or Obfuscation: The harmful intent is hidden through another representation. (Base64)
4. Multi-turn (Crescendo) Attacks: Instead of asking immediately, the conversation gradually shifts the context across several messages.
5. Many-shot Priming: The prompt contains numerous fabricated examples where an AI behaves in a particular way before the real request appears.

> What are meta-prompts, and how can they be used to generate prompts?
Meta-prompts are prompts that instruct an AI to generate, refine, or optimize other prompts.
Multi-agent / role-based meta-prompting
One model acts as "prompt author," another as "critic," another as "evaluator," iterating until quality thresholds are met.

> What is the "lost in the middle" problem in long-context prompting?
The Lost in the Middle problem is the behaviour where an LLM pays strong attention to the information placed at the beginning and at the end of a long input, and **pays very less attention to the information placed in the middle**

> How do you design a RAG system that handles conflicting information across sources?
I would design a conflict-aware RAG pipeline rather than relying on semantic similarity alone. First, I'd retrieve a larger candidate set using hybrid search, then rerank documents using metadata like source authority, recency, version, and document ownership. Before generation, I'd run a conflict detection stage—using rules for structured facts and an LLM for semantic contradictions—to classify whether the disagreement is due to freshness, regional differences, interpretation, or misinformation. The generator receives a structured evidence packet with both supporting and conflicting sources plus explicit prompt rules to prioritize authoritative sources, cite every claim, and surface uncertainty instead of averaging contradictory facts. For high-stakes domains, I'd abstain or request clarification when equally authoritative sources conflict. This approach aligns with recent research showing that explicit conflict detection and source-aware reasoning improve RAG reliability.

> How do you reduce LLM cost in production?
I approach it as a set of levers applied in order of impact, not just "use a cheaper model":
1. **Right-size the model** — route by task difficulty (a cheap/small model like Haiku for classification/extraction, reserve a frontier model like Opus/Sonnet for complex reasoning). Most cost blowups come from using one large model for everything.
2. **Prompt caching** — cache the stable prefix (system prompt, tool schemas, RAG knowledge base) so repeated requests pay ~10% of input price on that portion instead of 100%. This is usually the single biggest win for RAG/agentic apps since the same large context repeats across calls.
3. **Response caching (exact + semantic)** — for FAQ-style or repeated queries, skip the LLM call entirely: exact-match cache (hash of request) for byte-identical repeats, semantic cache (embedding similarity) for paraphrases, with the real call only on a true miss.
4. **Batch API for non-real-time workloads** — bulk classification/summarization jobs get ~50% off if results don't need to be synchronous.
5. **Control token counts directly** — trim conversation history/compact context instead of resending full history every turn, tighten `max_tokens` to the actual needed output length, use `stop_sequences` to cut generation short, and keep tool definitions lean (they cost input tokens on every call).
6. **Reduce retries from truncation** — a too-low `max_tokens` causing mid-JSON cutoffs forces a retry that pays for the wasted tokens twice; getting output length right the first time is itself a cost lever.
7. **Monitor and project cost at scale** — model cost at current, 10×, and 100× volume so an uncached, unbatched, wrong-tier design doesn't become an expensive surprise once traffic grows.

In short: pick the cheapest model that clears the quality bar, cache what repeats (both prefix-level and full-response-level), batch what can wait, and keep token counts (input and output) as tight as correctness allows.

> How do you optimize token usage/token spend in an advanced RAG chatbot?
For a RAG system specifically, most of the token cost is in the *retrieved context*, not the query or the answer, so I attack it at every stage of the pipeline:

1. **Retrieve narrow, not wide** — tune `top_k` down to the minimum that keeps recall/answer quality acceptable, and use metadata filters (source, date, tenant) before vector search to shrink the candidate pool instead of retrieving broadly and hoping reranking fixes it.
2. **Retrieve wide, send narrow (two-stage retrieval)** — pull a larger candidate set cheaply (bi-encoder similarity), rerank with a cross-encoder, and only pass the top 3-5 reranked chunks into the expensive generator prompt — the reranker itself is far cheaper per-token than the LLM call it's gatekeeping.
3. **Contextual compression** — instead of stuffing full retrieved chunks into the prompt, run an extraction/compression step (a small/cheap LLM or an extractive method) that keeps only the sentences relevant to the query and drops the rest before it ever reaches the generator.
4. **Right-size chunking** — chunk size and overlap directly set how many tokens each retrieved hit costs; oversized chunks or high overlap % silently inflate every single query's input cost. Tune chunk size for the corpus, not a default.
5. **Deduplicate retrieved chunks** — overlapping documents or repeated boilerplate (headers/footers/disclaimers) across multiple retrieved chunks waste tokens; dedupe near-identical chunks before building the prompt.
6. **Prompt caching for the stable parts** — system prompt, instructions, few-shot examples, and (if it's a small stable knowledge base) the KB itself are identical across queries — cache that prefix so it's charged at ~10% of input price after the first hit ([[40.llm_parameters_tokens_and_cost.md]]).
7. **Cache full responses (exact + semantic)** — FAQ-shaped or repeated queries can skip retrieval *and* generation entirely on a cache hit ([[39.llm_response_caching.md]]).
8. **Summarize/trim conversation history** — for multi-turn chat, don't resend the full turn history every request; compact older turns into a running summary once the conversation gets long, so history doesn't grow unbounded per query.
9. **Cheap query rewriting** — if you do query rewriting/HyDE/decomposition before retrieval, use a small/cheap model for that step, not the same frontier model doing final generation.
10. **Bound the answer, not just the context** — tight `max_tokens` and `stop_sequences` on the generation call so the expensive output side doesn't run longer than the answer actually needs.

The general principle: every token that reaches the generator's context window is priced, so the real lever is retrieval precision (fewer, more relevant, deduplicated, compressed chunks) — not just picking a cheaper model.
