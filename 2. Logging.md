## 1. Why `logging`, not `print()`

| | `print()` | `logging` |
|---|---|---|
| Destination | stdout only | stdout, file, network, cloud (configurable via Handlers) |
| Severity | none | DEBUG/INFO/WARNING/ERROR/CRITICAL |
| Can be turned off per-module in prod | No | Yes (`logger.setLevel`) |
| Structured metadata (timestamps, module, line no, custom fields) | Manual string building | Built-in via Formatter + `extra=` |
| Thread/process safe | Not guaranteed | Yes |
| Cost when disabled | Always pays string-format cost | Lazy — arguments aren't formatted if level is filtered out |

`print()` in production code means: no way to silence noisy debug output without a redeploy, no way to route errors to an alerting pipeline, no severity to filter/query on later.

## 2. Log Levels — what they mean and when to use them

| Level | Numeric | When to use | Example |
|---|---|---|---|
| DEBUG | 10 | Diagnostic detail, only useful while actively debugging | "LLM prompt payload: {...}", "cache key computed: X" |
| INFO | 20 | Normal operation, confirms things work | "Order 1023 matched to catalog item 55, confidence=0.91", "Agent 'planner' started" |
| WARNING | 30 | Unexpected but recoverable; app keeps running | "Retrying upstream call (attempt 2/3)", "Confidence score below threshold, flagging for review" |
| ERROR | 40 | A specific operation failed | "Failed to parse PO line item 7", "LLM call raised exception" |
| CRITICAL | 50 | The whole app/service is in trouble | "DB connection pool exhausted", "Cannot start: missing required config" |

**Why levels differ per environment:**
- **Local dev**: `DEBUG` — you want everything, verbosity doesn't matter.
- **Staging**: `INFO` — enough to trace behavior without drowning in noise.
- **Production**: `WARNING` or `INFO` depending on volume/cost. DEBUG in prod is expensive (log ingestion cost in Application Insights/Datadog is billed per GB) and can leak sensitive data (prompts, PII, tokens).
- Control this via env var, never hardcode: `LOG_LEVEL=INFO` → `logging.getLogger().setLevel(os.getenv("LOG_LEVEL", "INFO"))`.

**Interview trap**: logging.DEBUG < INFO < WARNING < ERROR < CRITICAL numerically — `logger.setLevel(logging.WARNING)` means DEBUG and INFO calls are silently dropped, cheaply (the log record is never even formatted if the level check fails first).

## 3. Core building blocks

```
Logger  --sends records to-->  Handler  --formats via-->  Formatter  --writes to-->  destination
   |                              |
   +-- has a level                +-- has its own level (can be stricter than logger's)
   +-- has Filters                +-- can be StreamHandler, FileHandler, RotatingFileHandler,
                                      SysLogHandler, HTTPHandler, or a custom cloud handler
```

- **Logger**: the object you call `.info()/.error()` on. Loggers are hierarchical by dotted name (`app.agents.planner` is a child of `app.agents`, which is a child of `app`). A log call **propagates up** the hierarchy unless `propagate = False`.
- **Handler**: decides *where* a record goes (console, file, Application Insights, etc). One logger can have multiple handlers (e.g., console + Azure).
- **Formatter**: decides the *string shape* of a record.
- **Filter**: fine-grained inclusion/exclusion logic beyond level (e.g., drop health-check logs).

```python
import logging

logger = logging.getLogger(__name__)  # __name__ gives module-qualified name, e.g. "app.services.po_matcher"
logger.setLevel(logging.INFO)

handler = logging.StreamHandler()
formatter = logging.Formatter(
    fmt="%(asctime)s | %(levelname)-8s | %(name)s | %(message)s",
    datefmt="%Y-%m-%dT%H:%M:%S%z",
)
handler.setFormatter(formatter)
logger.addHandler(handler)

logger.info("PO %s matched with confidence %.2f", po_id, confidence)
```

**Why `%s` lazy formatting instead of an f-string** — `logger.info(f"PO {po_id}")` always builds the string, even if the logger is set to WARNING and would discard it. `logger.info("PO %s", po_id)` only formats if the record actually gets emitted. Small thing, but it's a real interview probe ("why does `logging` use `%s` style args").

**`logging.basicConfig()`** — quick one-shot setup for the root logger, fine for scripts, risky in libraries (it silently no-ops if a handler already exists, and configures the *global* root logger — a library should never call this; only the application entry point should).

**Never `getLogger()` with no name at module level in a library** — always use `logging.getLogger(__name__)` so consumers can control verbosity per-module (`logging.getLogger("app.agents").setLevel(DEBUG)` without drowning in your HTTP client's debug logs too).

## 4. Log formatting — what a production log line needs

Minimum useful fields: **timestamp (with timezone), level, logger/module name, message**. Production systems add: **process/thread id, request/trace id, service name, environment**.

```python
formatter = logging.Formatter(
    "%(asctime)s.%(msecs)03d %(levelname)s [%(name)s:%(lineno)d] %(message)s",
    datefmt="%Y-%m-%d %H:%M:%S",
)
```

Common `LogRecord` attributes: `%(asctime)s`, `%(levelname)s`, `%(name)s`, `%(module)s`, `%(funcName)s`, `%(lineno)d`, `%(process)d`, `%(thread)d`, `%(message)s`.

### Human-readable vs JSON (structured) logs

- **Text formatter** — fine for local dev, readable in a terminal.
- **JSON formatter** — required once logs go to a log aggregator (Application Insights, ELK, Datadog) because it lets you **query/filter on fields** instead of regexing strings.

```python
from pythonjsonlogger import jsonlogger

handler = logging.StreamHandler()
handler.setFormatter(jsonlogger.JsonFormatter(
    "%(asctime)s %(levelname)s %(name)s %(message)s %(request_id)s %(agent_name)s"
))
logger.addHandler(handler)

logger.info("agent step completed", extra={"request_id": trace_id, "agent_name": "planner", "duration_ms": 240})
```

Output:
```json
{"asctime": "2026-08-28 10:03:11", "levelname": "INFO", "name": "app.agents", "message": "agent step completed", "request_id": "a1b2c3", "agent_name": "planner", "duration_ms": 240}
```

This is the foundation for **Topic 13 (Structured Logging & Correlation IDs)** below.

## 5. Structured Logging + Correlation IDs (tying one request across services)

**Problem**: a single user request may flow through FastAPI → Celery task → LangGraph agent graph → multiple LLM calls. Without a shared ID, you cannot reconstruct that path from logs after the fact.

**Pattern**: generate a `trace_id` (or reuse Application Insights' `operation_Id`) at the edge (API gateway/FastAPI middleware), and thread it through every log line and every downstream call (HTTP header, Celery task kwarg, LangGraph state field).

```python
import contextvars, uuid, logging

trace_id_var = contextvars.ContextVar("trace_id", default=None)

class TraceIdFilter(logging.Filter):
    def filter(self, record):
        record.trace_id = trace_id_var.get() or "-"
        return True

logger.addFilter(TraceIdFilter())
formatter = logging.Formatter("%(asctime)s %(levelname)s [trace=%(trace_id)s] %(name)s %(message)s")
```

FastAPI middleware to set it per request:

```python
from starlette.middleware.base import BaseHTTPMiddleware

class TraceIdMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        trace_id = request.headers.get("x-trace-id", str(uuid.uuid4()))
        token = trace_id_var.set(trace_id)
        try:
            response = await call_next(request)
        finally:
            trace_id_var.reset(token)
        response.headers["x-trace-id"] = trace_id
        return response
```

**Why `contextvars` and not a global variable**: `contextvars` is async-safe and thread-safe — each concurrent request/coroutine gets its own isolated value, unlike a plain module-level global which would leak between concurrent requests in the same process.

**Passing the trace_id into Celery**: attach it as a task kwarg (or in the task headers) since Celery workers are separate processes with no shared context:

```python
@celery_app.task
def process_po(po_id, trace_id):
    token = trace_id_var.set(trace_id)
    try:
        ...
    finally:
        trace_id_var.reset(token)
```

## 6. LangGraph — instrumenting multi-agent pipelines

This maps directly to the resume line: *"Instrumented multi-agent pipelines with structured logging and tracing to monitor step-level execution."*

### 6.1 Why this is harder than a normal request/response service
A LangGraph run is a **graph of nodes** (agents/tools), not a single function call. You need to know, per run:
- which node executed, in what order (the graph can branch/loop)
- how long each node took
- what state changed at each step
- which node failed, and what the state looked like right before failure
- token/cost per LLM call inside a node

Plain `print()`/ad-hoc logging inside each node function doesn't give you this — you need a **consistent wrapper** around every node so instrumentation isn't copy-pasted N times.

### 6.2 Node-wrapping decorator pattern

```python
import time, logging, functools

logger = logging.getLogger("app.agents")

def instrument_node(node_name):
    def decorator(fn):
        @functools.wraps(fn)
        def wrapper(state):
            trace_id = state.get("trace_id")
            start = time.perf_counter()
            logger.info("node started", extra={"trace_id": trace_id, "node": node_name})
            try:
                new_state = fn(state)
                duration_ms = (time.perf_counter() - start) * 1000
                logger.info(
                    "node completed",
                    extra={"trace_id": trace_id, "node": node_name, "duration_ms": round(duration_ms, 1)},
                )
                return new_state
            except Exception:
                logger.exception("node failed", extra={"trace_id": trace_id, "node": node_name})
                raise
        return wrapper
    return decorator

@instrument_node("planner")
def planner_node(state: AgentState) -> AgentState:
    ...
```

Wire it into the graph the same way regardless of node:

```python
from langgraph.graph import StateGraph

graph = StateGraph(AgentState)
graph.add_node("planner", planner_node)
graph.add_node("coder", coder_node)
graph.add_node("reviewer", reviewer_node)
```

`state.get("trace_id")` requires the trace id to be part of `AgentState` from the start (set once when the graph run is kicked off), so it flows through every node invocation and every conditional edge automatically — same correlation-id principle as section 5, just carried in graph state instead of a context var, because LangGraph nodes may run in different threads/processes depending on execution mode.

### 6.3 What to log at each level inside a node

| Level | What |
|---|---|
| DEBUG | full prompt sent to the LLM, full raw LLM response (only in dev — these can be huge and contain sensitive data) |
| INFO | node entered/exited, key decision made ("routed to reviewer because confidence < 0.8"), token usage, duration |
| WARNING | LLM output failed schema validation and was retried, a tool call returned an empty/degenerate result |
| ERROR | node raised, LLM call exhausted retries, output parsing failed after all retries |

### 6.4 Tracing vs logging for LangGraph — LangSmith / OpenTelemetry

- **LangSmith** (LangChain's own tracer): set `LANGCHAIN_TRACING_V2=true` and `LANGCHAIN_API_KEY` — every node/LLM call is automatically captured as a trace tree with inputs/outputs/latency/cost, no manual instrumentation needed. Good for local debugging and prompt iteration.
- **OpenTelemetry spans** (vendor-neutral, feeds Application Insights): wrap each node in a span so the graph run becomes a proper distributed trace, not just log lines.

```python
from opentelemetry import trace
tracer = trace.get_tracer("app.agents")

def instrument_node(node_name):
    def decorator(fn):
        @functools.wraps(fn)
        def wrapper(state):
            with tracer.start_as_current_span(node_name) as span:
                span.set_attribute("trace_id", state.get("trace_id"))
                span.set_attribute("agent.name", node_name)
                result = fn(state)
                span.set_attribute("agent.output_size", len(str(result)))
                return result
        return wrapper
    return decorator
```

With an OTel exporter configured for Azure Monitor (section 7), this gives you a **span per agent step**, nested under the parent HTTP request span — the exact "distributed trace across services/agents" described in Topic 18.

### 6.5 Evaluation pipelines vs logging — don't conflate them
Logging/tracing tells you **what happened** (execution path, latency, errors). Evaluation pipelines (Topic 28, resume: "built evaluation pipelines to track output quality and catch regressions") tell you **whether the output was good** — a separate, offline/async process that grades agent output against a golden dataset. Interviewers sometimes probe whether you conflate the two: tracing catches "the reviewer node threw an exception"; evaluation catches "the reviewer node ran fine but silently produced a worse code review than last release."

## 7. Application Insights — Azure-native observability

Application Insights (part of Azure Monitor) is the natural choice here since the resume's whole stack is Azure-deployed (Docker/Kubernetes/Azure across every project).

### 7.1 Two integration paths

| Approach | Package | Status |
|---|---|---|
| Legacy | `opencensus-ext-azure` (`AzureLogHandler`) | Still widely used, being phased out |
| Current | `azure-monitor-opentelemetry` (distro) | Recommended — standard OTel, auto-instruments FastAPI/requests/psycopg2/Celery |

### 7.2 Quick setup — OpenTelemetry distro (recommended)

```python
from azure.monitor.opentelemetry import configure_azure_monitor

configure_azure_monitor(
    connection_string=os.environ["APPLICATIONINSIGHTS_CONNECTION_STRING"],
)
```

One call, and it auto-instruments:
- every FastAPI request → **requests** table in App Insights (with duration, status code)
- every outbound `requests`/`httpx` call → **dependencies** table
- every `logging` call at your configured level → **traces** table
- unhandled exceptions → **exceptions** table

This means: **your existing `logging.getLogger(__name__).info(...)` calls throughout the app automatically show up in Application Insights** once this is configured at startup — you don't need to change call sites, only the bootstrap.

### 7.3 Custom dimensions — carrying trace_id / agent_name into App Insights

Plain log messages land in the `traces` table's `message` column, but to **query/filter/aggregate** by `agent_name` or `trace_id` in Kusto (KQL), attach them as **custom dimensions**:

```python
logger.info(
    "node completed",
    extra={"custom_dimensions": {"trace_id": trace_id, "node": "planner", "duration_ms": 240}},
)
```

App Insights surfaces this under `traces | extend node = customDimensions.node`.

### 7.4 Manual spans for LangGraph nodes (feeds directly off section 6.4)

Since `configure_azure_monitor()` sets up the global OTel tracer provider, the exact same `tracer.start_as_current_span(node_name)` code from section 6.4 is automatically exported to Application Insights — no separate Azure-specific span code needed. Each LangGraph node shows up as a span nested under the parent request, viewable as an **end-to-end transaction / application map** in the Azure portal.

### 7.5 Custom metrics (beyond logs) — for dashboards/alerts

Logs answer "what happened in this one run"; metrics answer "how is the system trending" (Topic 18: the three pillars). For aggregatable numbers (agent success rate, average confidence score, LLM cost per run):

```python
from opentelemetry import metrics
meter = metrics.get_meter("app.agents")
confidence_hist = meter.create_histogram("po_match.confidence")
node_duration = meter.create_histogram("agent.node.duration_ms")

confidence_hist.record(confidence, attributes={"po_source": "email"})
```

These land in the `customMetrics` table, and are what you'd actually alert on (e.g., "average confidence dropped 15% since last deploy → possible model/prompt regression") — versus traces, which you read after an incident, not before.

### 7.6 Sample KQL queries you should be able to talk through

```kusto
// All log lines for one request/trace across every service
traces
| where customDimensions.trace_id == "a1b2c3"
| order by timestamp asc

// Slowest LangGraph nodes in the last 24h
dependencies
| where cloud_RoleName == "sdlc-agents"
| summarize avg(duration), percentile(duration, 95) by name
| order by avg_duration desc

// Error rate per agent node
traces
| where severityLevel >= 3
| extend node = tostring(customDimensions.node)
| summarize errors = count() by node, bin(timestamp, 1h)
```

### 7.7 Sampling and cost — why you don't log everything at INFO in prod at Application Insights scale
App Insights bills per GB ingested. A chatty multi-agent pipeline logging every LLM prompt/response at INFO in production is a real cost problem. Standard mitigations:
- keep prompts/full LLM payloads at DEBUG, off in prod
- use **adaptive sampling** (`azure-monitor-opentelemetry` supports a sampling ratio) so you keep a representative slice of traces instead of 100%, while still keeping 100% of ERROR/CRITICAL and metrics
- aggregate first (metrics/histograms), log discrete events only when they're decision points or failures

## 8. Putting it all together — one request's journey

```
FastAPI request arrives
  -> TraceIdMiddleware generates/propagates trace_id (section 5)
  -> configure_azure_monitor() auto-creates the request span, auto-instruments logging (section 7.2)
  -> Celery task enqueued with trace_id in kwargs (section 5)
  -> Celery worker picks up task, sets trace_id in its own contextvar
  -> LangGraph run starts, trace_id stored in AgentState (section 6.2)
  -> each node wrapped with instrument_node(): logs start/end/error + OTel span (sections 6.2, 6.4)
  -> all logs + spans + metrics flow to Application Insights via the same connection string
  -> in Azure Portal: Transaction Search by trace_id reconstructs the entire path,
     Application Map shows FastAPI -> Celery -> per-agent-node timing,
     Metrics dashboard shows confidence-score trend and node duration percentiles over time
```
