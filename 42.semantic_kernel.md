# Semantic Kernel (SK) Tutorial — What It Is, Architecture, and Examples

**Semantic Kernel (SK)** is an open-source SDK from Microsoft (available in **C#, Python, and Java**) for building AI applications and agents that combine LLM calls ("semantic" functions) with regular code ("native" functions), plugins, memory, and planning — all orchestrated through a central object called the **Kernel**. It is Microsoft's answer to LangChain/LangGraph: an enterprise-grade orchestration layer designed to be embedded into existing .NET/Java/Python applications, with first-class support for Azure OpenAI, OpenAI, and other model providers.

In this tutorial, we will learn what Semantic Kernel is, why it exists, its architecture, core concepts, how it works step by step, a worked example, how it compares to LangChain/CrewAI/AutoGen, its advantages, limitations, and real-world applications.

## 1. What is Semantic Kernel and Why Do We Need It?

Building an AI application usually means gluing together several moving pieces: prompts, LLM API calls, business logic written in normal code, external APIs, some form of memory/state, and — increasingly — letting the LLM decide *which* function to call next. Doing this by hand for every project means re-inventing prompt templating, function-calling boilerplate, retry/telemetry logic, and orchestration each time.

**Semantic Kernel solves this by providing:**

1. A **Kernel** object that acts as a dependency-injection container and orchestrator — it knows about your AI services (chat models, embeddings) and your registered functions.
2. A unified abstraction — the **KernelFunction** — so that a hand-written prompt ("semantic function") and a piece of native code ("native function", e.g., a C#/Python method) look identical to the orchestrator and to the LLM doing function calling.
3. **Plugins**, which group related functions (like a cookbook groups related recipes) so an LLM can be handed a whole toolbox at once.
4. Built-in **planning / automatic function calling**, so the LLM itself can decide which plugin functions to invoke and in what order to satisfy a user's goal, instead of you hard-coding the control flow.
5. **Memory connectors** for vector stores (Azure AI Search, Qdrant, Redis, Chroma, etc.) so applications can ground responses in your own data (RAG).
6. First-class **enterprise concerns**: telemetry (via .NET's `ILogger`/OpenTelemetry), responsible-AI filters, dependency injection, and strong typing — reflecting SK's origin as a Microsoft-backed SDK meant to slot into existing production codebases rather than a research playground.

In short: LangChain popularized the "chain of LLM calls + tools" pattern for Python; Semantic Kernel brings a similar (and increasingly overlapping) capability set but with a strong emphasis on **enterprise integration, multi-language parity (C#/Python/Java), and native function-calling as a first-class citizen** rather than an afterthought.

## 2. Core Concepts of Semantic Kernel

| Concept | Meaning |
|---|---|
| **Kernel** | The central orchestrator/DI container. Holds registered AI services (chat completion, embeddings) and registered plugins/functions. Everything runs "through" the kernel. |
| **KernelFunction** | The atomic unit of work — either a **semantic function** (a prompt template executed by an LLM) or a **native function** (plain code, decorated so the kernel/LLM can discover and call it). |
| **Plugin (Skill)** | A named collection of related `KernelFunction`s, analogous to a class grouping methods, or a "toolbelt" the LLM can be given. |
| **Prompt Template** | A parameterized prompt (supports Handlebars/Jinja-like syntax) that becomes a semantic function when registered with the kernel. |
| **Planner** | A component that takes a user goal and automatically produces (and/or executes) a sequence of plugin function calls to achieve it. |
| **Connector** | An adapter to an external service — an AI service connector (OpenAI, Azure OpenAI, Hugging Face, etc.) or a memory/vector-store connector (Qdrant, Redis, Azure AI Search, etc.). |
| **Memory** | Semantic Kernel's abstraction over embeddings + vector storage, used for semantic search and RAG. |
| **Agent** | A higher-level abstraction (in the SK Agent Framework) representing an autonomous or semi-autonomous entity built on top of a kernel, capable of multi-turn conversations, using plugins, and collaborating with other agents. |

## 3. Architecture of Semantic Kernel

```
                         +---------------------------+
                         |          Kernel            |
                         |  (orchestrator / DI root)  |
                         +---------------------------+
                          |            |            |
                 registers|    registers|    uses    |
                          v            v            v
                +----------------+ +-----------+ +----------------+
                |    Plugins     | |  Memory   | |  AI Services   |
                | (KernelFns:    | | (vector   | | (Chat, Embed-  |
                |  semantic +    | |  store    | |  ding models — |
                |  native)       | |  connector)| |  OpenAI/Azure) |
                +----------------+ +-----------+ +----------------+
                          |
                          v
              +-------------------------+
              |  Planner / Function     |
              |  Calling (auto-invoke)  |
              +-------------------------+
                          |
                          v
                 LLM decides which
                 function(s) to call,
                 kernel executes them,
                 result fed back to LLM
```

- The **Kernel** is created once per app (or per request) and configured with one or more AI service connectors (e.g., `AddAzureOpenAIChatCompletion`).
- **Plugins** are registered into the kernel — either imported from native code classes/functions, or loaded from prompt template folders.
- When you invoke a chat completion with **automatic function calling** enabled, the kernel serializes the registered plugin functions' signatures (name, description, parameters) into the LLM's function-calling schema — the same mechanism as OpenAI/Azure "tools" — so the LLM can request a function be invoked.
- The kernel executes the requested function (semantic or native) and, for multi-step flows, feeds the result back to the LLM until a final answer is produced.

## 4. Plugins and Functions

A **plugin** groups functions the same way a class groups methods. Each function inside it is a `KernelFunction`.

### Native function (Python example)

```python
from semantic_kernel.functions import kernel_function

class LightsPlugin:
    @kernel_function(description="Gets the current state of the lights.")
    def get_state(self) -> str:
        return "off"

    @kernel_function(description="Changes the state of the light.")
    def change_state(self, state: str) -> str:
        return f"Lights are now {state}"
```

### Semantic function (a prompt-based function)

```python
from semantic_kernel.functions import KernelFunctionFromPrompt

summarize_fn = KernelFunctionFromPrompt(
    prompt="Summarize the following text in one sentence:\n\n{{$input}}",
    function_name="Summarize",
    description="Summarizes input text.",
)
```

Both kinds are registered into the kernel the same way, and both can be invoked directly, from a planner, or automatically via LLM function calling — the kernel treats them identically as `KernelFunction` objects.

```python
kernel.add_plugin(LightsPlugin(), plugin_name="Lights")
```

## 5. Planners and Function Calling (Automatic Orchestration)

Early Semantic Kernel versions relied on explicit **Planners** (e.g., `SequentialPlanner`, `StepwisePlanner`) that asked the LLM to output a plan (a sequence of function calls) up front, which the kernel then executed.

Modern Semantic Kernel leans primarily on **automatic function calling** (also called "auto-invoke"), which mirrors how OpenAI/Azure function-calling/tools work natively:

```python
from semantic_kernel.connectors.ai import FunctionChoiceBehavior

result = await kernel.invoke_prompt(
    "Turn the lights on and tell me the new state.",
    function_choice_behavior=FunctionChoiceBehavior.Auto(),
)
```

1. The kernel sends the prompt plus the JSON schema of all registered plugin functions to the LLM.
2. The LLM decides (like any tool-calling model) which function(s) to call and with what arguments.
3. The kernel executes those functions and returns the results to the LLM.
4. This loops until the LLM produces a final natural-language answer (no more function calls requested).

This makes SK's orchestration model conceptually close to "an LLM with tools" (same idea as OpenAI function calling, MCP tool use, or LangChain agents), but wrapped in the kernel's DI/plugin abstraction so the same function works whether invoked automatically, manually, or from a planner.

## 6. Memory and Connectors

Semantic Kernel exposes memory as a pluggable abstraction over embeddings + vector stores, enabling RAG-style grounding:

```python
from semantic_kernel.connectors.memory.qdrant import QdrantMemoryStore
from semantic_kernel.memory import SemanticTextMemory

memory_store = QdrantMemoryStore(url="http://localhost:6333")
memory = SemanticTextMemory(storage=memory_store, embeddings_generator=embedding_service)

await memory.save_information(collection="docs", text="SK is an SDK for AI orchestration.", id="1")
results = await memory.search(collection="docs", query="What is Semantic Kernel?")
```

Supported connectors span most popular vector databases (Azure AI Search, Qdrant, Redis, Chroma, Pinecone, Weaviate, Postgres/pgvector, etc.), plus connectors to different **AI services** (OpenAI, Azure OpenAI, Hugging Face, Ollama, Google, and others) — this pluggability is one of SK's core design goals: swap providers without rewriting application logic.

## 7. Agents in Semantic Kernel (Agent Framework)

Built on top of the kernel, the **Semantic Kernel Agent Framework** provides higher-level agent abstractions:

- **`ChatCompletionAgent`** — a single conversational agent backed by a kernel (with its plugins) and a persona/instructions.
- **`AgentGroupChat`** — lets multiple agents converse with each other in a shared chat, with a selection strategy deciding whose turn it is next (similar in spirit to AutoGen's multi-agent conversations).
- **Handoff / orchestration patterns** — newer SK releases add explicit multi-agent orchestration patterns (sequential, concurrent, hand-off) for composing agents into workflows, converging conceptually with what LangGraph/CrewAI offer for multi-agent systems.

```python
from semantic_kernel.agents import ChatCompletionAgent

agent = ChatCompletionAgent(
    kernel=kernel,
    name="AssistantAgent",
    instructions="You are a helpful assistant that can control smart home devices.",
)

response = await agent.get_response(messages="Turn off the lights.")
```

## 8. How Semantic Kernel Works — Step by Step

1. **Create a Kernel** and register one or more AI service connectors (chat/embedding models).
2. **Define/import Plugins** — native functions (plain code) and/or semantic functions (prompt templates) — and register them with the kernel.
3. **(Optional) Set up Memory** — configure a vector-store connector and ingest documents for retrieval.
4. **Invoke** the kernel — either directly call a specific function, run a **planner** to produce a plan, or send a prompt with **automatic function calling** enabled.
5. **The LLM (via the connector) decides** which function(s) to call, if any, based on the registered function schemas.
6. **The kernel executes** the requested function(s) — running native code or a nested semantic function — and returns results to the LLM.
7. **Loop until done** — for multi-step tasks, the LLM may request further function calls before producing the final response.
8. **(Optional) Wrap in an Agent** — for conversational, stateful, or multi-agent scenarios, expose the kernel through `ChatCompletionAgent`/`AgentGroupChat` instead of raw kernel calls.

## 9. Example: A Simple Kernel with a Plugin

```python
import asyncio
from semantic_kernel import Kernel
from semantic_kernel.connectors.ai.open_ai import AzureChatCompletion
from semantic_kernel.functions import kernel_function
from semantic_kernel.connectors.ai import FunctionChoiceBehavior

class WeatherPlugin:
    @kernel_function(description="Gets the current weather for a city.")
    def get_weather(self, city: str) -> str:
        # In real life, call a weather API here.
        return f"It is sunny and 25°C in {city}."

async def main():
    kernel = Kernel()
    kernel.add_service(AzureChatCompletion(
        deployment_name="gpt-4o",
        endpoint="https://<your-endpoint>.openai.azure.com/",
        api_key="<your-key>",
    ))
    kernel.add_plugin(WeatherPlugin(), plugin_name="Weather")

    result = await kernel.invoke_prompt(
        "What's the weather like in Paris right now?",
        function_choice_behavior=FunctionChoiceBehavior.Auto(),
    )
    print(result)

asyncio.run(main())
```

**Flow:**
```
User prompt -> Kernel sends prompt + Weather plugin schema to LLM
            -> LLM requests: get_weather(city="Paris")
            -> Kernel executes WeatherPlugin.get_weather("Paris")
            -> Result fed back to LLM
            -> LLM produces final natural-language answer
```

## 10. Semantic Kernel vs LangChain vs CrewAI vs AutoGen

| Aspect | Semantic Kernel | LangChain / LangGraph | CrewAI | AutoGen |
|---|---|---|---|---|
| Origin/backing | Microsoft | Open-source community | Open-source (crewAI Inc.) | Microsoft Research |
| Languages | C#, Python, Java (strong parity) | Python, JS/TS | Python | Python, .NET (preview) |
| Core abstraction | Kernel + Plugins (functions) | Chains/Graphs (LangGraph: nodes & edges) | Agents + Tasks + Crew | Conversable agents |
| Orchestration style | Auto function-calling + planners + agent orchestration patterns | Explicit graph/chain wiring (LangGraph) or high-level chains | Role-based team, sequential/hierarchical process | Multi-agent conversation loop |
| Enterprise focus | Strong (DI, telemetry, Azure integration, RAI filters) | Moderate (large ecosystem, less enterprise-opinionated) | Light | Moderate (research-driven, maturing) |
| Best for | .NET/enterprise apps, teams needing multi-language parity and native function calling as first-class | Custom, fine-grained control flow; huge integration ecosystem | Quickly modeling a "team of specialist agents" | Research-style multi-agent conversation/negotiation patterns |

**Rule of thumb:** choose **Semantic Kernel** when you're building in a Microsoft/Azure-centric or .NET stack, need first-class C#/Java parity, or want function calling and plugins to be the primary abstraction; choose **LangGraph** for maximum custom control flow; choose **CrewAI** for fast role-based team setups; choose **AutoGen** for research-flavored multi-agent conversation patterns.

## 11. Advantages of Semantic Kernel

- **Multi-language parity** — C#, Python, and Java implementations share the same core concepts, useful for polyglot/enterprise teams.
- **Native function calling as a first-class citizen** — plugins map cleanly onto the underlying LLM tool-calling APIs (OpenAI/Azure "tools"), with no impedance mismatch.
- **Enterprise-ready** — built-in DI, telemetry/OpenTelemetry support, and hooks for responsible-AI content filters, which matter for production .NET/Azure applications.
- **Uniform treatment of prompts and code** — semantic functions (prompts) and native functions (code) share the same `KernelFunction` interface, simplifying composition.
- **Pluggable connectors** — swapping the underlying LLM provider or vector store typically means changing configuration, not application logic.
- **Backed by Microsoft** — steady investment, first-class Azure OpenAI support, and integration with the broader Microsoft AI ecosystem (Copilot Studio, Azure AI Foundry).

## 12. Disadvantages / Limitations

- **Smaller community/ecosystem** than LangChain — fewer third-party integrations, tutorials, and community-contributed plugins.
- **API churn** — SK has gone through significant API redesigns (Skills → Plugins, planners evolving, Agent Framework introduced later), so older tutorials/code can be out of date.
- **Less mature multi-agent story** historically compared to CrewAI/AutoGen, though the Agent Framework is closing that gap.
- **Documentation gaps between languages** — Python and C# feature parity isn't always perfectly in sync at any given release.
- **Overkill for very simple use cases** — a single prompt-and-response app doesn't need a full kernel/plugin/DI setup.

## 13. Real-World Applications

- **Enterprise copilots** embedded in .NET/Azure applications (e.g., internal "Copilot"-style assistants over company data).
- **RAG applications** grounded in enterprise document stores via SK's memory connectors.
- **Smart automation** where an LLM decides which internal APIs/plugins to call to fulfill a request (IT helpdesk bots, workflow automation).
- **Multi-agent business workflows** using `AgentGroupChat`/orchestration patterns (e.g., a drafting agent and a reviewing agent collaborating on a document).
- **Microsoft ecosystem integrations** — Semantic Kernel underpins parts of Microsoft's own Copilot stack and is a common choice when building on Azure AI Foundry.

## 14. Conclusion

Semantic Kernel is Microsoft's SDK for composing prompts and code into orchestrated AI applications, built around a central **Kernel** that unifies **semantic functions** (prompts) and **native functions** (code) as **plugins**, with automatic function calling, planners, memory/RAG connectors, and — increasingly — a full multi-agent framework. It plays a similar role to LangChain/LangGraph but is distinguished by its **multi-language parity (C#/Python/Java)** and **enterprise-first design** (DI, telemetry, Azure integration), making it the natural choice for teams building production AI features inside .NET or Azure-centric ecosystems.
