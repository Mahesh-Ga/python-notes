# LangChain / LangGraph Fundamentals — Prep Notes

> Prerequisite notes for `15.RAG.md`. Covers LLMChain (legacy), LCEL, the `Runnable` protocol, and LangGraph's `StateGraph` in depth.

---

## Module 1: LLMChain (legacy pattern)

### 1.1 What it was

`LLMChain` was the original LangChain abstraction: bundle a `PromptTemplate` + an LLM (+ optionally an output parser) into one callable object.

```python
from langchain import LLMChain, PromptTemplate
from langchain_openai import ChatOpenAI

prompt = PromptTemplate.from_template("Translate to French: {text}")
llm = ChatOpenAI(model="gpt-4o-mini")

chain = LLMChain(llm=llm, prompt=prompt)
result = chain.invoke({"text": "good morning"})   # {'text': 'good morning', 'text': 'Bonjour'}... actually returns dict with output key
```

- Config-object style: you instantiate a class, pass `llm=`, `prompt=`, `output_key=`, `memory=`, etc.
- Chains were composed by nesting (`SimpleSequentialChain`, `SequentialChain`) — each wraps the previous, output/input keys had to be wired by name.
- Every chain type (`LLMChain`, `ConversationChain`, `RetrievalQA`, `LLMMathChain`, …) was its own class with its own quirks — not a uniform interface.

### 1.2 Why it was deprecated in favor of LCEL(langchain expression language)

- **Inflexible composition** — nesting chain classes inside each other doesn't compose the way plain function composition does; branching/parallelism required yet more special-purpose chain classes.
- **No uniform interface** — streaming, batching, and async each had to be separately implemented (or not implemented) per chain class.
- **Hard to introspect** — couldn't easily visualize or modify the pipeline shape; debugging required reading each chain's internals.
- LangChain's official guidance now: **use LCEL / `Runnable` composition for everything new**; `LLMChain` and friends are legacy, kept for backward compatibility only. You'll still see them in older tutorials and codebases, so recognize the pattern, but don't build new pipelines this way.

## Module 2: The `Runnable` Protocol

### 2.1 Core idea

An LCEL component is any object that implements the Runnable interface, which means it can be composed with `|` into a chain.

Concretely, in LangChain, these are all LCEL components:

- Prompt templates — ChatPromptTemplate, PromptTemplate
- Models — chat models (ChatOpenAI, etc.), LLMs
- Output parsers — StrOutputParser, JsonOutputParser, etc.
- Retrievers — anything from vectorstore.as_retriever()
- Wrapped plain functions — RunnableLambda
- Structural helpers — RunnablePassthrough, RunnableParallel, RunnableBranch
- Compiled LangGraph graphs — a compiled StateGraph is itself a Runnable, so it's an LCEL component too

`Runnable` is the **uniform interface** every LCEL component implements — prompts, LLMs/chat models, output parsers, retrievers, and your own functions all become interchangeable, composable units with the same method surface.

Every `Runnable` exposes:

| Method | Behavior |
|---|---|
| `.invoke(input, config=None)` | Run once, synchronously, return the output |
| `.batch(inputs, config=None)` | Run over a list of inputs, parallelized under the hood |
| `.stream(input, config=None)` | Yield output incrementally as it's produced |
| `.ainvoke` / `.abatch` / `.astream` | Async counterparts of the above |
| `.astream_events` | Fine-grained event stream (token-level, per-step start/end) — used for streaming intermediate steps in agents/graphs, not just final tokens |

Because **every** component — a `PromptTemplate`, a chat model, an output parser, a retriever, a plain Python function wrapped as `RunnableLambda` — implements this same interface, they all snap together identically regardless of what they are.

### 2.2 The pipe operator and `RunnableSequence`

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_openai import ChatOpenAI

prompt = ChatPromptTemplate.from_template("Translate to French: {text}")
llm = ChatOpenAI(model="gpt-4o-mini")
parser = StrOutputParser()

chain = prompt | llm | parser        # RunnableSequence under the hood
result = chain.invoke({"text": "good morning"})   # "Bonjour"
```

- `|` is Python's `__or__`, overloaded by `Runnable` to build a `RunnableSequence` — output of the left becomes input of the right.
- This is **the** LCEL idiom: build pipelines by piping, not by nesting config objects.
- `chain.invoke(...)` , `chain.stream(...)`, `chain.batch(...)` all work automatically on the composed chain — LCEL propagates streaming/batching/async through every step without you writing extra code, *as long as every step in the chain genuinely supports it* (a step that must buffer its full input before running, e.g. most output parsers acting on a complete JSON blob, breaks true token-level streaming even though the call doesn't error).

### 2.3 `RunnableParallel` — fan-out

Run multiple runnables on the same input concurrently, collect results into a dict.

```python
from langchain_core.runnables import RunnableParallel

map_chain = RunnableParallel(
    joke=joke_prompt | llm | parser,
    poem=poem_prompt | llm | parser,
)
result = map_chain.invoke({"topic": "cats"})
# {"joke": "...", "poem": "..."}
```

- Shorthand: a plain dict literal inside a pipe is auto-coerced to `RunnableParallel`:
```python
chain = {"joke": joke_chain, "poem": poem_chain} | combine_prompt | llm | parser
```
- Common use: fan out to multiple retrievers/prompts, or attach a "passthrough" branch that carries the original input alongside a transformed branch (see 2.4).

### 2.4 `RunnablePassthrough` — carrying data through

 is a LangChain component that takes an input and returns it unchanged, or adds new keys to a dictionary output (e.g. RAG: the retriever's output *and* the original question both need to reach the final prompt).

```python
from langchain_core.runnables import RunnablePassthrough

rag_chain = (
    {"context": retriever, "question": RunnablePassthrough()}
    | prompt
    | llm
    | parser
)
```
- `RunnablePassthrough()` — input flows through as-is.
- `RunnablePassthrough.assign(key=some_runnable)` — keeps existing input dict keys, adds a new key computed by `some_runnable`.

### 2.5 `RunnableLambda` — wrap plain functions

Any plain Python function can join the pipeline by wrapping it:

```python
from langchain_core.runnables import RunnableLambda

def word_count(text: str) -> int:
    return len(text.split())

chain = prompt | llm | parser | RunnableLambda(word_count)
```
- LCEL auto-coerces a plain function used directly in a `|` pipe into a `RunnableLambda` in most cases, but wrapping explicitly is clearer and required in some contexts (e.g. when you need `.batch`/async behavior configured, or when passing it as a named branch inside `RunnableParallel`).

### 2.6 `RunnableBranch` — conditional routing

Route to different sub-chains based on the input, evaluated as an if/elif/else chain:

```python
from langchain_core.runnables import RunnableBranch

branch = RunnableBranch(
    (lambda x: "billing" in x["topic"], billing_chain),
    (lambda x: "tech" in x["topic"], tech_chain),
    general_chain,   # default/else
)
```
- Simple, static conditional logic within a linear pipeline. For anything with **loops, retries, or multi-step agentic control flow**, that's what `StateGraph` (Module 3) is for — `RunnableBranch` doesn't support cycles.

### 2.7 Configuring runnables: `.bind`, `.with_config`, `.with_retry`, `.with_fallbacks`

```python
llm_with_stop = llm.bind(stop=["\n"])                       # bake in a fixed kwarg
chain_with_retry = chain.with_retry(stop_after_attempt=3)   # retry on transient failure
robust_chain = primary_chain.with_fallbacks([backup_chain]) # fallback if primary raises
traced_chain = chain.with_config({"run_name": "my-chain", "tags": ["prod"]})
```
- `.bind(**kwargs)` — partially apply fixed arguments to every call (e.g. always pass a `stop` sequence to an LLM).
- `.with_config(...)` — attach metadata (run name, tags, callbacks) used by tracing (LangSmith) without changing behavior.
- `.with_retry` / `.with_fallbacks` — resilience wrappers, composable like anything else since they still return a `Runnable`.

### 2.8 Why LCEL matters for agentic RAG (ties back to `15.RAG.md` §8.2)

The `@tool`-decorated retriever function and the `retriever` itself are both `Runnable`s — that's *why* they compose cleanly with `.invoke()` inside a LangGraph node, and why a plain `retriever | prompt | llm | parser` chain can be dropped into a graph node as a single callable.

## Module 3: LangGraph `StateGraph`

### 3.1 Why LangGraph exists (beyond LCEL)

LCEL composes **directed acyclic** pipelines — data flows one direction, no loops. Agentic workflows need:
- **Cycles** — retrieve → grade → (loop back to retrieve with a rewritten query) → generate.
- **Persistent, mutable state** threaded across many steps, not just single input→output per step.
- **Explicit control flow** — conditional branching that can route back to earlier nodes, human-in-the-loop pauses, retries with backoff logic.

`StateGraph` models the workflow as a **graph of nodes and edges over a shared state object**, which is what makes cycles and stateful multi-step agents expressible.

### 3.2 Core concepts

| Concept | What it is |
|---|---|
| **State** | A typed schema (`TypedDict`, dataclass, or Pydantic model) defining the shape of data threaded through the graph. Every node reads from and writes (partial) updates to this shared state. |
| **Node** | A plain function (or `Runnable`) with signature `state -> partial_state_update` (a dict of the keys it wants to change). |
| **Edge** | A fixed transition `add_edge("A", "B")` — always go from A to B. |
| **Conditional edge** | `add_conditional_edges("A", router_fn, {"path1": "B", "path2": "C"})` — `router_fn(state)` returns a key, graph follows the matching path. This is how loops happen (a router can point back to an earlier node). |
| **Entry point** | `set_entry_point("node_name")` (or the `START` sentinel) — where execution begins. |
| **`END`** | Sentinel node marking termination of that path. |
| **Checkpointer** | Persists state after each node runs (`MemorySaver` in-process, or a DB-backed saver for production) — enables resumability, human-in-the-loop interrupts, and multi-turn memory keyed by a `thread_id`. |

### 3.3 State reducers — how updates merge

By default, a node's returned dict **overwrites** the corresponding state key. For keys that should *accumulate* (e.g. a running message list), annotate the field with a reducer function:

```python
from typing import TypedDict, Annotated, List
import operator

class ChatState(TypedDict):
    messages: Annotated[List[str], operator.add]   # new messages get appended, not overwritten
    question: str
```
- `operator.add` on a list = append/concat instead of replace.
- LangGraph ships `add_messages` (from `langgraph.graph.message`) specifically for chat-message state — handles message-id-based upsert/dedup, not just naive concatenation.

### 3.4 Minimal end-to-end example

```python
from typing import TypedDict, List
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import MemorySaver

class GraphState(TypedDict):
    question: str
    documents: List[str]
    generation: str

def retrieve(state: GraphState):
    docs = retriever.invoke(state["question"])
    return {"documents": [d.page_content for d in docs]}

def generate(state: GraphState):
    answer = llm.invoke(build_prompt(state["question"], state["documents"]))
    return {"generation": answer.content}

def route(state: GraphState):
    return "generate" if state["documents"] else "retrieve"   # loop back if empty

graph = StateGraph(GraphState)
graph.add_node("retrieve", retrieve)
graph.add_node("generate", generate)
graph.add_edge(START, "retrieve")
graph.add_conditional_edges("retrieve", route, {"generate": "generate", "retrieve": "retrieve"})
graph.add_edge("generate", END)

app = graph.compile(checkpointer=MemorySaver())
result = app.invoke(
    {"question": "what is HNSW?"},
    config={"configurable": {"thread_id": "session-1"}},
)
```
- `.compile()` turns the graph definition into a runnable object — and the compiled graph is **itself a `Runnable`**, so it supports `.invoke`, `.stream`, `.batch`, and composes with everything in Module 2.
- `thread_id` scopes checkpointed state — reusing the same `thread_id` across calls resumes/continues that conversation's state (multi-turn memory); a new `thread_id` starts fresh.

### 3.5 Nodes that fan out: `Send`

Sometimes a node needs to dynamically spawn a variable number of parallel branches (e.g. "grade N retrieved documents in parallel," where N isn't known until runtime). `Send` lets a conditional-edge function emit multiple `Send(node_name, state_for_that_branch)` objects instead of a single next-node string — LangGraph runs each as its own parallel invocation of the target node, then merges results back via the state reducers.

```python
from langgraph.types import Send

def route_to_graders(state: GraphState):
    return [Send("grade_document", {"doc": d}) for d in state["documents"]]
```

### 3.6 Human-in-the-loop: `interrupt`

Because the checkpointer persists state after every node, execution can be **paused mid-graph** to wait for external (human) input, then resumed later from exactly that point — the mechanism `15.RAG.md` §8.3 references for checkpointing-enabled interrupts.

```python
from langgraph.types import interrupt

def human_review(state: GraphState):
    approved = interrupt({"proposed_answer": state["generation"]})  # execution pauses here
    return {"approved": approved}
```
Resuming: call `.invoke(Command(resume=user_input), config=...)` with the same `thread_id` — the graph picks up exactly where it paused.

### 3.7 Subgraphs

A compiled `StateGraph` can be embedded as a node inside another `StateGraph` — lets you build a reusable sub-workflow (e.g. a whole "retrieve-grade-rewrite" loop) and drop it into a larger agent graph as a single node, either sharing the parent's state schema or with an explicit state-transform at the boundary.

### 3.8 Prebuilt agent: `create_react_agent`

For the common ReAct loop (LLM decides tool calls → executes → feeds observation back → repeat until it answers), LangGraph ships a prebuilt constructor instead of hand-wiring the graph:

```python
from langgraph.prebuilt import create_react_agent

agent = create_react_agent(llm, tools=[search_knowledge_base])
result = agent.invoke({"messages": [("user", "what is HNSW?")]})
```
Internally this **is** a `StateGraph` (agent node ↔ tool node, conditional edge on "did the LLM request a tool call") — worth knowing the primitive underneath even when using the prebuilt.

## Module 4: How these three layers relate

```
LLMChain (legacy)          →  deprecated, class-per-chain-type, no uniform interface
        │
        ▼
Runnable + LCEL            →  uniform interface (invoke/batch/stream/async) + `|` composition
                               for linear/branching (acyclic) pipelines
        │
        ▼
StateGraph (LangGraph)     →  adds shared mutable state + cycles + checkpointing on top,
                               for anything needing loops, retries, multi-step agentic control,
                               or human-in-the-loop — nodes themselves are usually built from
                               Runnable/LCEL chains
```

Key takeaway for reading `15.RAG.md` Module 8: every retriever, chain, and tool used inside a LangGraph node is an ordinary `Runnable` — the graph just adds the stateful control flow (loops, conditional routing, checkpointing) around plain LCEL building blocks.
